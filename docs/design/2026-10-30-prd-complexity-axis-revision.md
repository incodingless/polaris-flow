# PRD 复杂度分级方案（判定轴 + 定档确认 + 流程分档）

> 状态：已裁定（待落盘执行）
> 权威源：`assets/zh/skills/prd/discovery/policies/complexity-assessment-policy.md`（判定/评分）、`docs/design/2026-10-29-prd-graded-workflow-design.md`（流程，本文档 §7 修正之）
> 关联：`docs/design/2026-10-29-prd-complexity-assessment-scheme.md`

## 0. 结论

1. **判定主轴从"逻辑复杂度"改为"变更的风险与代价"**：变更幅度 + 回归风险 + 可回滚性 + 现状复杂度。逻辑复杂度降为"全新场景"下变更幅度的代理。
2. **"简单"的主体是既有功能轻量迭代**。豁免从"CRUD 豁免"扩为"简单豁免"，覆盖全新 CRUD 与轻量迭代两类，只豁免规模类加分、风险类永不豁免。
3. **总分定档降权**：主轴 + 高危一票 + 简单豁免为权威，评分表降为复核 [COMPUTED]：50 分阈值是人为设定，加两维即崩，说明不该被它绑死。
4. **评分表技术维度增补两维**，总分 50 → 54，阈值重定。
5. **定档人机确认与回溯**：二次校准后回显评估结论 + 理由，用户认可或人工覆盖，系统评估值 + 最终值 + 覆盖理由落盘供校准。
6. **流程环节随复杂度分档**：阶段序列 / 交付物 / 章节裁剪 / 评审次数 / 人工确认次数，五类流程环节全部按档裁剪（见 §7）。

## 1. 背景与根因

现状政策判定主轴为"逻辑复杂度" + "CRUD 豁免"。实践反馈 [KNOWN，用户实践]：研发口径的"简单需求"主体是**现有功能的迭代 / 完善 / 增加业务逻辑**，全新简单需求极少。"轻量迭代"天然带业务规则，按逻辑复杂度轴被判到"标准"甚至"复杂"，"简单需求被流程拖死"换入口重现。

现状流程的量化事实 [KNOWN]：

| 维度 | 现状 | 代价 |
|---|---|---|
| 阶段序列 | `discovery → draft → refine → ship` 严格串行，`requirement` 无 `modePhases` | 简单/复杂走完全相同 4 阶段 |
| 评审 | review + testability + readiness 3 次固定执行 | 评审资源不流向风险最大处 |
| 模板 | 11 章 + 4 附录固定结构 | 简单 CRUD 也要产出完整终稿 |
| 人工确认 | 16~30 次往返，draft 硬性"一章一确认"、refine 反而可"全量" | 简单需求跨天等待 + 逐章确认轻重倒挂 |
| 复杂度联动 | 只联动扫描维度/澄清轮次/图表深度 | 分级是"装饰"不是"链路开关" |

根因：判定轴只建模"全新场景从零建什么"，漏掉迭代的三个变量——

| 漏掉变量 | 说明 |
|---|---|
| 现状理解成本 | 存量功能上动刀，需先摸清现有行为/规则/数据/代码 |
| 回归风险 | 逻辑再简单，改现有功能也可能破坏现有用户 |
| 增量写作形态 | 迭代 PRD 是"现状→改动→验收"差异稿，非从零重写 |

"回归风险/可回滚性"是 Worktile 四维度分级（影响范围/失败后果/不确定性/可回滚性）的核心 [COMMON，HIGH]。

### 公开资料三原则（论据）

1. **Cockburn 目标层级**（cloud/kite/sea/fish/clam）：详略由"目标层级"决定，CRUD 是 subfunction 级，不该按 sea-level 全量展开 [COMMON，HIGH]。
2. **DoR 是 checklist 不是 stage-gate**：bronze/silver/gold 分级，评审资源流向风险最大处，不机械套用全部条目 [COMMON，HIGH]。
3. **one-pager = 同模板删空行**：Lenny Rachitsky / techsy——"A one-pager isn't a different document. It's the same twelve sections with the empty rows deleted" [COMMON，HIGH]。

## 2. 新判定主轴（§4.1 替换稿）

复杂度主轴 = 变更的风险与代价，由「变更幅度 + 回归风险 + 可回滚性 + 现状复杂度」决定。

| 主轴信号 | 简单 | 标准 | 复杂 |
|---|---|---|---|
| 变更性质（首行分流） | 全新 CRUD；既有功能局部迭代 | 全新模块；既有功能多规则扩展 | 全新跨系统；既有核心链路改造 |
| 变更幅度 | 参数/文案/展示/单字段/单条规则 | 局部业务流程/多规则/多字段 | 新增完整流程 / 重构主干 |
| 业务规则变动 | 增改 ≤3 条或极简校验 | 4~15 条明确规则 | >15 条或规则联动/引擎级 |
| 状态流转变动 | ≤2 状态（或不动） | 3~5 状态 | 复杂状态机/并发/事务/幂等 |
| 计算/统计变动 | 无或极简 | 有聚合/统计/计算 | 复杂计算/资金/时序 |
| 现状复杂度（迭代必评） | 改的是简单功能，一眼可辨 | 现状中等，需梳理现有规则 | 现状复杂链路/数据，需代码级验证 |
| 回归风险 | 局部展示/单操作，不影响他人 | 多角色受影响，需常规回归 | 核心用户/核心链路受影响 |
| 可回滚性 | 可快速回滚或开关关闭 | 常规发布回滚 | 不可回滚或回滚成本极高 |
| 高危信号 | 无 | 无 | 资金/敏感个人信息/监管/核心链路（一票复杂起步） |

> 逻辑复杂度不再独立当主轴，降为"变更幅度"子项。数据实体、跨系统仍为辅助信号。

## 3. 简单豁免（§4.2 替换稿）

从"CRUD 豁免"扩为"简单豁免"，覆盖两类。**只豁免规模类加分，风险类（回归/现状/高危）永不豁免**。

**A. 全新极简 CRUD**（标准增删改查/表单/状态开关）：业务规则=0（仅必填/唯一/格式/范围）、流程分支≤1、无计算/并发/事务/幂等、单系统、无高危。

**B. 既有功能轻量迭代**（参数/文案/展示/单字段/单条规则的局部调整）：不新增完整业务流程、不重构主干、不改状态机、不新增计算逻辑、现状复杂度低、回归风险低、无高危。

> 堵漏：一条"改核心链路的单字段"——规模是单字段，但高危信号一票复杂，豁免不生效。

## 4. 评分表改法（§2 增量）

骨架"业务 20 + 技术 20 + 合规 10"不动，只改技术复杂度三处：

| 维度 | 原 | 新 |
|---|---|---|
| 新增核心数据实体 | 0/2/3 | 改名**数据模型变更幅度** 0/1/2/3（不动=0 / 加改字段=1 / 新增 1 实体=2 / 新增 2+ 或改核心结构=3） |
| 发布与迁移复杂度 | 0/1 | 改名**回归与可回滚风险** 0/1/2/3（常规发布可快回滚=0 / 需回归=1 / 联调灰度=2 / 不可回滚=3） |
| 技术栈适配成本 | 0/1 | **替换为现状复杂度** 0/2/3（迭代必评，全新记 0） |

技术满分 20 → 24，总分 50 → 54。

## 5. 阈值重定

| 档 | 原（50 分） | 新（54 分） |
|---|---|---|
| 简单 | 0-6 | 0-7 |
| 标准 | 7-18 | 8-20 |
| 复杂 | 19-30 | 21-33 |
| 极复杂 | 31+ | 34+ |

> 新阈值按原比例折算 [COMPUTED，需实测校准]。总分不作唯一判定，主轴 + 高危 + 豁免优先。

## 6. 定档人机确认与回溯（新增 §6.4）

### 6.1 触发时机

- **唯一强制确认点**：discovery Step 3.4 二次校准完成后立即执行一次"定档确认"。
- 初判（Step 2.2）只回显不确认——标注"初判，待二次校准后定档"。
- 澄清中触发高危升档：保底直接生效（宁严勿松），只回显"已升档 + 原因"，不打断澄清。

> 权衡：新增确认点是必要闸门，不是冗余确认——它把 policy §6.1"用户最终确认等级"落地为具体交互，统一了"下调须显式确认"的隐式确认。

### 6.2 回显内容

```
系统评估结论：
- 复杂度档位：标准
- 总分：11 分（业务 5 / 技术 4 / 合规 2）
- 主轴信号：多角色、局部业务流程、4~15 条规则、3~5 状态
- 高危信号：无　豁免规则：未命中
- 建议流程档位：normal（4 阶段，review + readiness，整稿确认）
```

### 6.3 用户选项（四档直选，系统建议高亮）

```
请确认复杂度档位（决定后续链路与评审强度）：
A. 简单   — 轻量链路：discovery → draft 单页 → ship 免评
B. 标准   — 标准链路：4 阶段 + review + readiness      ← 系统建议
C. 复杂   — 严格链路：4 阶段 + review + testability + readiness
D. 极复杂 — 严格链路最高强度
```

- 选系统建议档 = 认可，无需理由；选其它档 = 人工覆盖，须附一句理由（上调直接生效；下调按 §6.2 属显式确认）。

### 6.4 回溯落盘（无论认可或覆盖，均记录）

系统评估值（不可变）与最终值分两段写 `state.yaml` 的 `complexity` 块（增量长出），`req_baseline.md` 元数据区同步留痕：

```yaml
complexity:
  system_assessment:          # 系统评估，不可变，供回溯
    tier: standard
    score: 11
    business: 5
    technical: 4
    compliance: 2
    axis_signals: [多角色, 局部业务流程]
    risk_signals: []
    waiver: none
  final_tier: standard         # 最终档位（人工确认后）
  overridden: false            # 是否人工覆盖
  override_direction: none     # up / down / none
  override_reason: ""          # 覆盖理由（覆盖时必填）
  confirmed_at: ""
  confirmed_by: ""
```

> 用途：事后发现误判时，回溯"系统评了什么、人工怎么改、为什么"，据此校准主轴信号与阈值——policy §1.6"基于历史交付数据校准"的数据来源。

## 7. 流程环节分档（不同复杂度走不同链路）

### 7.1 三档路由总览

| 档 | workflow.mode | 阶段序列 | 交付物 |
|---|---|---|---|
| 简单 | `tweak` | discovery → draft(一次成稿) → ship(免评)，**跳 refine** | 单页需求说明 / 变更说明 |
| 标准 | `normal` | discovery → draft → refine(精简) → ship | 精简 PRD |
| 复杂/极复杂 | `strict` | discovery → draft → refine(11章) → ship | 完整 PRD 11章+4附录 |

> 迭代需求的"现状探查"在 discovery 内完成（Step 3.2 资源扫描升级为现状探查，产出《现状基线》作第三输入），不新增独立阶段。

### 7.2 交付物矩阵（变更性质 × 复杂度）

| | 全新（greenfield） | 迭代（brownfield） |
|---|---|---|
| 简单 | 单页需求说明 | 变更说明（现状→改动→验收） |
| 标准 | 精简 PRD | 精简 PRD + 现状基线 |
| 复杂 | 完整 PRD | 完整 PRD + 现状基线 + 回归/兼容专项 |

> **交付名后缀（开放点 1 裁定）**：简单档 `{前缀}-{中文名}-需求说明-v1.0.md`；标准/复杂档 `{前缀}-{中文名}-需求终稿-v1.0.md`。理由："终稿"对单页/变更说明不准确，文件名即让研发区分"轻量说明 vs 完整终稿"避免误读。代价：ship 命名规则加档位分支 + docs/prd 归档约定同步。

### 7.3 章节裁剪表（复用 refine 模板 `[必填]/[条件必填]/[可选]`）

简单档**不套完整 11 章模板**（单页 / 变更说明，形态见 7.2）；标准/复杂档按模板裁剪：

| 章节 | 简单 | 标准（精简） | 复杂（完整） |
|---|---|---|---|
| 一 概述 | 痛点≤1 + 范围 In/Out | 痛点2-3 + 目标 SMART + 假设 | 全量（痛点3-5、目标分层、假设+责任人） |
| 二 角色与权限 | 角色单表 ≤2，无权限矩阵 | 角色 + 权限矩阵（命中才写） | 完整 |
| 三 流程 | 仅 1 张核心流程图 | 主流程 + 关键旅程 | 端到端 + 旅程 + 异常边界清单全量 |
| 四 数据模型 | 字段表并入第 5 章 | 新增实体才写（L1） | L2 代码验证全量 |
| 五 功能需求 | 功能描述 + 输入输出 + 验收 | + 前置/后置/分支 | 全要素 + 核心算法 + UI + 接口 |
| 六 业务规则 | 并进第 5 章（≤3 条） | 精简汇总表 | 完整 + 全局唯一编码 |
| 七 状态流转 | 不适用（≤2 状态） | 命中才写 | 全状态机 + 流转规则 |
| 八 非功能 | 不适用 | 性能/安全精简 | 全量 + 量化指标 |
| 九 依赖约束 | 不适用（单系统） | 精简 | 全量 + 降级方案 |
| 十 验收 | 功能验收 + 验收标准 | + 数据一致性 + 成功度量 | 全量 + 回滚验收 |
| 十一 风险 | 风险 1-3 条 | 风险 + 待确认 | 全量风险登记册 |
| 附录 A-D | 仅 A（有基线时） | A + C | A + B + C + D |

> 篇幅上限（draft 模板已内建，沿用）：简单 ≤800 字 / 标准 ≤2000 字 / 复杂 ≤4000 字（不含图表表格）。

### 7.4 质量控制分档（评审次数）

| 档 | review(7维) | testability(4维) | readiness(5维) | 依据 |
|---|---|---|---|---|
| 简单 | 免 | 免 | **免评**（PASS(waived)+审计） | 验收=字段校验直接判定，缺陷代价低、可回滚 |
| 标准 | ✅ subagent | **降级**：主代理 inline 精简 checklist | ✅ 全评 | 验收可判定性并入 review 同一轮 |
| 复杂 | ✅ subagent | ✅ subagent 全量（4维+评级+GWT逐条补全） | ✅ 全评 | 资金/合规/核心链路需硬证据 |

> **testability 标准档是"降级"不是"免除"**：review 维度 4 查"规则可判定"、维度 2 查"验收存在性"，但不产 GWT 补全与 A/B/C/D 评级，而验收标准是测试侧唯一输入 [COMPUTED]。降级 = 主代理 inline 只查三个硬问题（功能点≥1 条可判定验收 / 规则可判定 / 指标可量化），不产评级、不逐条 GWT 补全。省的是第二次 dispatch 开销，不是检查本身。

### 7.5 人工介入点分档（确认次数 + 逐章/整稿）

| 档 | 确认点 | 逐章 vs 整稿 | 确认时展示 |
|---|---|---|---|
| 简单 | 命名 / 定档 / 基线+初稿整体 / 交付 = **4** | 整稿 | 增量 + 重点标注 + 待决清单 |
| 标准 | + 终稿整稿 = **5** | 整稿 | 评审重点指引 + 差异高亮 |
| 复杂 | 逐章(5+15) + 修复确认 = 全量 | 逐章 | 每章摘要 + 自检表 + 重点校验表 |

> 两条原则 [INFERRED，MED，依据 DoR "checklist not gate"]：
> 1. **逐章 vs 整稿由 `workflow.mode` 决定，不靠用户手动选**——现状 draft 硬性"一章一确认"、refine 反而让用户选"逐章/全量"（Step 1.5），轻重倒挂。改为 `tweak`/`normal` 整稿、`strict` 逐章，删除 refine 的 A/B 询问。
> 2. **压"阅读量"而非只压"确认次数"**——真正成本是阅读负荷与上下文切换。确认时只展示增量/差异视图 + 重点标注 + 待决清单，不贴全文。

**简单档确认点收口（开放点 2 裁定）**：确认点下限是 **4 个，压不到 2 个**——命名 / 定档 / 基线+初稿整体 / 交付。

- 成立的一条合并：**基线整体确认并入初稿整稿确认**（简单档基线就是初稿的全部输入，两次确认是同一件事）。
- 压不掉的两个：**命名**（全局命名空间，事后改名代价高，必须单独确认）与**定档**（§6 链路闸门，必须单独确认）。且三者时序分离——命名在 Step 2.6.1、定档在 Step 3.4、基线确认在 Step 7.7——无法物理合并。

> 修正：初版方案曾称"简单档 4 点可压到 2 点"，漏算了新增的定档确认 + 命名必须单独。最终下限 4 点。

### 7.6 机制修正（对 graded-workflow-design 草案的 6 处）

| # | 草案写法 | 修正为 | 理由 |
|---|---|---|---|
| D1 | 简单档新造"轻量需求说明"独立产物 | 复用 draft 单页 / 变更说明，模板删空行 | one-pager = 同模板删空行 [COMMON]；不新造产物 |
| D2 | 简单档 `discovery → ship` 跳 draft+refine | `discovery → draft(单页/变更说明) → ship` 跳 refine | discovery 保持纯澄清；draft 内建复杂度裁剪+重点保留率≥95%+交叉校验，是现成质量兜底 |
| D3 | 标准档"免 testability" | testability 降级为 inline 精简 checklist | review 不产验收补全，标准档最需要可判定验收 |
| D4 | 极复杂单列流程档 | 并入 strict 作 `critical` 标记 | 技术委员会/里程碑在单人平台不可执行 |
| D5 | readiness 免评 E1 只覆盖"纯文案变更" | 扩展免评信号"逻辑简单 CRUD / 轻量迭代（tweak 且无高危）" | 否则简单档仍被 readiness 拦下全评 |
| D6 | refine 让用户选逐章/全量 | 读 `workflow.mode` 自动决定 | 消除轻重倒挂 + 不把流程决策推给用户 |
