## 2. 四档评估标准（评分分级）

| 等级 | 总分 | 典型场景 | 管控要求 |
|------|------|----------|----------|
| 简单 | 0-6 | 增删改查、简单表单/展示、状态开关；文案/参数/样式修改 | 免正式评审，快速交付，常规功能测试 |
| 标准 | 7-18 | 多角色单系统新增模块、常规业务流程新增、局部逻辑调整 | 产品+技术常规评审，标准流程，全量功能测试 |
| 复杂 | 19-30 | 跨 2 系统、新增核心实体、改造核心链路、第三方对接、中高合规 | 架构师参与评审，方案先行，增强测试，上线前专项复核 |
| 极复杂 | 31+ | 跨多系统核心重构、大规模数据模型改造、强监管高危、核心链路重大调整 | 技术委员会评审，里程碑交付，专项测试+安全审计，全链路灰度 |

> 评分细则（50 分各维度分值、CRUD 豁免、高危分级升档、双向校准）见 `complexity-assessment-policy.md`。

## 3. 关键设计决策与理由

### 3.1 CRUD 豁免（保证「简单 = 增删改查」）

- **问题**：v2 评分表「新增核心数据实体 +2/+3」「新增完整业务流程 +4」会让标准 CRUD 得约 6-7 分，落「标准档」，与「简单 = CRUD」冲突。
- **决策**：逻辑极简的 CRUD（业务规则 = 0、流程分支 ≤ 1、无计算/并发/事务、单系统、无高危）时，`需求变更幅度` 与 `新增核心数据实体` 两维**不计分**，稳定落「简单档」；命中任一逻辑复杂度信号则豁免失效。
- **依据**：判定主轴 = **逻辑复杂度**（业务规则/状态/计算/并发），规模与实体数量为辅助。

### 3.2 评估四档、流程档位三档

- **问题**：`workflow.mode` 只有 `tweak/normal/strict` 三档，塞不下「极复杂」。
- **决策**：评估保留**四档**（更细的管控分级）；流程档位（`workflow.mode`）仍**三档**，复杂·极复杂都映射 `strict`，`strict` 内再分强度（极复杂 = 技术委员会/里程碑/专项审计）。因此「流程分级设计」呈现四档，但底层档位仍是三档。
- **依据**：复用 coding 族既有 `modePhases` 机制，不新造第四档。

### 3.3 高危分级升档

- **问题**：v2「逐级升档」有漏洞——「简单 + 资金」逐级只升到「标准」，不到位。
- **决策**：致命信号（资金/敏感个人信息/监管/核心链路）**一票升「复杂」起步**；严重信号（数据迁移/多租户隔离/底层组件/不可回滚）**逐级升一级**。
- **依据**：保留原 policy「一票否决」兜底语义，同时引入 v2 的精细化，堵住「高风险被轻判」与「低风险被一刀切」两个漏洞。

## 4. 四档流程分级（流程分级）

不同复杂度走不同流程，**评分四档 → 流程四档**（流程档位仍映射三档 `workflow.mode`）：

| 维度 | 简单（轻量） | 标准 | 复杂 | 极复杂（strict 最高强度） |
|------|-------------|------|------|--------------------------|
| 阶段序列 | `discovery → ship` | 4 阶段 | 4 阶段 | 4 阶段 + 里程碑拆分交付 |
| 评审次数 | 0（readiness 免评） | 2（review + readiness） | 3（review+testability+readiness） | 3 次 + 技术委员会评审 |
| 人工确认 | 2 个阻塞点 | ~5 个（整稿确认） | 逐章全量 | 逐章 + 里程碑确认 |
| 参与角色 | AI + 需求提出人 | AI + 产品 +（技术复核） | AI + 产品 + 技术 + 合规 | + 架构师/技术委员会 |
| 审批权限 | 单点确认 | 产品 + 技术复核 | 会签 + 合规硬性签字 | 技术委员会会签 |
| 交付物 | 轻量需求说明 | 标准 PRD（精简章节） | 完整 PRD | 完整 PRD + 里程碑计划 + 专项测试/安全审计 |

> 流程细节权威 = `prd-graded-workflow-design.md` §4（已升级四档：§4.1 四档总览、§4.5 极复杂档、§4.6~4.9 分档细节、附录 A/B 对齐四档）。
