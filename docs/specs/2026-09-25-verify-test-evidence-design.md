## 一、目标与范围判定

### 1.1 目标 = 三重符合性

| 层 | 含义 | 工程落点 |
| --- | --- | --- |
| Validation | 符合需求 | 意图验收（4.0.1）+ 规格场景可追溯 + **业务语义确认（4.4，人工）** |
| Compliance | 满足规范 | Constitution 审计（Step 2）+ scorer（Step 3） |
| Verification | 正确实现 | **执行测试套件 + 判读（本文主体）** + 独立代码评审（4.3） |

依据：用户 2026-09-25 的定义。注意「可信」不是目标而是**手段** —— 4.3 独立裁判存在的目的是让符合性判断可信。

### 1.2 由目标直接推出的裁剪：L4 划出 v1

L4 增强验证（**变异测试 / 属性测试 / 性能压测 / 多模型交叉**）验的是「**测试本身有没有意义**」，不是「实现对不对」。

- 它属**测试质量**，不属**实现正确性** → **不在三重符合性内**，划出 v1（可作为后续独立里程碑）
- 报告 §5.4 的「一个无法失败的测试比没有测试更糟」成立，但它论证的是**测试有效性**这条独立的轴，不能并进本目标

这条裁剪消掉了整个方案里最贵的一块。`coding/codereview/SKILL.md` 已把「多模型交叉验证」标注为推迟 v2。

### 1.3 目标边界内的三层测试

「正确实现」靠测试用例验证，测试用例不止单测。三层按**环境代价**与**归因难度**递增：

| 轨道 | 经典含义 | 环境 | 成本 | 归因 |
| --- | --- | --- | --- | --- |
| 单元 | 碎片正确性 | 零依赖 | 秒级 | 直接 |
| 集成 | **模块间接口与真实依赖的交互**（如 DAO ↔ 真实 DB） | 需 DB / 容器 | 分钟级 | 中 |
| 主干功能（E2E / smoke） | 业务流程跑通 | 完整运行环境 | 分钟+ | 难 |

> 术语澄清：「集成测试 = 功能测试用例」不成立 —— 集成测试验的是**接口交互**，可以完全不涉及业务流程；「主干功能跑通」在工程上叫 **E2E / 冒烟测试**。二者是两个不同轨道，不能合并成一档。
>
> 报告侧印证：§5.3 的 L3 本来就含**契约测试** → 补集成层不是新目标，是**回到报告 L3**。

### 1.4 执行顺序及其依据

`4.0 → 4.3` 的排列依据两条，冲突时**方向优先**。

1. **方向优先** —— 先确认「做的是要的东西」，再确认「做得对」。方向错了，后面所有测试与评审都白费，所以 `4.0.1 意图验收` 排最前，**尽管它靠判断完成、代价最高**。
   *依据*：IEEE 1012（Validation 先于 Verification）；报告 §4.1「缺失前置环节会导致 AI 在错误的方向上高效生成」。
2. **先机器后人工** —— 代价低、可自动化的先做完，人工只接机器覆盖不了的**判断性**工作。
   *依据*：注意力稀缺 —— 人工审查有效性超 400 行骤降（报告 §2.2）；「把人类注意力释放给判断性决策，而非机械性检查」（报告 §5.2，遵守率 60% → 90%+）。

**第 2 条的边界**：人工接的不是「机器剩下来的全部」。机械性残留 —— 环境没起、需手工跑一条命令 —— 走 §4.0.4 第 2 级 / `No-Verification`，**不占人工**；否则人工层被这些琐事撑满，越过 400 行就形同虚设。

```
4.0.1 意图验收        ← 方向优先，排最前
  → 4.0.2 命令获取    ← 人工确认一次（属配置，不属验证）
  → 4.0.3/4/5 三档执行 + 三级分叉 + 三段判读   ← unit → integration → smoke，代价递增
  → 4.2 自动检查项     ← scorer / Constitution / 编译，零注意力成本
  → 4.3 独立代码评审   ← 机器侧最后一道，此时输入已可信
  → 4.4 人工验证       ← 人工侧唯一落点：业务语义确认
  → 决策点             ← 人 = 裁决者（与 4.4 的验证者角色不同）
```

> 人工在 verify 里共三个角色：**配置确认者**（`4.0.2` 命令、`4.0.5` 红名单）、**验证者**（`4.4` 业务语义确认）、**裁决者**（验证失败 / override / 规格漂移）。**验证者**一档原为缺口（报告 §5.5.1 第 3 项在本文无落点），2026-09-27 由 `4.4` 补上。
>
> `4.0.1` 与 `4.4` 同在**方向轴**上，一前一后不矛盾：`4.0.1` 是最前的**粗粒度闸门**（决定要不要继续往下验），`4.4` 是最后的**细粒度复核**（决定能否放行）。细粒度复核放最后，因为它需要机器侧结论作输入，且人工注意力要留给机器覆盖不了的部分。

**探测由脚本执行**（2026-09-27 定）：新增 `assets/shared/scripts/detect-test-command.sh`，**判定表是唯一可执行实现**，verify 正文只写「调用它」与执行期增量。

**脚本契约**（仓库既无显式脚本退出码约定 —— `constitution-validity.sh` / `complexity-scorer.sh` 里零 `exit` 语句 —— 故此处新定）：

| 项 | 约定 |
| --- | --- |
| 入参 | `--repo-root <path>`（必填）；`--slot unit\|integration\|smoke`（默认 `unit`） |
| stdout | 机器可解析的 `key: value` 行：`framework` / `command` / `evidence`（判定依据，含文件:行）/ `confidence` / `excluded`；**退出码 `1` / `2` 时另有 `reason`**（说明为何探测不到 / 为何不可执行 —— 让 agent 能区分「无构建文件」与「有包但无 test 脚本」） |
| 退出码 | `0` = 探测到可用命令 · `1` = 探测不到（项目无此层验证） · `2` = 探测到但不可执行（不在 PATH / 非可执行。入参错误同用 `2`，属「外部命令不可用」同族） |

退出码 `1` / `2` 与 §4.0.4 的三级分叉一一对应（第 1 级 / 第 2 级），**不得合并** —— 合并会把「项目没测试」与「环境坏了」混为一谈，正是 4.0.4 要防的那个坑。

**探测优先级**（逐段降级；即脚本内部顺序）：

| 序 | 来源 | 判定 |
| --- | --- | --- |
| 1 | **项目显式声明**：项目根说明文件（README / CONTRIBUTING / CLAUDE.md）的 **`## Testing` / `## 测试` 章节** | **权威来源**。有则直接采用，不再往下探测 |
| 2 | **Makefile 显式 target**（`test:` / `smoke:` / `integration:` …） | 同属「**声明**」（作者写下来的），故排在「推断」之前。**原表把它列在清单末尾，实现时上提** |
| 3 | **清单文件检测**（见下表） | 属「**推断**」 |
| 4 | 无 | → 退出码 `1` |

> 顺序依据：「**声明 > 推断**」。`## Testing` 是项目作者的明文；Makefile target 也是明文（只是形式不同）；清单文件的存在只是推断。
>
> `config.command`（历史确认值）**不在脚本职责内** —— 由 4.0.2 入口先行读取，脚本输出仅用于「与之冲突」的比对。

**章节目录的门槛（实现时踩到，记录备查）**：`## Testing` 必须匹配**二级标题**；三级 `### Tests` **不算** —— 它常是 CHANGELOG 模板的分类项。同理，从章节里取命令要求**两道闸**：① 含测试语义词；② **首词像命令**（已知命令名 / `./` 路径 / `.sh`）。缺第 ② 条时，「单元测试放在 `test/ts/`」这类路径说明会被当成命令。

**清单文件判定表**（第 2 序；目标＝**单测命令**，右列是**明确排除项**；本表随脚本走，verify 正文只留「单测边界」这一条增量）：

| 检出标志 | 框架 | 该跑 | 明确排除 |
| --- | --- | --- | --- |
| `pom.xml` | Maven · Surefire | `mvn -B test` | `mvn verify`（Failsafe `*IT.java` = 集成） |
| `build.gradle(.kts)` | Gradle | `./gradlew test` | `check`（含集成 / 静态分析） |
| `package.json` + lockfile | npm / pnpm / yarn / bun | 对应 `<pm> test` | e2e 脚本（`test:e2e`） |
| `requirements.txt` / `pyproject.toml` / `pytest.ini` | pytest / unittest | `pytest` | `tox` / `nox` 的集成环境 |
| `go.mod` | go test | `go test ./...` | `-tags integration` |

**修正须按反馈类型分流**（不得一律重探）：

| 人工反馈类型 | 例 | 处置 |
| --- | --- | --- |
| **明确命令** | 「就跑 `npm run test:unit`」 | **不再探测** → 校验后采用。理由：再探测会让系统猜测**覆盖**人的明确指令，甚至回到刚被否定的答案 |
| **线索 / 纠错** | 「这是 monorepo」「包管理器用 pnpm」「用 `./mvnw`」 | **必须重探**（人给的是不完整信息，系统负责落实到命令） |

**收敛条件**：重探 ≤ **2 轮**；超限则请人工直接给命令，或记 `No-Verification`。不得伪造选项。

**落盘**（`.polaris/config.yaml`）：`command` + `source: probed|confirmed|corrected` + `confirmed_at`。

- config 不靠手填 —— 值 = **探测结果 + 人工确认的产物**
- **确认一次长期有效**：已有 confirmed 值 → 下次 verify 直接读、不再问（否则每轮都停一次，高频变更会烦）
- **冲突时 config 优先**：项目换了框架、探测结果不符 → 不打断，仅在报告记一行提示

**可执行确认 4 项**：

1. 命令在 PATH（可复用 `src/core/integrations/detect.ts` 的 `commandAvailable()` 模式：`which`/`where` + 超时）
2. 脚本 / target 存在（`npm pkg get scripts.test` 非 null；`make -n test` 不报错）
3. **不是 watch 模式** —— 统一加 **`CI=true`** 前缀（多数框架据此从 watch 转单次运行）
4. 环境依赖（**探测不出来**，只能首跑时暴露 → 走 4.0.4 第 2 级）

### 4.0.3 三档执行

| 轨 | 命令槽（`test.commands.*`） | 触发条件 | 环境 | 超时默认 |
| --- | --- | --- | --- | --- |
| 1 单元 | `unit` | **总是跑**（`light` / `full` 都要） | 零依赖 | 300s（JVM 生态 600s） |
| 2 集成 | `integration` | 改动跨模块边界 / DAO / 外部接口 | 需 DB / 容器 | 600s |
| 3 主干功能 | `smoke` | `verify_mode=full` **且**该槽位存在 | 完整运行环境 | 900s |

**超时策略**（2026-09-25 定）：**按框架给默认表 + config 可覆盖**。

| 生态 | 默认 | 依据 |
| --- | --- | --- |
| Node / Go / Python / Ruby / PHP | 300s | 无 JVM 启动开销，单测多为秒级 |
| Maven / Gradle（JVM） | 600s | JVM 启动 + 编译重 |

- **首次超时自动放宽 1 次**（×2）—— 冷缓存、依赖首次下载、首次编译是常见假超时
- **仍超时** → 落 4.0.4 第 2 级（无结果摘要 → 环境）处置。**但须保留已产生的部分输出**：若已有「执行 N 用例」摘要后卡在某条，证据留档供人看 —— 它可能是**死锁类真缺陷**（并发 / 未释放锁），而非环境问题。判定仍按第 2 级（不自动回 build），但报告须写明「卡在第 N 条」这一事实
- 超时值落 `test.timeout.{unit,integration,smoke}`，与命令同属 config 的**确认产物**

- **槽位缺失 → 记 `No-Verification: 无 … 入口`** + 报告声明，**不阻断**（技能不自己拼装环境）
- **三档共用 4.0.2 的同一套回路**（探测 → 展示 → 人工确认 → 落盘），只是多两个槽位；**一次展示、一次确认**，不逐个问
- **v1 范围**：三档**接口**进 v1；集成 / 功能档**按项目可用性降级**（无入口 → `No-Verification`），避免无环境的项目卡死

### 4.0.4 三级分叉判读

「环境由项目负责」使「**入口存在但环境没起好**」成为高频情形。若只写「非零退出码 → 回 build」，则 **Docker 没起 / DB 连不上**会被误判为**代码缺陷** → agent 去 build 里找一个不存在的 bug。

| 级 | 现象 | 性质 | 处置 |
| --- | --- | --- | --- |
| 1 | **探测不到入口**（项目本来就没有这层验证） | **项目属性** | **`light` → 记 `No-Verification` 放行 + 报告声明；`full` → 阻断**（见下） |
| 2 | 入口存在但**无测试结果摘要**（0 用例 / 进程异常退出 / 命令不存在 / 超时） | **环境 / 基础设施问题** | 重试 1 次 → 仍失败记 `No-Verification: 环境不可用`；**不当作代码缺陷、不回 build**；超时若已有部分摘要须留档（见 4.0.3） |
| 3 | 跑起来且**有测试结果摘要**（执行 N 用例 / M 失败） | **真实验证失败** | 进 4.0.5 三段判读 |

**第 1 级的判定（2026-09-25 定）＝按 `verify_mode` 分**：`light` 放行 + 声明、`full` 阻断。这是「**风险决定做不做**」的直接应用 —— 小改动没有测试证据可以放，大改动不行。

- 第 1 级的声明**复用既有措辞**：`项目无测试框架，建议先引入`（出处 `coding/tasks/references/test-review-methodology.md:25`，避免同一件事出现第二种说法）
- 与既有措辞的关系：既有的那句写在**计划期**的报告里（评审计划的测试覆盖，不阻断）；本处写在**执行期**（`full` 时阻断）。措辞一致、时机不同
- ⚠️ 由此推出的风险：`full` 下的阻断会让**尚无测试框架的项目无法完成 verify**。这是有意的 —— 但它把这类项目挡在门外。若你希望给它们一条路径（如「首次 `full` 只警告、二次起阻断」），属新增决策，见 §八

**判据**：*有没有测试结果摘要* —— 测试框架跑起来必输出「执行 N 个用例」；环境问题通常连收集都没开始。**可机械判定，不硬编码任何错误消息。**

**防滥用**：「环境由项目负责」**≠**「技能可预判环境不可用而跳过」。**必须真调用一次让失败暴露** —— 否则会冒出新的逃避路径（自判「环境估计不行」→ 静默放行）。这是「环境不归我管」这一自由的镜像锁。

### 4.0.5 三段判读 + 基线红名单

**一次执行、三段判读**（否决「先跑增量再跑全量」：增量轨是全量的**子集**，跑两遍等于把子集测两次）。

**前置：flaky 处置**（2026-09-25 定 = **`retry_and_mark`**）—— 任一条红**先自动重试 1 次**再判读：

| 重试结果 | 判定 | 报告 |
| --- | --- | --- |
| 通过 | **算通过**（不阻断），但**强制标注** `首次失败 · 重试通过` | 必须写入报告的「flaky」段 |
| 仍失败 | 进下方三段判读，按真失败处置 | 正常记录 |

- **强制标注是这个选项的全部价值**：重试解决「偶发抖动卡流程」，标注解决「flaky 被静默掩盖 → 永远没人修」。
- 一个 change 内**同一用例两次重试才过** → 升级 **CRITICAL**（不是抖动，是设计问题）。
- 与报告原则的偏差**须登记**：报告 §5.4 倾向「不重试」（`fail_on_flake`，「一个无法失败的测试比没有测试更糟」）。本设计取 `retry_and_mark` 是**工程折中**——代价是「首次失败」不再阻断，用**强制标注**换回可观测性。策略键 `test.flaky_policy`，config 可改回 `fail_on_flake`。

| 判读段 | 规则 |
| --- | --- |
| a **增量轨** | 本次新写的测试有红 → **回 build**（**本次新增的测试必须绿** —— 属 build 的欠账）。**不比对红名单** |
| b **存量轨** | 红且**不在**红名单 → 回 build（**回归**）；红且**在**红名单 → 记 `No-Verification: 历史欠债` 放行 |
| c **清单增删** | 测试文件**删除 / 加 skip**（`@skip` / `xfail` / `.only` / 注释掉断言）且无理由 → **CRITICAL** |

判读 c 的依据：报告 §5.4「一个无法失败的测试比没有测试更糟，因为它制造虚假信心」。写清要求：新增 N / 修改 M / **删除必须为 0**（或逐条显式声明理由）。「全绿」报告对这一点完全无感。

**证据落盘**：每轨执行必须留「**命令 + 退出码 + 输出摘要 + commit SHA**」。

**基线红名单**（定义见 §十）—— 默认走 A，红名单为可选逃生门：

| 序 | 来源 | 成本 | 前提 |
| --- | --- | --- | --- |
| 1 | 项目提供的命令 / CI artifact（`test.baseline.command` / `file`） | 零 | 需项目提供 |
| 2 | **人工确认一次** → 落盘快照，绑定本 change | 低（一次性） | 无 |
| 3 | 跑 base commit（临时 worktree + 可能重装依赖） | **分钟级重操作** | base SHA 可得 |
| 4 | 降级 **A（全绿）** + 报告显式标注 | 零 | 兜底 |

**为什么默认 A 就够了**：红名单只对「**CI 本身有红**」的项目有意义。项目 CI 全绿时红名单 = 空集，B ≡ A，不需要任何额外机制。于是健康项目**零额外成本**，只有存量有红的项目才付出红名单代价 —— 而它们本来就需要。

**人工确认的交互形态**（复用「探测 → 展示 → 确认 → 落盘」回路，同一机制第 4 次出现）：

1. `4.0` 跑完全量 → 有红 → 无基线可用
2. **AI 先按影响面启发式预填**：失败的测试所覆盖的代码**是否落在本次 diff 内**？命中 → 倾向「本次回归」；未命中 → 倾向「历史欠债」。**预填而非空白**
3. 展示「红列表 + 预判」+ 三选项（[A] 预判正确 · [B] 修正 · [C] 全部按严格处理）→ 人工勾选
4. 落盘 `baseline-tests.*`（**绑定本 change 的一次性快照**）；判定：名单内 → `No-Verification` 放行，名单外 → 回 build

**三条防滥用**：

- **「不确定」默认按严格处理**（当作回归）—— 防随手全选放行真回归
- **每个 change 只问一次**，落盘后复用，不再重复问
- **新增测试红了不问** —— 新测试本来就该绿，直接回 build，不进红名单判定

**实现细节**：

- 粒度取**用例级**（文件级太粗：一个文件里 3 个用例红，把整个文件列进名单等于连带放行另外那些没人看过的失败）
- 采集时机：**verify 首次执行时采集一次、落盘缓存**（`openspec/changes/<task_id>/reviews/baseline-tests.*`），后续复用，不每次重跑 base
- ⚠️ **polaris 未记录 base commit**：`assets/shared/templates/state.example.yaml` 的 `worktree` 段只有 `created_by_polaris_flow / path / branch / origin_repo / status / created_at`，**无 `base_commit`**；`src/core/hooks/worktree.ts` 里唯一的 `merge-base` 用法是 `--is-ancestor`（判分支是否为 HEAD 祖先），**不取起点**。⇒ 第 3 序「跑 base commit」在现架构下需用 git 推导（`merge-base(<worktree.branch>, 主仓库当前分支)` 或 `@{upstream}`），**推导可行但脆弱** —— 这正是把人工确认（第 2 序）排到它前面的理由

### 4.4 人工验证（业务语义确认）

**性质**：verify 里**唯一的「人工验证者」**角色（其余人工触点为配置确认者 / 裁决者，见 §1.4）。位置在既有 `4.3 独立代码评审` **之后**、验证失败决策点**之前**。

**为什么放最后**（与 `4.0.1` 同在方向轴，一前一后不矛盾）：

- `4.0.1` 是最前的**粗粒度方向闸门** —— 决定「要不要往下验」
- `4.4` 是最后的**细粒度方向复核** —— 决定「能否放行」
- 放最后两条理由：① 它需要机器侧结论作输入（哪些改到了、哪些没验到、评审提了哪些 CRITICAL）；② 人工注意力稀缺（报告 §5.2 / §5.5），必须先让机器把噪声清掉

**输入（给人看这三样，不给人看原始 diff）**：

| # | 输入 | 来源 |
| --- | --- | --- |
| 1 | 意图基线 | `4.0.1` 产出 |
| 2 | **术语 → 实现**映射清单 | 从 specs + diff 提取，逐条列「业务术语 → 落到哪个实现」 |
| 3 | 机器侧结论摘要 | `4.0.4/5` 的轨结果 + `4.3` 的 CRITICAL / IMPORTANT 列表 + `No-Verification` 清单 |

**人只判一件事**：*AI 是否正确理解了业务术语，实现是否符合业务规则的真实意图*（报告 §5.5.1 第 3 项）。

典型误读（报告 §4.3 券商案例：跨客群额度复用漏洞绕过监管沙盒三重校验，UAT 阶段才被**人工审计**捕获）：

| 误读类型 | 例 |
| --- | --- |
| **作用域错** | 本客群 / 本租户的校验用到了别处的数据（券商案例） |
| **口径错** | 「逾期」的起算点、「金额」含税与否、「有效期」是否含当天 |
| **同名不同义** | 代码里的 `User` / `Account` 与需求文档里的同名术语不是一回事 |

**聚焦边界**（§1.4 第 3 条依据的落地）：**不做机械性检查** —— 不让人跑命令、对行号、查格式、核编译。那些属 `4.0.3` / `4.2`；环境类问题走 `4.0.4` 第 2 级。原因：报告 §5.5 明说人工审查有效性超 400 行骤降，**把机械性残留派给人会当场清空这一档的效用**。

**输出与处置**：

| 人的结论 | 落盘 | 后续 |
| --- | --- | --- |
| 确认无误 | `runtime.verify.semantics_review=confirmed` | 进决策点 |
| **发现偏** | 记入报告「业务语义确认」段 | 进「验证失败决策」 |
| **明确跳过** | `semantics_review=skipped_by_user` + **原因必填** | `full` 下记 `No-Verification: 用户跳过业务语义确认`；不额外阻断 |

- **触发**：`light` / `full` **都必现** —— 业务语义误读与改动规模无关，改 3 行一样可能把「逾期」理解错
- **不得默认跳过**（与 `codereview` 的降级三选项同构：**可降级、必须标**）。允许跳过是因为人是稀缺资源、可能不在场；要求留原因是因为这一步一旦静默消失，报告会看起来「全绿」而这层根本没做
- **与 `4.3` 不可互相替代**：`4.3` 是机器（独立 subagent）审「**代码写得对不对**」，`4.4` 是人审「**写的业务含义对不对**」。4.3 做不出业务语义判断（它没有业务上下文），4.4 不做逐行代码审查（那是 4.3 的活）
- **落盘**：`openspec/changes/<task_id>/reviews/verify-report.md` 的「业务语义确认」段 + `runtime.verify.semantics_review`

| 键 | 默认 | 依据 |
| --- | --- | --- |
| `timeout.*` | 300 / 600 / 900 | 按生态：无 JVM 启动开销的 300s 足够；JVM 600s；smoke 含环境准备故 900s。首次超时自动放宽 1 次 |

## 六、边界与不变量（写进正文的总闸）

1. **防扩张总闸**：*技能显式要求的必须跑；没显式要求的不许自行扩张。*
   —— 2026-09-25 的失败样本：技能只说「跑测试」，AI 自行扩张成 `mvn verify`。界线在**显式 vs 隐含**。
2. **单测边界写死**：只执行单测命令（`mvn test` / `./gradlew test` …）；**不执行**需外部环境的集成测试（`mvn verify` / `*IT.java`）。映射表只解决「怎么找到命令」，**边界声明才防得住扩张**。
3. **环境由项目负责**：技能只调用「一条命令跑通、自带环境准备」的项目入口，**不自己起容器、不灌数据**。这是「技能定规矩、项目定参数」的延续，保证技能可装到任意技术栈。
4. **`No-Verification` 的三种合法触发**：① 探测不到入口（项目属性）；② 环境不可用（重试 1 次后）；③ 存量轨红且在红名单内。**必须真调用一次**才可判 ②。
5. **`No-Verification` 不是免罪金牌**：`full` 模式下**既无单测证据也无功能验证证据 → 阻断**；`light` 模式可放行 + 声明。（「风险决定做不做」的应用）
6. **4.3 的入口条件**：**不存在未归因的红**（所有红要么已回 build 修掉、要么已记入 `No-Verification`）才允许开始独立评审。4.3 目前只受 `review_mode` 控制，缺这个前置。
7. **检测口径的唯一实现**：判定逻辑活在 **`assets/shared/scripts/detect-test-command.sh`**；`coding/verify` 是**调用方**、`coding/tasks` 是**描述方 + 指针**（`references/test-review-methodology.md` Step 1 只用于**认出框架**，命令串一律以脚本输出为准）。**改口径＝改脚本一处**。（2026-09-25 曾登记为「两份判定表须同步」，2026-09-27 脚本化后**降级**；同日「加指针」待决项亦结项。）
8. **同一件事不出现第二种说法**：`No-Verification` 是**报告字段名**（本设计新造）；其下各触发的**声明文案**复用既有措辞，例：探测不到框架 → 「项目无测试框架，建议先引入」（出处 `test-review-methodology.md:25`）。禁止为同一现象新造第二套术语。
9. **人工验证者只有 `4.4` 一个落点**：机械性残留（环境没起、需手工跑一条命令）**不得派给 `4.4`**；`4.4` 只做业务语义判断。`4.4` 允许被用户**明确跳过**，但**不得默认跳过**，且跳过必须留原因。

### 7.1 脚本形态决策（实现时新定）

`assets/shared/scripts/` 的 14 个既有脚本都是**薄包装**（`source _polaris-cli.sh` → `exec_polaris <subcommand>`，逻辑在 `src/core/` TS 层），该目录 README 也如此陈述。新脚本**有意不遵循这一约定**，做成**自包含 POSIX bash**（对齐 `shared/scorers/test-coverage-scorer.sh` 的形态）。

理由：探测逻辑无法预先知道用户项目的技术栈；脚本随技能资产分发，须在任意项目里独立可跑。若走薄包装，逻辑会落到 `src/core/`，**用户项目必须先升级全局 CLI 才能用上新脚本** —— 版本耦合不可接受。这也让本次改动严格落在「不碰 `src/`」的范围内。

代价：`shared/scripts/README.md` 的「本目录为薄包装」陈述对本脚本不成立。该 README 属 `manifest.ignoredFiles`（不入仓、不随安装走），改动它属**不可 diff 的本地补丁**，故本次**未改**，改在本文与脚本头注释里登记。

## 十、术语与边界

### 10.1 基线红名单

**定义**＝**本次改动开始之前（base commit），本来就已经失败的测试清单**（CI 术语 known / pre-existing failures）。

**唯一作用是归因**：跑完全量后拿到「N 条红」，只有对比红名单才能把**本次引入的回归**从**历史欠债**里摘出来。没有它，每条红都无法归属 → 4.3 独立裁判的每条 CRITICAL 都无法归因，评审结论作废。

与 **C 案（`.polaris/known-failures.*` 长期清单）**的本质区别：C 是**长期清单、跨 change 复用 → 会腐烂**（修好没删、新增没加）；红名单的**人工确认是绑定当前 change 的一次性快照、用完即弃 → 不会腐烂**。

### 10.2 与 `testing` 族的边界（防双源）

`zh/skills/testing` 族两个技能：`acceptance`（写可验证的验收标准）+ `case`（写明测试用例集 + 需求-用例追溯矩阵）——**产出测试资产**，答「该测什么」。

`verify 4.0` —— **执行已有测试套件并判读**，答「测了没有、结果如何」。

二者不重叠。已在两处 `SKILL.md` 的 description 中定位为「测试设计阶段」，与本设计无职能交叉。
