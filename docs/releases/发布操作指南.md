# Polaris Flow 发布操作指南

> 给维护者看的发版手册。安装侧（使用者视角）见《安装手册（macOS / Linux）》（`docs/安装手册-macOS.md`）与《安装手册（Windows）》（`docs/安装手册-Windows.md`）。
> 权威配置以 `package.json`、`.github/workflows/publish.yml` 为准，本文只讲操作顺序。

## 怎么读这份文档

发布有两条**互斥**通道，包发到不同地方：

- **通道 A：公司 Nexus** —— 当前主路径，给内网使用者装。
- **通道 B：公网 npmjs** —— 可选，只在外部分发时才用。

**选一条，从第一节走完那一节到底，不要跳着看另一条。** 两条通道的操作是平行的完整流程，不是互补片段；混着读必然乱。

> **一条全局前提**：源码托管在 GitHub，但 Nexus 在内网 `192.168.2.96`——GitHub 的托管 runner 访问不到内网地址。所以**发 Nexus 这件事只能在内网机器上手动做**，GitHub Actions 只负责构建与自检（`Release Check`），不碰内网。

| 通道 | 包发到哪 | 谁能装 | 发布方式 | 涉及配置 | 何时用 |
| ---- | -------- | ------ | -------- | -------- | ------ |
| **A. 公司 Nexus** | `npm-hosted`（内网） | 能访问 `192.168.2.96:8081` 的人 | **内网机器执行 `./release.sh`**（GitHub Actions 只做校验） | `~/.npmrc` | **默认，日常发版就走这条** |
| **B. 公网 npmjs** | registry.npmjs.org | 任何能上网的人 | 手动触发 Actions（勾 `publish_public`）或本地手动 | `.github/workflows/publish.yml` | 需要给外部人装时 |

## 一、通用前置步骤

### 1. 升版本号

```bash
npm version patch --no-git-tag-version    # 或手动改 package.json
```

| 变更性质 | 版本位 | 示例 |
| -------- | ------ | ---- |
| 修 Bug、改文案、内部重构 | patch | 0.1.2 → 0.1.3 |
| 新增命令 / 新增能力，兼容旧用法 | minor | 0.1.3 → 0.2.0 |
| 破坏性变更（删命令、改配置语义） | major | 0.2.0 → 1.0.0 |

### 2. 写 Changelog

在 `CHANGELOG.md` 顶部新增对应版本条目，按 `Added / Changed / Fixed / Tests / Removed / Security` 分组（规范见 `AGENTS.md`）。**`package.json` 的 `version` 必须与标题版本号一致**。

### 3. 发布前自检

| 检查项 | 命令 / 位置 | 不合格的后果 |
| ------ | ----------- | ------------ |
| 版本号与 Changelog 一致 | `package.json` vs `CHANGELOG.md` 顶部 | 用户看到的版本与变更记录对不上 |
| 文件清单完整（dist / assets / bin） | `npm pack --dry-run` | 装完缺技能或跑不起来 |
| 密钥扫描通过 | `node scripts/prepublish-check.js` | 发布流程会自动拦截 |
| 构建通过 | `pnpm run build` | `prepublishOnly` 会自动拦截 |
| 测试通过 | `pnpm test` | CI 会拦截（`ci.yml`） |
| 工作区干净、分支正确 | `git status` / `git branch --show-current` | tag 指向的提交与预期不符 |

**若 `npm pack` / `npm publish` 报 `Cannot find module .../corepack/v1/pnpm/<版本>/bin/pnpm.cjs`**：

这是本机 pnpm 工具链坏了，不是包的问题。`prepare` 脚本是 `husky && pnpm run build`，`pnpm` 一跑不起来，打包就整体失败。根因是 `package.json` 的 `packageManager` 指向了 pnpm 12+（它把入口从 `bin/pnpm.cjs` 改名为 `bin/pnpm.mjs`），而 Node 自带的 corepack 0.34.x 仍按 `pnpm.cjs` 启动。

处理：把 `packageManager` 固定回 `pnpm@10.18.3`（与 `.github/workflows/*.yml` 里 `pnpm/action-setup` 锁的版本一致），再验证 `pnpm --version` 能正常输出。**要升 pnpm 大版本是另一件事**：必须同时升级 corepack 或改为独立安装 pnpm，并同步两处 workflow 的版本号，否则 CI 与本地会各跑一个版本。

### 4. 提交（先不发布）

```bash
git add -A && git commit -m "chore: release v0.1.3"
git push origin main
```

提交完，接着进**通道 A** 或**通道 B**，完成发布动作。

## 二、通道 A：发布到公司 Nexus

### A-1 一次性准备（只做一次）

**仓库布局**（已在 Nexus 2.15.1 建好并实测可读）：

| 仓库 | 类型 | 地址 | 用途 |
| ---- | ---- | ---- | ---- |
| `npm-group` | group | `http://192.168.2.96:8081/nexus/content/groups/npm-group/` | 使用者安装（托管 + 公网代理聚合） |
| `npm-hosted` | hosted | `http://192.168.2.96:8081/nexus/content/repositories/npm-hosted/` | 我们发布 |
| `npmjs` | proxy | `http://192.168.2.96:8081/nexus/content/repositories/npmjs/` | 代理 registry.npmjs.org |

**配本地认证**——Nexus 2 走 **Basic 认证**，没有 Nexus 3 那套 `npm login` / Bearer Realm：

```bash
# 1. 生成凭据（-n 不能省，带换行会认证失败）
echo -n "npm_deployment:admin123" | base64

# 2. ~/.npmrc 追加两行：read 走 group，publish 走 hosted
echo "registry=http://192.168.2.96:8081/nexus/content/groups/npm-group/" >> ~/.npmrc
echo "//192.168.2.96:8081/nexus/content/repositories/npm-hosted/:_auth=<上一步的base64>" >> ~/.npmrc
```

**不需要配任何 CI 变量**：发布在内网机器上手动执行，凭据只在你自己机器的 `~/.npmrc` 里。

**准备完先验收一次**（能返回版本号说明读链路通，与发布无关）：

```bash
npm view commander version --registry http://192.168.2.96:8081/nexus/content/groups/npm-group/
```

### A-2 首次发布

**方式一：脚本（推荐）**——把下面的检查全串起来，任一项不合格就停在发布之前：

```bash
./release.sh --dry-run    # 先空跑：检查环境 / 版本一致性 / git 状态 / 重复发布 / 认证 / 文件清单
./release.sh              # 真正发布：每步确认后执行 npm publish，并发完自动验证三条
```

| 脚本做的事 | 失败时 |
| ---------- | ------ |
| 环境（node ≥ 20 / npm / pnpm）、缺 `node_modules` 自动 `pnpm install --frozen-lockfile` | 直接报缺什么 |
| `package.json` 版本 与 `CHANGELOG.md` 顶部版本一致 | 版本不一致则拦截 |
| git 分支 / 是否在 tag 上 / 工作区脏（`.workbuddy/` 自动排除） | 列出改动，要你确认 |
| **该版本是否已存在于 registry** | 已存在则拦截（防 Allow Redeploy 静默覆盖），确需覆盖加 `--force` |
| `~/.npmrc` 是否有目标 registry 的 `_auth` | 提示 Nexus 2 的两行写法 |
| `npm pack --dry-run` 文件清单 + 关键路径（bin / dist / assets） | 附件缺失给出警告 |

参数：`--dry-run` 只检查不发布；`--yes` 跳过确认；`--allow-dirty` 放行未提交改动；`--force` 覆盖已存在版本；`--registry <url>` 换发布目标。

**方式二：手工三步**（与脚本等价，脚本调试时对照用）

```bash
pnpm install --frozen-lockfile
npm pack --dry-run    # 干跑，确认包名 polaris-flow@x.y.z 与文件清单
npm publish --registry http://192.168.2.96:8081/nexus/content/repositories/npm-hosted/
```

`prepublishOnly` 会自动跑密钥扫描 + build，耗时长是正常的（脚本走的就是这条命令）。

### A-3 以后每次发版

前置步骤（第一节 1–4 步）做完后，两步：

**第 1 步：打 tag 推送**（GitHub 跑 `Release Check`：构建 + 密钥扫描 + 文件清单自检，**不发任何包**）

```bash
git tag v0.1.3
git push origin v0.1.3
```

**第 2 步：在连得上内网的机器上发布**

```bash
git fetch --tags && git checkout v0.1.3
./release.sh              # 脚本会自己装依赖、检查版本一致性、发布、验证
```

不想用脚本就照 A-2「方式二」手工三步执行，产物完全一致。

不需要先手动 build —— `prepublishOnly` 会自动跑密钥扫描 + build，保证发出去的是当前 tag 的产物。

> `git checkout v0.1.3` 会进入 detached HEAD，发完记得 `git checkout main` 回分支再改代码。

> **为什么第 2 步不能省**：GitHub 托管 runner 在公网，路由不到 `192.168.2.96`。GitHub Actions 里**没有**、也不会有发 Nexus 的步骤——这是网络边界决定的，不是配置缺失。

> **红线：同一版本不要重复发布。** 若 `npm-hosted` 开了 Allow Redeploy，重复发布会**静默覆盖**旧版本，造成同一版本号内容不一致（排查极难）；没开则直接失败。

### A-4 发布后验证（三条都跑）

```bash
# 1. hosted 里有了
curl -s -o /dev/null -w "%{http_code}\n" http://192.168.2.96:8081/nexus/content/repositories/npm-hosted/polaris-flow
# 2. group 能读到（验证 hosted 已加入 group 聚合）
curl -s -o /dev/null -w "%{http_code}\n" http://192.168.2.96:8081/nexus/content/groups/npm-group/polaris-flow
# 3. 用 npm 客户端读（最终使用者视角）
npm view polaris-flow version --registry http://192.168.2.96:8081/nexus/content/groups/npm-group/
```

| 现象 | 原因 | 处理 |
| ---- | ---- | ---- |
| 第 1 条 200、第 2 条 404 | `npm-hosted` 没加进 `npm-group` 成员列表 | 去 Nexus 补成员，顺序把 hosted 放前面 |
| 三条全 404 | 发布其实没成功 | 回看 A-2 的输出与 hosted 权限 |
| 第 3 条版本号是旧的 | 本机或 Nexus 缓存 | `npm cache clean --force` 后重试；Nexus 侧等缓存过期 |

最后在干净机器上装一遍：`NPM_REGISTRY=http://192.168.2.96:8081/nexus/content/groups/npm-group/ bash install.sh`。

### A-5 通道 A 常见报错

| 报错 | 根因 | 处理 |
| ---- | ---- | ---- |
| `E401 Unauthorized`（publish） | `.npmrc` 里 `_auth` 的 host 段写错，或 base64 带换行 | 确认 host 段与 publish URL 完全一致（含 `//` 和结尾 `/`）；重跑 `echo -n` |
| `E403 Forbidden`（publish） | 凭据已认证但发布账号对 `npm-hosted` 无写权限。判据：带凭据访问 `service/local/repositories` 返回 **403**（而非 401）= 认证通过、权限不足；匿名 PUT 返回 401 可作对照 | Nexus 2：Security → Roles → 新建角色，勾选 `npm-hosted` 的 (browse)/(read)/(create)/(update) → 分配给发布账号。**若用 admin 账号 PUT 仍 403**，说明该 Nexus 2 的 npm hosted 不支持发布，改用 Verdaccio |
| `ETIMEDOUT 192.168.2.96` | 不在内网 / VPN 没连 | 连上公司网络或 VPN 后重试 |
| `E404` 但 hosted 有包 | `npm-group` 缺 hosted 成员 | 见 A-4 判定表 |
| `husky: command not found` / prepare 报错 | 在无 `.git` 的环境触发 `prepare` | 确认在仓库内执行；CI 侧 checkout 已带 `.git` |

## 三、通道 B：发布到公网 npmjs（可选）

### B-1 一次性准备（只做一次）

| 事项 | 操作 | 说明 |
| ---- | ---- | ---- |
| npm 账号 | 到 [npmjs.com](https://www.npmjs.com) 注册 | 包名 `polaris-flow` 发布后永久归该账号 |
| 本地登录 | `npm login` | 浏览器授权，或输入账号密码 + OTP |
| CI 令牌 | npm → Access Tokens → Generate New Token → 选 **Automation** | Automation 类型绕过 2FA，专供 CI 使用 |
| GitHub 侧配置 | 仓库 Settings → Secrets and variables → Actions → 新建 `NPM_TOKEN` | 供手动触发的公网发布使用（推 tag 不自动发） |

**确认包名可用**：

```bash
npm view polaris-flow version    # 404 = 未占用；返回版本号 = 已被占用，需改名后再发
```

**注意本机 registry**：如果 `~/.npmrc` 里留着通道 A 的 `registry=…npm-group/`，公网发布会打错地方。发布前确认：

```bash
npm config get registry          # 应为 https://registry.npmjs.org/
```

### B-2 首次发布（手动）

```bash
npm login                    # 首次需登录
npm pack --dry-run           # 干跑，确认包名 polaris-flow@x.y.z 与文件清单
npm publish                  # prepublishOnly 自动跑密钥扫描 + build
npm publish --otp=123456     # 账号开了 2FA 时改用这条
```

### B-3 以后每次发版

前置步骤（第一节 1–4 步）做完后，二选一：

**在 Actions 页手动触发**（推荐，构建与发布都在干净环境里跑）：

1. 打 tag 推送：`git tag v0.1.3 && git push origin v0.1.3`
2. GitHub → Actions → `Release Check` → Run workflow → 分支选刚打的 tag → **勾选 `publish_public`** → Run
3. 等 job 变绿，第 5 步 `Publish to public npm` 会执行

> 推 tag 本身**不会**发公网包（流水线默认只构建校验），发公网必须第 2 步显式勾选——这是刻意设计，防止误发。

**本地手动发布**——同 B-2。

> **红线：同一版本不要既手动发又走 Actions。** 公网 npm 一个版本只允许发布一次，第二次必然 `E409`。

### B-4 发布后验证

```bash
npm view polaris-flow version     # registry 上的版本，应等于刚发的版本
npm install -g polaris-flow && polaris --version
```

### B-5 通道 B 常见报错

| 报错 | 根因 | 处理 |
| ---- | ---- | ---- |
| `E403 Forbidden` | 未登录 / token 无发布权限 / 包名不属于该账号 | 重新 `npm login`；核对包的所有者；CI 检查 `NPM_TOKEN` |
| `E404 Not Found`（publish 时） | registry 指向了私服或镜像 | `npm config get registry` 确认是 `https://registry.npmjs.org` |
| `E409 Conflict` | 该版本号已存在 | 升版本号后重发 |
| `EOTP` | 账号开了 2FA，命令行需要一次性验证码 | 本地加 `--otp=<6位码>`；CI 必须用 Automation 类型 token |
| `husky: command not found` / prepare 报错 | 在无 `.git` 的环境触发 `prepare` | 确认在仓库内执行；CI 侧 checkout 已带 `.git` |

## 四、发错了怎么办（两条通用，差异在最后一列）

| 情况 | 处理 | 通道差异 |
| ---- | ---- | -------- |
| 刚发布、内容有严重问题 | 优先**直接发下一个版本修复** | — |
| 必须撤掉某个版本 | 通道 B：`npm unpublish polaris-flow@x.y.z`（仅 72 小时内可删，**该版本号永久作废**）<br>通道 A：在 Nexus 界面删除 hosted 里的该版本资产，或 `npm unpublish --registry <hosted>` | 公网 72 小时后不能再删，只能 `npm deprecate` 标注 + 发修复版；Nexus 无时限限制（取决于仓库 delete 权限） |
| tag 打错（指向错误提交） | `git tag -d vX.Y.Z && git push origin :refs/tags/vX.Y.Z`，修正后重打 | — |
| 发布任务报错但包已发出 | `npm view`（或 A-4 第 1 条）确认；已发出按上面两条处理，**不要重跑同一个 job** | — |

**永远优先「发新版本修复」而不是删包**：删包会连带破坏已锁旧版本的依赖方。

## 五、两个通道都要发（可选）

`npm publish` 一次只写一个 registry。两边都要，就按顺序各走一遍：

```bash
# 1. 先发 Nexus（通道 A）
./release.sh

# 2. 再发公网（通道 B，显式指向公网，避免被 .npmrc 带偏）
npm publish --registry https://registry.npmjs.org/
```

两次都在本地手动执行，`--registry` 各自显式指定，互不影响；GitHub 上的 `Release Check` 只做校验，不参与任何一端的发布。

实际上内部分发只需 Nexus——公网 npm 是否维护，按需要决定。不维护的话，Actions 里**不勾** `publish_public` 即可，推 tag 不会误发。
