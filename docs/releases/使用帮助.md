# Polaris Flow 使用帮助

> 面向刚开始用 Polaris Flow 的团队同学。本文讲清四件事：**它是什么、怎么装、怎么上手、你该用哪个命令**。
> 想逐条了解每个命令的详细流程、会问几次、产出什么，看《命令使用说明》（`docs/command-usage-guide.md`）。

---

## 一、它是什么

Polaris Flow 是装在 AI 编码工具里的一套工作流。它把「提需求 → 写文档 → 画原型 → 写代码 → 测试 → 修 Bug」这条链路上本该靠人反复判断和盯的环节，交给 AI 按固定流程引导，你只需要在关键节点确认方向。

它解决三个反复出现的问题：

1. **需求没想清就开工，做完发现方向错了** —— 开工前强制澄清、判复杂度、确认意图，方向不对在改代码前就被拦住。
2. **每个环节标准不一，质量靠自觉** —— 每个阶段都有固定产物和评审，不通过就不放行到下一步。
3. **复杂任务不知道从哪下手** —— 按复杂度自动分三档（简单 / 常规 / 复杂），复杂程度不同，走的流程深度也不同。

一句话：**它不替你写代码，它保证你「没走错路」再写。**

---

## 二、怎么装

### 前提

- Node.js >= 20
- 装了支持命令的 AI 编码工具：**Claude Code** / **Trae** / **Cursor** 三者之一

### 安装

在你自己的项目目录里跑：

```bash
polaris init
```

装完自检一遍：

```bash
polaris doctor
```

> 公司网络访问 GitHub 不通时，需要配置镜像或本地 Superpowers 路径，见 `README-zh.md` 的「Superpowers 安装与网络」一节。这一步通常由先跑通的同学统一整理后分享。

## 三、三步上手

第一次用，走这三步就能感受到它怎么运作：

1. 在对话里输入 `/psfl:flow`，说一句话：你想做什么（比如「把订单列表加上筛选功能」）。
2. 按提示回答，最多问 4 件事：做哪类事 → 做哪一项 → 要不要自动评估复杂度 → 有没有材料要先读。
3. 在它停下来问你的地方确认方向，让它继续。

**拿不准用什么命令时，一律先 `/psfl:flow`**，它会帮你判档并路由到对的流程。

## 四、你该用哪个命令

按「你是谁 + 你要做什么」对号入座：

### 产品 / 设计

| 你要做的事 | 用这个命令 | 一句话 |
| ---------- | ---------- | ------ |
| 把想法整理成正式需求文档 | `/psfl:prd` | 产出需求基线和澄清纪要 |
| 自查这份需求够不够格让研发开工 | `/psfl:prd:readiness` | 五维打分，给通过 / 未通过结论 |
| 做可点击的页面原型 | `/psfl:prototype` | 先出蓝图再动手，确认后才做 HTML 原型 |
| 检查已有原型做没做对 | `/psfl:prototype:review` | 只出评审报告，不改文件 |

### 研发

| 你要做的事 | 用这个命令 | 一句话 |
| ---------- | ---------- | ------ |
| 改个小地方（改文案、加字段、调参数） | `/psfl:coding:tweak` | 最快通道，一次会话跑完 |
| 实现一个功能（多模块协作） | `/psfl:coding:normal` | 常规档，含规格和任务拆分 |
| 做复杂 / 高风险功能（跨服务、跨系统） | `/psfl:coding:sdd` | 完整阶段链，带深度设计 |
| 线上出故障了，用户在受影响 | `/psfl:maintance:hotfix` | 生产通道，先保现场再改 |
| 测试提了缺陷 | `/psfl:maintance:bugfix` | 测试通道，收尾归档到故障记录 |

### 测试

| 你要做的事 | 用这个命令 | 一句话 |
| ---------- | ---------- | ------ |
| 写验收标准（「怎么算做完」的判据） | `/psfl:testing:acceptance` | 产出 GWT 格式验收清单 |
| 设计测试用例 | `/psfl:testing:create-testcase` | 产出测试计划 + 用例集 |
| 评审已有用例集（找漏测） | `/psfl:testing:review-testcase` | 只出报告，不改用例 |

> **命令名随工具不同**：Claude Code / Trae 用 `:` 分隔（如 `/psfl:coding:normal`）；Cursor 把 `:` 换成 `-`（如 `/psfl-coding-normal`）。词还是那些词。

## 五、一个完整任务长什么样

### 场景 A：产品提需求，研发实现（中等复杂度）

```
1. /psfl:prd              产品把想法整理成需求文档
2. /psfl:prd:readiness    产品自查够不够格开工（可选，强烈建议）
3. /psfl:flow             研发说「根据这份 PRD 实现功能」→ 自动判为常规档
4. 走完 澄清 → 提案 → 任务规划 → 编码 → 验收 → 交付
```

如果研发一开始就确定这是复杂需求，第 3 步可换成 `/psfl:coding:sdd` 直接开完整链路。

### 场景 B：测试提了缺陷

```
1. /psfl:maintance:bugfix
2. 说清复现步骤 / 实际结果 / 预期结果 / 环境版本
3. 诊断 → 修复 → 自验 → 关闭归档
```

### 场景 C：线上出故障

```
1. /psfl:maintance:hotfix
2. 说清现象 + 时间线 + 影响面 + 变更清单
3. 诊断 → 修复 → 独立验证 → 由你执行发布
```

## 六、新手最容易有的疑问

**Q：它老问我确认，是不是太啰嗦？**  
不是。简单需求问 3 次，完整流程问 10 次以上——这是刻意的。在改代码前花几分钟确认方向，比改完 20 个文件发现方向错了便宜得多。

**Q：我不知道自己这活儿算简单还是复杂。**  
交给 `/psfl:flow`，答「让命令自动评估」。它会按模糊点、范围、方案分叉、风险四件事打分，并把评分依据摊开给你看。

**Q：它说我的需求不合格，要求补充。**  
开发类开工前必须有最低限度的有效输入（做什么 + 对哪个对象 + 至少 2 项细节）。这不是刁难，是防止产出和你的意图对不上。

**Q：它提示我「新开会话」。**  
照做。同会话硬续会丢上下文，反而更容易出错。记下它给的下一阶段命令名，新会话里直接输入继续。

**Q：跑一半发现方向错了。**  
能改。它会提示你切换档位或回退到上一阶段，由你决定。

---

## 需要记住的三点

1. **拿不准就用 `/psfl:flow`**，它会判档。
2. **每个阶段之间会停**，让你确认方向——这是设计如此，别嫌慢。
3. **提示「新开会话」就照做**，中断了直接输入当前命令名就能续上。
