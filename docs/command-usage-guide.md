# Polaris Flow 命令使用说明

> 面向使用者。你不需要知道命令背后加载了哪些技能、文件放在仓库哪个目录——照着下面的场景表选命令，把该准备的材料准备好，剩下的按提示回答即可。

---

## 一、我该用哪个命令？

**先看你要做的事属于哪一类，再对号入座。**

| 任务分类              | 你要做的事                       | 用这个命令                                | 一句话说明                             |
| ----------------- | --------------------------- | ------------------------------------ | --------------------------------- |
| 全局                | 冒出一个想法，还没说清楚                | `/polaris:flow` → 选「需求 · R01 编写用户需求」 | ⚠️ 该功能暂不可用，可先用 R02 描述想法           |
| 需求                | 把想法整理成正式的需求文档               | `/polaris:prd`                       | 产出需求基线与需求澄清纪要                     |
| 需求                | 判断这份 PRD 够不够格让研发开工          | `/polaris:prd:readiness`             | 五维度打分，出 PASS / CONDITIONAL / FAIL |
| 原型                | 做一个可点击的页面原型                 | `/polaris:prototype`                 | 出原型蓝图 → 高保真 HTML 原型 → 评审 → 归档     |
| 原型                | 检查已有的原型做得对不对                | `/polaris:prototype:review`          | 只出评审报告，不改文件、不归档                   |
| 编码                | **改一个小地方**（单文件、单模块）         | `/polaris:coding:tweak`              | 最快通道，一次会话跑完                       |
| 编码                | **实现一个功能**（多模块协作）           | `/polaris:coding:normal`             | 常规档，含规格契约与任务拆分                    |
| 编码                | **做一个复杂/高风险功能**（跨服务、跨系统）    | `/polaris:coding:sdd`                | 完整阶段链，带深度设计与加强评审                   |
| Debug             | **线上出故障了**，用户在受影响           | `/polaris:maintance:hotfix`          | 生产通道，带现场保全与止血确认                   |
| Debug             | **测试环境挂了 / 提测后回归失败**         | `/polaris:maintance:bugfix`          | 测试通道，收尾归档到故障记录目录                  |
| 验证                | 给功能写测试用例                    | `/polaris:testing:testcase`          | 产出用例集 + 测试计划                      |
| 验证                | 写验收标准（GWT 格式）               | `/polaris:flow` → 选「测试 · T02 编写验收标准」 | 产出验收标准清单                          |
| 验证                | 评审已有的测试用例集                  | `/polaris:testing:review-testcase`   | 只出报告，不改用例、不阻断流程                   |
| 维护                | 看看我的代码写得怎么样                 | `/polaris:flow` → 选「维护 · M11 评审代码」   | 五维系统化审查                           |
| 维护                | 重构既有代码（不改外部行为）              | `/polaris:flow` → 选「维护 · M12 重构代码」   | ⚠️ 该功能暂不可用                        |

### 懒得选？用总入口

`/polaris:flow` 会一步步问你要做什么，然后自动进对应流程。**如果你对复杂度拿不准（比如「这算简单还是复杂改动」），首选它**——它可以自动判档并路由。

```bash
/polaris:flow
```

它会依次问你四件事：

1. **这次要执行哪一类功能？** —— 需求 / 原型 / 开发 / 测试 / 维护
2. **做哪一项？** —— 根据你选的类别给出具体项（比如开发类给「简单 / 常规 / 复杂」三档）
3. **要不要让命令自动评估复杂度？** —— 开发类专属，答「是」就由命令判档并自动路由
4. **有没有需要技能先读的材料？** —— 设计稿、接口文档、目标代码路径等，可以直接跳过

全程 4 问，中间会停下来等你回答，不会自答自续。

## 二、命令名怎么敲？

**命令名随你用的工具而不同**，`:` 和 `-` 的差别只是命名风格，含义完全一样。

| 你用的工具          | 敲法示例                                                                                                                        |
| -------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Claude Code    | `/polaris:flow`、`/polaris:prd`、`/polaris:testing:testcase`、`/polaris:coding:tweak`、`/polaris:prototype`、`/polaris:prototype:review` |
| Trae / Trae-CN | 同上                                                                                                                          |
| Cursor         | `/polaris-flow`、`/polaris-prd`、`/polaris-testing-testcase`、`/polaris-coding-tweak`、`/polaris-prototype`、`/polaris-prototype-review` |

**记法**：Cursor 下把 `:` 全换成 `-` 即可，词还是那些词。

> **族级命令**：`/polaris:prd`、`/polaris:prototype` 是「族级」命令——命令名即工作流名。  
> 其余命令一律是 `<族>:<动作>` 形式（如 `/polaris:testing:testcase`、`/polaris:prd:readiness`、`/polaris:testing:review-testcase`）。

> 工具里还没装 Polaris 时，先跑一次 `/polaris init` 装上，详见 `README-zh.md`。

## 三、每个命令怎么用

### `/polaris:flow` —— 总入口

**适合**：任何拿不准的场景，或本来就只是想「告诉 AI 我要干什么」。

**你要准备的**：一句话说清目标即可。但如果走开发类，命令会要求你补充细节（见下）。

**开发类会额外问你**：

- 「未检测到完整需求内容，是否补充？」——必须二选一：**给文件路径**，或**补一段文字**（说明：做什么 + 对哪个对象 + 至少 2 项细节，如角色 / 数据 / 流程 / 约束 / 验收条件）。  
  这里**没有「直接开始」选项**——开发类不允许没需求就开工，这是防止产出跟你的意图错位。
- 「是否让命令自动评估复杂度？」——答「是」由命令判档（简单 / 常规 / 复杂），答「否」你自己手动选三档之一。

**自动评估怎么判**：看四件事——**模糊点**（需求里没写清、实现时必须猜的点）、**范围**（涉及几个模块）、**方案分叉**（有几条可行实现路径）、**风险**（失败或回滚的影响面）。打总分后：

- 0 分 → 简单档
- 1–3 分 → 常规档
- 4 分以上，或触及安全 / 数据迁移 / 对外接口破坏性变更 → 复杂档

判完会**把评分依据摊开给你看**（级别、每项打分、具体证据摘录、最终路由）。你觉得判高了可以说，但要往低了调不行（宁可严不可松）。

**「修 bug」怎么区分**：如果你只说「修 bug」而没说场景，命令会问你——**线上/生产受影响，还是测试环境/回归失败**。这个必须回答，它决定后面要不要做现场保全、要不要独立验证、收尾归档到哪里，不能替你猜。

---

### `/polaris:coding:tweak` —— 小改动

**适合**：单模块、单文件级、无跨模块设计、无复杂状态流转、风险低。比如改个文案、加个字段、调一个参数。

**怎么判断够不够小**：影响面在 3 个顶层任务以内、只涉及 1 个规格变更包。超过就别用这个。

**你要准备的**：一句话说清改什么。可以顺带把目标文件路径贴上，技能会先读。

**流程有多快**：一次会话内跑完 `简报 → 任务规划 → 编码构建 → 交付`，跳过深度设计和独立验收。

**会问你 3 次**：理解确认 → 任务命名 → 简报定稿。

**产出**：一份简报 + 一份任务清单，交付归档时补齐规格文件。

**中途会升档**：如果做到一半发现改动变复杂了，技能会提示你切到 `/polaris:coding:normal` 或 `/polaris:coding:sdd`。听它的，别硬扛。

---

### `/polaris:coding:normal` —— 实现常规功能

**适合**：多模块协作、需要规格契约、要拆任务、有一定风险。

**流程**：`澄清 → 提案 → 深度设计 → 任务规划 → 编码构建 → 验收 → 交付`

**你要准备的**：一份能说清「做什么 + 给谁用 + 关键规则」的需求描述。命令会就模糊点追问你。

**产出**：规格四件套（提案 / 设计 / 规格说明 / 任务清单）+ 意图说明 + 任务清单。

---

### `/polaris:coding:sdd` —— 实现复杂功能

**适合**：跨系统 / 跨服务、高风险、需要专项设计（数据模型 / 接口契约 / 领域模型）。

**流程**：`澄清 → 提案 → 深度设计（可选）→ 任务规划 → 编码构建 → 验收 → 交付 → 复盘（可选）`

深度设计要不要做，会在提案完成后问你。复盘是交付之后你主动触发的可选动作，不影响交付。

**它和 `/polaris:flow` 的关系**：`sdd` 就是 `flow` 判档到「复杂」后自动进去的那条链路，行为一模一样。区别只是：`sdd` 适合你**已经确定**这是复杂需求、直接开八阶段；`flow` 适合你**还不确定**复杂度、想让命令先评一评。

**注意**：`sdd` 虽然是直达命令（不进菜单），但仍要求你先把需求说清楚——没达到「做什么 + 对哪个对象 + 至少 2 项细节」会被拦住。

---

### `/polaris:maintance:hotfix` —— 修生产故障

**适合**：线上 / 生产 / 灰度真实流量出问题，真实用户或数据已受影响，来源是线上告警、监控或客服工单。

**和 bugfix 的区别只在「现场」**——这一个要求先保现场再改代码。

**你要准备的**（不全也没关系，命令会问，但先想清楚能省几轮）：

- 故障现象
- **时间线**：什么时候开始的
- **影响面**：哪些用户 / 哪些数据受影响
- **变更清单**：出事前改过什么

**流程**：`诊断与方案 → 实现与自验 → 关闭 Bug`

生产通道会**加严**：现场保全清单、止血与回退路径确认、数据脚本 / 埋点 / 开关的谨慎处理、实现完做**独立验证**、发布确认。**发布 / 灰度 / 回滚动作始终由你执行**，命令只负责把该确认的都问你。

**硬门禁**：如果诊断发现根因没定位、跨 3 个以上模块、涉及表结构变更、或对外接口破坏性变更——**会被强制退回 `/polaris:coding:normal`**。这不是刁难，是这四类改动的风险已经超出快速修复能兜的范围。

---

### `/polaris:maintance:bugfix` —— 修测试环境缺陷

**适合**：测试环境异常、提测后回归失败、用例失败、测试同学提单。

**你要准备的**：复现步骤、实际结果、预期结果、环境版本。这四项会一次性问你，不会分多轮挤牙膏。

**流程**：`诊断与方案 → 实现与自验 → 关闭 Bug`

**和 hotfix 的差别**：不加严现场保全和独立验证。收尾归档到仓库的 `docs/troubleshooting/<问题编号>/`，**不走交付归档**。

---

### `/polaris:prd` —— 编写需求文档

**适合**：手里有一个模糊想法、一段口头描述、一份杂乱的需求文档，需要整理成正式的需求文档（PRD）。

**你要准备的**：原始素材越多越好——想法、背景、已知约束、竞品参考、用户反馈。原样给就行，不需要你提前整理。

**流程**：`探索澄清 → 起草 → 细化 → 评审 → 定稿归档`

**产出**：《需求基线》（含功能架构草案）+《需求澄清纪要》。后续阶段会把 PRD 一路带到定稿。

**同族另一个入口**：`/polaris:prd:readiness` —— 需求就绪度评估，用于判断定稿 PRD 够不够格让研发开工。

> **注**：需求族里「编写用户需求」（R01）的能力尚未上线，菜单里标为暂不可用。需要时可直接把用户想法 / 原始描述交给 `/polaris:prd` 起步。

---

### `/polaris:prd:readiness` —— 需求就绪度评估

**适合**：PRD 写完了，想在交给研发之前先自查一遍——够不够格开工。

**硬前置**：评估对象**必须是已定稿的 PRD 终稿**。草稿阶段不给评——这是为了防止拿半成品得出「可以开工」的误导结论。**没有终稿会直接被拦住**，让你先去走完定稿。

**软前置**：测试维度那两份评审报告（评审报告、可测试性报告）**缺了不阻断**，对应维度会标「证据不足」并按 3 分封顶。

**会怎么做**：五个维度加权打分 → 给 PASS / CONDITIONAL / FAIL → 附缺陷清单。**只评不改**，不碰你的 PRD 原文。

**判 FAIL 会阻断交付**，并把你退回细化阶段修复。这是它的价值所在——宁可现在拦，也不让问题漏到研发手上。

---

### `/polaris:testing:testcase` —— 设计测试用例

**适合**：PRD 已定稿，要把它变成一份可执行的测试用例集。

**硬前置**：需要**已定稿的 PRD 且含验收标准**。没有 → 会提示你先走 `/polaris:prd`（编写需求文档）或 `/polaris:flow` 的 T02（编写验收标准）。

**你要准备的**：定稿 PRD；顺带可以给交互原型、数据库表设计、接口清单，这几样缺了不影响启动。

**流程**：`澄清测试意图 → 编写用例集 → 完善与独立评审 → 准出交付`

**产出**：《测试计划》+ 测试用例集。

**有一条容易踩的规则**：用例只能源于需求，不能源于想象——每条用例都要挂到 PRD 的原始需求条目编号上。所以 PRD 写得越清楚，这一步越顺。

**同族另一个入口**：`/polaris:testing:review-testcase` —— 用例集写完后单独评审一次（只出报告，不回改、不阻断）。

---

### `/polaris:testing:review-testcase` —— 评审测试用例集

**适合**：用例集写好了，想找找漏测、重复覆盖、颗粒度问题。

**硬前置**：必须能拿到**待评审的用例集**，二选一：

- 你把用例文档路径贴进来
- 或者已有活跃的测试用例任务，用例集在 `.polaris/testcases/<任务编号>/test-cases.md`

两者都没有 → **直接阻断**，会提示你先走 T01 产出用例集，或把路径贴上。

**不阻断的前置**：《测试计划》和 PRD 缺了不影响启动，只是覆盖类维度会标「无法执行」并说明原因。

**重要差异**：这个命令**只出报告**——不改用例、不推流程、不阻断任何东西。用例集的准出门禁（严重问题清零才放行交付）只在它被测试流程内部调用时才生效。作为独立入口调用时，你拿到报告，怎么处置由你决定。

**产出**：一份评审报告，问题分**严重 / 主要 / 次要 / 建议**四级，每条都带可核对的定位（用例编号或章节），7 个维度一个不落。

---

### `/polaris:prototype` —— 制作原型

**适合**：手里有需求（需求基线 / 定稿 PRD / 建设方案 / 设计文档任一份），想把它变成一份能点、能演示的页面原型。

**第一步不是画原型，是先出《原型蓝图》**——也就是「这个需求要做哪些页面、页面之间怎么跳、每个页面放什么」。这份蓝图会停下来等你确认，**确认之后才开始真正做原型**。

不做这一步的话，最容易出的问题是做了一堆页面却发现方向理解错了，返工成本很高。

**你要准备的**：一份可读的需求输入（上面四类任一）。都没有 → 会提示你先走 `/polaris:prd` 把需求整理出来，或者把方案文档附上。

**顺带可以给的**：已有的需求文档、目标页面清单、参考设计稿。

**流程**：`蓝图（等你确认）→ 按蓝图做高保真 HTML 原型（做完交你确认）→ 独立评审 → 确认后归档`

**产出**：一份可离线双击打开、能在桌面 / 平板 / 手机三档分辨率下操作的高保真 HTML 原型，附带页面结构说明与研发交接说明。

**它会问你**：蓝图确认、原型完成后确认、评审结论确认。中间不会自己往下跑。

---

### `/polaris:prototype:review` —— 评审已有原型

**适合**：原型已经做出来了，想在交给研发之前先自查一遍——能不能交、有没有明显问题。

**硬前置**：必须提供**待评审的原型文件（`.html`）**。没有就直接停下要路径，**不会凭口头描述评审**。

**强烈建议给的（缺了不阻断，但结论会降级）**：

| 材料         | 缺了会怎样                                    |
| ---------- | ---------------------------------------- |
| 需求文档 / PRD | 业务方向维度改用「无需求文档取证法」判，结论降级为「证据不足 / 待需求方确认」 |
| 已确认的《原型蓝图》 | 「是否符合已确认设计」一项进「证据不足」，**不会因此判缺陷**         |

想拿到最硬的结论，这两份最好都带上——尤其是蓝图，它是「原型有没有照着自己确认过的设计做」的唯一依据。

**可选**：黄金流定义 `flow.json`，附上则链路审查更完整。

**重要差异**：这个命令**只出报告**——不改原型、不改蓝图、不推流程、不阻断任何事。归不归档、改不改，由你拿报告自己决定。

**产出**：一份评审报告，结论为**可交付 / 修复后可交付 / 不得交付**，附分级问题清单（严重 / 主要 / 次要 / 建议），每条带可核对定位。

## 四、完整任务串起来看

一个真实任务，从头到尾会用到的命令：

### 场景 A：做一个中等复杂度的功能

```
1. /polaris:prd                  想清楚要做什么
2. /polaris:prd:readiness        自查够不够格开工        ← 可选但强烈建议
3. /polaris:flow                 说「根据这份 PRD 实现功能」
   └ 自动评估 → 判为常规 → 自动进 normal
4. （执行中）走完 澄清→提案→设计→任务→编码→验收→交付
```

如果你一开始就知道这活儿是复杂档，可以第 3 步换成 `/polaris:coding:sdd`，跳过评估。

### 场景 B：线上出故障

```
1. /polaris:maintance:hotfix     立刻进入
2. 说清现象 + 时间线 + 影响面 + 变更清单
3. 诊断（生产通道：先保现场、给止血方案和回退路径）
4. 修复 + 独立验证
5. 你自己执行发布 / 灰度
6. 关闭 Bug + 归档
```

⚠️ 如果诊断发现是根因不明 / 跨 3+ 模块 / 表结构变更 / 对外接口破坏性变更，会被退回走常规开发流程。

### 场景 C：测试提了个缺陷

```
1. /polaris:maintance:bugfix
2. 说清复现步骤 / 实际 / 预期 / 环境版本
3. 诊断 → 修复 → 自验 → 关闭归档
```

### 场景 D：需求到原型

```
1. /polaris:prd                    先把需求整理出来
2. /polaris:prototype              制作原型
   └ 先出蓝图 → 你确认 → 做 HTML 原型 → 你确认 → 独立评审 → 归档
3. /polaris:prototype:review       若还想单独把关一次（可选）
   └ 必须把原型 .html 路径贴进来，否则会被拦
```

## 五、每个阶段要停下来做什么

工作流**不会一口气跑完**。每个阶段之间有停顿，这是设计如此——你要在关键点确认方向，别让它一路狂奔。

一般规律：

- **自动衔接**还是**让你新开会话**，由项目配置决定。**如果它提示你「新开会话」，就照做**——同会话硬续跑会丢上下文，反而更容易出错。
- 提示你新开会话时，把**下一阶段的命令名**记下来，新会话里直接输入那个名字继续。
- 中断了想续上，直接输当前阶段的命令名，技能会读已落盘的产物判断续跑位置，不用从头再来。

## 六、常见问题

**Q：我不知道该选简单还是复杂，直接 `/polaris:flow` 就行？**  
行。选「开发」，答「让命令自动评估」，它会判档并把依据摊给你看。

**Q：命令说我给的需求不合格，要求补充，为什么这么严？**  
开发类要产出代码。需求给得含糊，产出的东西跟你的想法对不上，你还得返工。它要求「做什么 + 对哪个对象 + 至少 2 项细节」是最小的有效输入。

**Q：它老是问我确认，是不是太啰嗦了？**  
简单需求上是 3 次确认，完整流程是 10 次以上。这是刻意的——在便宜的时候确认，比在改完 20 个文件后发现方向错了划算。

**Q：R01 编写用户需求 / M12 重构代码 为什么用不了？**  
这两个功能对应的能力还没上线。菜单里会标「暂不可用」，并明确告诉你缺的是哪个能力，不会糊弄你。你想描述想法，直接用 `/polaris:prd` 即可（它就是 R02 的独立入口）。

**Q：`/polaris:prd` 和 `/polaris:prd:readiness` 有什么区别？**  
`/polaris:prd` 是**写**需求文档（从想法到定稿）；`/polaris:prd:readiness` 是**查**需求文档够不够格开工（打分，只评不改）。先写后查。

**Q：命令说「检测到平台不支持询问工具」，改用文字选项？**  
说明没读到项目平台配置。你可以直接回编号（A / B / C），它照样能往下走。想根治就检查一下项目里的平台配置。

**Q：为什么有的命令要贴文件路径才能用？**  
像评审原型、评审用例这类命令，判据全靠你给的材料——没有原型文件就评不了「是否符合设计」，没有用例集就评不了覆盖度。这类**硬前置缺失会直接阻断**，不会硬跑。

**Q：命令跑一半我发现方向错了，能改吗？**  
能。执行过程中它会提示切换档位，由你决定。需求阶段发现问题，回退细化修；实现阶段发现问题，回退提案修。

**Q：做原型为什么先出「蓝图」而不直接画？**  
蓝图就是「要做哪些页面、怎么跳、每页放什么」。先确认它，再动手，避免做完一堆页面才发现方向理解错了。确认蓝图只花几分钟，返工可能是几小时。

**Q：我想只改原型的某几个页面，怎么办？**  
直接说清楚要改哪几个页面、改成什么样。原型制作的返工由流程内部处理，不需要你重新走一遍制作入口。

**Q：`/polaris:prototype` 和 `/polaris:flow` 选「原型」有什么区别？**  
没有区别，进的是同一条流程。`/polaris:prototype` 少一次选择，适合已经确定要做原型的人；`/polaris:flow` 适合还没想好要做什么的人。
