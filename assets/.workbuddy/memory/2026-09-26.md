### 落进文档的具体值

- **超时**：unit 300s（JVM 生态 600s）/ integration 600s / smoke 900s；**首次超时自动放宽 1 次**（×2，冷缓存/依赖首下/首次编译是常见假超时）；仍超时 → 4.0.4 第 2 级，**但须保留部分输出**（已有「执行 N 用例」后卡住 → 可能是**死锁类真缺陷**，判定仍按第 2 级不回 build，但报告须写明「卡在第 N 条」）
- **flaky `retry_and_mark`**：红 → 先重试 1 次 → 通过则算过但**强制标注** `首次失败 · 重试通过`；**同一用例两次重试才过 → 升 CRITICAL**。与报告 §5.4（倾向 `fail_on_flake`，「无法失败的测试比没有测试更糟」）的偏差**已登记**：代价是首次失败不再阻断，用强制标注换回可观测性
- **无框架按 mode 分**：light 放行 + 声明 / full 阻断 = 「风险决定做不做」。⚠️ 推出风险：**尚无测试框架的项目在 full 下无法完成 verify** —— 是否给宽限期列为新未决项（我倾向**不给**，宽限期会变永久豁免）
- **config 新增键**：`test.no_framework_policy`（`by_mode | block | pass`，默认 `by_mode`）；`timeout.*` / `flaky_policy` 改为定值（不再是「未决」注释）

## 立「验证顺序律」（用户提出 → 落进设计文档 §1.4）

用户主张：*build 的 TDD 是为当前功能开发；做验证时先做代价低、可自动化的，最后由人工完成剩余的验证工作*，并问是否与报告一致。

**核实结论：一致，但报告给的理由不同，且报告比用户表述严格一档。**

### 报告支撑（原文位置已核）

| 报告处 | 原文要点 |
|---|---|
| §5.2（P6） | 「静态验证是**零人类注意力成本**的基础层，应通过 pre-commit hook 和 CI 流水线**全自动**执行」 |
| §5.2 💡关键规则（P7） | 「每一条你的 Linter 能强制执行的规则，都应该从你的 Agent 提示词中移除。将**人类注意力释放出来用于判断性决策，而非机械性检查**」（遵守率 60% → 90%+） |
| §5.5（P8） | 「人工审查应**聚焦于自动化无法覆盖的判断性领域**」（400 行有效性骤降） |
| §5.6.4（P9-10） | L1–L3 全自动门禁 → L4 增强 → **L5 人工闸门** |
| §9 原则 2（P12） | 分层防御「**每一层捕获下层遗漏**」← 报告的**排序理由**是覆盖残留，**不是**成本 |

⇒ 用户表述 = 报告里散落的「成本/注意力」论据的**归纳**；报告本身没把它写成律。

### 我加的三点精确化（已落文档）

1. **第 3 律（聚焦律）是必需的，不是修辞**：报告说的是「自动化无法覆盖的**判断性**领域」，不是「剩余的全部」。只按「剩余」派人，人工层会被**机械性残留**撑满（环境没起、需手工跑一条命令）—— 而 400 行后有效性骤降，撑满即失效。这条正好接上已定的**三级分叉**：环境类失败（第 2 级）正确处置是 `No-Verification`，**不进人工**。
2. **顺序律有优先级，不是并列**：方向律 > 代价律 > 聚焦律。冲突时方向律胜 —— 故 `4.0.1 意图验收` 尽管靠判断完成，仍排最前（方向错了后面全白做）。**注意这不违反用户表述**：用户说的是「剩余的**验证工作**」，而 `4.0.1` 是**闸门**不是验证工作。
3. **⚠️ 暴露真实缺口（已列 §八 第 6 项）**：verify 里人工只有两个角色 —— **裁决者**（验证失败决策 / override / 规格漂移）与**配置确认者**（4.0.2 命令、4.0.5 红名单），**没有「验证者」**。报告 §5.5.1 五项焦点中「**业务语义确认**」完全无落点（＝三维覆盖表 §5.5.1-3 记「部分」的实质）。**所以缺的不是顺序，是「最后那一档」本身。** 三选项：① 补业务语义确认为显式人工确认项（我倾向）② 维持现状 ③ 移交 `ship` 的人工确认环节。
