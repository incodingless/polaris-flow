## 覆盖度复核的自我纠错（用户追问「为什么契约/功能测试不是 verify 职责」）

上一轮我把 6 项缺口全摆成「真漏」，判据是「报告有 → 技能找不到落点」。用户追问后核实，**两处归类是错的**，且错因同一个：**拿「找不到落点」当「职责不属」，两步并一步**。

### 正确的三分法（以后判「要不要加」先用它）

| 轴 | 内容 | 归属 |
| --- | --- | --- |
| 测试**执行** | 跑命令、拿证据、判读 | **verify**（`4.0.3/4/5` 三轨） |
| 测试**设计 / 编写** | 写哪些用例、覆盖哪些等价类 | `tasks` / `build` |
| 测试**有效性** | 测试本身有没有意义（变异 / 属性） | **L4，已划出 v1** |

- **功能测试**：**是** verify 职责，且已在（`4.0.3` 第 3 轨 = 主干功能 E2E/smoke）。我说「任务是三类用例覆盖审计」时把它简写成「功能测试」→ 词不达意，造成「verify 不跑功能测试」的错觉。
- **契约测试**：**部分已在** —— `docs/specs/2026-09-25-...design.md` §1.3 的按语原话「报告 §5.3 的 L3 本来就含契约测试 → 补集成层不是新目标，是回到报告 L3」→ 契约测试并进 **integration 轨**。但报告 §5.3.3 的契约测试是**静态 AST 校验**（PDF 第 8 页原话），所以 integration 轨只覆盖了一部分；**真正的残留＝「接口契约」（函数签名 vs OpenAPI Schema / Protobuf）**，其成立前提是项目**有**契约文档 → 归入「静态门禁」那一小块，不单开条目。
- **三类用例覆盖（功能/边界/对抗）**：属**测试设计**标准；verify 侧若审计它，那是**测试有效性**（＝L4 性质）→ **已随 L4 划出 v1**。结论（不新增）对，**理由我上一轮写错了**。

### 真问题：三轨的开关轴不一致 → ⑦ tier 才是缺件

| 轨 | 开关 |
| --- | --- |
| 1 单元 | 总是跑 |
| 2 集成 | **改动性质**（跨模块边界 / DAO / 外部接口） |
| 3 主干功能 smoke | **规模**（`verify_mode=full`） |

而 `verify_mode` 由**规模**推出（`4.1`：tasks > 3 / capability 目录 > 1 / 变更文件 > 8）。

⇒ **小改动碰高危路径两头落空**：改 3 行认证代码 → 规模小 → `light` → 不跑 smoke；若不跨模块边界 → 也不跑 integration。此时「印证正确性」只剩单测 + `4.3` + `4.4`。
⇒ 报告 §6 正相反：Tier3（认证 / 支付 / 隐私 / 并发 / 加密）要「独立测试 + 领域专家近距人工审查」，**不看规模**。
⇒ 所以 **⑦ tier 不是「不卡开工的挂起项」，而是「功能测试何时该跑」的那个缺件**：它要补的是**风险轴**，现在只有规模轴。**结论：不该往 verify 加「契约/功能测试」条目，该开 ⑦ 那一轮。**
