**判据（可检验）**：阶段边界只在同时满足三条时成立 —— ① 边界上有真实判断（过则继续 / 不过回流，且回流目标唯一）；② 与相邻阶段失败模式不同（否则门禁无法区分退回哪一步）；③ 承载一类不可替代的证据（复现 / 根因 / 验证 / 交付）。推论：**失败处理相同的相邻动作合并，失败模式不同的必须分开**。

**结论：bugfix 应为 4 段** —— ① 定性（输入校验 + 复现合并，出口＝最小可重复失败；生产信号分流在阶段入口）、② 定位（根因 + 排除反证 + 影响面，出口＝解释全部现象 + 人确认）、③ 修复（方案 + 编码 + 自验 + 回归合并，方案确认仅在有分叉时触发）、④ 交付（报告 + 提交信息 + 归档 + INDEX 合并，出口＝交付物齐全 + 回读通过）。现 6+1 的两处过度拆分：Step1|Step2 与 Step6|Step7 都不是「有分叉的位置」。**不能压到 3**（定性+定位合并后无法区分"信息不足"与"假设错误"；修复+交付合并会出现验证未过先出报告）。**拆阶段的成本是维护面与回流歧义，不是时间**。另：**阶段数 ≠ 人确认点数**——人确认只需 2 个（根因必选、方案仅分叉时），确认点决定门禁位置、不决定阶段划分。

**阶段原子 + 装配（两条通道共用一份定义）**：8 个原子 = 定性 / 定位 / 方案 / 实现 / 验证 / 交付 / 发布观测 / 止损。
- 测试通道（bugfix）4 段：定性 → 定位 → [方案+实现+验证 折叠为「修复」] → 交付
- 生产通道 6 段 + 1 支路 + 1 人在环：① 定性（出口改为"时间线·影响面·变更三对齐"，复现降为可选）→ ② 定位（多源交叉）→ ③ 方案（独立，必人确认）→ ④ 实现（+数据脚本/埋点/开关）→ ⑤ 验证（五维，独立门禁）→ ⑥ 交付（+发布确认）→ ⑦ 发布观测（人在环，技能只出指引与阈值）+ **止损支路**（可在任意时点插入，出口是"业务指标恢复"而非"原因查清"）
- **折叠条件（三条同时成立才折叠）**：同一执行者、同一环境、失败后回同一处修正、且无独立人确认点。生产通道三条全不成立 → 全部展开。

**对《生产 Bug 修复技能设计思路》的三处异议**
1. **一致性硬伤**：原则 1「止血优先、禁止未止血直接修复」，但 6 节点里没有止血节点（回滚预案在节点 3、回滚指南在节点 6）→ 按该流程走，止血最晚发生。实战主流是「已知变更诱因 → 先回滚止血 → 再查根因」。止血必须是**支路**而非末位节点。
2. **「类生产环境稳定复现」作为根因硬门禁会死锁**：流量相关 / 数据相关 / 依赖外部的故障常不可复现。门禁应改为**证据充分性**（多源交叉 + 解释全部现象 + 有排除记录），复现是加分项。侧证：现有 hotfix 的「根因已定位」前提反而更贴近现实。
3. **能力可得性**：告警拉取、指标曲线、链路 Trace、脱敏数据样本、灰度切流、回滚执行都依赖平台接入，文档全写成「自动」，实际多为 C 档（只能人提供 / 人执行）。生产通道 C 档远多于测试通道 —— 正是 bugfix 已有 A/B/C 分档要解决的问题。

**待用户决策的落地口径**：这份文档描述的生产通道远大于现有 hotfix（后者前提是「根因已定位、影响面已知、≤3 task」，与文档「根因未定位 + 现场保全 + 多维验证」直接冲突）。二选一：**(a)** 把 hotfix 扩成按 P 级裁剪的多档通道；**(b)** 新增生产故障响应技能、hotfix 退化为其中的「最小修复档」。此项决定 `flow.md` M01 路由与技能族划分，建议先定再谈阶段。分档维度：测试通道 L1–L3（缺陷复杂度），生产通道 P0–P3（故障等级 × 影响面）；**等级决定门禁强度与评审人数，不决定阶段数**。

## 18:3x debug 族技能解耦方案（阶段子技能复用，用户真问题）

**user 的真实诉求**：不是阶段数，而是「像 prototype 那样把技能拆成阶段叶子技能，让 bugfix / hotfix 共用的子技能不重复编写」。

**复用分两类，必须同时做，否则拆完更啰嗦**
- **水平复用（阶段跨通道）** → 拆阶段叶子技能
- **垂直复用（样板跨技能）** → 下沉 `policies/`（入口引导 / 活跃任务恢复 / 决策点协议 / A-B-C 能力分档 / H 清单 / 门禁话术），一次编写、注入所有叶技能

**prototype 族的实测教训（只做了水平复用）**：4 个叶技能（blueprint 302 / build 338 / review 244 / ship 235 行）各自重写入口 —— `get-active-changes` 活跃任务检查写了 3/4、决策点引用 4/3/3/0 次、`PLUGIN_ROOT unset` 校验从 4 次漂到 **1 次**（已不一致）。即"不做垂直复用必然漂移"的现场证据。另：prototype **路由靠 description**（每个叶技能显式写「不触发 → 走 polaris:prototype:build」），没有中心路由表、没有编排大技能。

**拆的判据**：① 有独立出口 + 独立人确认（可自证）② 两通道对它的差异化方式不同 ③ 会被单独进入。成本判据：每份 ≈ prototype 实测 235–338 行的固定开销。

**推荐切分：7 个叶技能 = 5 阶段 + 2 通道**
- `debug/scene` 定性（保全 / 信息对齐 / 复现）— 技能内分支 + 通道档位
- `debug/rca` 定位（根因 + 排除反证）— 两通道同构，门禁项按档
- `debug/plan` 方案（风险 + 回滚 + 观测）— **bugfix 可折叠、hotfix 必做**，「是否出现」由通道声明
- `debug/patch` 实现 + 验证（同一「改—跑」循环）— 产物与验证项按档
- `debug/deliver` 交付 + 沉淀
- `debug/bugfix` / `debug/hotfix` 通道技能，各 ≈100–150 行，只写「装配哪几段 + 每段档位 + 加严项 + 人确认 + 场景分流」。**硬规则：通道技能内不得出现任何阶段执行细节**，只引技能名
- **人在环节点（现场保全 / 止血 / 发布执行）不建技能**：无技能可执行的动作，建了是空壳；应是 `templates/` 下的可执行指引模板（止血选项卡 / 发布·回滚·灰度指引 / 观测口径），由 `deliver` 产出
- 待用户拍板的唯一边界：`patch` 是否拆回 `fix` + `verify`（生产通道验证可能跨人跨环境独立进行）

**拆完必须补的两个前提（唯一需动代码处）**
1. `PHASE_TO_SKILL`（`src/core/hooks/state-next.ts:59`）的 key 是 **family（kind）**，一个 family 仅一张 phase→skill 表；debug 族是**两条通道 × 两套阶段序列**，一张表表达不了 → 需把 key 提升为「通道」，或允许 family 下按通道分表
2. **回流要跨技能**：现状是技能内回流；拆成技能后「验证失败回方案」必须变成「退出当前技能 → phase 回退 → 重进上游技能」。交接协议不支持 phase 回退，则拆出来的是一条不能回头的单行道，比不拆更危险

**成本实测（诚实披露）**：不拆＝2 份 SKILL.md、阶段细节重复 ~90%；拆 7 份 ≈ 1450–1950 行（**总字数上升约 2 倍**，重复量趋零）。收益是单一真相源（改一处两通道生效）+ 每段可单独进入。再叠加 policies 下沉可把每份压到 120–180 行 → 总量回到 ~900–1200 行。

## 18:4x 五段命名与出口判据（用户提法 + 修正，已对齐）

用户提法：**定性 → 定位 → 方案 → 实现 → 交付**（命名采纳，优于「输入校验/复现确认」）。对其内涵做了三处修正，定为后续写作基准：

| 段 | 用户原话 | 修正后的出口（判定依据归谁） |
|----|---------|---------------------------|
| 定性 | 讨论清楚需要修复的问题 | 出口不是"讨论清楚"（无判定标准），而是**可核对的证据集**：可重复的失败（测试）或 时间线·影响面·变更清单（生产）；**含分流判定**（需求错 / 代码错、生产 / 测试、是否走本通道）—— 技能自证 |
| 定位 | 确认问题点及问题根因 | 必须区分**报错点 ≠ 根因**（最早引入异常的节点）+ **解释全部现象** + **有排除反证记录**；此处**必须人确认** |
| 方案 | 确定修复步骤及细节 | 「步骤细节」是 `tasks.md` 的产物、不是方案本身。方案的核心是**影响面 + 回归范围 + 回退路径 + 改动边界（明确不做什么）+ 分叉取舍**；生产场景回退路径是硬门禁 |
| 实现 | 执行修复、验证 | 先写失败用例再改代码（红→绿）；diff 全部落在方案清单内、夹带回退；出口是**证据化**（命令+输出+结论）。生产额外含回滚验证与数据兼容 |
| 交付 | 提交代码、形成交付包、归档问题/修复报告 | ①**技能不提交代码**，只产出提交信息文本 + 人在环动作（生产连合并/发布也只由人做）；②"问题报告/修复报告"是同一份结论报告，但**过程档案（简报）必须保留**——原始证据丢失则无法复盘与同类复用；③出口是**回读校验通过**（文件落盘且非空），这是最易静默失败处 |

**注**：这五段是**测试通道**的表述。生产通道在其上再挂三个「人在环节点」——①前：现场保全执行；①后任意时点：止血执行（支路）；⑤后：发布/灰度/回滚执行。人在环节点**不建技能**，只出 `templates/` 下可执行指引。
