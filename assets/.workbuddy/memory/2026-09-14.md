## coding 阶段技能骨架盘点（供 prototype §四 改造参考）

11 个 coding 技能章节骨架高度统一，可称「polaris 阶段技能骨架」：
`<HARD-GATE>`（**11/11**）→ `## 标识约定`（9/11）→ `## 前置条件`（4/11）→
`## 流程（按顺序执行；任一步未完成不得进入下一步）`（**11/11**）→ `## 退出条件`（7/11）→
`## 上下文压缩恢复`（7/11）→ `## 自动衔接下一阶段`（4/11）。
每步内的固定件：要读的文件 / 要跑的脚本 + **退出码表** / 按 `./policies/decision-point.md` 的**阻塞点** /
写 state.yaml 的字段 / 状态行输出（H8）。

**我的意见（用户问"要不要照 coding 的方式改 prototype §四"）**：同意方向，**分三档搬、不整副照搬**。
- A 档直接搬（不依赖运行时）：HARD-GATE 集中硬门、"任一步未完成不得进入下一步"纪律语、
  **每阶段完成判据**（现在 9 阶段只有阶段 9 有 verify 退出码，阶段 1 只有个孤零零的 Gate 1，2–8 全无）、
  决策点协议、**标识约定表**、**退出条件**、**上下文压缩恢复**（原型一次会话跑不完 9 阶段，这条比 coding 更值钱）、
  把 scaffold/verify 调用点从 §九 插回各阶段。
- B 档适配搬：Step 0「定位 change_id」→ 改为「定位原型工程」；bash 退出码表 → verify 退出码 0/1/2/3 表；
  「自动衔接下一阶段」→ 阶段 9 → prototype-review 的移交。
- C 档**不搬**：state.yaml / workflow.yaml / $PLUGIN_ROOT / workflow-entry.sh / SessionStart / auto-transition
  ——prototype 没有这套运行时，硬塞即**假接口**（本仓库最警惕的「脚本全绿但规范已变」类假象）；
  Constitution 注入点的对应物是已有的「冻结原则」，不套壳。
- **性质差异**：coding 步骤是机械的（脚本驱动可判成败），原型阶段 1–8 是认知的（判断与取舍，
  `SKILL.md:75` 自己写着"没有客观完成判据"）。压平成单一 Step 0–N 流水线会诱导形式合规而丢判断。
  → 建议**保留"9 阶段"外壳，阶段内加 Step/判据/决策点**，不压平。
**追问「原型生成适合做成流程式的吗」——结论：半适合，且我上一轮的建议有一处是错的。**
- **判断层（阶段 1–8）不适合流程式，执行层（阶段 9）非常适合。**
  理由：coding 的阶段是**转换器**（上一步产物是下一步的不可变输入，build 发现计划缺陷要 pause 回 plan，是*异常*）；
  原型阶段 1–8 是**同一份设计的八个视角**，阶段 5 选模式推翻阶段 4 页面划分、阶段 7 状态设计暴露阶段 3 的 IA 缺口，
  是*常态*。压平即把回填定义成违规。
- **流程化防跳步，防不了敷衍**：§34 三十一条里 1/3/5/6/7/14/16 全是判断类，没有一条是"漏做某步"。
  硬套流水线的实际后果是「走完九步、每步都很浅」的**形式合规**。
- **判定规则（可复用）**：*某阶段配不配硬门禁，看它的产物是不是下游工具直接消费的不可变输入。*
  原型里只有两处配门禁——阶段 4 定稿（→ `scaffold init`，软门禁）、阶段 9（verify 退出码 + 评审无 P0，硬门禁）；
  阶段 1–8 其余只给「产出物 + 落盘路径 + 完成判据」，**不给锁**。
- **上一轮错在哪**：把 coding 的「任一步未完成不得进入下一步」列进 A 档「直接搬」是错的。
  原型应改写为「**判据未过不收口；回填是正常动作，回填后须复检下游产物**」。
- **比流程化更值钱的两件事**：①**6+1 产物强制落盘**——产物本身就是原型的状态文件（原型没有 state.yaml，
  上下文一压缩流程就蒸发，落盘产物才是可恢复点）；②**上下文压缩恢复**以落盘产物为恢复点。
