## 原型评审拆成独立技能 `polaris:prd:prototype-review`

**判据先查清再决定拆法**。盘点发现「评审已有原型」在原技能里只有一句话（`SKILL.md §四` 那句
「直接走 §33 + §34，产出问题清单与整改建议」）+ `ref07 §35.6/§35.7` 两条调用话术，**没有**输入契约、
走查步骤、取证要求、缺陷分级、报告模板，也**没有「只评不改」约束**——评审模式下模型完全可能顺手改原型。

**关键判断：只拆「方法与输出」，不拆判据。**
`ref07 §33`（首行「生成前必须自检」）、`§34`（「必须主动纠正」）、`§27.1`、`scripts/verify.mjs` **留在 prototype**：
主消费者是建造侧（出口自检 + 交付门禁，`§34` 第 30 条拿 verify 退出码当门禁），且 verify 的引用锚点
（`§33.6` 等）都在那边。新技能只拥有：输入契约 / 走查流程 / 取证要求 / P0–P3 分级 / 报告模板 / 只评不改。
**判据单向流动：评审技能 → prototype**（照 `prd:readiness` 第 16 行的写法）。先例来自 `prd` 族自己的
`refine → review`、`ship → readiness`。

**安装器的两条硬约束（这次查实了，写代码前必须先看 `src/core/install/skills.ts`）**：
1. 顶层 `zh/policies/*` 会被**注入每个叶技能**的 `./policies/`，所以 `./policies/…`、`./templates/…` 可用；
2. 跨技能相对路径（`../specify/…`、`../../policies/…`）**在 flat 布局下必然断裂**，只能按**技能名**引用
   或走技能内自包含路径。这正是评审技能按技能名读 prototype 的 `ref07` 的原因。

**改动清单**：新增 `zh/skills/prd/prototype-review/`（SKILL.md + templates/ 报告模板 + evals/）；
prototype 的 `§四` 改建造单入口、`§九`/`§十一` 同步、frontmatter `description` 删掉
「评审已有原型能否交研发」触发（**两技能不得抢同一触发**）、PROVENANCE 记第十二轮；
`flow.md` 的 R12 入口改指新技能；`zh/skills/prd/README.md` 补主链路 / 阶段一览 / 目录结构 / 评审类技能表。

**用户的编号变更**：第十一轮建的 R04/R05 被用户在 `flow.md` 里改成 **R11/R12**（只改了 4 处），
余下 6 处引用（`已选功能` 枚举、零步说明、`需求内容` 清单、前置依赖表）由本轮按新编号补齐。
**教训：改共享文件前先重读，别信自己上一轮的上下文。**

**评测的做法**：新技能配 `evals/run.mjs`（零依赖、不写盘、不需浏览器），r1 判报告结构与取证合规、
r2 判「只评不改」（sha256 与实测一致 + 无「我顺手改了」类声称）。**第一次跑参照物就 FAIL**——
F4/F5 把「等级写在节标题（### P3 待确认）」这种合规写法误判为缺等级，同时暴露模板 P3 表缺「定位证据」列。
修法：**等级可来自所在小节标题，定位证据必须在该行**（标题是维度名不是证据），并给模板补列。
反例用一个真实偷懒报告 + 两个从参照物派生的定向变异（改 sha / 加「顺手修复」句子）。

**踩坑（会重复遇到）**：`zh/skills/prd/README.md` 与各 `evals/README.md` 被**用户全局 gitignore**
（`~/.gitignore_global` 的 `README.md` 一行）忽略，**从未入仓**，改动不会随提交走；要入库得 `git add -f`。
另：`manifest.json` 的 `ignoredFiles` 也含 `README.md`（安装器同样不装）。

**回归（三项全绿）**：`verify example --strict` → 三层 PASS · HARD 0 · WARN 0 · 退出码 0；
`prototype/evals --selftest` → 通过；`prototype-review/evals --selftest` → 参照物全过、反例全被拦下。

## 复查：prototype 里还有没有评审环节（残留清理，同第十二轮）

问：prototype 技能里有没有评审环节、引用的是哪个评审内容？
查实：**已经没有「评审环节」了**，只剩「自检 + 交付门禁」——
判据本体是自己的 `ref07 §33 质量审查清单`（首行「生成前必须自检」）、`§34 一票否决 31 条`（唯一来源）、

`§十 交付前自检 16 条` / `§四 阶段 9.2 验收`；对外评审（流程 / 取证 / 分级 / 报告 / 只评不改）
全在 `prototype-review`，prototype 只留指针（`§四` / `§九` 的 ref07 行 / `§十一`）。

**查出并修掉的残留（第十二轮漏改）**：`ref07 §35.6 原型评审` / `§35.7 检查能否交研发` 两条调用话术
仍写着「调用本技能」——照它办事会被引到错的技能上。已移到 `prototype-review` 的《标准调用方式》一节，
`ref07 §35` 改为「建造 5 种」+ 一句指向评审技能的指针（两边不各留一份）；`SKILL.md §九` 的 ref07 描述
由「7 种标准调用方式」改为「建造 5 种；评审 2 种已移交评审技能」。
**可复用判据：调用话术（「调用本技能，做 X」）属路由信息，必须跟着服务它的技能走——
拆技能时最容易漏的就是它，因为判据搬没搬很容易自检，话术搬没搬不会自己出声。**

另修一处自己写岔的交叉引用：评审技能 Step 1「用途决定结论措辞，见 §五」→ 实为 §四（§五是分工）。
回归三项仍全绿（`verify --strict` / `prototype evals` / `prototype-review evals`）。
