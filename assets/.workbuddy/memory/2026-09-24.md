## verify 补齐路线的六波排序（提案，未拍板）

判据不是照报告 §8 路线图抄，而是三条**代码评审效力杠杆**：机械项先摘出评审注意力 → 评审基线先可信 → 审查强度先分级。

| 波 | 内容 | 落点 | 依赖 | 成本 |
|---|---|---|---|---|
| 0 | 契约冻结 / 术语词典 / TDD 红绿循环 | specify · plan · tasks · build | — | 归属其他阶段 |
| 1 | Lint / 依赖校验 / SAST 扩到 CWE 模式 | verify 4.2a 附近 | 无 | 低 |
| 2 | 存量单测全通过 · 增量三类用例 · 「未验证项声明」标准化成字段 | verify 4.2a 第 4 项 + 报告格式 | 无 | 低 |
| 3 | Tier1–3 领域风险轴 + 高风险人工闸门 | verify 4.3 + codereview 入参校验 | 波 2 | 中 |
| 4 | 业务语义确认 · §5.5.2 证书机制 · 契约测试 | verify 4.2b + 新 policy | 波 3 | 中 |
| 5 | 变异 / 属性 / 性能 · 证据链 L1–L5 分级归档 | metrics + 报告 | 波 1–4 | 高 |

**与报告 §8 的两处有意偏差**：① 报告把「未验证项声明 / 证据闭环」放阶段 4 最末，本提案把前者提前到波 2（1 个字段、零成本，且直接决定评审报告可用性），后者保留在波 5；② 波 3 分级早于波 4 契约测试——分级是「要不要做、做多深」的开关，契约/变异都昂贵，没有分级必然一刀切。

**明写不早做的三样**：变异测试（验证的是测试有效性，须等双轨跑通才有意义，且成本最高）、多模型交叉（codereview 已明确推迟 v2）、CI/CD 门禁（平台层，非技能资产能落地）。

**并行轨道**（不占波次）：平台层阻断型 Hook / CI 门禁随时可加；`retro` 的知识回流排在最后。

## 讨论：评审前是否要全量重跑单测（用户提出，结论采纳 + 三条限定）

**用户主张**：第 0 波 TDD 执行完不一定形成测试报告 → 评审前应重新**完整**跑一遍单测（含既有），不只跑本次新增。

**结论：同意，但这不是「新增项」，是既有设计里的「双轨测试 · 旧轨」** —— `verify-redesign-proposal.md:49` 已列 ✅纳入，metrics 示例里也有 `functional.baseline_pass_rate`。属落地，不属再设计。

**必须补的三条限定**（否则「重跑」等于没做）：
1. **谁跑 + 落盘**：TDD 绿灯是 build 生成方的自报告（报告 §2.1「A self-report is not evidence」）→ 必须由 verify 侧重跑，并落盘**命令 + 退出码 + 输出摘要**。只写「已重跑，全绿」＝又变成自报告。对应提案 §7「每项结论附命令日志路径」。
2. **范围 = 全量存量**，不是「相关测试」。理由不是「更保险」，而是**归因**：存量有红时，评审者分不清「新增引入」与「本来就坏」，4.3 产出的每条 CRITICAL 都无法归因 → 属**评审前提**，不是评审增强。
3. **比对测试清单增删，不只看全绿**（这条是我加的）：最阴的失败模式是 AI 为让测试过而**删测试 / 加 skip**（`@skip` / `xfail` / `.only` / 注释断言）。「全绿」报告对此完全无感 —— 报告 §5.4 原话：「一个无法失败的测试比没有测试更糟，因为它制造虚假信心」。要求：新增 N / 修改 M / **删除必须为 0**（或逐条显式声明理由）。

**我提出的部分反对**：无差别全量重跑不是所有场景最优 —— 大仓会成瓶颈。若同一 **commit SHA** 上已有可信 CI 全量结果（有 artifact + exit code），**引用它比再跑一遍更好**（证据同样成立）。硬前提：SHA 必须与当前 HEAD 一致，不一致即视为无效、回退本地全量跑；报告须写清引用来源 + SHA。`test impact analysis` 只在有可靠全量兜底时才可用 —— polaris 的 verify 是合并前最后一道机器闸，所以本项目默认全量成立。

**边界**：全量绿只解决「基线可信」，**不解决「测试有效性」**（新增测试可能只是「确认已产出内容（含 bug）的测试」，报告 §4.1）—— 那是变异测试（波 5）的活。别让全量绿冒充测试有意义。

**对排序的两处修正**：
- 波 2 细化为「双轨测试 + 原始证据落盘」，并把原排波 5 的「命令退出码与日志」**提前到波 2**（它是评审前提而非收尾）。
- 4.3 增加**入口条件**：`functional.baseline_pass_rate` 必须为 1.0 且证据已落盘，否则不得开始独立评审（现在 4.3 只受 `review_mode` 控制，无此前置）。

**上一轮排序的漏项（自查）**：遗漏「**意图验收前置**」（提案 §9 第 1 项）—— 把 4.2b 的 5 项意图核验搬到 Step 2，内容零增删、成本低、且对应 IEEE 1012 的 Validation 先于 Verification。我上一轮答「波 1–5」时把它错划成「归属其他阶段」。

**更重要的发现**：`verify/verify-redesign-proposal.md` 的 §2（报告增量三档评估：纳入/裁剪/推迟）+ §9（六步落地顺序）**已经是一份完整设计**，我上一轮的「波 1–5」基本是把它重排了一遍。建议**不要重排**，直接沿用 §9，只改三处（双轨/证据提前、No-Verification 提前、意图验收归位）。另发现 `test-coverage-scorer.sh` 只读覆盖率报告、不跑测试。

**我对 ② 的评估（方向对，两处要改）**：
- (a) **执行顺序不提供归因能力**。归因需要「改动**之前**哪些测试就是红的」，必须在 change 起点采集（或读同 SHA 的 CI），与先跑哪个无关。反例：增量绿、全量红 → 红的是存量测试 ＝ 你的改动破坏既有行为（**回归**，比「本来就坏」更严重）；但存量本来就有 11 条红时，分不清这条新红是回归还是老红 → 先跑增量救不了。
- (b) **执行两次多余**。增量测试是**全量的子集**，跑一次全量后从结果切出增量子集即可；跑两遍＝同一批用例测两次。「先跑增量」的唯一合理动机是大仓 fail fast，需 test impact analysis + 全量兜底，属优化项非 v1。
- (c) **用词**：全量跑的是**回归套件**，不是 TDD（TDD＝红绿重构开发方法）。混用会导致设计走偏。
- **替代设计**：一次执行 + 三段判读 —— ① 环境预检 ② 跑一次全量并落盘「命令+退出码+输出+SHA」③ 判读 a 增量轨全绿 / b 存量轨失败集合 / c 清单增删（删除必须 0）。a 红 → **回 build**（不是「退出」，属 build 欠账）；b 红且不在红名单 → 回 build；b 红在红名单 → 记 No-Verification 放行；c 有删除无理由 → CRITICAL。
- **④ 与 ② 是同一约束的两面**：因不能动 build → verify 无法复用 build 的 TDD 结果 → 才想在 verify 内自己跑两轨。但 (b) 说明跑两遍省不下什么，结论仍是「跑一次全量」。

**⑤ 加子步的具体形态（我提）**：`4.0 意图验收`插在 `4.1 决定 verify_mode` **之前**（先验方向再定规模）；**从 4.2b 抽走的 5 项原位保留计数** —— 4.2b 仍写 7 项，其中 5 项改为「结论见 4.0，此处不重复展开」。收益：Step 编号不变（无断链）+ 4.2b 项数不变（`tweak/exit-check.md:5`「7 项」不断）+ 意图验收可早退。手法与 09-24 在 `4.2a` 第 6 项用的**完全同构**（「本项 = 4.3 已按 review_mode 处理完毕，不在此重复展开」）。

**tier 歧义（留待专门讨论）**：proposal §4.1 用「数字越大越高危」（3=最高）。但业内方向是**反的** —— 数据中心分级 Tier I–IV 中 Tier 1 是**最低**、IT 服务分级中 Tier 1 是**最高**。不是错，但必须写死在文档里否则换人会读反。另有保留质疑：**路径 glob 是弱代理**，同时误报（`auth/` 改注释 → 最重验证）与漏报（`utils/isAdmin()` 改鉴权 → 判低危）。
