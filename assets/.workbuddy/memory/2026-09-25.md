### 第 3 项的完整设计（我提出，待用户裁决）

**四级形态**：框架检出 → 候选命令 → config 覆盖 → 可执行确认。

- **映射表要点**：Node 按 lockfile 选包管理器（npm/pnpm/yarn/bun）；Maven `test` **漏 `*IT.java`**（需 `verify`）；Gradle `test` vs `check`；Python 优先 `tox`/`nox`（它们才是「全量」的定义）；Go `go test ./...`、Cargo `cargo test` 天然全量；Makefile 有 `test` target 时可能是项目最权威入口。**判据：探测到的「框架默认命令」必须升格为「全量回归命令」**。
- **可执行确认的 4 项**：① 命令在 PATH；② 脚本/target 存在（`npm pkg get scripts.test` / `make -n test`）；③ **不是 watch 模式**；④ 环境依赖（探测不了，只能首跑时失败）。
- **实用招**：统一加 **`CI=true`** 前缀 —— 多数测试框架（vitest/jest 等）据此自动退出 watch 模式转单次运行。

**🔴 新发现的分叉（必须分开，否则会互相伪装）**：
- **探测不到**（项目本就没有测试体系）＝ **项目属性**，不是失败 → 记 `No-Verification` 放行合理。
- **探测到但执行失败**（环境缺依赖 / 命令报错）＝ **本次验证失败** → 阻断或回 build。
- 若不分开，「环境坏了」会被伪装成「项目没测试」而放行。

**三个兜底参数（仍待裁决）**：① 超时（固定值 / config 必填 / **按框架给默认表**）；② flaky（`fail_on_flake` 严格符合报告原则 / `retry_once` 宽容 / **`retry_and_mark` 重试但强制标注**）；③ 探测不到时（阻断 / 放行 / **按 `verify_mode` 分：light 放行·full 阻断**）。

## 🔴 第 3 项重大修正：目标收窄为「单元测试」（用户纠偏）

**本段取代上方「映射表要点」中「必须升格为全量回归命令」的结论（即上一条的判据错误）。**

用户明确指出：本阶段要跑的是**单元测试**，探测目标是**项目中的单元测试框架**（Maven → `mvn test`）。

**错误性质 = 偷换概念（维度错位）**：用户最初的原话是「重新完整的跑一下**单测**，不仅本次新增，也包括既有的」——「全量」是**范围轴**（存量 + 新增）；我读成了**套件轴**（单元 + 集成），于是推出「`mvn test` 漏 `*IT.java`，必须升格到 `mvn verify`」。**答错了题。**

其荒谬处在我自己的论证里就暴露了：一边说「集成测试要 DB / Redis / 容器，verify 环境可能没有」，一边主张把集成测试拉进 verify —— **坑是我自己造的，又拿它当论据**。

**修正后的判据**：探测目标 = **单测框架**，得到该框架的**单测命令**；追求「就是单测」，不追求「最全」。

| 检出标志 | 框架 | 该跑 | **明确排除** |
|---|---|---|---|
| `pom.xml` | Maven · Surefire | `mvn -B test` | `mvn verify`（Failsafe `*IT.java`＝集成） |
| `build.gradle(.kts)` | Gradle | `./gradlew test` | `check`（含集成/静态分析） |
| `package.json` + lockfile | npm/pnpm/yarn/bun | 对应 `<pm> test`（防 watch） | e2e 脚本（`test:e2e`） |
| `pyproject.toml` / `pytest.ini` | pytest | `pytest` | `tox` / `nox` 的集成环境 |
| `go.mod` | go test | `go test ./...` | `-tags integration` |
| `Cargo.toml` | cargo test | `cargo test` | `--features integration` |

**同一列语义反转**：旧表右列是「不能直接用默认（要升格）」，新表右列是「明确排除」。

**因收窄而消解**：① 「升格」争议消失（目标确定）；② 环境依赖从「必然」降为「部分」；③ 优先级收敛为 `config.command` > 项目显式声明（`Makefile: test`）> 框架默认。

**仍真实的三坑**（与「单测 vs 集成」无关，勿误伤）：① **`npm test` 可能是 watch 模式**（框架默认行为）→ `CI=true` / `--run`；② **框架默认 ≠ 项目配置**（`package.json` scripts 可被改写为只跑子集；Maven 多模块可能只覆盖一个 module）→ 框架命令是**起点**，项目 config 才能覆盖；③ **单测也可能要环境**（Spring `@SpringBootTest` / Testcontainers / 内存 DB）→ 走「探测到但执行失败」处置（阻断 / 回 build），**不得伪装成「项目没测试」放行**。

**🔑 从我的错误反推出的设计教训（比探测表更值钱）**：技能正文**必须显式声明「单测边界」**。只写「跑全量单测」会被 AI 自行扩张成 `mvn verify`（**我就是现成失败样本**）。须写死：「只执行**单元测试**命令（如 `mvn test` / `./gradlew test`）；**不**执行需外部环境（DB / 容器 / 网络）的集成测试（`mvn verify` / `*IT.java`）」。

**兜底参数随收窄重定**：超时下调 —— **Node/Go/Python 300s、Maven/Gradle 600s**（少了集成重头，只剩编译 + 启动）；flaky 仍倾向 `fail_on_flake`（单测 flaky 概率低，但真 flaky 即设计问题）；「探测不到」仍倾向按 `verify_mode` 分（light 放行 + 声明、full 阻断）。

**仓库现状补充**：`assets/shared/scripts/` 共 20 个脚本，**无任何「跑测试」脚本**（`test-coverage-scorer.sh` 只读覆盖率报告文件、不跑测试）→ 此能力需新建，可参照 `constitution-validity.sh` 的「预检脚本 + 退出码」形态。

## 第 3 项补充：探测结果的人工确认回路（用户提出）

用户要求：**探测出单测框架后，展示给人工确认或修正；修正则根据人工反馈再次探测。**

**我的建设性修正：「一律再探测」是错的，人工反馈须按类型分流。**
- **「明确命令」**（例：「就跑 `npm run test:unit`」）→ **不再探测**，直接校验（命令存在 + 非 watch）后采用。
  理由：再探测会让系统的猜测**覆盖**人的明确指令，甚至回到刚被否定的原答案 —— 不尊重输入。
- **「线索 / 纠错」**（例：「这是 monorepo」「包管理器用 pnpm」「要用 `./mvnw`」）→ **必须重探**。
  人给的是**不完整信息**，需系统落实到可执行命令。
- **收敛条件**：重探 **≤ 2 轮**；超限则请人工直接给命令，或记 `No-Verification`。

**展示内容要求**：框架 | 命令 | **判定依据（哪个文件触发）** | 置信度 ——
给机器看结论，**给人看依据**（「自报告不是证据」的反向应用：人没有依据就无法有效确认）。

**🔑 落盘是本方案的关键闭环 —— 补上一轮「config 从哪来」的缺口**：
- 人工确认的产物 = `.polaris/config.yaml` 的 `test.command` + `source: probed | confirmed | corrected` + `confirmed_at`。
- 即：**config 不靠用户手填，由「探测 + 人工确认」产生**。上一轮只答了「config 覆盖 > 项目声明 > 框架默认」，
  **未答 config 的来源** —— 本环补上。
- **确认一次长期有效**：config 已有 confirmed 命令 → 下次 verify 直接读、**不再问**（否则每轮 verify 都停一次，高频变更会烦）。
- 冲突处理：config 有值但探测结果不符（项目换了框架）→ **config 优先**，报告里记一行提示，不打断。
- 形态复用既有机制：`policies/decision-point.md`（停顿等用户选）+ `policies/ask-question-react.md`（选项上限 10）。

## 🔄 第 3 项再扩展：验证分三档（用户提出「集成测试应执行主干功能测试」）

用户论点：目标第 3 点「正确实现（Verification）」在软件工程中靠测试用例验证；测试用例不止单测，还含集成测试；
认为**集成测试应执行功能测试用例（至少主干功能）**。

**评估结论：前提对，但那个等号不成立。**
- ✅ **同意前提**：单测全绿只证「碎片正确」，不证「业务正确」—— 单测可以是「描述现状（含 bug）的测试」（报告 §4.1）。
- ⚠️ **修正术语**：「集成测试 = 功能测试」混了**两个正交轴** ——
  **层级轴**（单元 → 集成 → 系统 → 验收）与 **目的轴**（功能 / 非功能）。
  集成测试的经典含义 = 验证**模块间接口与真实依赖的交互**（例：DAO ↔ 真实 DB），**不必走通业务流程**；
  用户说的「主干功能跑通」工程上叫 **E2E / 冒烟（smoke）**。
- **报告侧印证**：§5.3 的 L3 本来就含**契约测试**（此前对照表已指出 verify 缺它 —— 4.2b 第 6 项是
  「specs ↔ detailed-design 文档一致性」，非接口/行为/安全契约）→ 补集成层**不是新目标，是回到报告 L3**。

**形态：分三档（不是合并成一档）**

| 轨道 | 命令 | 环境 | 成本 | 触发 |
|---|---|---|---|---|
| 1 单元 | `mvn test` / `go test ./...` / `pytest` | 零依赖 | 秒级 | **总是跑**（light / full 都要） |
| 2 集成 | `mvn verify`（Failsafe `*IT`）/ 契约测试 | 需 DB / 容器 | 分钟级 | 改动跨模块边界 / DAO / 外部接口 |
| 3 主干功能（E2E / smoke） | 项目声明的 smoke / e2e 入口 | 完整运行环境 | 分钟+ | **`verify_mode=full` 且项目提供该入口** |

**限定 1｜环境由项目负责，技能不自己拼装**：技能只调用「一条命令跑通、自带环境准备」的项目入口（如 `make smoke`），
**不自己起容器 / 灌数据**。没有该入口 → 记 `No-Verification: 无主干功能验证入口` 并在报告声明。
（延续「技能定规矩、项目定参数」原则，保持技术栈中立。）

**限定 2｜`No-Verification` 不是免罪金牌**：`full` 模式下**既无单测证据也无功能验证证据 → 阻断**；
`light` 模式可放行 + 声明。这是「探测不到时按 verify_mode 分」的自然延伸。

**限定 3｜与「排除集成测试」不矛盾，界线在「显式 vs 隐含」**：
- 上一轮的排除防的是 **AI 自行扩张**（技能说「跑测试」，AI 自己跑去 `mvn verify`）；
- 本轮的纳入是 **技能显式规定**（「`full` 模式下必须跑项目声明的主干功能入口」）。
- **判据：技能显式要求的必须跑；没显式要求的不许自行扩张。** 这条要写进正文，作为防扩张的总闸。

**落点（复用同一回路，不新造）**：`config.yaml` 的 `test.commands.{unit, integration, smoke}` 三槽位，
共用「探测 → 展示 → 人工确认 → 落盘」回路。
**v1 范围建议**：三档**接口**进 v1；集成 / 功能档**按项目可用性降级**（无入口 → `No-Verification`），
避免无环境的项目卡死。

### ✅ 限定 1 已获用户确认：「环境由项目负责，技能不自己拼装」

技能只调用项目声明的、**自带环境准备**的一键入口（如 `make smoke`）；入口缺失 →
`No-Verification: 无主干功能验证入口`。**三档形态由此定下。**

### ⚠️ 由该确认连带出的必答项：**三级分叉**（区分「执行失败」与「断言失败」）

「环境由项目负责」使「**入口存在但环境没起好**」成为高频情形。若技能只写「非零退出码 → 回 build」，
则 **Docker 没起 / DB 连不上**会被误判为**代码缺陷** → agent 去 build 里找一个不存在的 bug，产出错误结论。

| 级 | 现象 | 性质 | 处置 |
|---|---|---|---|
| 1 | 探测不到入口 | **项目属性**（本就没这层验证） | 记 `No-Verification: 无 … 入口` + 报告声明 |
| 2 | 入口存在但**无测试结果摘要**（0 用例 / 进程异常退出 / 命令不存在） | **环境 / 基础设施问题** | 重试 1 次 → 仍失败记 `No-Verification: 环境不可用`；**不当作代码缺陷、不回 build** |
| 3 | 跑起来且**有测试结果摘要**（执行 N 用例 / M 失败） | **真实验证失败** | 按三段判读处置（增量轨红 → 回 build；存量轨红且不在红名单 → 回 build；在红名单 → `No-Verification`） |

**判据（可实现、不硬编码错误信息）**：*有没有测试结果摘要* —— 测试框架跑起来必输出「执行 N 个用例」；
环境问题通常连收集都没开始。此分叉与「探测不到 vs 探测到但跑不起来」**同构 → 统一成一条三级递进**。

**⚠️ 防滥用补充**：「环境由项目负责」≠「技能可预判环境不可用而跳过」—— **必须真调用一次让失败暴露**，
否则会变成新的逃避路径（自判「环境不行」→ 静默放行）。

**人工确认的成本控制**：三槽位（unit / integration / smoke）**一次展示、一次确认**，不逐个问。

### 术语定义：「基线红名单」（我造的词，必须记定义否则将来读不懂）

**定义** = **本次改动开始之前（base commit），本来就已经失败的测试清单**（对应 CI 术语 known / pre-existing failures）。

**唯一作用是归因**：跑完全量后拿到「N 条红」，只有对比红名单才能把**本次引入的回归**从**历史欠债**里摘出来。
没有它，红名单外的每条红都无法判断归属 → 4.3 独立裁判产出的每条 CRITICAL 都无法归因，评审结论作废。

**判读规则**：红在名单内 → 记 `No-Verification` 放行（历史欠债）；红不在名单内 → **本次回归 → 回 build**。
（红名单只对**存量轨**有意义；增量轨是新写的测试，红了直接回 build，无需比对。）

**三种获取途径（即待决的 A/B/C 三案）**：

| 案 | 含义 | 落点 | 代价 |
|---|---|---|---|
| A 全绿 | 任意红都阻断，无名单 | 最简 | **存量有红的项目直接无法使用 verify** |
| **B 只防新增**（我倾向） | 与 base 比对 | 红名单来源可配：**CI artifact 优先 → 跑 base commit 兜底 → 拿不到则降级为 A 并在报告显式标注** | 需采集基线（CI 零成本；跑 base 需另一 worktree / 成本×2） |
| C 固化清单 | 人工维护 `.polaris/known-failures.*` | 本质是 B 的输入 | **清单会腐烂**（修好没删、新增没加） |

**实现细节（待定）**：① 粒度取**用例级**（文件级太粗，会连带放行同文件里未被发现的失败）；② 采集时机建议
**verify 首次执行时采集并落盘缓存**（`openspec/changes/<task_id>/reviews/baseline-tests.*`），后续复用，不每次重跑 base；
③ base 即本 change 的 worktree 起点。

**为何在 polaris-flow 上尤其尖锐**：**它自己有 11 条存量失败** → 按 A 案，polaris 用自己的 verify 时**永远无法通过**（自举失败）。

### ✅ B 案已获裁决（「只防新增」）—— 以及来源的核实结果

**🔴 核实发现（修正我上一轮的「跑 base 兜底」说法）：polaris 里没有记录 base commit。**
- `assets/shared/templates/state.example.yaml:140-153` 的 `worktree` 段只有
  `created_by_polaris_flow / path / branch / origin_repo / status / created_at`，**无 `base_commit` 字段**。
- `src/core/hooks/worktree.ts` 里唯一的 `merge-base` 用法是**第 204 行 `--is-ancestor`**（判断分支是否为 HEAD 祖先，
  用于合并判定），**不取起点**；写入 state 的只有 `branch` / `created_at`（第 150-152 行）。
- ⇒ B 案的「跑 base commit 兜底」在现有架构下**要么改 `src/` + state 模板（越出「只动 verify」）**，
  要么用 git 推导：`merge-base(<worktree.branch>, 主仓库当前分支)`，或分支的 `@{upstream}`。
  **推导可行但脆弱**（依赖「主仓库当前分支 = 主干」这一假设；主仓库切过分支就不准）。

**🔑 更重要的观察（可简化实现）**：**红名单只对「CI 本身有红」的项目有意义。**
项目 CI 全绿时红名单 = 空集，**B ≡ A**，不需要任何额外机制。
⇒ 建议 **默认走 A，红名单作为可选逃生门**（有存量红的项目才启用）。**这不推翻 B**，只是把 B 从「默认路径」降为「可选路径」。

**修正后的来源优先级**（把「人工确认」插到「跑 base」之前 —— 跑 base 是极重操作）：

| 序 | 来源 | 成本 | 前提 |
|---|---|---|---|
| 1 | 项目提供的命令 / CI artifact（`test.baseline.command` / `file`） | 零 | 需项目提供 |
| 2 | **人工确认一次**（展示红列表，人勾选历史欠债）→ 落盘 `baseline-tests.*` | 低（一次性） | 无 |
| 3 | 跑 base commit（临时 worktree + 可能重装依赖） | **分钟级重操作** | base SHA 可得（需推导或改 src） |
| 4 | 降级 A（全绿）+ 报告显式标注 | 零 | 兜底 |

### ✅「默认 A + 红名单作可选逃生门」—— 用户同意（2026-09-25）

### 红名单「人工确认」路径的完整设计（用户追问后细化）

**问题本质**：判断「这条红是本次引入的，还是改之前就红的」，需要的是一份**历史事实** ——
它**不在当前工作区里**，AI 无法从代码推导出来。三条来源对比：

| 来源 | 成本 | 可靠性 |
|---|---|---|
| ① CI artifact / 项目命令 | 零 | 高（需项目提供） |
| ② **人工勾选一次** | 低（一次性） | 中（依赖人的记忆） |
| ③ 跑 base commit | **重**（临时 worktree + 可能重装依赖 + 跑全量） | 高 |

⇒ 人工确认**不是给 AI 找的捷径，而是该信息在「拿不到 CI」时唯一的低成本来源**。

**交互形态（复用「探测 → 展示 → 确认 → 落盘」回路 —— 第 4 次出现）**：
1. `4.0` 跑全量 → 有红 → 无基线可用
2. **AI 先按「影响面启发式」预填**：失败的测试所覆盖的代码是否落在本次 diff 内？
   命中 → 倾向「本次回归」；未命中 → 倾向「历史欠债」。**预填而非空白，人只做确认/修正。**
3. 展示「红列表 + 预判」→ 人工勾选/修正 → 落盘 `baseline-tests.*`（**绑定本 change 的一次性快照**）
4. 判定：名单内 → `No-Verification` 放行；名单外 → 回 build

**三条防滥用设计**：
- **「不确定」默认按严格处理**（当作回归）—— 防止随手全选、放行真回归
- **每个 change 只问一次**，落盘后复用，不再重复问
- **新增测试红了不问** —— 新测试本来就该绿，直接回 build，不进入红名单判定

**与 C 案（`.polaris/known-failures.*` 长期清单）的本质区别**：
- C = **长期清单、跨 change 复用 → 会腐烂**（修好没删、新增没加）
- B 的人工确认 = **绑定当前 change 的一次性快照、用完即弃 → 不会腐烂**

**只在「A 走不通」时才激活**：项目 CI 全绿（多数健康项目）→ 红必然全是回归 → **根本不问**。
