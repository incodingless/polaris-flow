## 工具教训（重要，会重复遇到）

**沙箱内 git 写操作不可用**：

- `.git/index.lock` 能**创建**但 **unlink 被沙箱拦截**（`Operation not permitted`），
  导致 `git add` / `git commit` 报 `index.lock: File exists`。
- 即使只读的 `git status` 也会创建 lock 并留下 stale lock（0 字节），
  下一次写操作就被挡住 —— 现象是「锁文件反复出现且删不掉」。
- **结论**：git 写操作必须用 `dangerouslyDisableSandbox: true`，并在命令前置 `rm -f .git/index.lock`。
- 另：`git commit -F - <<'EOF' … EOF` 的 heredoc 在本 shell 下**静默失败**（无输出、无错误、提交未发生）。
  改用多个 `-m` 参数（每个 `-m` 是一个段落），已验证可用。

**判别方法**：提交后必查 `git log --oneline -3` 确认 HEAD 已前移，不要以「命令无报错」当作成功。

### ★ 重要教训：Edit 报成功 ≠ 落盘（并发编辑）
给 `discovery` 补恢复章节时，Edit 返回成功，**但内容不在文件里**。线索：该文件 mtime 在那一刻被写入过，
且文件中出现了**不是我改的**改动（`### Step 1: 状态检查及中断恢复` → `#### 1.1 状态检查及中断恢复`）。
判定：**用户在用编辑器同时改这个文件，其保存覆盖了 agent 的写入**。重试后成功，且用户改动完整保留

## 核查：`state next` 命令引用（用户质疑「执行方式」一节）

**用户提问**：文档说「脚本根据 `phase`、`workflow`、`auto_transition` 输出」，但命令只有一个参数，

### 核查结论：用户怀疑成立，且比「没关联」更严重 —— **该命令执行会失败**

**实测**（2026-09-23）：
| 形式 | 结果 |
|---|---|
| `node polaris-flow state next test-id`（**文档现行写法**） | ❌ `node:internal/modules/cjs/loader:1386 throw err` —— `node` 把 `polaris-flow` 当模块名解析 |
| `node bin/polaris-flow.js state next test-id` | ✅ 输出 `NEXT: done` |
| 正确形式 | **`polaris-flow state next <change-name>`**（bin 在 PATH） |

**为什么错**：`bin/` 下两个入口（`package.json` bin 字段）——
`polaris` → 给人用的 CLI（init/status/update）；**`polaris-flow` → 给 hooks/scripts 的运行时入口**。
`_polaris-cli.sh` 注释写明了两者分工，且它 `exec polaris-flow <subcmd> --platform @PLATFORM_ID@`。
「node」前缀是历史残留 —— **我上一轮（批 4）修这条时只删了多余的 `flow` 字（`node polaris-flow flow state next`），
没发现 `node` 本身就不对**。

### 「关联」的真实机制（这才是用户困惑的来源）
`runStateNext` 的签名是 `{ changeName, repoRoot }`，**三个判定值都不在命令参数里，是脚本自己读盘**：

| 文档说的判定值 | 实际来源 |
|---|---|
| `phase` | `.polaris/workflow.yaml` 中该任务条目的 `phase`（**即上文所说的游标**） |
| `workflow` | 同一条目的 `kind` —— 决定映射到哪个族的技能（`FAMILY_BY_KIND`） |
| `auto_transition` | `.polaris/config.yaml` **与** `.polaris/tasks/<task_id>/state.yaml`（`isAutoTransitionEnabled` 判定，任务级可否决） |

⇒ 文档只写「根据 X 输出」却不说 X 从哪读，读者自然觉得命令与输出无关。**修法是把来源表补上**，
并呼应上文的「进度判据」（phase 就是那个游标）。

### 影响面（5 处文档 + 2 处源码注释）
- 文档：`zh/policies/auto-transition.md:22`、`coding/{specify:238, plan:435, normal:602, tweak:490}/SKILL.md`

  —— 也错（`polaris` 是用户 CLI，运行时应是 `polaris-flow`）

### 一个「设计意图」要注意（勿误改）
`assets/shared/scripts/` 里**没有** `state-next.sh` wrapper，而其他命令（task-state-entry / workflow-entry …）都有。
**这是刻意的**：wrapper 是给 hooks 用的（自动补 `--platform`），`state next` 是给 **skill 判断下一步**用的
