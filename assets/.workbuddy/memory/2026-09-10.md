## prd 链「研发就绪度（DoR）评估」必要性论证

用户提问：prd 流程是否需补「需求交付给研发进入设计阶段的就绪程度评估」。

**核查结论**：
- prd 现有检查只有两个视角：`review`（业务对不对，7 维度 P0~P3）与 `testability`（测试能否验证，4 维度 T0~T3 + A/B/C/D 评级），均为「查错型」，无「齐套型」判定。
- `review` 维度 5「可实现性」查的是 **feasibility（技术能不能做）**，不是 **readiness（描述够不够开工设计）**——"技术上完全可做但描述不足"的 PRD 会全绿通过。
- **关键前提缺口**：`coding/specify`、`coding/plan` 全文无任何 PRD 字样，prd 链与 coding 链**无正式输入契约**。此时新增就绪度评估，判据只能靠 AI 脑补通用 DoR 清单，会退化成形式主义工件。

**给出的建议（待用户选型）**：
- 顺序上「契约先行 → 再谈评估」：先定义 PRD→coding 的输入契约，就绪度才有客观判据。
- 方案 A（推荐）：refine Step 3 后加 Step 3.5 轻量 DoR——只做「齐套性核验 + 聚合两报告」，零新增评审维度，输出 R0/R1/R2；ship 确认卡带就绪度。
- 方案 B：独立 `readiness` 技能（对称 review/testability，可被 subagent 调度），重量级。
- 方案 C（止血）：不改流程，只在 `prd-template.md` 的 11.2 待确认事项加硬约束——影响技术设计的待确认项必须有决策人+决策时间。

**用户追加输入（同日）**：
- 研发设计阶段 = coding 链的 specify/plan。
- 评估目的 = **给人工评审提供重点方向**，避免全量通读；文档不过关就不进技术设计；得分过低不具准出条件。
- 用户给出 7 维度评分表 D1–D7（权重 15/15/20/30/12/5/3），双门槛（一票否决 D1/D3/D4 <60 + 加权总分），PASS ≥80 / CONDITIONAL 60–79 / FAIL <60，配套缺陷清单模板。

**我对该评分表的评审意见（待用户逐条表态）**：
- 硬伤：D1/D2/D3 与已有 review/testability 维度高度重叠 → 就绪度会变成第三遍通读，与"不全量阅读"目的冲突。**改法：评分证据源改为消费已有两份报告（D2←review 维度7/3，D3←可测性维度2，D1←review 维度2/7 + 补系统边界与数据生命周期，D5←11.2 待确认 + 补假设失效影响），仅 D4 全量新查。副作用：readiness 必须串行在 review/testability 之后（现有两者并行），refine Step 3 编排要改。**

**免评机制**（用户问"满足哪些条件可以不做"）：
- 立场：**默认评估、命中才豁免（黑名单式）**，不做白名单式——漏评代价（研发拿到不可设计的文档，人天级）远大于多评一次（分钟级 AI 算力），代价不对称决定豁免须收紧。
- 关键原则：**豁免的是评估动作，不是准出判定**。免评仍须落 `PASS（免评）` 结论 + 命中依据 + 审计信息，「没评估」≠「评估通过」，下游不能面对状态真空。
- 免评条件 E1~E3（全满足）：E1 纯文案/格式变更、无功能点·规则·D4 五子项变更；E2 有历史 PASS/CONDITIONAL 报告；E3 终稿 11.2 无阻断级未决项且 P0/T0 清零。
- 强制信号 F1~F5（命中任一即全评）：首次交付 / D4 子项变更 / 本轮修过 P0·T0 / 跨团队或外部接口 / 用户要求。
- 漂移防护：连续免评 2 次后第 3 次强制全评（`ship.readiness_waive_count`，全评清零）。
- FAIL 修复后不得免评；免评须在 ship Step 2 话术显式标注，人工可选「改为全评」。
- ship Step 1 重编号：1.1 解析 → 1.2 版本复用 → **1.3 免评判定** → 1.4 全量评估 → 1.5 FAIL 处理。
