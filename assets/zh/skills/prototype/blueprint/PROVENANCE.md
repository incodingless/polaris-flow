## 为什么拆出本技能

原型开发原由一个技能（`generate`）一次跑完「需求理解 → 设计细化 → 实现 → 评审」。问题不在能力，而在**人工确认没有落脚点**：

- 判断层（需求理解、任务流、IA、页面体系）本该由产品经理确认方向后再动手，但在一个技能内部只能做成软动作，用户往往是在原型做完后才发现方向不对；
- 一次交付的东西太长——页面模式、结构 12 项、状态 11 种这类细节，人既读不过来也没有判断依据，把它们摆到确认台上等于没有门禁。

拆成三个环节后，确认点从技能内的软动作变成**环节间的交付物门禁**：

```
blueprint（本技能）→ build → review
   人工确认冻结        verify 门禁    P0 清零
```

## 切分点为什么在页面清单之后

判据沿用 `references/00-basis.md §31.1 / §31.2`：

| 步骤 | 性质 | 归属 |
|---|---|---|
| 3.1 理解卡、3.2 黄金流、3.3 IA、3.4 页面体系与职责 | `§31.2`：页面数量、范围取舍、建设批次、实现深度——**产品经理拍板** | 本技能（人确认） |
| 3.5 页面模式、3.6 结构 12 项、3.7 状态 11 种、3.8 视觉系统 | `§31.1`：本技能的专业职责——**人确认不了，也不该确认** | `build`（技能自主） |

> **人工门禁只卡在人判断得了且有权限判断的事上。**

## 命名

`blueprint`（蓝图）而非 `plan` / `think`：工程名词，与 `build` / `review` 层级齐整；且"蓝图"自带冻结意味——蓝图定稿后施工必须按图进行，要改走变更单，与本环节的 `WEB-DESIGN-CHANGE-XXX` 机制同构。

## 工作流接线

`--kind requirement --skill blueprint`（`--kind` 合法值仅 `change|requirement|testcase`；`--skill` 是锁文件写者标识，按全仓惯例取技能名）。
`state.yaml` 只记身份与指针（`task_id` / `phase` / `naming` / `output_dir`），**不记做到第几步**——环节内进度以落盘产物为准（产物即状态）。
