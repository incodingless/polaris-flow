## 27.1 原型运行时验证 · 三层法（强制）

> **已脚本化，本节是规格说明，脚本是执行体。**
>
> ```bash
> node scripts/verify.mjs <原型.html> [--flow=<黄金流.json>] [--layer=1,2,3]
> ```
>
> 交付前必须运行且退出码为 0（`0` 通过 / `1` 有硬失败 / `2` 用法环境错 / `3 --strict` 下必需层被跳过）。
> 脚本的边界要说清楚：**它能判「有没有」，判不了「好不好」**——语法、配平、跳转、图标引用、
> 对比度、横向溢出、页面是否空壳、链路是否走通、数据是否含个人信息，这些可判定项由脚本说了算；
> 设计是否专业、状态取舍是否恰当、信息层级是否清楚，脚本一律不表态，仍须人工按 §33 审查。
> 脚本报 WARN 的项需要人工判断，不等于通过。
>
> 三层与脚本能力对应关系：第一层全自动；第二层全自动（含加载期 JS 错误采集与逐页激活）；
> 第三层的分辨率溢出全自动，**黄金流点击链路需要 `--flow` 提供步骤定义**（用 `--print-flow-example` 取模板）。
> 未提供 `--flow` 时第三层只跑分辨率，会被标记为「必需层跳过」。
>
> 下表「验证方法自身的坑」的规避逻辑**已内建在脚本里**，保留在此作为实现依据与手工核验时的参照。

> **静态检查通过 ≠ 原型可用。** JS 语法校验、标签配平全部通过的原型，仍可能因一处运行时错误（多余括号、未定义引用、DOM 时序）整页白屏或交互失效。交付前必须依次完成三层验证，任何一层缺失不得交付。

**第一层｜静态检查（秒级）**

- JS 语法校验：抽出 `<script>` 内容用 `node --check`（或 `new Function(scriptText)`）不抛错；
- HTML 标签配平：div/span 等容器标签开闭数量一致；
- 页面注册完整性：所有 `goto('xxx')` / `onclick` 跳转目标页面 ID 都已存在；
- 引用完整性：所有 `<use href="#i-xxx"/>` 的 symbol 都已定义。

**第二层｜无头浏览器逐页冒烟（分钟级）**

Windows 下无需安装 Playwright，直接用系统 Edge：`msedge.exe --headless=new --disable-gpu --dump-dom "file:///..."`。逐页检查：

- 每个页面真实渲染：目标 `<section>` 存在、**激活后可见文本非空**，不是空白壳。
  ⚠️ **innerHTML 非空 ≠ 可见**：状态层 / 分页容器没被激活时，标记里内容齐全而屏幕上什么都没有，
  只看 markup 长度会给出空转的绿（脚本 `L2-7` 专抓这一类：标记有内容、可见文本却近于零）；
- JS 无运行时错误（探针执行后页面仍可交互、关键元素可查询）；
- **多入口覆盖**：同一页面的所有入口（侧边栏直达 / 首页快捷卡 / 列表跳详情）逐一进入验证，不能只测一个入口。

**第三层｜黄金流链路 + 三档分辨率实测**

- 黄金任务流点击链路实测：从工作台点击走通主任务流到最后一页，每步断言关键内容出现（选择状态、合计金额、提交按钮、成功反馈），不是"页能打开"就算过；
- 分辨率溢出检测：1366×768 / 1440×900 / 1920×1080 三档逐一打开全部页面，检查横向溢出与关键操作可达。
- **链路断言的硬约束（写流程定义前先看这条）**：全流程的步骤在**同一帧内**执行，脚本**不会真正等待**。
  因此**要断言的中间状态必须同步可达**（例如点「保存」同步渲染结果页）。靠 `setTimeout` / 动画推进的过程态
  无法被链路断言——`wait` 步骤会**直接判失败**，而不是静默忽略。
  需要展示「处理中」这类派生状态时，把它放进结果页的过程时间线（如三步 track 全部 done），
  或用 `?demo=1` 演示浮层单独演，不要指望流程能停在中间态上。

**实测踩坑的验证方法 bug 模式**（静态检查查不出来、验证方法本身也会出错，引以为戒）：

| 坑 | 现象 | 正确做法 |
|---|---|---|
| 替换脚本多留/漏掉一个花括号 | 整页白屏 | 每轮修改后必须重新抽 `<script>` 做 `--check`，不能只看替换成功数 |
| dump-dom 输出用正则全文匹配提取断言结果 | 正则先命中注入探针自身的源码字符串，真结果被误判 | 断言结果写入带 id 的渲染锚点元素（如 `<pre id="probeResult">`），按元素提取 |
| 探针写在父页、通过 iframe 读原型内容 | `file://` 下跨 frame 读取被拦，读不到内容 | 探针脚本注入原型副本同文档执行，再 dump-dom |
| 断言写死整句文案（含动态拼接的单号、金额） | 正确行为被判 FAIL，误报 | 断言用稳定子串或元素存在性，不匹配含动态值的整句 |
| setTimeout 动效后立即断言 | 断言时机早于渲染完成 | dump-dom 加 `--virtual-time-budget` 或断言前留足延时 |

## 27.2 大文件编辑纪律（强制）

骨架（App Shell / Token / 图标 / 路由 / 导航）已由 `scripts/scaffold.mjs` 生成并接管（新增页面/图标走 `add-page` / `add-icon` 定点插入，内部已实现「唯一匹配断言 + 任一失败不写盘」），本节纪律只适用于**页面主体**的编辑：

- **禁止并行 Edit 同一文件**：多个 Edit 并发写同一文件会互相覆盖，出现部分写入回滚、文件呈新旧混合状态。同一文件的多处修改必须严格串行；
- **多处修改用断言式替换脚本**：把全部替换写成一个 Node 脚本，每处替换先验证目标串在全文中**唯一匹配**（count === 1），任何一处失败立即中止、**不写盘**；全部通过才一次性写入；
- **构造目标串前必须先 Read 原文**：类名、属性名、内联样式、缩进层级极易凭记忆写错，禁止凭记忆拼写；
- **误改后先用 Read 确认实际结构**，再决定回滚还是修复，不做叠加猜测式修改；
- **改 `scripts/` 下的脚本时**：USAGE、探针源码住在模板字面量里，注释里出现反引号会提前终止模板字符串、出现 `${` 会被当插值——改完先跑 `node --check`。

## 27.3 演示数据去个人化（强制）

原型交付前必须全局扫描示例数据（**`verify L1-15` 已自动扫描**，命中为疑似、需人工确认是否确为真实数据）：

- **禁止**出现用户本人或真实同事的**真实姓名、手机号、工号、真实内部项目名**；
- 一律使用通用演示身份（如"林远 / 陈默 / 李明"等明确虚构名），审批人用"部门负责人 / X 总"类通用称谓；
- 姓名类数据集中在数据区定义、页面引用变量，不散落硬编码在各页面——便于一键替换与全局扫描；
- 该检查纳入演示就绪审查（`polaris{{SKN_SPR}}prototype{{SKN_SPR}}review` → `references/01-quality-criteria.md §33.6`），违反等同 P0 缺陷。


# 28. 技术实现基线

**分两层，不要混为一谈。**

## 28.1 原型自身（本技能产出的东西）

单文件 HTML，原生 CSS / JS，**零外部依赖**。`scaffold.mjs` 生成的就是这个形态，`verify.mjs` 也按这套机制工作——
`<section id>` 页面容器、`data-goto` 跳转、`<symbol id="i-*">` + `<use href="#i-*">` 图标。

**因此原型内不得引入外部 UI 库或图标字体**：它必须能离线双击打开、发给任何人都能看、
在演示机与投影上不因 CDN 不可达而白屏。图表用静态 SVG / 内联示意，不用外部图表库。

## 28.2 目标系统的实现栈（研发拿原型去实现的东西）

**由项目决定，本技能不预设、不推荐。** 交接时说明「原型的哪个区块对应哪类组件」即可；
研发用什么框架实现，都不改变设计原则（第一原则与视觉判据都与框架无关）。

> **图标机制没有两种**：原型里的界面图标一律是**内联 SVG symbol 一套线性体系**。
> 字体图标库（Font Awesome 之类）若出现在目标系统里，那是研发期实现细节，**不得进入原型**——
> 否则同时违反一票否决第 27 条（混用图片 / 字符图标），并让 `verify L1-7` 的 symbol 引用完整性失去意义。

# 30. 需求追踪

关键能力尽量建立：

> **业务场景 → 用户任务 → Flow → Page → 交互 → API / AI → Test Case**

例如：

```text
SCENE-001
AI合同审查
    ↓
TASK-001
合约专员完成风险审查
    ↓
FLOW-001
上传→AI审查→确认→输出
    ↓
WEB-PAGE-001 / 002 / 003
    ↓
API / Agent / Test
```

如果一个页面无法追溯到明确任务，应重新判断其必要性。

# 35. 标准调用方式

> 以下是**建造**的标准调用方式。**原型评审与「能否交研发」检查不在本技能**——已移交 `polaris{{SKN_SPR}}prototype{{SKN_SPR}}review`，其调用话术见该技能的《标准调用方式》一节（不要在本技能里再复制一份）。

## 35.1 从零开始

> **调用本技能，我要做一个 XXX Web 产品原型。这是需求和相关资料。先帮我理解用户、场景、核心任务和黄金任务流，不要马上画页面。**

## 35.2 从方案文档继续

> **调用本技能，承接当前已确认的建设方案 / 产品方案，将服务对象、核心场景、业务闭环、一期建设内容和业务成果转成 Web 产品原型。已冻结内容不得擅自改变。**

## 35.3 从 Agent 设计文档继续

> **调用本技能，承接当前已确认的 Agent 岗位、Workflow 和人工卡口设计，设计高保真 Web 工作台和交互。**

## 35.4 直接做高保真原型

> **页面结构已经确认，调用本技能 按统一视觉规范生成高保真可交互 Web 原型，并补齐 Loading、Empty、Error、AI处理中和人工确认状态。**

## 35.5 带项目约束开展设计

> **调用本技能，这是当前项目的时间、研发资源、交付目标和其他约束：XXX。先按完整产品设计方法形成原型，不要擅自删减页面或降低实现深度；需要取舍的地方单独列出，由我决定。**
