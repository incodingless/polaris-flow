# 25. 桌面 Web 响应式与视口自适应设计

本技能 的主目标是桌面企业 Web。响应式设计不能只理解为“设置几个断点”，而应保证：

> **同一个业务页面在不同电脑、不同浏览器窗口、不同桌面分辨率下，核心任务不变、信息层级不乱、主要操作可见、工作区合理利用、组件不会被挤坏或出现大面积无效空白。**

本章为强化规则。

## 25.1 核心目标

桌面端适配同时处理五个问题：

1. **宽度自适应**：屏幕变宽或变窄时，模块能够重新分配宽度；
2. **高度自适应**：窗口高度变化时，核心工作区合理使用剩余视口；
3. **信息密度自适应**：窄屏时减少非关键展示，宽屏时提升信息利用率；
4. **组件自适应**：表格、图表、Drawer、Dialog、Split Pane 等不因尺寸变化失真；
5. **有效工作区利用**：避免页面内容只占上半屏、下半屏出现大面积无业务意义空白。

响应式的目标不是把同一张设计稿机械缩放，而是：

> **保持任务结构稳定，让布局、尺寸、密度和局部呈现方式随可用空间变化。**


## 25.2 默认桌面适配基线

必须优先检查：

- **1366×768**：紧凑型办公屏；
- **1440×900**：标准设计基准；
- **1920×1080**：常见大屏办公环境。

建议增加检查：

- **1600×900**；
- **2560×1440**：超宽 / 高分辨率桌面。

原有断点思路继续保留：

- 480px；
- 768px；
- 992px；
- 1200px；
- 1600px。

但这些断点只是布局触发参考，不等于所有页面必须使用完全相同的响应方式。

复杂 Web 工作台不要求在手机端保持完整业务能力；移动场景应优先独立设计 APP。


## 25.3 页面外壳 App Shell 自适应

企业 Web 推荐采用稳定的应用外壳：

```text
Viewport
├─ Header
└─ Body
   ├─ Sidebar
   └─ Main
      ├─ Page Header / Breadcrumb
      └─ Page Workspace
```

推荐原则：

- 页面整体优先以 `100vh` 建立视口基准；
- Header 使用明确高度；
- Body / Main 使用 `flex: 1`；
- 主内容容器必须允许 `min-width: 0`、`min-height: 0`，避免 Flex 子项溢出；
- 页面级滚动与工作区内部滚动要有明确边界；
- 不要让 Header、Sidebar、内容区各自使用互不关联的固定高度。

推荐实现思路：

```css
.app {
  min-height: 100vh;
  display: flex;
  flex-direction: column;
}

.app-body {
  flex: 1;
  min-height: 0;
  display: flex;
}

.main {
  flex: 1;
  min-width: 0;
  min-height: 0;
}
```

以上为实现参考，不要求项目机械复制代码。


## 25.4 宽度自适应原则

### 25.4.1 主内容区

业务后台的主要工作区通常应跟随浏览器宽度变化，而不是固定为某个设计稿宽度。

优先：

- `width: 100%`；
- Flex；
- CSS Grid；
- `minmax()`；
- `clamp()`；
- 百分比；
- 合理的 `max-width`。

避免：

- 主要卡片全部使用固定像素宽度；
- 只针对 1920px 设计；
- 通过绝对定位维持版式；
- 屏幕变宽后仍只占中央一小块区域；
- 屏幕变窄后内容被强行压缩到不可读。

### 25.4.2 Max Width 不是所有页面都需要

以下页面通常可充分利用横向空间：

- 工作台；
- 数据列表；
- AI 工作台；
- 主从页；
- 对照审核页；
- 配置页；
- 复杂业务处理页。

以下页面可以设置适当最大宽度，提高阅读效率：

- 简单表单；
- 单列详情；
- 说明文档；
- 设置向导；
- 以阅读为主的页面。

原则：

> **工作型页面优先利用空间，阅读型页面优先控制行宽。**


## 25.5 栅格与模块重排

卡片区、指标区、分析区不应只靠固定宽度。

例如 KPI 区：

```text
宽屏：4 列
标准屏：4 列
较窄桌面：2×2 或自动压缩
极窄窗口：允许进一步降级
```

推荐使用：

```css
grid-template-columns: repeat(auto-fit, minmax(220px, 1fr));
```

但必须结合业务决定最小宽度，不能为了自适应让关键指标卡变得过窄。

页面模块重排时：

- 保持重要模块顺序；
- 主任务区优先；
- 辅助分析区可后移；
- 不得因重排导致核心操作消失或上下文断裂。


## 25.6 高度自适应与有效工作区利用

这是本章的重点。

### 25.6.1 基本原则

桌面 Web 页面不得因为固定高度设计，使业务内容在页面上半部分提前结束，而下半部分留下大面积无业务意义背景。

但同时：

> **消灭空白 ≠ 为了填满页面而新增 KPI、图表、卡片或伪功能。**

应优先通过：

- 工作区 `flex: 1`；
- Grid 行高；
- 模块比例；
- 表格动态高度；
- 左右分栏；
- 内部滚动；
- Empty 状态居中；
- 真实业务内容重新组织；

改善空间利用。

### 25.6.2 不同页面模式的纵向策略

**工作台**

- 不强制所有模块铺满整屏；
- 首屏不得出现明显的大面积无效空白；
- 若业务内容不足，优先调整模块纵向比例与组合；
- 只能增加真实有价值的信息，不得为了填空创造指标。

**AI 工作台**

- AI 主工作区原则上应使用 Header / 页面标题以下的剩余视口高度；
- 输入配置区与 AI 结果区优先形成稳定工作面；
- AI Empty、Processing、Result 状态都应在同一有效工作区内切换；
- 不应给结果区写死 300px、400px 等固定高度后让页面下方空置。

**列表页**

- 表格区优先自适应剩余高度；
- 表格数据多时内部滚动或分页；
- 数据少时仍保持合理工作区，不应让分页和操作栏漂浮在页面中部。

**主从式工作页 / 对照审核页**

- 左右 Pane 原则上共同占满剩余工作区；
- 左侧列表与右侧详情可独立滚动；
- 不应因某一侧内容短导致整个页面高度提前结束。

**配置管理页**

- Tree 与右侧配置区原则上跟随剩余视口高度；
- 长内容区域内部滚动；
- 避免左树很短、右侧很短、底部大面积空白。

**详情页**

- 允许内容自然撑开并使用页面级滚动；
- 不为了“铺满”而强制拉伸文本、时间线或附件区。

**Empty 页面**

- Empty 状态应位于“有效工作区”的视觉中心；
- 不是固定在页面上方某个像素位置。


## 25.7 大面积无效空白 Dead Space 判断

以下情况应主动审查：

- 首屏下半部分存在连续大面积背景色，且没有业务含义；
- 工作区已经结束，但浏览器仍有明显剩余视口；
- Empty 状态只出现在上半屏，下面大面积空置；
- 1920×1080 下正常，但 2560×1440 下内容缩成一小块；
- 1366×768 下必须上下滚动才能看到本应同时可见的核心操作。

如果大面积空白是明确的：

- 阅读留白；
- 安全边距；
- 视觉聚焦；
- 空状态；
- 流程等待态；

则可以保留。

原则：

> **判断的是“是否有业务意义”，不是单纯追求页面填满率。**


## 25.8 侧边栏自适应

默认（取值与 `references/02 §14.4` / `--sidebar-w` 一致）：

- 展开约 216～224px（`--sidebar-w` 默认 216px）；
- 折叠约 64px。

建议：

- ≥ 1440px：默认可展开；
- 1366px 或窗口明显变窄时：允许自动收窄或记忆用户折叠状态；
- 更窄桌面窗口：可折叠为图标导航。

侧栏变化后，Main 必须自动重新计算宽度，不得依赖固定 `margin-left` 写死页面。


## 25.9 表格自适应

企业后台表格必须考虑不同宽度。

推荐优先级：

1. 关键列始终保留；
2. 名称 / 描述列可弹性伸缩；
3. 操作列保持可用；
4. 非关键列可隐藏、折叠或进入“自定义列”；
5. 复杂表格允许横向滚动；
6. 必要时固定首列 / 操作列；
7. 表格高度根据剩余视口动态计算。

禁止：

- 所有列强行压缩；
- 字号不断缩小以适配；
- 列宽全部写死；
- 窄屏时按钮被挤成不可点击状态。


## 25.10 图表自适应

图表组件（不限定具体库）必须：

- 宽度跟随容器；
- 容器尺寸变化后触发 resize；
- 高度可根据页面模式使用 `clamp()`、比例或 Flex 分配；
- 图例在窄屏时允许换行或调整位置；
- Tooltip 不应超出主要工作区；
- 图表数据标签过密时应减少或隐藏非关键标签。

禁止：

- 图表 Canvas / SVG 固定宽高；
- 屏幕缩小时图表被裁切；
- 大屏时图表被无限拉宽导致可读性下降。


## 25.11 Drawer / Dialog 自适应

### Drawer

- 宽度应结合视口，而不是只写固定像素；
- 大屏可保持舒适阅读宽度；
- 较窄桌面端可增加占屏比例；
- 复杂业务 Drawer 如果在窄屏无法保证可用性，应升级为独立页面。

### Dialog

- 设置合理最大宽度；
- 不得超出视口；
- 内容过高时 Dialog Body 内部滚动；
- 底部操作区保持可见。

推荐思路：

> 固定舒适宽度 + `max-width: calc(100vw - 安全边距)`


## 25.12 超宽屏控制

屏幕越宽，不代表所有内容都应该无限拉伸。

在 1920px 以上尤其注意：

- 长文本行宽；
- 表单字段长度；
- 图表横向跨度；
- 卡片之间距离；
- 主从区域比例。

可通过：

- 最大内容宽度；
- 最大列宽；
- 固定 / 弹性混合布局；
- 中央工作区 + 两侧合理留白；

保证信息不会过度分散。

原则：

> **宽屏增加的是工作空间，不是把所有元素等比例拉长。**


## 25.13 紧凑桌面与浏览器缩放

1366×768 等紧凑屏幕应重点检查：

- 页面标题是否占用过高；
- KPI 卡是否过高；
- 表格首屏是否能看到有效数据；
- 主操作是否在首屏；
- Drawer / Dialog 是否超高；
- Sidebar 是否挤占过多宽度。

建议关键 P0 页面额外检查：

- 浏览器 100%；
- 浏览器 125% 缩放下是否出现严重遮挡、横向溢出或按钮不可用。

不要求所有页面在高缩放下保持完全相同的信息密度，但核心任务必须可完成。


## 25.14 禁止“截图式布局”

高保真 HTML 原型不得只在生成时的某一个分辨率看起来正确。

以下属于高风险实现：

- 大量绝对定位；
- 页面主体固定宽高；
- 卡片通过 `left/top` 定位；
- 结果区域固定高度；
- 通过大段 margin / padding 撑出位置；
- 只使用像素值且没有弹性规则；
- 浏览器 Resize 后布局不重新计算。

原型应优先使用真实 Web 布局能力：

> **Flex + Grid + Responsive Width + Dynamic Height + Overflow Strategy**


## 25.15 P0 页面响应式说明

每个 P0 页面研发交接时，应至少写清：

- 基准分辨率；
- 窄屏时哪些区域收缩 / 换行 / 折叠；
- 宽屏时哪些区域扩展；
- 哪个区域使用剩余高度；
- 页面级滚动还是区域内滚动；
- 表格列的保留 / 隐藏策略；
- Drawer / Dialog 的尺寸策略；
- Empty / Loading / AI Processing 的定位方式。


## 25.16 多分辨率验收矩阵

P0 页面完成后必须至少检查：

| 检查项 | 1366×768 | 1440×900 | 1920×1080 |
|---|---|---|---|
| Header / Sidebar 正常 | 必须 | 必须 | 必须 |
| 核心操作首屏可达 | 必须 | 必须 | 必须 |
| 无异常横向溢出 | 必须 | 必须 | 必须 |
| 主要模块不重叠 | 必须 | 必须 | 必须 |
| 无大面积无效空白 | 检查 | 检查 | 检查 |
| 表格 / 图表正常 | 必须 | 必须 | 必须 |
| Drawer / Dialog 可用 | 必须 | 必须 | 必须 |
| Empty / Loading 居中合理 | 必须 | 必须 | 必须 |

建议 2560×1440 额外检查超宽屏信息分散问题。

### 25.16.1 页面类型专项验收

除通用矩阵外，按页面类型增加：

- **工作台**：不得出现少量待办却产生内部滚动；模块高度与信息量匹配；
- **列表页**：分页紧跟数据区；当前页行数随视口合理变化；
- **看板页**：少量卡片时不得强制满高；总数与当前展示量关系明确；
- **分析页**：图表和结论共同回答业务问题，不能只铺一行 KPI 后留下大面积空白；
- **规则 / 资产页**：总量较大时应展示合理数量的条目或分页，不把 3 条内容放在整屏大容器里；
- **AI 工作台**：Full Workspace 可以铺满，但 Empty / Processing / Result 三态均应有完整任务结构。



## 25.17 响应式设计最终判断

不能只问：

> “1440×900 好不好看？”

必须同时问：

> **窗口变窄，核心任务还能完成吗？**  
> **窗口变高，工作区会合理延展吗？**  
> **窗口变宽，内容会不会过散？**  
> **表格、图表、Drawer 会不会被挤坏？**  
> **页面有没有因为固定高度出现大面积无效空白？**


# 26. 可用性与可访问性增强

本部分为本技能对原规范的增强。

## 26.1 点击区域
按钮、图标、可点击区域应有足够尺寸。

## 26.2 颜色不是唯一信息
状态不能只靠颜色，应同时有文字 / 图标。

## 26.3 对比度
正文和关键状态保持足够对比度。

**量化要求**：文本对白底对比度 ≥ **WCAG AA 4.5:1**，由 `verify L1-9` 强制。完整判据、WCAG 相对亮度公式与实例教训（`#8f94ad` 不达标 / `#646b85` 为合格最浅灰）见 `references/02 §14.3`（**唯一来源**，此处不再复制）。

## 26.4 键盘 / Focus
高频业务系统应保留明显 focus 状态。

**基线**：弹窗/Drawer/浮层必须支持 **Esc 关闭**；聊天输入、搜索框支持 **Enter 提交**；浮层支持点击外部关闭。禁止全局 `outline: none`。完整 Tab 遍历与 ARIA 可留给研发，但须写入交接文档"由研发实现"。

## 26.5 错误提示
不能只提示“失败”，必须尽量告诉用户：
- 为什么；
- 怎么处理。

## 26.6 新 CSS 特性兼容门槛

高保真原型常在企业内网旧浏览器壳中打开（演示、评审场景），对 2023 年后新 CSS 特性设立使用门槛：

- **`:has()` 选择器**：Chrome 105+（2022.8）才支持，企业内网壳（基于旧 Chromium 嵌入）打开会出现"圆点与图标并存"等半渲染状态。**禁止用于关键视觉路径**（如 tag 前的圆点显示）；确需使用必须配显式兜底（如 `tag-none` 类直接写死图标/圆点），且全站盘点不能有遗漏点；
- 同类约束适用于 `:user-invalid`、CSS 嵌套原生语法、`color-mix()`、容器查询单位（`cqw` 等）；
- 判定原则：**该特性失效时页面是"完整但少了点增强"还是"结构错误"**——后者一律不用，前者可用但须验证降级态可接受；
- 验收时用无头浏览器（内核版本接近目标环境）实际打开验证，不凭兼容表想象。
