# 14. Step 3.4｜视觉设计系统

本章只讲**方法与判据**。
**具体取值不写在本规范内**——本规范只回答"按什么规则取、阈值是多少、命名是什么"，
取值本身见 §14.2 指向的 Token 文件。

## 14.1 接口契约：脚本与产出物的约定（不可改）

`verify.mjs` 与 `scaffold.mjs` 靠下面这组约定识别原型结构。**改这里必须同步改两个脚本**，
否则会出现「脚本全绿，但实际上什么都没查」的假通过。

| 项 | 契约 | 谁依赖它 |
|---|---|---|
| 页面容器 | `<section id="…" class="page" data-title="…">`，id 即跳转目标 | verify L2/L3、scaffold add-page |
| 跳转 | `data-goto="<page-id>"`，且目标必须存在 | verify L1-4 |
| 图标 | `<symbol id="i-*">` 定义 + `<use href="#i-*">` 引用 | verify L1-7 |
| 路由函数 | `window.goto(id)` / `showPage(id)` | verify L2 激活页面 |
| 文本色 Token 命名 | `--text-*` \| `--title-color` \| `--heading-color` \| `--font-color` \| `--label-color` | verify L1-9 按名匹配 |
| 背景色 Token 命名 | `--bg-*` \| `--background*` \| `--surface*` \| `--fill-*` | verify L1-9 按名匹配 |
| 文本对比度 | 文本类 Token 对白底 ≥ **4.5:1**（见 §14.3） | verify L1-9 |
| 区域标记 | `@TOKENS`（CSS 注释）/ `@ICONS` `@NAV` `@PAGES`（HTML 注释） | scaffold 定点插入 |

**取值可整套替换，命名不可替换。** 命名一改，L1-9 就认不出文本色——那不是"通过"，是"没查"。
`scaffold.mjs` 因此在注入 Token 前会校验命名契约，缺了文本色或背景色就直接失败。

## 14.2 Token 取值：来源与覆盖优先级

**具体色值、间距、圆角、阴影、字号不属于规范，属于项目。** 默认取值放在
`assets/default-tokens.css`（技能的兜底基线），落地时按优先级取用：

| 优先级 | 来源 | 落地方式 |
|---:|---|---|
| 1 | 需求包提供的设计系统 / 视觉规范 | `init --tokens=<规范.css>`；已有原型用 `set-tokens <原型.html> --tokens=<规范.css>` |
| 2 | 技能兜底基线 | `assets/default-tokens.css`（不传 `--tokens` 时自动使用） |
| 3 | 项目内微调 | 只改原型的 `@TOKENS` 区，不散落到页面样式 |

**为什么取值不写进规范**：同一套取值若在规范正文与脚手架里各存一份，必然漂移——已经发生过
一次（`--text-placeholder` 在正文是 `#999999`、在脚手架里是 `#646b85`），而且两边都能"看起来对"。
规范只负责规则与阈值，取值的唯一来源是 Token 文件。

**Token 文件的格式**：裸声明片段（可含 CSS 注释），会被原样拼进原型的 `:root{}` 内；
传完整 CSS 也可以，`:root{}` 外壳会被自动拆掉。同一 Token 重复定义会直接报错。

**三条与取值无关的约束，必须遵守**：

- 间距只从一组固定刻度里选（默认 `--sp-*`），不出现随机间距；
- 圆角只用有限档位（默认 `--radius-sm/md/lg`），不出现"每处一个圆角"；
- 阴影保持轻量，禁止大面积重阴影。

## 14.3 文本对比度硬指标（不可放宽）

文本 Token 用于辅助信息（12～13px 小字、元数据、时间线描述）时，对白底对比度不得低于 **WCAG AA 4.5:1**。原型演示常在投影环境，后排观众必须能看清辅助文字。

校验方法：对每个文本 Token 按 WCAG 相对亮度公式计算对比度（白底 #ffffff 与 Token 色的比值）。
实例教训：`#8f94ad` 辅助灰对白底仅 3.0:1，不达标，需加深至 `#646b85`（5.27:1）一级。

规则：

- 定文本 Token 时必须用公式校验，禁止凭"看起来还行"定灰度；
- 同一灰度层级在全站只定义一次（CSS 变量），修正一处全局生效；
- 更深的灰不等于更好看——修正方向是"达到 4.5:1 的最浅合格灰"，保持界面轻盈。

> 本条是**阈值**，与取值来源无关：换设计规范时同样适用。规范给了不达标的灰，也必须加深后
> 再落地——投影环境下看不清的演示，比"用了公司色"更严重。

## 14.4 企业级视觉比例基线

视觉系统不能只定义颜色、圆角和阴影，还必须定义"比例"。

正式企业 Web 原型默认优先采用以下比例基线，并允许根据页面类型做小范围调整：

| 项目 | 默认建议 |
|---|---|
| Header 高度 | 56～60px |
| Logo / 品牌图标 | 28～30px |
| Sidebar 展开宽度 | 216～224px |
| Sidebar 折叠宽度 | 64px |
| 页面左右 Padding | 20～24px |
| 页面上下主要间距 | 16～20px |
| 一级模块间距 | 16px |
| 卡片内边距 | 16～20px |
| 普通卡片圆角 | 8px |
| 主按钮高度 | 36px |
| 紧凑按钮高度 | 32px |
| 输入框 / Select 常规高度 | 36px |
| 表格表头高度 | 42～44px |
| 表格正文行高 | 44～48px |

上表是**建议范围**，采用时收敛为 Token 文件里的确定值（`--header-h` / `--sidebar-w` /
`--page-pad-x` / `--ctl-h` / `--ctl-h-compact` 等）。以下为默认视觉基线，不是机械尺寸模板。
真正目标是：

> **让页面在 1366×768、1440×900、1920×1080 下都保持"清楚、舒展、专业"，而不是通过缩小字号、压缩间距来强行塞入更多内容。**

### 14.4.1 尺寸收敛原则

同一系统内应尽量减少随机尺寸。

例如按钮不要同时出现：

> 30 / 31 / 34 / 35 / 37 / 39px

而应优先收敛到：

> 32 / 36 / 40px

间距优先收敛到：

> 8 / 12 / 16 / 20 / 24 / 32px

圆角优先收敛到：

> 4 / 8 / 12px

这样能显著提升跨页面一致性。

### 14.4.2 视觉比例优先于"塞满一屏"

如果为了让更多内容同时出现而导致：

- 页面标题过小；
- 表格正文低于正常阅读尺寸；
- 按钮变得过矮；
- 行距过密；
- 卡片 Padding 被过度压缩；

应优先保持可读性和视觉比例，而不是追求"全部塞在首屏"。


# 15. 字体、信息层级与页面密度

字体不仅决定可读性，也决定系统是否看起来像正式企业产品。

## 15.1 字体层级映射

本表是**层级 → Token 的映射**，字号取值本身在 `assets/default-tokens.css`（§14.2）。
调字号改 Token，不改本表；本表回答的是"这一层承担什么角色、配什么字重"。

| 层级 | Token（默认值） | 字重建议 | 使用场景 |
|---|---|---:|---|
| 系统名称 | `--fs-section`（16px） | 600 | Header 当前系统正式名称 |
| 页面主标题 | `--fs-page-title`（22px） | 600 | 工作台、列表页、详情页标题 |
| 页面副标题 | `--fs-sm`（13px） | 400 | 页面目标、业务说明 |
| 一级区域标题 | `--fs-section`（16px） | 600 | 图表、待办、业务分区 |
| 卡片标题 | `--fs-card-title`（15px） | 600 | 单个业务卡片 |
| 正文 / 表格 | `--fs-body`（14px） | 400 | 默认主体信息 |
| 辅助信息 | `--fs-caption`（12px） | 400 | 时间、来源、提示、元数据 |
| KPI 数值 | `--fs-kpi`（28px） | 600 | 工作台关键指标 |
| 特殊展示数值 | `--fs-display`（32px） | 600 | 仅在确有强调需求时使用 |

## 15.2 字号底线

先分清「规则」与「脚本阈值」——脚本只能判「一定不可读」的那部分，两者不是一回事：

| 层 | 内容 | 谁执行 |
|---|---|---|
| 规则 | 大面积正文不得低于 13px；不得为了塞内容压到 11～12px | 人工审查 + 设计自律 |
| 脚本阈值 | 低于 11px，任何场合都判 HARD | `verify L1-13` |
| 脚本提示 | 11～12px 成片出现判 WARN，需人工确认 | `verify L1-14` |

**13px 不做成脚本阈值**：`--fs-caption` 本身就是 12px，把 13px 提成硬阈值会把辅助信息的合法用法一起判死。

- 大面积正文（承担阅读任务的正文级文本）不得低于 13px，落值用 `--fs-body`（默认 14px）；
- 11～12px 只允许用于辅助信息（时间、来源、提示、元数据、徽标），且不得成片；
- 表格正文、Sidebar 菜单、按钮文字默认 `--fs-body`；
- `--fs-caption` 只用于辅助、标签、元数据；
- 以上与字号取值来源无关：换设计规范后，规则与脚本阈值都不放宽（脚本阈值是按可判定性设计的，不是按规范设计）。

## 15.3 字重规则

建议只使用有限字重层级：

- 400：正文；
- 500：轻强调；
- 600：标题 / 核心状态。

避免：

- 同一页面大量使用粗体；
- 700 / 800 到处出现；
- 所有卡片标题都与页面标题同样醒目。

## 15.4 行高

建议：

- 标题：1.3～1.4；
- 正文：1.5～1.7；
- 表格：结合固定行高处理；
- 辅助文字：至少保证可读，不因密度压缩导致文字粘连。

## 15.5 页面密度模式

本技能 将企业 Web 页面密度分为三类：

### 标准密度

默认模式，适用于：

- 工作台；
- 详情页；
- 风险分析；
- 配置管理；
- AI 工作台。

特征：

- 正文 `--fs-body`；
- 控件 `--ctl-h`；
- 卡片 Padding `--sp-4`～`--sp-5`；
- 模块间距 `--sp-4`。

### 紧凑密度

适用于：

- 高数据量列表；
- 审核任务中心；
- 大量字段对照；
- 高频运营后台。

特征：

- 正文仍尽量保持 `--fs-body`；
- 控件可使用 `--ctl-h-compact`；
- 表格行高可适当下降；
- 通过减少 Padding 和非关键辅助信息实现紧凑；
- 不通过大幅缩小字体实现紧凑。

### 展示密度

适用于：

- 领导展示；
- 首页关键指标；
- 少量核心数据；
- 重点风险态势。

特征：

- 标题、KPI 可适当放大；
- 留白更充分；
- 信息数量更少；
- 不用于高频业务处理表格。

## 15.6 同系统密度一致性

同一产品内，相邻业务页面不得出现明显的“设计语言切换”。

例如不应出现：

> 工作台非常舒展  
> → 隐患台账突然变成 11px 极密表格  
> → AI 工作台又变成巨大空画布  
> → 规则库再次变成极小文字

允许页面模式不同，但必须保持：

- 相同字号体系；
- 相同控件高度；
- 相同页面 Padding；
- 相同圆角；
- 相同状态色；
- 相同表格密度逻辑；
- 相同标题层级。

## 15.7 1920×1080 可读性原则

1920×1080 是常见企业办公分辨率。

在该分辨率下，系统不得呈现为“缩小版后台”。

重点检查：

- 页面标题是否足够清楚；
- Sidebar 是否可读；
- 表格正文是否清楚；
- 卡片说明文字是否过细过小；
- 按钮是否具有足够点击面积；
- 业务内容是否因为页面变大而显得零散。

原则：

> **屏幕变大时，优先增加工作空间和合理留白，不是把所有元素缩小。**


# 16. 导航布局标准

- 顶部导航高度默认 56～60px；
- 侧边栏展开默认 216～224px；
- 折叠约 64px；
- 浅色侧栏作为默认推荐；
- 页面主体保持较大可用工作区；
- 系统名称默认 16px / 600；
- 一级菜单文字默认 14px；
- 菜单单行高度建议 40～44px；
- 图标与文字间距建议 10～12px。

## 导航要求

- 当前菜单状态明显；
- 支持折叠；
- 一级导航数量可控；
- 图标与文字配合；
- 不允许菜单名称高度重复或语义模糊。

## 16.1 全局产品命名与品牌层级规范

Web 原型进入高保真设计前，必须先明确“用户当前进入的到底是什么系统”。

### 16.1.1 产品身份定义

至少检查以下 5 个层级是否存在、是否已经确认：

1. **企业 / 组织品牌**：例如公司名称、集团名称；
2. **产品族 / 母平台**：仅在上游已经明确存在时使用；
3. **当前平台 / 系统正式名称**：用户当前实际进入的系统名称；
4. **子系统 / 业务模块**：例如隐患排查、风险分析、整改复核；
5. **项目 / 租户 / 组织上下文**：例如“某园区二期项目”“XX公司”。

如果资料只确认了第 3 项“当前平台 / 系统正式名称”，则原型默认**只使用这一正式名称作为全局主名称**，不得自行补造产品族或母平台名称。

### 16.1.2 Header 单一主名称原则

顶部 Header 原则上只允许出现 **1 个视觉主系统名称**。

推荐：

> Logo + **智慧园区综合管理平台**

项目、租户、组织等上下文信息应放在 Header 右侧、项目切换器、Breadcrumb 或独立上下文区域，例如：

> 某园区二期项目｜数据更新时间｜当前用户

禁止：

> **集团数字化平台　智慧园区综合管理平台**

当两个名称视觉权重接近、且页面无法直接判断二者上下级关系时，视为命名层级设计失败。

### 16.1.3 多层品牌确有必要时

只有在上游资料已经明确存在“企业品牌 → 产品族 → 平台 / 系统”的情况下，才允许同时展示多层名称，并必须通过视觉层级明确主次：

- 企业品牌：Logo 或弱化文字；
- 产品族 / 母平台：辅助信息，可弱化；
- 当前系统正式名称：主要标题，视觉权重最高；
- 当前模块：通过菜单选中态、页面标题或 Breadcrumb 表达；
- 当前项目 / 租户：作为业务上下文，不与系统名称并列争夺主视觉。

### 16.1.4 正式名称一致性

以下位置如出现系统名称，应保持一致：

- 登录页；
- 浏览器标题；
- 顶部 Header；
- 首页 / 工作台；
- 导出文件标题；
- 打印页面；
- 页面截图 / 演示模式；
- 研发交接文档。

未经产品经理确认，不得在不同页面交替使用简称、旧名称、暂定名称和正式名称。

### 16.1.5 名称冲突处理

如果输入资料中出现多个可能的系统名称，且无法判断：

- 哪个是正式名称；
- 哪个是历史名称；
- 哪个是产品族；
- 哪个是子系统；

不得自行猜测。

必须标记：

> **WEB-DESIGN-CHANGE-NAME-XXX｜产品命名 / 品牌层级待确认**

在确认前，高保真原型优先使用资料中**最近一次明确确认的正式名称**；若不存在明确确认项，则使用中性占位名称并列为待确认项。

### 16.1.6 菜单命名去冗余

当系统上下文已经明确时，菜单名称应优先表达“任务”，避免机械重复平台业务域。

例如当前系统本身已经是“客户关系管理平台”：

推荐：

> 工作台 / 客户跟进 / 商机管理 / 合同与回款 / 数据分析 / 话术库

不推荐：

> 客户跟进工作台 / 客户数据分析 / 客户合同管理 / 客户话术管理

除非重复词是业务上必须区分不同对象。

### 16.1.7 原型生成前检查

生成首屏前必须回答：

> **当前系统正式名称是什么？**  
> **是否存在已确认的上级品牌 / 产品族？**  
> **项目名称是系统名称的一部分，还是业务上下文？**  
> **Header 中谁是唯一主名称？**

无法回答时，不应直接生成正式 Header。


# 16.2 内容卡片与工作容器高度策略

本节明确区分两类容器：

## 16.2.1 内容卡片 Content Card

适用：

- KPI；
- 排行榜；
- 管理建议；
- 规则条目；
- 简短业务摘要；
- 单个分析结论。

原则：

> **内容决定高度。**

不得为了“填满页面”而机械设置 `flex: 1`、`height: 100%`，造成卡片内部大面积空白。

## 16.2.2 工作容器 Workspace

适用：

- AI 工作台；
- 表格工作区；
- 看板；
- 主从页；
- 对照审核页；
- 地图 / GIS / BIM；
- 配置工作区；
- 长任务办理区。

原则：

> **任务决定高度。**

工作容器可以使用 `flex: 1` 占用剩余视口，并通过内部滚动保持任务连续性。

## 16.2.3 判断公式

如果容器主要承载：

> “看一组结果”

优先作为 **Content Card**。

如果容器主要承载：

> “持续完成一项任务”

优先作为 **Workspace**。

这一区分用于解决：

- 页面外部无空白，但卡片内部被强行拉出大面积空白；
- 风险排行榜只有 4 行却被撑满整屏；
- 管理建议只有 3 条却被拉到页面底部；
- AI 工作区本应铺满却只占 400px。


# 16.3 内容感知式布局 Content-aware Layout

本节将“页面是否铺满”升级为“**内容量、任务类型与容器面积是否匹配**”。

页面不能简单用 `height:auto` 或 `flex:1` 二选一处理，而应根据业务内容选择以下三类高度模式：

## 16.3.1 Auto Content｜内容自适应

适用：

- KPI；
- 排行榜；
- 管理建议；
- 规则条目；
- 简短详情；
- 少量看板卡片；
- 分析结论。

原则：

> **内容决定高度，不为填屏机械拉伸。**

## 16.3.2 Adaptive Data｜数据量自适应

适用：

- 隐患台账；
- 任务列表；
- 审核列表；
- 日志；
- 规则列表；
- 历史记录。

原则：

> **根据可用视口和业务密度决定当前页展示数量，使分页紧跟数据，不让少量数据悬在巨大空容器顶部。**

推荐逻辑：

- 1366×768：约 8～10 行；
- 1440×900：约 10～12 行；
- 1920×1080：约 12～15 行；
- 具体行数结合表格行高、工具栏和页面标题动态计算。

如果业务声明“共 128 条”，却只展示 6 行并把分页强行贴到底部，应判定为布局不合理。

## 16.3.3 Full Workspace｜完整工作区

适用：

- AI 工作台；
- GIS / BIM / 地图；
- 对照审核；
- 主从式深度处理；
- 大型配置编辑；
- 需要持续滚动、拖拽、定位和上下文保持的业务空间。

原则：

> **任务决定高度，可使用剩余视口，但内部区域必须真的承载持续任务。**

## 16.3.4 看板的特殊规则

Kanban 不默认等于 Full Workspace。

当每列只有 1～3 张卡片，且不存在拖拽、持续滚动或大量任务浏览时：

- 列高优先跟随内容；
- 可以设置合理 `min-height` 保持四列齐整；
- 应显示“当前展示 X / 总数 Y”或“查看全部”，解释总数与当前卡片数量；
- 禁止把只有 1 张卡片的列机械拉到页面底部。

当卡片数量确实较多时，才允许列内滚动和占满剩余视口。

## 16.3.5 容器空置率检查

P0 页面应检查主要容器的有效占用情况。

如果一个主要容器在正常业务状态下：

> **超过约 50% 面积长期没有信息、没有操作、没有 Empty / Loading / Processing 含义**

必须重新审查：

- 容器是否过高；
- 当前页展示数量是否过少；
- 是否误用了 Full Workspace；
- 是否应调整版式；
- 是否应显示更多已有业务数据；
- 是否存在无意义的内部滚动。

该阈值用于设计审查，不作为机械计算指标。

## 16.3.6 内部滚动使用门槛

内部滚动只在以下情况使用：

- 内容确实超过稳定工作区；
- 保持上下文比页面级滚动更重要；
- 左右 Pane 需要独立浏览；
- 表格 / 日志 / AI 结果列表需要持续操作。

以下情况禁止内部滚动：

- 只有 3～5 条待办却出现滚动条；
- 内容明明可自然撑开，却为了固定高度增加滚动；
- 页面本身已经很短，又在卡片内部制造第二层滚动。

原则：

> **能自然展示就不滚；需要稳定工作面时再滚。**

## 16.3.7 首屏占用不是越高越好

桌面后台首屏允许存在合理背景留白。

判断标准不是“是否 100% 填满”，而是：

- 页面主任务是否完整；
- 核心信息是否进入首屏；
- 内容面积与信息量是否匹配；
- 页面是否出现明显头重脚轻；
- 留白是否具有呼吸感，而不是布局失败。


# 17. 按钮规范

- 每个操作区原则上最多 1 个主要按钮；
- 次要操作使用默认 / 文本；
- 危险操作使用危险样式并二次确认；
- 列表操作优先文字按钮；
- 常规按钮高度默认 36px；
- 紧凑型工具栏按钮可使用 32px；
- 按钮文字默认 14px；
- 同一操作区按钮高度必须一致。

## 新增原则

主要操作必须围绕当前页面核心任务。

例如：

> “提交审查”应比“导出”“刷新”更突出。


# 18. 表格规范

- 表头浅色；
- Hover反馈；
- 斑马纹可用；
- 操作列固定；
- 分页；
- 大数据量用分页或虚拟滚动。

## 对齐规则优化

不要所有列机械居中。

推荐：

- 名称 / 描述 / 长文本：左对齐；
- 金额 / 数值：右对齐；
- 状态 / 日期 / 编号：居中或左对齐；
- 操作：居中。

## 18.1 表格视觉密度

默认建议：

- 表头高度：42～44px；
- 正文行高：44～48px；
- 正文：14px；
- 辅助信息：12～13px；
- 表头可使用轻微灰底，但不要过深；
- 单元格水平 Padding 应保持统一。

紧凑业务表格可以适当压缩行高，但不应通过缩小正文到 11～12px 实现。

当字段很多时，优先：

- 列宽优化；
- 关键列保留；
- 非关键列隐藏；
- 横向滚动；
- 自定义列；

而不是无限缩小字体。

## 表格交互

需要时支持：

- 行点击；
- 批量选择；
- 批量操作；
- 列筛选；
- 排序；
- 固定列；
- 快速详情；
- 自定义列。


# 19. 表单规范

- 标签清晰；
- 必填标识；
- 输入宽度一致；
- 表单校验；
- 提交 Loading；
- 常规输入框 / Select 高度默认 36px；
- 表单标签与正文默认 14px；
- 同一表单区域的控件高度、圆角、边框视觉必须一致。

## 补充原则

- 字段较多时按业务主题分组；
- 不要超过用户认知负担；
- 高级字段可折叠；
- 输入错误尽量靠近字段提示；
- 表单关闭前如存在未保存修改，需确认。


# 20. Dialog 与 Drawer 选择规范

原规范已有三种 Dialog 模式，继续保留：

## Dialog 模式一
多板块 + 基本信息，适合详情。

## Dialog 模式二
复杂管理，适合内嵌表格 / 动态卡片。

## Dialog 模式三
简单新增 / 编辑。

### 宽度参考
- 900px：标准；
- 1200px：复杂；
- 高度：最大约 80vh。


## 20.1 新增 Drawer 规范

Drawer 与 Dialog 同等级考虑。

### 更适合 Drawer
- 快速查看详情；
- 列表上下文不能丢；
- 审核 / AI结果；
- 快速编辑；
- 辅助信息。

### 更适合 Dialog
- 需要强制用户完成一个短任务；
- 确认；
- 简单表单；
- 高风险确认。

### 更适合独立页面
- 内容非常复杂；
- 多 Tab；
- 长流程；
- 深度业务处理。


# 21. 复杂交互组件规范

根据业务需要主动评估：

- Tabs；
- Drawer；
- Breadcrumb；
- Steps；
- Tree；
- Timeline；
- Split Pane；
- Sticky Action Bar；
- Batch Action；
- Advanced Filter；
- Collapse；
- Tooltip；
- Popover；
- Upload Progress；
- Contextual Panel；
- Inline Edit。

不得为了炫技机械使用。


# 22. 数据可视化规范

**图表实现方案由项目决定，规范不预设具体库。** 判据（回答什么业务问题、数据与口径、坐标轴与图例规则）
与实现无关；原型内用静态 SVG / 内联示意即可，**不引入外部图表库**（见 `references/07 §28`：原型零外部依赖）。

## 图表使用原则

图表必须回答业务问题，例如：

> 风险在哪里？  
> 哪类问题最多？  
> 趋势是否改善？  
> 哪个项目异常？

禁止为了“页面好看”随便加饼图、柱状图。

## 默认要求

- 图表标题明确；
- 单位明确；
- tooltip 可读；
- 颜色含义一致；
- 避免颜色过多；
- 有数据钻取需求时再设计点击交互；
- 无数据要有 Empty 状态。


# 23. 动效规范

- 页面 / 弹窗：约 0.3s；
- Hover：约 0.2s；
- 点击反馈：约 0.1s。

## 使用原则

动效用于：

- 表示状态变化；
- 强化操作反馈；
- 帮助理解层级；
- 提示用户下一步。

不用于纯装饰。

## 特别约束

不要所有组件 Hover 都统一“上浮 2px”。

建议：

- 卡片：可轻微上浮；
- 按钮：颜色 / 阴影反馈；
- 表格行：背景变化；
- 菜单：背景和文字变化；
- 输入框：边框 / focus ring。


# 24. 页面视觉质量原则

默认风格：

> **企业级、专业、现代、简洁、有适度科技感，但不花哨。**

## 24.1 必须做到

- 页面有明确视觉焦点；
- 主要动作明显；
- 重要风险 / 状态清楚；
- 区域边界合理；
- 留白适度；
- 页面间视觉统一；
- 示例数据真实；
- 内容密度符合业务。

## 24.1.1 页面视觉构图

企业级页面至少应形成清晰的 4～5 层视觉关系：

> 页面背景  
> → 页面 / 工作区  
> → 业务区域  
> → 内容组件  
> → 状态 / 操作

不要求通过重阴影实现层级。

优先使用：

- 背景明度差；
- 1px 边框；
- 8px 圆角；
- 标题层级；
- 统一 Padding；
- 模块间距；
- 状态色；

建立视觉结构。

### 页面背景与卡片关系

避免：

> 浅灰背景 + 巨大白块 + 白块内部继续白块

导致层级不清。

建议：

- 页面背景保持轻灰蓝；
- 主要业务模块使用白色；
- 次级区块可使用极浅灰 / 浅蓝；
- 嵌套层级不宜超过 2～3 层。

## 24.1.2 页面首屏比例

页面首屏应检查：

- Header 是否过矮；
- 页面标题区是否过薄；
- KPI 是否过矮或过高；
- 图表是否被强行拉高；
- 表格是否过密；
- 内容是否集中在上方一条带状区域；
- 主要业务模块是否形成合理面积比例。

“填满屏幕”不是目标。

目标是：

> **各业务区域所占面积与其任务重要性相匹配。**

## 24.1.3 视觉一致性检查

同一个系统的 3 个以上核心页面并排查看时，应能明显判断它们属于同一个产品。

必须统一：

- Header；
- Sidebar；
- 页面标题；
- 字号体系；
- 按钮体系；
- 表单体系；
- 表格体系；
- 状态标签；
- 卡片圆角；
- 页面 Padding；
- 背景层级。


## 24.1.4 页面级视觉验收基线

本节要求核心页面在完成高保真原型后进行“整页截图审查”，不得只看局部组件。

至少检查：

1. **顶部是否压得过薄**：Header、页面标题和操作区是否有足够存在感；
2. **左侧是否过窄**：菜单是否像“缩小版工具条”；
3. **正文是否过小**：1920×1080 下正文 / 表格 / 菜单仍应清晰；
4. **页面是否头重脚轻**：内容是否全部挤在上半屏；
5. **容器内部是否空**：是否通过拉高白色卡片“伪装”成满屏；
6. **分页是否脱离数据**：分页应与当前数据区域保持视觉关联；
7. **滚动条是否合理**：只有确有内容溢出时才出现；
8. **跨页面是否像同一产品**：字号、间距、圆角、控件高度和信息密度是否一致。

### 截图验收要求

核心 P0 页面至少对以下尺寸进行整页截图审查：

- 1366×768；
- 1440×900；
- 1920×1080。

不能只检查 DOM 是否不溢出，还必须人工观察整体比例。


## 24.2 避免

- 卡片套卡片；
- 大面积渐变；
- 强装饰纹理；
- 无业务意义的大数字；
- 一屏全是 KPI；
- 每个模块都加阴影；
- 颜色超过业务实际需要；
- AI 页面满屏"科技蓝光"。

## 24.3 高级感的正确来源

**背景**：实测案例中，用户对"不够科技感/不够高级"的第一版响应（更换深色主题、换主色调）被明确否定，反馈为"高级感、科技感不是说换个颜色主题，而是一些图标、板块细节、交互形式之类的"。此为用户确认的视觉升级方向，已固化为规则。

**优先级公式**：

> **高级感 = 图标体系 > 板块细节 > 交互形式 > 色彩微调**

任何"提升高级感"的优化请求，必须按此优先级顺序投入，色彩永远排最后且只做微调（对比度修正、色相微调），**更换主色/主题必须用户明确要求**。

### 24.3.1 图标体系

图标是性价比最高的高级感来源：

- 全站一套**线性图标库**：内联 SVG `<symbol>` 定义 + `<use href="#i-xxx"/>` 引用，统一 2px 描边、统一 viewBox（推荐 24×24）；
- 规模参考：36 个左右符号覆盖企业后台常规需求（导航、操作、状态、业务对象四类）；
- **三级图标底座体系**（从侧边栏到卡片逐级缩小，形成秩序感）：
  - 侧边栏导航：28px 圆角方座，选中态渐变底座 + 白色图标；
  - 卡片标题（ct-ic）：20px 左右圆角方座 + 线性图标 + 标题文字；
  - 行内/元信息：11～12px 裸图标，无底座；
- 允许有限混用实心图标做**点睛**（如评分星、AI 星光 sparkle），但主体必须线性统一；
- 禁止：彩色 emoji 图标、字符图标（▶ ◀ › ✓ 等在 Windows 渲染成蓝色 emoji，演示机就是 Windows 时必踩）、网络图片图标、多套风格混用。

### 24.3.2 板块细节（结构隐喻）

用有业务隐喻的结构细节替代扁平卡片：

- **票据式结构隐喻**：机票卡用登机牌式布局（承运方徽章盘、虚线撕票位、圆形选择指示器、准点率/余票状态点）；火车票、发票等票据类对象同理；
- **卡片头图标底座**：每个业务卡片标题配"底座 + 图标"结构，而非裸标题文字；
- **状态徽章体系**：账号能力、认证状态、审批状态用小徽章表达，而非纯文字；
- **时间线头像呼吸环**：审批/进度时间线的当前节点头像加呼吸态光圈，暗示"正在处理"；
- **星级酒店/评分可视化**：数据本身带星级的，直接渲染星，不写"五星级"文字。

### 24.3.3 交互形式

低成本交互细节比静态装饰有效：

- **骨架屏**：列表/卡片初次加载用 shimmer 骨架卡，而非空白或转圈；
- **金额数字滚动**：结算栏/合计金额 400ms 左右滚动到位，强化"计算过程感"；
- **语音声波动效**：语音输入时 4 柱声波动画，明确"正在听"；
- **Enter 快捷提交**：输入框回车即提交，与按钮等价；
- **toast 去重限流**：重复提示合并，同屏最多 3 条，避免提示刷屏。

### 24.3.4 色彩纪律

- 渐变收敛：渐变只保留在全页 1～2 个视觉锚点（如快捷入口 hero、主按钮），禁止每张卡片价格都用渐变红；
- 选中态克制：选中一个选项用不超过 3 重强调（推荐：边框变色 + 选择指示器 + 浅色底），五重强调（边框+渐变底+竖条+ring+实心圆）必须砍到三重以内；
- 换 Tab 等视图切换时，金额等关键数字不得从旧值"滚回 0"再滚回来（观感像取消选择），应保持或直接切换。

## 24.4 视觉升级方向自查

原型收到"不够高级/不够科技感"反馈时，按以下顺序自查并升级，禁止跳到换主题：

1. 图标是否成体系？有没有底座层级？有没有字符图标/emoji 混入？
2. 核心业务对象（票据、订单、单据）有没有结构隐喻细节？
3. 加载/提交/选中过程有没有动态反馈（骨架屏/滚动/声波）？
4. 渐变和强调是否收敛到锚点？选中态是否 ≤3 重强调？
5. 以上都做完仍不够，才考虑色彩微调，且不动主色。
