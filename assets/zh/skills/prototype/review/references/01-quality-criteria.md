# 33. 质量审查清单

生成前必须自检（建造侧用法）；评审时按本节逐条核对，缺证据的维度标注「证据不足」而不是记为空。

## 33.1 业务
- 用户是谁？
- 核心任务清楚吗？
- 黄金任务流走通吗？
- 页面是否服务真实任务？
- 是否存在为了页面丰富新增的伪需求？

## 33.2 结构
- IA是否清楚？
- 页面层级是否过深？
- 页面是否重复，或存在职责模糊、任务重叠？
- 页面数量是否由真实用户任务和业务闭环自然产生？
- 首页是否真正服务高频任务？
- **当前系统正式名称是否唯一、明确？**
- **企业品牌 / 产品族 / 平台 / 子系统 / 项目上下文是否层级清楚？**
- **Header 是否只突出一个主系统名称？**
- **是否存在未经确认而自行创造的“母平台”或第二套系统名称？**
- **页面结构是否具备宽度和高度自适应能力？**
- **核心工作区是否能合理使用剩余视口？**

## 33.3 交互
- 每个按钮点击后发生什么？
- 是否有 Loading / Empty / Error？
- AI处理中用户是否知道当前进度？
- 人工确认是否明确？
- 错误后是否知道下一步怎么办？

## 33.4 视觉
- 信息层级是否清楚？
- 主操作是否突出？
- 是否过花？
- 卡片是否过多？
- 数据密度是否合适？
- 页面之间是否统一？
- **1366×768 / 1440×900 / 1920×1080 下是否都保持合理布局？**
- **是否存在页面上半部结束、下半部大面积无业务意义空白？**
- **超宽屏下内容是否被过度拉伸或过度分散？**
- **Empty / Loading / AI Processing 是否位于有效工作区合理位置？**
- **页面标题、正文、表格、Sidebar 字号是否符合统一层级？**
- **不同页面的信息密度是否明显失衡？**
- **Content Card 是否因强制拉伸产生内部大面积空白？**
- **Header / Sidebar / 页面 Padding / 控件高度比例是否协调？**
- **1920×1080 下是否仍保持正式产品级可读性？**
- **页面是否选择了正确的 Auto Content / Adaptive Data / Full Workspace 高度模式？**
- **主要容器是否存在超过约 50% 的无意义空置？**
- **列表当前页数据量是否与视口匹配，分页是否紧跟数据？**
- **少量内容是否错误出现内部滚动条？**
- **看板列高是否与当前卡片数量匹配？**
- **图标是否一套线性体系、有底座层级、无字符图标/emoji/图片图标混入？**
- **渐变是否收敛到 1～2 个视觉锚点？选中态是否 ≤3 重强调？**
- **辅助文本对比度是否 ≥4.5:1？**
- **`:has()` 等新 CSS 是否避开了关键视觉路径或有兜底？**

## 33.5 研发
- 页面字段是否清楚？
- 点击行为是否清楚？
- 状态变化是否清楚？
- AI / API 调用点是否清楚？
- **响应式规则和断点行为是否清楚？**
- **页面级滚动 / 区域滚动边界是否清楚？**
- **表格、图表、Drawer / Dialog 的自适应方式是否清楚？**
- **全局视觉 Token 是否统一定义并可复用？**
- **页面密度模式是否明确？**
- 待研发确认项是否标记？

## 33.6 演示就绪审查

原型用于对外演示/评审/比赛前，在 33.1～33.5 之外加查一层"演示可信度"：

- **数据自洽**：同一单号/对象在所有页面状态一致（单一数据源，操作后各页回写联动）；费用数字口径统一（预估=推荐合计，预算=标准上限合计）；跨页引用的班次/日期/金额与来源页一致；
- **动态内容非硬编码**：问候语、日期等由 JS 按当前时间生成，非写死在 HTML（第二天打开就穿帮）；
- **版本标识真实**：侧边栏/关于处版本号与实际迭代版本一致，不残留"V1.0 首版"字样；
- **演示入口收拢**：演示辅助按钮（模拟审批、模拟涨价等"上帝视角"操作）收进头部演示浮层或 `?demo=1` 才显示，不与业务按钮混排，避免评审者误点；
- **演示可重复**：同一演示脚本（如价格变化）可重复执行，不出现"只能演一次"的状态污染；
- **音字闭环**：语音演示识别结果必须回填可见并触发下一步；
- **Windows 兼容**：字符图标（▶ 等）已清除，Windows 演示机不出现 emoji 化图标；
- **演示数据去个人化**：无用户本人/真实同事的真实姓名、手机号、工号、真实内部项目名；姓名集中定义可一键替换（详见 27.3）。

# 34. 一票否决

**本清单是唯一来源。** 建造侧（`polaris{{SKN_SPR}}prototype{{SKN_SPR}}generate` 的 `SKILL.md §八`）只摘最高频的 8 条作提醒，措辞与本清单不一致时**以本清单为准**；
新增 / 修改条目只改这里一处，不必两处同改（建造侧那 8 条同步对齐即可）。

出现以下任一情况，本技能 必须主动纠正：

1. 一上来直接画页面；
2. 用户和业务场景不清；
3. 没有黄金任务流；
4. 为了追求页面少而强行合并复杂任务，或为了显得功能丰富而堆砌无明确任务的页面；
5. 所有页面都用查询表格模板；
6. 页面很好看但没有业务闭环；
7. 页面只有正常状态；
8. AI按钮点击后没有执行过程；
9. AI结果没有依据或人工确认；
10. 为了科技感大量渐变和装饰；
11. 无意义卡片过多；
12. 关键长文本全部居中；
13. 所有交互统一上浮动效；
14. 原型阶段擅自改变上游冻结需求；
15. 研发看完仍不知道页面怎么实现；
16. Skill 未经产品经理确认，擅自根据工期、比赛或资源条件删减页面、降低实现深度或改变产品设计范围；
17. **未经确认自行新增平台 / 产品族 / 系统名称，或在 Header 中并列展示多个同等视觉权重的“XX平台 / XX系统”，导致用户无法判断当前系统身份；**
18. **高保真原型只在单一分辨率下正常，浏览器窗口变化后出现重叠、裁切、横向异常溢出、关键操作不可达；**
19. **因固定宽高或截图式布局导致工作台、AI工作台、列表页、主从页等核心页面出现大面积无业务意义空白，且未设计合理的视口自适应策略；**
20. **为了塞入更多内容而大面积使用 11～12px 正文、过矮按钮或过密表格，导致 1920×1080 下系统呈现为“小字缩放版后台”；**
21. **将 Content Card 机械设置为铺满剩余高度，造成卡片内部大面积无业务意义空白；**
22. **同一系统核心页面在字号、控件高度、页面 Padding、卡片圆角、表格密度等方面明显不一致，无法形成统一产品视觉语言；**
23. **列表总量明显较大却只展示少量数据，并通过强制撑高容器把分页推到底部；**
24. **少量看板卡片、排行榜或建议卡片被机械拉伸到整屏，产生大量卡片内部空白；**
25. **只有少量内容却出现无意义内部滚动，或滚动条成为弥补错误固定高度的手段；**
26. **用户要求提升"高级感/科技感"时，第一响应是更换主题色或转深色模式，而不是按"图标体系 > 板块细节 > 交互形式 > 色彩微调"的优先级升级；**
27. **裸用 ▶ ◀ › ✓ 等字符图标或彩色 emoji 充当界面图标，Windows 演示机出现 emoji 化图标；**
28. **同一业务单号/对象在不同页面状态矛盾，费用数字口径不一或无来源，Tab 计数与实际数据不符；**
29. **问候语/日期等动态内容硬编码在 HTML 中；`:has()` 等新 CSS 特性用于关键视觉路径且无兜底；弹窗不支持 Esc 关闭；**
30. **未运行 `scripts/verify.mjs` 全三层并取得退出码 0 就交付（含 `--strict` 下必需层被跳过仍交付、脚本报 HARD 仍交付、以"人工看过"替代脚本判定）；**
31. **演示数据含用户本人或真实同事的真实姓名、手机号、工号、真实内部项目名。**

# 36. 最终判断标准

一个好的 Web 原型，不以：

> 页面数量、动画数量、图表数量、卡片数量

为标准。

而以：

> **用户一看会用  
> 领导一看懂价值  
> 业务一看符合流程  
> 页面一看专业成熟  
> 交互一跑自然顺畅  
> AI一看有边界、有反馈  
> 研发一看知道怎么做**

为标准。
