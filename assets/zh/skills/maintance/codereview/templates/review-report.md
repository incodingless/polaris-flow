# 代码审查报告模板

生成审查报告时，按以下结构输出（输出时去掉代码块标记，直接输出标题与正文）。语言与用户输入保持一致。

```
# 代码审查报告

## 1 审查概览

| 项 | 内容 |
| --- | --- |
| 合并建议 | ✅ 可合并 ／ ⚠️ 修改后可合并 ／ ❌ 不建议合并（AI 建议，不构成门禁；门禁结论以规则层为准） |
| 总体评分 | X / 10 |
| 发现统计 | 🔴 N ｜ 🟠 N ｜ 🟡 N ｜ 🔵 N（共 N） |
| 审查目标 | 【文件 / 目录 / 仓库路径】 |
| 评审标识 ★ | 【`task_id` / MR 编号 / commit SHA；独立调用写 `—`】 |
| 审查范围 | 【全量 / 仅 diff / 提交区间 / 粘贴片段；diff 类写明基线 base-ref 与变更文件数】 |
| 技术栈 | 【识别的语言与框架】 |
| 审查覆盖 | 【通用五维度 + 本次实际加载的清单；没走到、未下结论的范围也写在这里】 |
| 执行者 ★ | 主代理 ／ 独立 subagent（平台 / agent） ／ 降级 · 非独立裁判 |
| 静态扫描 | 脚本：已执行 `analyze.py` ／ 未执行（原因）；SonarQube：已执行（门禁 ✅ PASSED ｜ ❌ FAILED，规则：质量门禁 FAILED / Blocker+Critical > 0 / 仅新增问题）／ 未启用，用户确认继续（AI 兜底核查，非权威）／ 不可用且未获用户确认（流程停于 Step 2，不应有报告） |

## 2 风险摘要

【一段话：最该优先处理的风险 + 它会造成什么后果。SonarQube 门禁未过时，首句写出门禁未过与所用规则。】

## 3 静态扫描门禁（SonarQube，可选）

【仅 Step 2 启用了 SonarQube 时输出本节；未启用时整节删除，只在上表「静态扫描」行注明未执行及原因】

| 项 | 内容 |
| --- | --- |
| 项目 / 分支 | 【projectKey / branch】 |
| 门禁结论 | 【✅ PASSED ／ ❌ FAILED】 |
| 所用规则 | 【质量门禁 FAILED ／ Blocker+Critical > 0 ／ 仅新增问题 ／ 仅记录（不参与结论）】 |
| 阻塞项 | 【`文件:行` — 规则 id — 严重度，逐条列出；无则写「无」】 |

## 4 问题清单（发现 ≥ 5 条时输出）

| 编号 | 级别 | 问题 | 位置 |
| --- | --- | --- | --- |
| [F-1] | 🔴 Critical | 【问题标题】 | `文件:行` |
| [F-2] | 🟠 Major | 【问题标题】 | `文件:行` |

## 5 问题明细

### 🔴 Critical（N）

#### [F-1] 【问题标题】 — 🔴 Critical

- **位置**：`文件:行`
- **风险域**：【安全 · 注入类 ／ 正确性 ／ 性能 ／ 可维护性 ／ 架构】
- **违反约定**：【清单编号（如 SEC-01 / DB-13 / CQ-04）／ 项目规范条目 ／ 既有先例（`文件:行`）——三者给不出则降级「待人工确认」或「建议」档，不写成缺陷】
- **置信度**：【高（路径级证据）／ 中（静态推断，需佐证）】——低置信不输出；清单静态边界「可审=高」「部分可审=中」；中置信按 §评分与结论不计入评分与合并建议，进「待人工确认」
- **现象**：【读到的客观事实：哪段代码、哪条路径出了问题】
- **触发条件**：【什么输入 / 时序 / 配置会让它发生】
- **后果**：【数据泄露、资金损失、生产事故、无法维护……】
- **修复建议**：【改成什么；附可直接使用的代码，不用伪代码】
- **风险代码**（可选）：【片段本身即证据时贴关键行（不超过 10 行）；改法一目了然则省略】

### 🟠 Major（N）

#### [F-2] 【问题标题】 — 🟠 Major

- 要素同 Critical：位置 / 风险域 / 违反约定 / 置信度 / 现象 / 触发条件 / 后果 / 修复建议

### 🟡 Minor（N）

#### [F-5] 【问题标题】 — 🟡 Minor

- **位置**：`文件:行`
- **问题**：【现象 + 后果，可合并成一行】
- **修复建议**：【……】

### 🔵 Nit（N）

| 编号 | 位置 | 建议 |
| --- | --- | --- |
| [F-9] | `文件:行` | 【命名 / 注释 / 格式等非功能性建议】 |

## 6 待人工确认（不计分）

【仅存在「部分可审 / 需佐证」发现时输出本节，否则整节删除。此节条目不计入总体评分与合并建议（见 rubric §评分与结论计分排除规则），供人工复核优先查看高置信发现后处理】

| 编号 | 位置 | 问题 | 为何需佐证 |
| --- | --- | --- | --- |
| [P-1] | `文件:行` | 【可疑模式描述】 | 【缺什么配置 / 运行时 / 元数据证据】 |

> 中置信发现超 3 条时折叠：保留最关键 3 条，其余写一句「另有 N 条待佐证项已折叠，见审查覆盖的未下结论项」。

## 7 架构评估（可选：审查范围含多文件 / 模块时）

| 项 | 结论 |
| --- | --- |
| 模块边界 | 【……】 |
| 依赖方向 | 【……】 |
| 主要风险 | 【……】 |

## 8 复核反馈（可选：人工复核后填写，无反馈时删除本节）

| 编号 | 结论 | 备注 |
| --- | --- | --- |
| [F-1] | 误报 ／ 有用 ／ 已修复 | 【理由 / 处理记录】 |

> 本技能不自动统计反馈（不写 workflow metrics）；重审同一目标时可读取上次报告的本节作对照。
```

## 报告注意事项

- **级别**：只用四档——🔴 Critical / 🟠 Major / 🟡 Minor / 🔵 Nit。含义与处置要求以 `references/review-rubric.md` §严重级别定义 为唯一源，报告不复制该表；报告需作 MR 附件或归档时，按该表原样引用一节「级别图例」。
- **编号**：全报告统一 `[F-n]`，按出现顺序自增（不按级别分段编号）；「问题清单」与「问题明细」的编号一一对应。
- **详略随级别**：Critical / Major 逐条列全六要素；Minor 可把现象与后果压成一行；Nit 只进表格，不展开。
- **只报有问题的项**：未发现问题的维度 / 清单不列条目，覆盖情况由「审查概览 · 审查覆盖」说明。
- **问题清单**：发现少于 5 条时删除该节——明细本身已够短，索引只会造成重复。
- **★ 行**：`评审标识` / `执行者` 两行必须落到具体值，不留 `【】` 占位——工作流内评审（`polaris{{SKN_SPR}}coding{{SKN_SPR}}verify` Step 15）分别写 `task_id` 与 `独立 subagent（平台 / agent）`；独立调用写 `—` 与 `主代理`。走降级路径时 `执行者` **必须**写 `降级 · 非独立裁判`，不得描述成独立评审。
- **依据可追溯**：合并了脚本或 SonarQube 结论时，在「问题清单」加一列「依据」（人工走读 / `analyze.py` / SonarQube `rule id`）；同一位置同一根因只留一条，不因两处上报而重复计数。
- **规则误报申诉**：SonarQube 检出即定论——AI 有异议时，在该条发现的「依据」后附 `申诉：判定为误报，理由 …`，不得直接修改级别或删除条目；`analyze.py` 命中仍是坐标，须人工核实。
- **SonarQube 留痕**：未执行时不得省略——「审查概览 · 静态扫描」必须写明未执行及原因（含「用户确认继续」的跳过事件），不得让读者误以为扫描已通过；门禁未过时「合并建议」钉 `❌ 不建议合并`，不被其他维度的高分抵消；门禁未执行时写「门禁未执行（Sonar 跳过）」，不伪造门禁结论。
- **修复建议**：写成「改成什么」，代码示例要可直接使用，避免伪代码。
- **重点优先**：Critical / Major 排在前面；小范围 diff 不展开 Nit，不补「建议关注」。
