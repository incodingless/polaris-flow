# Polaris 工作流 - 服务技能：代码审查（codereview）

<HARD-GATE>
本 skill **仅**负责：对用户指定的代码做系统化审查，输出一份带优先级分级与具体修复建议的评审报告。它是**服务技能**——不写 `phase`、不写 workflow 游标、不写 metrics、不推进任何阶段。

- **禁止**修改任何被审对象（代码 / 测试 / 配置 / specs）；只评不改
- **禁止**在未阅读代码的情况下，仅凭文件名、路径或调用方描述下结论
- **禁止**报告空泛套话（如「代码质量有待提高」而无具体位置与理由）
- **禁止**捏造不存在的漏洞或过度夸大风险（无依据的问题一律不报）
- **禁止**把脚本粗筛结果当作最终结论——脚本没报 ≠ 安全，深度检查必须逐项人工核查
- **禁止**把 SonarQube（或任何外部扫描）结果当作深度核查的替代——外部扫描没报 ≠ 安全；也不得臆造扫描结果，或把内部脚本结论冒名为 SonarQube 结论
- **禁止**把本技能当风格检查器使用——风格、命名、复杂度、已知漏洞模式属规则层（脚本 / Sonar），本技能默认只引用不重查；AI 的职责是语义层（意图、边界、并发、事务、架构）
- **禁止**对单个小文件输出数百行的冗长报告（重点优先，Minor / Nit 从简）
- **H8**（状态行）：每个 Step 入口输出 `[polaris-flow 维护]代码审查 - 进入 codereview Step <N>: <动作>`
</HARD-GATE>

**启动时必须先输出**：`[polaris-flow 维护]代码审查 - 进入阶段：使用 polaris{{SKN_SPR}}maintance{{SKN_SPR}}codereview 技能。`

## 定位与边界

这是「工作流之外的通用代码审查」服务技能：用户随时要求审任意代码时直接触发，**主代理执行**（跑脚本 + 读代码 + 对照清单）。它**不是**工作流内对本次变更 diff 的独立评审——那是 `polaris{{SKN_SPR}}coding{{SKN_SPR}}verify` Step 15 按 `review_mode` 自行派发独立 subagent 的职责，不在此重造。若用户要求「换个 context 独立审本次 diff」，走 `verify` Step 14。

| 维度 | 本技能（通用审查） |
|---|---|
| 触发 | 用户直接要求审任意代码 / 文件 / 仓库 / 贴代码 |
| 执行者 | 主代理（跑脚本 + 走读 + 对照清单） |
| 审查对象 | 用户指定范围（可含非工作流代码） |
| 外部扫描（必选通道） | SonarQube（Step 2；探测不到/执行失败时须告警并经用户确认「继续」才能跳过，跳过事件落报告留痕） |
| 严重度 | Critical / Major / Minor / Nit（定义见 rubric） |
| 是否推进 phase | **否** |

**刻意不做**（都有明确归属）：
- **修代码**——只评不改，修复交给用户
- **工作流内 diff 的独立裁判评审**——那是 `polaris{{SKN_SPR}}coding{{SKN_SPR}}verify` Step 15 的职责，不在本技能重造 subagent 派发
- **跑测试 / 变异测试 / 性能压测**——本技能只做静态走读与静态扫描（内部脚本 + 可选 SonarQube），不执行测试

## 标识约定

| 项 | 路径 / 值 |
|----|-----------|
| 审查对象 | 用户指定：单个文件 / 目录 / Git 仓库 / 粘贴片段 |

| 外部静态扫描（可选） | SonarQube：`mvn -B sonar:sonar` / `./gradlew sonar` / `sonar-scanner`（探测顺序与凭据见 Step 2） |
| 审查维度与严重级别 | `references/review-rubric.md` |
| 安全检查清单（§一 通用速查 + §二 OWASP 语言无关 + §三 Java/Spring 专有） | `references/security-checklist.md` |
| 代码异味目录 | `references/code-smells.md` |
| Java/Spring 专项清单 | `references/java-api-design.md` / `java-code-quality.md` / `java-concurrency.md` / `java-database.md` / `java-performance.md` |

| 项目规范 / 团队禁忌清单（可选） | 用户可指定路径（项目规范文件、团队红线清单）；指定后 Step 4 判定对照之，发现的依据绑定到该文件条目 |
| 报告落盘（唯一源） | 位置由用户定（也可声明「仅在会话内输出」，则不落盘）；未指定时默认与审查目标同目录（目标是仓库 / 目录时取该目录），文件名 `代码审查报告_<目标名>_<YYYYMMDD>.md`。落盘文件同时是本技能的**进度载体**：Step 1 建立、Step 3/4 增量追加、Step 5 收口（见「上下文压缩恢复」） |

## 流程

### Step 0 — 确定评审范围（用户决策点）

按 `./policies/decision-point.md` 发起询问。范围共 8 种，超出询问工具有效选项上限（4），走文本降级（`./policies/ask-question-react.md`），逐个列出让用户**单选**：

[决策点 1/1] 本次代码评审的范围？

A 本地工作区 - worktree 中的代码
B 本地暂存区 - 已 git add 未提交的代码
C 单提交 - 单个提交的改动
D 提交区间 - 自由选取一段连续提交
E 分支历史 - 全分支提交序列
F MR 基线差异 - 分支相对 merge-base 的改动（三点）
G 快照直比 - 两端快照直接对比（两点）
H 全量代码 - 仓库全部跟踪代码（**脚本全量扫描 + 走读抽样**；走读策略与未覆盖声明见 Step 4）

请回复编号（如 A）。

**Token 消耗提示**（发起询问时随选项一并向用户说明）：
- **A–G（diff 类，推荐）**：消耗与本次变更量成正比——固定开销约 1.5 万 tokens（技能与清单加载）+ 变更文件读取 + 报告输出，单提交 / 工作区级别的常规改动通常数万 tokens 内完成；
- **H（全量）**：随仓库规模线性增长，大仓可达数十万 tokens，且架构走查需分批执行——除非明确要做全量体检，建议优先选 diff 类范围。

**基线（base）**（仅 D / E / F 需要）：用户选 D / E / F 后，再确认基线——默认主干（`git symbolic-ref --short refs/remotes/origin/HEAD`，取不到再试 `main` / `master`）；用户可指定 `origin/develop`、tag、commit。

**技术栈**：若无法从文件类型自动识别，请用户说明语言与框架（Java/Spring 栈命中时 Step 4 加载专项清单）。

**报告落盘路径**：按「标识约定 · 报告落盘」的默认值定，用户可在本步指定路径覆盖。落盘文件是本技能全程的进度载体——**Step 1 就要建立，不要等到 Step 5**。

### Step 1 — 圈定文件清单并运行扫描脚本

按 Step 0 选定的范围，用对应 git 命令圈定「变更文件清单」并读取变更内容：

| 范围 | 圈定文件清单 | 读变更内容 |
|---|---|---|
| A 本地工作区 | `git diff HEAD --name-only` | `git diff HEAD` |
| B 本地暂存区 | `git diff --cached --name-only` | `git diff --cached` |
| C 单提交 | `git show <commit> --name-only` | `git show <commit>` |
| D 提交区间 | `git log <from>..<to> --name-only` | 逐条 `git show` |
| E 分支历史 | `git log <base>..HEAD --name-only` | 逐条 `git show` |
| F MR 基线差异 | `git diff <base>...<head> --name-only` | `git diff <base>...<head>` |
| G 快照直比 | `git diff <from>..<to> --name-only` | `git diff <from>..<to>` |
| H 全量代码 | `git ls-files` | 脚本 full 模式递归扫描；走读按 Step 4「读取策略」抽样，**不等于读完所有文件** |

**再运行扫描脚本**（位于本技能包 `scripts/` 目录，按语言选择）：

- **Python 项目**（优先，精确）：`python3 scripts/analyze.py <路径>`
  AST 静态分析，检测：硬编码密钥（赋值/字典/关键字参数）、SQL 注入（数据流追踪，含变量拼接）、命令注入（精确判断 `shell=True`）、不安全反序列化（pickle/yaml）、N+1 查询、可变默认参数、裸 except/吞异常、函数行数、圈复杂度、嵌套深度、魔法数字、未使用导入。
- **非 Python 项目**（兜底，粗筛）：`bash scripts/analyze.sh <路径>`
  正则扫描，覆盖常见安全模式。

**范围 ↔ 脚本衔接**：
- 增量范围（A–G）：脚本用 `--diff` 列变更清单（⚠️脚本 `--diff` 只覆盖 `git diff` 未暂存，暂存区 / 提交类由上方 git 命令圈定，脚本作粗筛参考）；深度审查由 AI 阅读上方圈定的 diff 完成。
- 全量（H）：脚本 full 模式（不传 `--diff`）全量粗筛，AI 做架构级走查。
- **脚本输出兼作「读取坐标」**：`analyze.py` 每条 finding 都带 `文件:行`，Step 4 用它定位精读位置（见 Step 4「读取策略」）。脚本的结论照旧须人工核查；命中位置只作坐标，**不构成审查范围**。

**非 Git 场景（用户直接粘贴代码片段）**：写入临时文件（`/tmp/review_input.<ext>`，扩展名按语言推断），扫描完成后删除。

- 报「找不到脚本」→ 当前工作目录不是技能目录，按「降级决策」处理。

**建报告落盘文件**：按「标识约定 · 报告落盘」建立文件，先写入报告头部（审查目标 / 评审标识 / 审查范围 / 技术栈）——范围决策由此落盘，压缩后不再回头问；结论性字段（合并建议、总体评分、发现统计、风险摘要）留待 Step 5 收口。

> 脚本是**粗筛**（AST 版也只能做静态结构分析）。深度安全必须按 Step 4 对照清单逐项人工核查；性能、正确性、架构维度依赖 AI 读代码完成。**脚本没报 ≠ 安全**。

### Step 2 — SonarQube 扫描（必选通道，用户决策点）

**Sonar 是规则层的权威检出源，必须在**：注入、加密、事务失效等规则层检查项以它为准。探测不到或执行失败时**不得静默降级**——必须停下告警，经用户明确选择「继续」后才能进入 Step 3，且跳过事件在报告「审查概览 · 静态扫描」留痕。

按 `./policies/decision-point.md` 发起询问。本步含 2 个决策点（编号为本步内序号）：第 2 个仅在「启用」且扫描成功后问，**跨决策点串行**。

> **被工作流调用时（`verify` Step 15）**：subagent 非交互、问不出用户，两个决策点改由**主代理在派发前一次问全**，结论随 `constraints` 下传，扫描结果与门禁判定在报告内一并给出。通道探测、凭据读取、范围收窄与结果读取口径**不变，仍以本步为唯一源**。

[决策点 1/2] SonarQube 通道处理？

A 启用 — 先探测可用通道，探到即执行（**默认**）
B 本次跳过 — 仍须走下方「不可用确认」：告警后用户明确点「继续」才得进入 Step 3，报告记「SonarQube 未启用，用户确认继续（AI 兜底核查，非权威）」

**通道探测**（命中即用，不并发）：

| 序 | 命令 | 命中判据 |
|---|---|---|
| 1 | `mvn -B sonar:sonar` | 仓库根有 `pom.xml`，且 sonar 插件或 `sonar.host.url` 可解析 |
| 2 | `./gradlew sonar` | 仓库根有 `gradlew`，且 `build.gradle*` 声明了 sonar 插件 |
| 3 | `sonar-scanner` | `command -v sonar-scanner` 有输出，配置读 `sonar-project.properties` |

**凭据与目标**：`SONAR_TOKEN` 必填（缺失即判该通道不可用）；服务端地址读 `SONAR_HOST_URL` 或仓库内既有 `sonar.host.url`。**只从环境与本仓既有配置读**——不向用户索要 token 明文、不写入任何文件、不新增 `sonar-project.properties`。

**范围限定**：扫描范围必须等于 Step 0 选定的评审范围——用 `-Dsonar.inclusions=`（或既有配置的 `sonar.inclusions`）收窄到范围内的文件；范围是 diff 类（A–G）时只列本次变更文件，**不整仓全扫**，否则会把未变更的旧问题算进本次结论。

**探测不到 / 执行失败 → 不可用确认（硬约束）**：按 `decision-point.md` 的停止条件处理——**先告警**：写明阻塞原因与恢复条件（缺哪个命令 / 缺 token / 缺服务端地址），并明确告知「规则平台不可用——注入类、加密、事务失效等规则层检查项将失去权威检出源，AI 兜底属概率性检查」；再给出选项「去配置后重试 / 继续」。**用户明确选择「继续」后才得进入 Step 3，禁止静默跳过**。用户确认继续后：规则层条目改由 AI 兜底核查，逐条标注「AI 兜底（无规则平台）」；门禁扫描同样不可执行，报告标注「门禁未执行（Sonar 跳过）」，不伪造门禁结论。**不得伪造扫描结果，也不得把 `analyze.py` / `analyze.sh` 的结论冒名为 SonarQube 结论。**

**结果读取**：门禁取 `/api/qualitygates/project_status?projectKey=<key>[&branch=<b>]`，问题取 `/api/issues/search`（`resolved=false` + 严重度过滤）。门禁判据**只认服务端返回的 `status`**，技能不自行折算严重度。

**脚本与 Sonar 去重**：SonarQube 启用且扫描成功时，`analyze.py`/`analyze.sh` 结果只作 Step 4 读取坐标，其指标类发现（行数/复杂度/魔法数字/未使用导入等 Sonar 已覆盖项）不再计入报告，标注「由 Sonar 覆盖」。

[决策点 2/2] SonarQube 门禁规则（仅决策点 1 选「启用」且扫描成功后问）

A 质量门禁 FAILED → 评审不通过（**默认**）— 直接用服务端 Quality Gate 的 PASSED/FAILED
B 存在 Blocker/Critical 问题 → 评审不通过 — 判据在技能侧可见，不看服务端门禁配置
C 仅新增问题 → 评审不通过 — 只卡本次范围内新引入的 Blocker/Critical，与 `verify` 的「仅阻止新增失败」基线口径一致
D 仅记录，不改评审结论 — 结果只进报告

**门禁未过时**：报告「审查概览」的「合并建议」钉为 `❌ 不建议合并`（不得被其他维度的高分抵消），「风险摘要」首句写出门禁未过与所用规则；扫描出的具体问题在 Step 5 与人工发现合并（去重口径见 Step 4「归并」），同一位置同一根因只留一条。门禁 FAILED 时，后续 Step 3/4 **收窄执行**：只解释阻塞项成因与修复 + 走查门禁盲区的高危面（外部输入、信任边界、并发与事务），不再平铺五维；未走到的维度记入审查覆盖。门禁「未执行」（上方跳过路径）不适用收窄——报告标注「门禁未执行」，审查口径由用户在确认时一并知晓。

> 扫描是**外部粗筛**，定位与 `scripts/` 相同：它没报 ≠ 安全，Step 4 的逐项人工核查不因此减免；也不把它的结论当作「已覆盖某维度」的理由。

### Step 3 — 架构分析

门禁 FAILED（Step 2 判定）时按收窄口径执行（见 Step 2「门禁未过时」），只查门禁盲区的高危面。

按范围侧重不同：
- **增量范围（A–G）**：聚焦「变更是否破坏架构边界」——变更是否跨层调用、引入循环依赖、破坏依赖方向、越出模块职责；
- **全量（H）**：基于脚本输出的文件分布与超大文件清单做完整架构审查：
  - **模块边界**：目录 / 包划分是否清晰，职责是否内聚；
  - **依赖方向**：循环依赖、跨层调用、依赖倒置被破坏；
  - **耦合与内聚**：上帝对象、超大文件、散弹式修改迹象。

### Step 4 — 深度审查

门禁 FAILED（Step 2 判定）时按收窄口径执行（见 Step 2「门禁未过时」）；Sonar 经用户确认跳过时，规则层条目按分工声明由 AI 兜底核查并标注「AI 兜底（无规则平台）」。

**兜底模式的清单加载（省 token）**：Sonar 跳过后加载规则对照组时，只读各清单的「分工声明」与**已命中条目**，跳过正反例节——正反例仅在两处回读：写误报申诉需要引用判定标准，或某条判定需要细节佐证时。不得为「保险」而整份通读。

只消费五样输入：Step 1 的脚本命中、Step 2 的 SonarQube 结果（若启用）、Step 3 的架构结论、本次被审文件（含粘贴片段）、用户提供的任务/需求描述（如有，作意图符合性对照，没有则不作臆测）。`review-rubric.md` 只提供五维定义和严重级别。**打开哪些专项以本步触发器为准**；仓库根有 `pom.xml` / `build.gradle` 不构成加载五份 `java-*.md` 的理由。技术栈看被审文件里的 import、注解、XML 和语言。用户已声明审查重点时，只打开与该重点对应的触发器。

**读取策略（先定位、后精读）** —— 范围由 Step 0 决定，读什么由走查入口与 Step 1 的脚本坐标共同决定，**不整文件读入**：

- 精读位置 = Step 1 脚本命中的 `文件:行` ∪ 走查入口（入口 / 外部输入 / 持久化 / 信任边界）。两处取并集，**谁都不能单独定范围**。
- 只读定位到的片段，**连同该片段的契约**（函数签名、注解、配置项）一起读——脱离契约看片段会误判。
- 脚本没覆盖到、但走查入口要求看的位置，**仍要读**。
- 读片段属于「已阅读代码」，不违反「禁止未阅读代码下结论」；反之**只凭脚本定位、未读片段就报发现**仍被禁止。

**分批与增量落盘** —— Step 3 / 4 的结论**边产生边落盘**，不等 Step 5：

- **Step 3** 的架构结论写入报告落盘文件的「架构评估」节（模板 §6），写完再进 Step 4。
- **Step 4** 按 Step 0 圈定的文件清单分批走读（分批粒度取清单的自然划分，如按目录 / 按变更文件条目，**不引入新的阈值判据**）：每批走完**立即**把该批发现**归并后**追加到落盘文件（归并口径见下「归并」，**跨批生效**——追加前先看落盘文件已有条目），再进下一批。
- 已写入落盘文件的范围**不重读、不重查**；后续步骤只吃落盘文件，不回溯原文。
- 每批追加后可给一句不阻塞的压缩提示（模板见 `./policies/auto-transition.md` 的「层级 A 提示语模板」）。

**发现必须落在范围内**：
- **增量（A–G）**：落在变更行，或变更直接调用 / 被调用的代码上。变更没碰到的旧代码不报。
- **全量（H）、单文件、粘贴片段**：沿入口、外部输入、持久化、信任边界走。没走到的目录记入报告「审查概览」的审查覆盖，写明未下结论；不写成已检查，也不因此加分或扣分。总体评分只依据已报出的发现。
- **全量（H）存量护栏**：审查目标为存量/遗留代码时，架构类与「建议关注」类发现默认降一级，是否按完整口径评审先向用户确认——避免整体重构式批评。

清单项在代码里没有对应 API 时跳过。看不到项目级机制（例如单文件里没有 `@ControllerAdvice`）不等于项目缺失，审查范围没覆盖应用入口或配置时不报缺失。

**通用路径**（任何语言都走）：
1. **正确性**：逻辑、边界、错误处理、返回值与副作用；变更涉及对外契约（API 签名 / DB schema / 消息协议）时，检查下游兼容与迁移。意图符合性对照需求文本 / 接口契约（有则对照，无则记未下结论项）。只报读到的缺陷。
2. **安全性**：对照 `ai-checklist.md` 的 security 分节（AI 主导 SEC-10/12/13/18 + 重叠语义面）逐项核查；规则层（注入、密钥、加密误用、Cookie/配置类）引用脚本与 Sonar 结论，Sonar 跳过时按规则对照组兜底核查。CVE、缺索引、「是否该加缓存」没有外部证据时写入审查覆盖的未下结论项，不报发现。
3. **性能**：出现循环内 IO、查询、无界集合或明显高复杂度时才评估。
4. **可维护性**：对照 `code-smells.md` 的「归属」标注——只补归属「AI」的异味（数据泥团、特性依恋、散弹式修改、平行继承体系）与「重叠」项的语义面（职责判断、名实不符、注释质量、破环方案、委托权衡）；「规则层」项（行数、复杂度、魔法数字、死代码、重复代码等）引用 Step 1 脚本与 Sonar 结论，不重查，脚本盲区的不代查，标「建议补规则」。
5. **架构**：不重做。Step 3 的模块边界、依赖方向、耦合结论直接带入 Step 5。
6. **测试充分性（静态）**：改动点对应的测试是否断言行为而非仅跑通；只看测试代码，不执行测试——与「刻意不做跑测试」不冲突。

**清单加载（按文件走，不靠跳读）**。日常精读清单 = `references/ai-checklist.md`（AI 主导 17 条 + 重叠语义面 24 条，每次深度审查必载）。原 6 份清单（security-checklist / java-*.md）属**规则对照组**，仅在三种时机打开：① Sonar 经用户确认跳过后的 AI 兜底核查（规则层条目逐项核查，发现标注「AI 兜底（无规则平台）」，脚本未覆盖的标「建议补规则」而非代查）；② 规则误报申诉核对；③ 重叠项佐证核对。Sonar 可用时规则层一律引用 Sonar 结论（见 Step 2 三路分支）。正反例只在某一条已经命中时读。未命中的专项不加载，也不写入审查覆盖。

**Java/Spring 触发器**。被审文件命中才加载 `ai-checklist.md` 的对应分节：

| 代码里出现 | 加载 `ai-checklist.md` 分节 | 只看 |
|---|---|---|
| SQL / MyBatis / Repository / `@Transactional` | java-database 节 | 事务原子性、条件下推、异步与事务边界；规则层（无条件删改、SQL 拼接、事务失效）引用 Step 1/2 结论 |
| `Thread` / 线程池 / `@Async` / 锁 | java-concurrency 节 | 异步一致性、死锁锁序；规则层（new Thread、工具类误用）引用结论 |
| Controller、对外接口、参数绑定 | java-api-design 节 | 接口拆分合理性、校验与分层语义面；鉴权另看 security 节 SEC-12/13 |
| 循环内 RPC / 查库、无界集合 | java-performance 节 | 缓存缺失、递归改迭代；重叠项（N+1、无分页）补语义面 |
| `catch`、日志、异常返回调用方 | java-code-quality 节 | 日志上下文充分性、外部调用日志；异常信息泄漏归 SEC-29 |
| 注入 API、密钥、路径拼接、反序列化、放开的鉴权 | security 节 | SEC-10/12/13/18 逐项核查；规则层注入/密钥项引用 Step 1/2 结论，Java/Spring 特有项见规则对照组 §三 |
| 对外 API 签名 / DB schema / 消息协议变更 | 通用路径 · 正确性 | 下游兼容：调用方是否同步适配、是否需要迁移脚本/灰度 |

**归并**（写入发现前做）：
- 同一位置、同一根因只留一条。脚本已报的引用其结论，不重写推理。
- 安全清单与质量清单冲突时归安全，级别取更高的一级。日志里的密码、证件号是安全问题。
- 事务不回滚、无条件删改归**正确性**。N+1 与循环远程调用归**性能**。分层越界若 Step 3 已写，不重复。
- SonarQube 与人工发现同一位置、同一根因只留一条，**优先级分层**：SonarQube 检出 → **定论**，人工只解释成因与给修复，不改判定、不另起判定逻辑；认为误报时唯一合法动作是在该条发现的「依据」后附 `申诉：判定为误报，理由 …`（级别维持服务端结论，见模板「规则误报申诉」）。`analyze.py`/`analyze.sh` 命中 → 仍为**坐标**，须人工核实（自建粗筛不是权威规则平台）。门禁结论（通过/未通过）不逐条重复计入评分。

**停**：高危面走完即停。小范围 diff 不展开 Nit。禁止为了清单看起来完整而补「建议关注」。

### Step 5 — 输出评审报告

按 `templates/review-report.md` 输出，**收口到 Step 1 建的报告落盘文件**（路径见「标识约定 · 报告落盘」）。**报告结构、每条发现的字段、各档详略规则全部以该模板为唯一源**，本步不重述；增量落盘的半成品在**本步一次性补齐**（审查概览的结论性字段、风险摘要、问题清单与明细的编号对齐）。

本步只定两条模板之外的约束：

1. **合并输出**：Step 1 脚本扫描（与 Step 2 SonarQube，若启用）发现的客观问题，与 Step 3/4 深度审查发现的问题，必须合并为**同一份报告**——不遗漏脚本与扫描已发现的 Critical/Major，也不重复报告同一问题（已报的直接引用结论，不必复述推理过程）。
2. **可核查**：每条发现必须带 `文件:行` 定位与 rubric 四档之一的级别；给不出定位的观察写进「审查概览 · 审查覆盖」的未下结论项，不写成缺陷。
3. **置信度**：Critical/Major 明细带置信度（高=路径级证据 / 中=静态推断需佐证），映射清单静态边界「可审=高」「部分可审=中」「不可审=不报」；中置信条目按 rubric 计分排除规则进「待人工确认」，超 3 条折叠（字段与折叠规则以模板为唯一源）。

## 质量标准（未达标需返工）

- **零臆造**：每条发现必须有代码依据或脚本/扫描证据，不得凭想象下结论；引用 SonarQube 结论时须带规则 id 与位置，不得转述成自己的判断；
- **分级准确**：严重级别必须与 rubric 定义一致，不得拔高或淡化；
- **可落地**：修复建议必须具体到「改成什么」，而非空泛的「注意安全」；
- **依据绑定**：每条发现须指向清单编号（如 SEC-01 / DB-13）、项目规范 / 团队禁忌清单条目或既有先例（`文件:行`）；三者都给不出的观察降级为「待人工确认」或「建议」档，不写成缺陷——与「零臆造」互补；
- **重点优先**：Critical/Major 问题排在前面，详略按模板分级（Minor 压缩、Nit 只进表格）；
- **语言一致**：报告语言与用户输入语言保持一致。

## 降级决策（脚本不可用时）

触发条件：脚本缺失 / 报错无法执行 / 找不到脚本路径。

处理（按序）：
1. 先用 `find` 定位脚本实际路径，改用绝对路径重试；
2. 仍不可用 → **跳过脚本，仅 AI 走读**，并在报告「审查概览」如实标注「脚本未执行，结论仅基于静态走读」；
3. **不得**假装已跑脚本、不得把走读结论冒充脚本证据。

> 脚本是粗筛辅助，跳过**不阻断**审查，但必须留痕。

## 退出条件

- 已按 `templates/review-report.md` 输出评审报告，并**落盘**到「标识约定 · 报告落盘」的路径（结构完整：★ 行已填、每条发现带 `文件:行` 与 rubric 级别）
- 未修改任何被审对象
- SonarQube 的启用情况已在报告「审查概览」留痕（未执行含原因 / 已执行含门禁结论与所用规则）
- 未写 workflow 游标 / `phase` / metrics

## 上下文压缩恢复

重载：审查目标（范围 + base-ref / 重点 / 技术栈）、脚本执行情况、SonarQube 的启用情况与门禁结论、报告落盘文件已写入到哪、停在哪个 Step。

- **恢复依据就是落盘产物** —— 本技能不写 `state.yaml`，进度以报告落盘文件为准，不依赖会话记忆（范围决策在 Step 1 已写进报告头部）
- 范围确定之前（停在 **Step 0**）→ 按 Step 0 重新询问，**不代答、不默认**
- **Step 1 / 2 是原子段**（圈定清单 → 脚本扫描 → 可选 SonarQube）：中断即从 Step 1 重跑；已答过的 SonarQube 决策不重问，探测成功过的通道不重跑
- **Step 3 / 4 有恢复点**（架构结论与每批发现已增量落盘）：从报告落盘文件的最后一批续，**已落盘的范围不重读**
- 停在 **Step 5** → 从报告落盘文件合并输出，不重跑前面各步
- 用户声明「仅在会话内输出」→ **无落盘载体，即无恢复点**，中断按 Step 1 重跑
- 「压缩上下文」与「恢复清单」的用词、提示语模板见 `./policies/auto-transition.md` 的「压缩时机与恢复清单」
