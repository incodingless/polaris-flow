# DDD 领域模型设计实践（精简参考）

> **用途**：供 `design-domain-model-policy` 在生成 `domain-model-design.md` 时 `read_file`。  
> **定位**：划分与自检清单，**不是**需求来源。业务对象与规则必须来自 `detailed-design.md` / proposal / specs。  
> **禁止**：把本文件中的范例名、行业模板直接抄进当前变更。

---

## 1. 何时用领域模型专项

适合：有明确业务不变式、状态流转、多对象协作，或 detailed-design 只点了模块名未给出可实施的对象关系。  
不适合：纯 CRUD 配置表、无行为的 DTO 堆砌——可留在 detailed-design / data-model，不必硬套聚合。

---

## 2. 核心概念（工作定义）

| 概念 | 工作定义 | 判定提示 |
|------|----------|----------|
| 限界上下文 | 同一套术语与模型成立的边界 | 与 proposal 范围、高层 design 模块对齐；跨上下文用集成关系，不硬揉成一张大图 |
| 实体 | 有稳定身份、生命周期内可变 | 问「换掉属性后是否仍是同一个？」→ 是则偏实体 |
| 值对象 | 无独立身份、由属性整体描述、宜不可变 | 金钱、地址、区间、枚举包装等；相等看值不看引用 |
| 聚合 / 聚合根 | 一组强一致修改的边界；对外只通过根引用 | 一次业务命令应落在**一个**聚合内完成强一致；跨聚合用领域事件或应用服务编排 |
| 领域服务 | 无自然归属单一实体/值对象的领域操作 | 先问能否放进实体；不能再上升为领域服务 |
| 领域事件 | 领域内已发生的事实 | 过去时命名；载荷够下游决策，不泄漏他聚合内部结构 |

---

## 3. 聚合划分实践

1. **按不变式切**：必须一起校验/一起提交的规则，放进同一聚合  
2. **宜小不宜神**：聚合过大（多实体深图）→ 拆分并明确跨聚合一致性（最终一致 / 进程外消息）  
3. **引用方式**：聚合外只持有他聚合根的 ID，不直接改他聚合内部实体  
4. **与事务**：一个事务默认对应一个聚合的强一致更新；需要分布式事务时在设计里显式写出代价与替代方案  

---

## 4. 命名与语言

- 用**业务语言**（与 intention / specs 一致），不用表名、框架名当模型名  
- 一个上下文内同一概念一名；出现多名 → 先统一语言再建模  
- 状态机：列出合法状态与迁移触发，禁止「任意改字段」式描述  

---

## 5. 生成后自检（写入前过一遍）

| # | 检查项 | 失败时 |
|---|--------|--------|
| C1 | 每个实体/值对象/服务/事件都能指回 detailed-design 或 spec 的依据 | 删除或标 TBD，禁止保留 |
| C2 | 聚合根清晰；跨聚合没有「直接改内部实体」 | 改为 ID 引用 + 事件/应用编排 |
| C3 | 值对象未冒充实体（无必要身份） | 降为值对象或并入实体属性 |
| C4 | 领域服务不是应用层流程脚本（无编排 UI/API/事务边界的废话） | 下沉到实体或上移说明为应用服务（本专项可不展开应用层） |
| C5 | 未写入 DDL、REST 路径、缓存键等持久化/接口细节 | 挪到 data-model / restful-api / repository |
| C6 | Non-goals 内对象未进模型 | 删除 |
| C7 | §9 仓储映射能让下游知道「按哪个聚合落地」 | 补映射，仍不写表字段 |

## 6. 与下游专项的关系

```text
domain-model-design.md（本参考服务的对象）
        ↓ 聚合/实体边界
repository-design.md（仓储接口与一致性）
        ↓ 持久化形状
data-model-design.md（表/ER/索引/迁移）
```

本参考**到领域边界为止**；表与 API 的对错不在此裁决。
