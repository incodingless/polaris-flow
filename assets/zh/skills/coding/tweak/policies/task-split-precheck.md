# 任务拆分预检 — 需求规模检测与拆分决策

## 核心原则

- 拆分预检**必须**基于已形成的澄清摘要（目标、非目标、范围边界、关键未知项、验收场景草案），不得凭空拆分
- 拆分决策是阻塞点，必须按 `./policies/decision-point.md` 协议暂停并等待用户选择
- 不得在用户完成拆分选择前创建 `proposal.md`、`design.md` 或 `tasks.md`
- 每个被接受的拆分项必须通过 `/polaris{{SKN_SPR}}coding{{SKN_SPR}}clarify` 创建独立 change，**禁止**直接调用 `/opsx:new`

---

## 1. 可跳过预检（唯一判定门）

仅当以下**全部**满足时，可跳过拆分预检并明确说明「本次需求规模适中，无需拆分预检」：

- 澄清摘要仅覆盖单一 capability、单一模块、单一用户路径
- 不存在可独立交付的子集
- 预计产出 ≤ 1 个 delta spec 且 ≤ 3 个大任务
- 不存在分阶段里程碑，或各阶段强耦合无法独立推进

## 2. 拆分预检

### 2.1 不推荐拆分

满足以下**全部**条件时，可明确推荐「保持为一个 change」：

- 各 capability / 模块 / 用户路径强耦合，拆分后无法独立验收
- 拆分会导致共享基础设施重复建设或接口不一致
- 用户已明确表示希望单 change 交付且理由充分

### 2.2 推荐拆分条件

满足**任一**条件时，**应推荐拆分**：

| # | 判定条件 |
|---|---------|
| S1 | PRD 包含多个可独立设计、构建、验证、归档的 capability |
| S2 | 涉及多个模块或用户路径，且其中一部分可独立交付 |
| S3 | 存在明显分阶段里程碑 |
| S4 | 预计会产生多个 delta spec 或超过 3 个大任务 |
| S5 | 任一部分失败或延期不应阻塞其他部分进入后续阶段 |

## 3. 候选拆分清单输出格式

执行预检后，**必须**输出以下结构：

```markdown
📦 Change 拆分预检

**规模评估结论**：<推荐拆分 / 建议保持单 change / 边界情况需用户判断>

**触发依据**（引用澄清摘要，1-3 条）：
  · <依据 1>
  · <依据 2>
  · <依据 3>（如有）

---

### 候选拆分项

#### 拆分项 1：<建议 change 名称（kebab-case slug 草案）>

- **目标与范围边界**：<本 change 要达成什么、覆盖哪些模块/用户/平台>
- **明确非目标**：<本 change 明确不做的事项>
- **依赖关系 / 推荐执行顺序**：<依赖项编号或无依赖；推荐第 N 个执行>
- **核心验收场景**：
  1. <场景 1>
  2. <场景 2>
  3. <场景 N>

#### 拆分项 2：<建议 change 名称>
（同上结构，按需列出所有候选项）

---

### 若不拆分的风险（仅当推荐拆分时呈现）

  · <风险 1>
  · <风险 2>

---
```

**每个候选拆分项必须包含**上述 5 个字段，缺一不可。验收场景至少覆盖 1 个核心成功场景。

## 4. 用户决策点（阻塞点）

**必须**按 `./policies/decision-point.md` 暂停，呈现以下选项并等待用户选择：

```
请选择一个选项：

  A.「创建多个 OpenSpec changes」— 按候选拆分清单逐个创建独立 change
  B.「保持为一个 change」— 继续单 change 流程；将在后续 proposal / design / tasks 中记录不拆分原因
  C.「调整拆分方案后继续」— 请直接说明调整方向（合并/拆分/重命名/调整顺序等），我将重新输出候选拆分清单
```

### 4.1 用户选择处理

| 选择 | 后续动作 |
|------|---------|
| A（创建多个） | 进入 **§5 批量拆分模式**；当前 `/polaris{{SKN_SPR}}coding{{SKN_SPR}}clarify` 调用仅完成拆分确认与调度 |
| B（保持单 change） | 记录「用户选择不拆分」及理由，跳过批量模式，继续 clarify 后续步骤 |
| C（调整方案） | 合并用户调整说明，重新输出 §3 候选拆分清单，再次呈现 §4 决策点（**最多 3 轮**） |

> 用户回复未使用 A/B/C 但语义明确时按对应分支处理。语义不明确时必须重新呈现选项，禁止主观判定。

**禁止**：未收到用户明确选择前创建任何 OpenSpec artifacts 或执行 `/polaris{{SKN_SPR}}coding{{SKN_SPR}}clarify`。

---

## 5. 批量拆分模式

用户选择 **A（创建多个 OpenSpec changes）** 后进入本模式。

### 5.1 创建规则

- 每个被接受的拆分项**必须**通过 `/polaris{{SKN_SPR}}coding{{SKN_SPR}}clarify` 创建独立 change
- **禁止**直接调用 `/opsx:new`
- 按用户确认的顺序（或推荐执行顺序）逐个调度 `/polaris{{SKN_SPR}}coding{{SKN_SPR}}clarify`
- 当前会话的 `/polaris{{SKN_SPR}}coding{{SKN_SPR}}clarify` 调用**仅负责**拆分确认与调度，不推进 design 阶段

### 5.2 单个拆分项的调用要求

进入每个拆分项的 `/polaris{{SKN_SPR}}coding{{SKN_SPR}}clarify` 时，**必须**明确标注：

```
[已确认拆分项] <change 名称>

目标与范围边界：<...>
明确非目标：<...>
核心验收场景：
  1. <...>
  2. <...>
```

已确认拆分项**默认跳过** PRD 拆分预检，除非该拆分项本身仍明显包含多个独立 capability（此时仅对该项重新执行本预检）。

### 5.3 批量完成后的暂停规则

- 单个拆分项完成 clarify 阶段后，**不得**自动流转到 `/polaris{{SKN_SPR}}coding{{SKN_SPR}}propose`
- 全部分拆项 clarify 完毕后，**必须**暂停并询问用户：

```
以下 change 已创建并就绪：
  · <change-1>
  · <change-2>
  · ...

请选择要先推进 propose 阶段的 change（回复名称或编号）：
```

- 用户选择后，**仅**推进该 change 进入 `/polaris{{SKN_SPR}}coding{{SKN_SPR}}propose`
- 其他 change 保持 active，稍后通过 `/polaris-flow` 恢复

---

### 6. 选择不拆分时

在 `intention.md` 的 `## 任务范围` 节记录：

```markdown
### 拆分决策
- 结论：保持单 change
- 不拆分原因：<用户确认的理由或评估依据>
- 评估日期：<日期>
```

## 7. 断点恢复规则

不新增专用批量状态文件。批量拆分过程中断后，按以下顺序恢复：

### 7.1 恢复检查

1. 扫描已创建的 active changes（含 `state.yaml` 的目录）
2. 与对话中已确认的拆分清单比对

### 7.2 恢复动作

| 状态 | 动作 |
|------|------|
| 拆分项已存在且含 `state.yaml` | **不得**重复创建，标记为「已完成 propose」 |
| 拆分项尚未创建 | 按已确认清单继续通过 `/polaris{{SKN_SPR}}coding{{SKN_SPR}}clarify` 创建 |
| 对话中已确认的拆分清单不可恢复 | **必须**按 `./policies/ask-question-react.md` 重新向用户确认拆分清单（重新呈现 §3 + §4），确认后再继续 |

### 7.3 恢复后继续

- 仍有未 open 的拆分项 → 继续 §5.1 逐个创建
- 全部 open 完成 → 执行 §5.3 暂停，等待用户选择 design 起点

**硬门**：本步骤未完成（含批量模式下全部拆分项 open 未完成）前，禁止进入 Reframe Check、Premise Challenge 及 Step 4 产出。
