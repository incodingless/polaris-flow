# 前提挑战 - Premise Challenge

## 核心原则

设计阶段必须主动识别并挑战用户描述中的**未验证前提**。前提 ≠ 事实，除非有证据支撑。

挑战的目的不是攻击用户，而是把"被当作事实的假设"显式化，让任一前提不成立时设计方案能及时调整。**语气必须合作式，禁止做成攻击**。

---

## 一、什么是"未验证前提"

用户陈述中被当作事实但实际未经证实的假设，例如：
- "用户不会做 X" — 如何确认？
- "这个 API 性能足够" — 有基准测试吗？
- "现有系统不支持 Y" — 验证过吗？
- "这是唯一的方案" — 真的搜索过替代方案？

---

## 二、前提选取规则

提炼前提时**必须**覆盖以下类型中的至少 3 类（不强求全覆盖）。其中**硬约束层必须覆盖**（`数据/规模前提` + `技术选型前提` 至少各一条）；判断输入层按需。

### 三层语义（前置输入约束的三类，分列，勿混为一谈）

| 层 | 内容 | 性质 | 强制 |
|----|------|------|------|
| **硬约束**（红线） | 算力 / 内存 / 并发上限、技术栈限制、合规要求、成本预算、交付周期 | 不可突破的边界 | **必覆盖** |
| **判断输入** | 现有系统基线、团队能力边界、用户行为 | 影响选型，非红线 | 建议覆盖 |
| **优先级锚点** | 核心矛盾（Top3）+ 优先级前提 | 决定「抓核心 vs 平均用力」 | **必覆盖** |

| 类型 | 层 | 例子 |
|------|----|------|
| **范围前提** | 判断输入 | "本次仅改造下单主链路，购物车与售后链路不在范围内" |
| **依赖前提** | 判断输入 | "假设上游订单中心的 `order_id` 字段在本季度内不会扩位或变更类型" |
| **数据/规模前提** | 硬约束 | "假设每日新增审计日志 ≤ 500MB，超出该规模需重新评估存储方案" |
| **用户行为前提** | 判断输入 | "假设运营人员会在导入失败后 24h 内查看告警邮件，而非依赖工单催办" |
| **技术选型前提** | 硬约束 / 判断输入 | "假设继续基于 Redis 6.x 做幂等键存储，不引入 KV 数据库或外部锁服务"（硬约束：技术栈限制）；"团队仅熟悉 MySQL，不引入需专职运维的分布式数据库"（判断输入：团队能力边界）；"必须在 X 月 Y 日前上线、成本预算 ≤ ¥Z"（硬约束：交付周期 / 成本） |
| **优先级前提** | 优先级锚点 | "数据一致性优先于写入吞吐，可接受 P99 延迟从 50ms 升到 150ms"（核心矛盾在具体点的落地） |

> 三类边界：**硬约束**是「不能突破的红线」，**判断输入**是「选型时权衡的参考」，**优先级锚点**是「决定把设计力量花在哪」。团队能力、现有系统基线是判断输入，不是红线——不得把它们当成「必须绕开」的硬约束，避免把参考信息误当边界。

每条前提**必须满足**：单句、可证伪、不成立时影响明确。**禁止**写成"用户会认可 X"这种空话。

每次提炼 **3-5 条**前提呈现给用户。

### 核心矛盾提炼（优先级锚点，Top3）

除逐条前提外，从「目标 + 已认可前提」中提炼 **3 个全局核心矛盾**（业务主次取舍，如「高并发 vs 强一致」「快速上线 vs 功能完备」「成本 vs 性能」）。核心矛盾是**全局主次**，优先级前提是其**在具体技术点的落地**——两者是「全局 → 局部」关系，不重复。核心矛盾进入 `intention.md` 的 `## 核心矛盾` 节（见「五、阶段产出」），用于指导设计「抓核心、不平均用力」。

---

## 三、输出格式

```
🧩 前提挑战（Premise Challenge）

请逐条确认以下前提是否成立。任何一条不成立都会改变设计方案。

前提:
1. <前提陈述，单句、可证伪> — 认可 / 不认可 / 不确定
   类型：<范围 / 依赖 / 数据规模 / 用户行为 / 技术选型 / 优先级>
   风险：<高 / 低>（高 = 不成立会导致架构返工；低 = 影响有限）
   依据：<这条前提是从对话哪里推出来的>
   不成立的影响：<如果不成立，设计的哪个部分需要改>
   验证方式：<如何确认这条前提，例如基准测试 / 抽样调研 / 查阅文档>

2. <前提陈述> — 认可 / 不认可 / 不确定
   ...

3. <前提陈述> — 认可 / 不认可 / 不确定
   ...
```

---

## 四、用户回复处理

| 用户回复 | 后续动作 |
|---------|---------|
| 全部确认 | 进入"完整方案确认询问"阶段 |
| 任何 不认可 | 针对该条回到讨论：让用户给出修正后的前提；修正后**必须**重新生成 Premise Challenge 清单（**最多 3 轮**） |
| 任何 不确定 | AI 必须给出具体追问（具体例子 / 边界场景 / 可验证标准），帮用户从 不确定 → 认可/不认可 |
| 模糊回复（"差不多"/"大概吧"） | 视为 不确定，按上一行处理 |

---

## 五、阶段产出

通过的所有前提**必须**在 `intention.md` 中以 `## 前提` 节单独列出（位于 `## 结论` 节之前），格式：

```markdown
## 前提
<!-- 进入实施前已与用户逐条确认的前提，任一不成立会改变设计 -->

1. <前提原文>
2. <前提原文>
3. <前提原文>
```

被用户拒绝 / 修改过的前提历史以单独的 `## 前提历史` 节写入 `intention.md`，作为 lock 阶段评审建议落地时的"假设变更日志"参考。

提炼出的 **3 个全局核心矛盾**以单独的 `## 核心矛盾` 节写入 `intention.md`（位于 `## 目标` 之后、`## 结论` 之前），格式：

```markdown
## 核心矛盾
<!-- Top3 全局业务主次取舍，指导设计「抓核心、不平均用力」 -->

1. <核心矛盾 1：A 优先于 B，一句话说明为什么这是本次设计的核心张力>
2. <核心矛盾 2：…>
3. <核心矛盾 3：…>
```

核心矛盾须随「前提」一并呈现用户确认，与「前提」一样是「不成立会改变设计」的锚点。

## 六、唯一禁止行为

**禁止把挑战做成攻击**——语气必须合作式，对事不对人。
