# 轻量调研（`tweak` 档的澄清细则）

> **触发**：`state.yaml` 的 `workflow.mode = tweak`（本技能只读，不覆盖）。
> **替代**：`SKILL.md` Step 3 的 3.0–3.4 全部探索环节（本档**豁免，非缺失**）。
> **汇合**：本细则产出的摘要即 Step 4 写 `intention.md` 的输入源（9 个节仍写满，内容极简）。

## 为什么是「调研」而不是「探索」

`tweak` 是**简单改动**：事实**主要在代码里**（改哪个文件、谁在调用、有没有现成同类实现），
不在用户脑子里。所以本档的第一动作是**读代码**，不是问问题 —— 探索式提问在这里是**成本**
（用户被问本该自己查的东西），不是价值。

## L1 现场勘察（先做，不可跳）

**不提问**，先并行读：

| 读什么 | 目的 |
|------|------|
| 需求指向的文件 / 模块 | 确认改动落点与现有实现 |
| 同类既有实现（同目录 / 同命名规律） | 复用现有模式，不另造 |
| 相关测试 | 知道改完怎么验、会不会碰坏 |
| 调用方 / 依赖方（`grep` 引用点） | 判断影响面是否只在本模块内 |

**产出**：一份「现状事实」清单，每条带 `文件:行` —— 它是后面 6 项摘要的**唯一依据**，
**不得**凭对话印象填。

## L2 一次理解确认（6 项，**本档唯一一次澄清确认**）

按 `./policies/decision-point.md` 一次性整体确认下面 6 项（**不逐项问**）：

| # | 项 | 来源 |
|---|----|------|
| 1 | **改什么**（范围：文件 / 函数） | L1 勘察 |
| 2 | **为什么**（目标） | 用户原始诉求 |
| 3 | **不改什么**（非目标 / 边界） | L1 影响面 |
| 4 | **怎么算完成**（验收） | L1 相关测试 |
| 5 | **有什么坑**（会碰到的既有约束 / 风险） | L1 现状事实 |
| 6 | **谁受影响**（下游依赖） | L1 引用点 |

用户可逐条纠正 → 纠正后**重出摘要再确认**（不算新一轮探索）。

## L3 信息不足时：一次聚焦追问，仍不足则升档

- 6 项里**缺哪项就问哪项**，一次问完，**≤ 2 轮**（不展开成探索式对话）。
- 2 轮后仍无法确认 → **停止追问**，把未闭合项记入摘要的「关键未知项」，
  并在 **`SKILL.md` Step 5.5 的出口判档**升到 `normal`（由后续 `plan` / `tasks` 承担更完整的澄清）。
- ⚠️ **不要**在本档内补做 3.0–3.4 的任何一环来"救"信息不足 —— 那会让档位名不副实。

## 本档明确不做（对照表）

| 不做 | 为什么可以不做 |
|------|----------------|
| `openspec-explore` 强制交互（≥3 问 / ≥3 类） | 事实在代码里，L1 勘察已覆盖 |
| 3.1 需求拆分预检 | 简单改动不存在"拆成多个 change"的问题 |
| 3.2 Reframe Check | 目标由用户直接给出，无需重构问题框架 |
| 3.3 设计决策 Options | 本档不产出设计（`plan` / `design` 都不在序列内） |
| 3.4 Premise Challenge | 前提即 L2 的第 3 / 5 项，已随摘要一并确认 |

> ✅ 这些是**本档豁免**，不是"实现缺失"。审计时**不要**把它们当漏洞补回来 ——
> 补回来就等于取消了 `tweak` 档。

## 发现"其实很复杂"怎么办

勘察中出现下列任一信号 → **不在此处补做完整探索**，而是记入「关键未知项」并在
**Step 5.5 出口判档**升档：

- 跨服务 / 跨系统（`risk-signals.md` §4 D1）
- 需专项设计（D2）／数据迁移（D3）／破坏性契约变更（D4）
- 顶层任务预计 > 8（D5）／需求不稳（D6）／高危领域（D7）
- 需要拆分到多个 change

> 依据：`specify` 出口时本任务的产物**只有 `intention.md`**（见 `SKILL.md` Step 5.5），
> 所以那里改档**零返工**；在别处补做探索反而会与已落盘的摘要冲突。
