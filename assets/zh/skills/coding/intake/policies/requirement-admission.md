# 需求准入性质判定（`intake` 私有）

## 一、三分类判定

对 `需求内容` 原文（为主）+ `附加上下文`（为辅）做性质判定，落三态之一：

| 态 | 判定标准 | 处置 |
|---|---|---|
| **功能开发** | 新增能力，或改变现有功能的行为（非缺陷） | 放行，进入正常流程 |
| **缺陷修复** | 描述的是**现状缺陷**：报错 / 崩溃 / 失败 / 线上故障 / 回归失败 | 拒绝，路由 debug |
| **非开发输入** | 既非功能开发也非缺陷：迁移方案 / 开发思路 / 设计文档 / 排期 / 闲聊等 | 拒绝，按内容路由 |

判定依据是**输入原文的谓语与对象**，不是 AI 的猜测。

### 判定信号

| 态 | 谓语（判据） | 对象（判据） |
|---|---|---|
| 功能开发 | 新增 / 支持 / 做 / 实现 / 优化 / 改成 / 加 | 目标行为、目标状态（「要做成什么」） |
| 缺陷修复 | 修复 / 报错 / 崩溃 / 失败 / 回归 | 现状缺陷（「哪里坏了」） |
| 非开发输入 | 迁 / 想 / 设计 / 排 / 无谓语 | 步骤、思路、设计本身（「怎么做」而非「要什么」） |

非开发输入的典型形态：

- **迁移方案**：描述「怎么把代码从 A 迁到 B」的步骤，不是「要实现什么功能」。
- **开发思路**：描述「怎么实现」的思路 / 技术选型，不是「要做什么」的目标。
- **设计文档**：描述「设计」本身，不是「要实现的用户可见功能」。
- **排期 / 闲聊**：无明确功能目标。

## 二、拒绝的形态

拒绝**不是**「请走开」，而是「这不是功能开发需求 + 你可能想走 X + 若要按功能开发执行请补 Y」。
拒绝 = **不建任务**，先提示后停下，等用户改选或补全。

| 输入性质 | 处置 |
|---|---|
| 缺陷修复 | 提示走 `polaris{{SKN_SPR}}debug{{SKN_SPR}}diagnose`（生产故障 / 测试缺陷由它分流） |
| 需求 / PRD 相关 | 提示走 `polaris{{SKN_SPR}}prd{{SKN_SPR}}discovery` |
| 迁移方案 / 开发思路，但确要按功能开发执行 | 要求补「目标（要做成什么）+ 任务范围（改哪些）+ 验收场景（怎么算完成）」三点后重新进入 |

## 三、边界

- 本判定只问**性质**（是不是功能开发），**不问质量**（够不够详细）——后者由 `specify` 澄清期追问。
- **`ambiguous`**（性质难辨，如「帮我看下这段代码」可能评审也可能改代码）→ 按 `./policies/decision-point.md` 问用户，**不自行猜**。
- 判定输入只准用 `需求内容` 原文 + `附加上下文`，**不得**凭对话印象。
- 附加上下文里即使带了「设计文档 / 方案」等文件，只要 `需求内容` 原文是功能开发诉求，就是**参考资料**，不据此拒绝。
