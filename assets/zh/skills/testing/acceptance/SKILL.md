# 编写验收标准

## 定位

把需求条目或功能点转换为可判定、可验证的验收标准，作为开发自测、测试设计与需求验收的共同依据。

**核心原则**：验收标准是「怎么算做完」的客观判据。无法判定通过/失败的表述，不是验收标准。

<HARD-STOP>
1. ❌ 禁止输出无法判定通过/失败的表述（如"功能正常"、"响应迅速"、"体验良好"）
2. ❌ 禁止脑补需求未声明的行为、文案、数值、错误码
3. ❌ 禁止只写主流程，异常与边界场景必须覆盖
4. ❌ 禁止把技术实现方案写成验收标准（用哪个接口、哪张表、什么算法）
5. ❌ 禁止一条标准混入多个验证点，一条标准只判一个结论
6. ❌ 禁止与 PRD 已有业务规则冲突，发现冲突须指出而非自行改写
7. ❌ 禁止输出不可观察的内部状态作为预期结果
</HARD-STOP>

## 输入

- **必需**：需求条目 / 功能点清单（来自 PRD、需求基线或用户输入）
- **可选**：PRD 中的业务规则与非功能需求（用于补充量化判据）
- **可选**：可测性报告（用于定位待补全的条目）
- **可选**：指定范围（全量 / 指定章节 / 指定功能点）

## 总流程

Step1 需求条目拆解 > Step2 按场景编写验收标准 > Step3 可验证性自检 > Step4 输出验收标准清单

## Step 1 — 需求条目拆解

### 执行步骤

1. **提取待编写条目**
   - 遍历范围内的每个功能点 / 需求条目
   - 沿用 PRD 原编号；无编号则按 `F{章节}-{序号}` 补编
   - 读取该条目关联的业务规则、状态流转、非功能需求，作为判据来源

2. **判定条目复杂度**

| 复杂度 | 特征 | 验收标准条数要求 |
|---|---|---|
| 简单 | 单步骤、无分支、无状态流转 | ≥1 条（主流程） |
| 常规 | 多步骤或有 1-2 个分支 | ≥3 条（主流程 + 主要异常 + 边界） |
| 复杂 | 多分支、多状态、涉及权限/并发/外部依赖 | ≥6 条（主流程 + 多异常 + 多边界） |

3. **标记信息缺口**
   - 若条目缺少编写验收标准所必需的信息（提示文案、边界数值、状态定义）→ 记入「待确认清单」
   - **禁止自行编造填补**，在 Step 4 输出时明确提出

## Step 2 — 按场景编写验收标准

> 使用 GWT 格式，每个条目按「正常 → 异常 → 边界」顺序编写。

### 格式规范

```
Given {前置条件：数据状态、用户权限、环境}
When  {操作动作：用户执行的具体操作，含输入数据}
Then  {预期结果：可观察、可判定的具体结果}
And   {附加验证点：数据变化、状态变更、记录生成}
```

### 场景1：主流程验收标准

验证在合法输入下，功能按需求声明完成。

- `Given` 取需求声明的标准前置（已登录、有权限、数据存在）
- `Then` 必须包含：界面反馈（具体文案）+ 数据变化（具体内容）
- 需求中声明了量化指标的（响应时间、成功率），必须写入 `And`

### 场景2：异常验收标准

验证需求声明的约束与错误处理被正确执行。

**按 7 类异常源选取**（需求未声明的类别不编写）：

| 异常源 | 典型验收点 |
|---|---|
| 输入异常 | 空值、格式错误、超长、特殊字符被拦截并提示 |
| 权限异常 | 未登录、无权限被拦截，不暴露数据 |
| 状态异常 | 非法状态下操作被拦截，状态不流转 |
| 数据异常 | 数据不存在、重复提交的处理 |
| 并发异常 | 重复提交幂等、并发修改冲突处理 |
| 依赖异常 | 外部系统失败时的降级或提示 |
| 规则异常 | 超出额度、次数、时效时受限 |

### 场景3：边界验收标准

验证数值、长度、数量、时间的边界行为。

- 每个数值型约束取：最小值、最大值、越界值
- 每个长度型约束取：空、最大长度、超限
- 每个批量约束取：0 条、上限、上限+1
- 每个时效约束取：生效前、失效后

### 不合格 vs 合格示例

| 不合格 | 合格 |
|---|---|
| 载体创建功能正常 | Given 用户已登录且有创建权限，When 填写合法载体信息并提交，Then 系统创建载体记录并返回载体编号，列表中可见新记录 |
| 查询要快 | Given 系统中存在 ≤100 条符合条件的载体，When 执行查询，Then 结果在 3 秒内返回且分页总数与实际一致 |
| 重复编号要处理 | Given 系统中已存在编号 C001，When 提交编号为 C001 的创建请求，Then 提示"载体编号已存在"且不新增记录 |
| 批量导入支持大数据量 | Given 准备 1000 条合法数据，When 提交导入，Then 全部导入成功；When 提交 1001 条，Then 提示"单次导入不超过1000条"且任务未创建 |
| 无权限要拦截 | Given 用户无创建权限，When 访问创建页面，Then 页面不可见且不返回载体列表数据 |

## Step 3 — 可验证性自检

对每条写出的验收标准逐条过检，不通过则重写：

| 检查项 | 通过标准 |
|---|---|
| 可判定 | 能明确回答"通过还是没通过"，不含主观词 |
| 可观察 | 预期结果可通过界面、接口响应、数据记录观察到 |
| 有输入 | `When` 含具体操作与输入数据，非抽象动作 |
| 有量化 | 涉及性能、数量、时效的给了具体数值与单位 |
| 单结论 | 一条标准只判一个结论，多结论需拆分 |
| 无冲突 | 与 PRD 已声明的业务规则一致 |
| 无脑补 | 所有文案、数值、状态均可在需求中溯源 |

未通过的项：能改则改，缺信息则移入「待确认清单」。

## Step 4 — 输出验收标准清单

输出到 `openspec/changes/<change_id>/test/acceptance-criteria.md`，结构如下：

```
# 验收标准清单 — {需求/变更名称}

## 1. 概览
- 需求条目总数 / 已编写数 / 覆盖率
- 复杂度分布

## 2. 验收标准
### {需求编号} {需求名称}
**主流程**
- AC-{编号}-01：Given … When … Then …

**异常场景**
- AC-{编号}-02：…

**边界场景**
- AC-{编号}-03：…

## 3. 待确认清单
| 需求编号 | 缺口描述 | 需要用户提供的信息 |
|---|---|---|

## 4. 覆盖率结论
- 主流程 / 异常 / 边界 覆盖统计
- 阻塞项（无验收标准导致无法验收的条目）
```

输出后向用户报告：条目覆盖数、标准总条数、待确认项数量，并提示可继续调用 `polaris{{SKN_SPR}}testing{{SKN_SPR}}case` 基于本标准编写测试用例。

## 常见错误

| # | 反模式 | 正确做法 |
|:---:|---|---|
| 1 | 写"功能正常""响应快" | 给出具体文案、数值、状态变化 |
| 2 | 只写主流程 | 按复杂度要求补齐异常与边界 |
| 3 | 一条标准塞多个结论 | 拆成多条，一条一个判定 |
| 4 | 需求没写就自己编 | 记入待确认清单，向用户提问 |
| 5 | 用技术方案描述预期 | 描述用户可观察的结果 |
| 6 | 与 PRD 规则冲突时自行改写 | 指出冲突，交由用户裁决 |
