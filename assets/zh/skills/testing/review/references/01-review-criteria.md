## 评审维度（7 项，逐项必过）

### 维度 1：需求覆盖完整性

**检查目标**：范围内每条需求条目是否都被用例覆盖，有无漏测。

| 检查点 | 检查方法 | 判为问题 |
|---|---|---|
| 条目正向覆盖 | 遍历《测试计划》的测试意图清单与需求条目编号，在用例集检索 | 有条目无用例（漏测） |
| 场景覆盖 | 按 6 大类逐类核对用例集「分类覆盖声明」 | 某类标「无」但理由不成立（实际有对应场景） |
| 等价类完备 | 逐字段 / 逐约束核对有效、无效等价类是否各有用例 | 某个有效或无效等价类**一条用例都没有**（整类漏测） |
| 状态流转覆盖 | 对带状态对象，核对状态机的合法与非法转移是否各有用例 | 只有合法转移、缺非法跳转（终态/不可达/乱序）用例 |
| 扩展覆盖 | 按 E1–E8 逐项核对 | 应覆盖项标「本版不适用」而无依据 |
| 边界覆盖 | 核对数值/长度/数量/时间/文件/集合约束是否取了边界值 | 有约束却无边界用例 |
| 异常覆盖 | 核对 PRD 声明的约束与错误处理是否都有用例 | 有约束却无异常用例 |

### 维度 2：追溯双向闭合

| 检查点 | 检查方法 | 判为问题 |
|---|---|---|
| 反向追溯（用例 → 需求） | 遍历每条用例的「来源需求」 | 来源缺失 / 指向不存在的条目（**孤儿用例**） |
| 编号规范 | 核对用例编号是否符合 `TC-{需求条目编号}-{序号}` | 编号重复、格式不合规、与来源不匹配 |
| 矩阵一致 | 比对追溯矩阵与用例正文 | 矩阵列出的用例与正文不一致（漏列/多列） |

### 维度 3：可执行性

| 检查点 | 检查方法 | 判为问题 |
|---|---|---|
| 步骤可观察 | 逐条读操作步骤 | 出现「检查系统是否正常」类不可执行/不可观察的步骤 |
| 前置明确 | 读前置条件 | 前置条件缺失或含糊（无法准备执行环境） |
| 有具体输入 | 读操作步骤 | 只有抽象动作，无具体输入数据 |
| 无技术实现语言 | 通读步骤 | 用「调用 X 接口 / 改 Y 表 / 加 Z 日志」等技术语言描述业务用例 |

### 维度 4：无歧义（预期结果可判定）

| 检查点 | 检查方法 | 判为问题 |
|---|---|---|
| 预期可判定 | 逐条读预期结果 | 出现「功能正常」「显示正确」「响应及时」等不可判定表述 |
| 三层覆盖 | 核对预期结果 | 缺页面表现 / 业务结果 / **数据落库状态**中应覆盖的层 |
| 单结论 | 核对每条用例的验证点 | 一条用例含多个可独立失败的验证点 |
| 量化 | 核对涉及性能/数量/时效的预期 | 应给具体数值与单位却只给定性描述 |

### 维度 5：分级正确性（优先级 + 执行分层）

| 检查点 | 检查方法 | 判为问题 |
|---|---|---|
| 双轴齐备 | 核对每条用例 | 只标优先级或只标分层（缺一即问题） |
| P 级正确 | 按 `./01-case-design-criteria.md §四` 核对 | P0 未覆盖核心业务路径/核心异常 |
| L 级正确 | 按 `§五` 核对 | **L1 不含 P0 主流程**（违反 `L1 ⊇ P0 主流程`）；异常用例被标为 L1 |
| 准入可用 | 核对 L1 用例集 | L1 无法独立构成「端到端正常主流程」的冒烟集合 |

### 维度 6：数据独立性

| 检查点 | 检查方法 | 判为问题 |
|---|---|---|
| 可构造 | 核对前置数据是否有构造入口与参数 | 依赖无法构造的数据 |
| 可清理 | 核对方案是否含清理方式 | 执行后残留脏数据，用例不可重复执行 |
| 无顺序依赖 | 通读用例集 | 依赖其它用例的残留或执行顺序 |
| 无历史依赖 | 通读用例集 | 依赖历史数据/环境既有状态 |

### 维度 7：自动化就绪

| 检查点 | 检查方法 | 判为问题 |
|---|---|---|
| 批次有序 | 核对自动化用例清单的转化批次 | 未按「先核心后边缘、先正向后反向」排序（如先转 L3 再转 L1） |
| 断言可自动判定 | 读自动化用例的断言 | 断言依赖人工判断 |
| 语义保留 | 读转化后的用例 | 退化为纯元素操作流水，丢失业务语义 |
| 入参可配置 | 核对参数化 | 环境/账号/数据硬编码 |

## 问题分级（统一严重度口径）

级别定义以 `polaris{{SKN_SPR}}maintance{{SKN_SPR}}codereview` 的 `references/review-rubric.md` §严重级别定义 为**唯一源**，本节按用例集的语境落地：

| 级别 | 在本语境下的含义 | 处理要求 |
|---|---|---|
| 🔴 **Critical** | 关键需求条目漏测、孤儿用例、追溯断裂、L1 准入集合不成立、预期结果整体不可判定——**不修复则用例集不可用于验收/准入** | **必须修复后才能放行 `ship`** |
| 🟠 **Major** | 场景覆盖缺口、边界/异常缺失、优先级或分层错标、数据不可构造、断言不可自动判定 | 建议在本次迭代内修复；不修复须在报告记录风险与接受理由 |
| 🟡 **Minor** | 表述可优化、颗粒度可调整、个别前置条件不够明确 | 建议修复，可排期 |
| 🔵 **Nit** | 编号格式、术语不统一、排版 | 可选，不强制 |

**级别定义不在此复制**——报告作附件/归档时按 `review-rubric.md` §严重级别定义 **原样引用**一节「级别图例」。

**编号**：问题统一用 `[F-n]` 按出现顺序自增，**不按级别分段**。

## 评审结论

| 结论 | 条件 | 含义 |
|---|---|---|
| **通过** | Critical = 0 | 用例集可用于验收与准入 |
| **有条件通过** | Critical = 0 且 Major > 0 | 带着 Major 清单跟踪，不阻断 |
| **不通过** | Critical > 0 | 阻断；须修复后重评审 |

## 重评审机制

1. **触发**：存在 Critical，或用户要求重评审
2. **范围**：**只重评修复项及其关联内容**，不重复评审已通过部分
3. **流程**：用户确认已修复 → 加载修复后的用例集 → 针对修复项定向复查 → 确认真正修复且未引入新问题 → 更新报告，记录重评审结果
4. **终止**：Critical 清零，或用户显式接受剩余风险（须留风险接受记录）
