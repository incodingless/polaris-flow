# 测试用例集独立评审

## 定位

对**已产出的测试用例集**做独立评审：覆盖是否完整、追溯是否双向闭合、用例是否可执行且无歧义、分级是否正确、数据是否独立、是否具备自动化就绪条件。产出**分级问题清单**与**可核对的评审报告**。

**核心原则**：

1. **只评不改**——本技能不修改任何文件，只输出问题与建议；
2. **生成与裁决分离**——评审在**独立上下文**执行（由 `refine` 派发的 subagent 承担），不是产生用例的人在同一个会话里自审；
3. **定位可核对**——每条问题必须给到用例编号或章节，禁止泛泛而谈。

<HARD-STOP>
1. ❌ 禁止在评审过程中修改任何文件（用例集、测试计划、PRD 都不改）
2. ❌ 禁止只给结论不给出问题位置与改进建议
3. ❌ 禁止泛泛而谈，如「覆盖不够全」而不说明缺哪条需求条目
4. ❌ 禁止不分级——所有问题必须明确 Critical / Major / Minor / Nit
5. ❌ 禁止跳过任何维度——7 个维度必须全部执行；输入不足以执行某项时**显式标注「无法执行 + 原因」**，不得静默跳过
6. ❌ 禁止把个人偏好当问题——必须基于判据的客观标准
7. ❌ 禁止臆测需求——用例集未覆盖某场景时，须回 PRD 确认该场景确实存在才算漏测；PRD 未声明的不算问题
</HARD-STOP>

## 触发与输入

| 触发 | 输入 | 落盘 |
|---|---|---|
| **① 链上派发**（主路径，`refine` Step 6） | 派发方在 `materials` 中给定：用例集四份全文 + `testcase_plan.md` + 定稿 PRD（可选）+ 本技能 SKILL.md 路径 | `constraints.output_path`（`.polaris/testcases/<task_id>/testcase-review-report.md`）——**只回报路径，禁止把报告正文贴回** |
| **② 独立调用**（flow「测试」类 T03 / 用户直接要求） | 用户指定的**既有用例集**（可以是本任务，也可以是别处文档）；可选：需求文档作覆盖判据 | 与用例集同目录，或用户指定路径 |

**缺输入时不得凭印象评审**：链上派发缺 PRD 时，覆盖类问题降级为「无法执行」（须标注）；独立调用无用例集时阻断并要求给出路径。

## 流程

Step 0 触发判定与输入加载 > Step 1 七维度逐项评审 > Step 2 问题分级与统计 > Step 3 覆盖与追溯核对 > Step 4 报告输出与重评审机制

### Step 0：触发判定与输入加载

#### 0.1 判定触发通道

- 由 `refine` Step 6 派发（材料已在 prompt 中给定）→ **链上模式**：不再向用户提问（subagent 是非交互的），评审范围取派发方 `constraints` 的给定值，缺省**全量**
- 用户独立调用 → **独立模式**：进入 0.3 的范围询问

#### 0.2 加载评审对象

**链上模式**：从 `materials` 读四份用例产物（`test-cases.md` + `test-cases-nonfunctional.md` + `test-cases-interface.md` + `test-cases-automation.md`）、`testcase_plan.md`（覆盖判据）、PRD（取证源）。

**独立模式**：确认用户给出的用例集路径并完整读取；询问是否有配套的《测试计划》或 PRD 可作覆盖判据——**有则读、无则覆盖类维度标「无法执行」并说明**。

**加载失败处理**：文件不存在 / 不可读 → 明确回报是哪一份、为什么，**不得静默跳过**。

#### 0.3 评审范围确认（仅独立模式 · 阻塞点）

按 `./policies/decision-point.md` 暂停、按 `./policies/ask-question-react.md` 询问一次：

> 请确定本轮的**评审范围**：
> A. 全量评审（全部维度 + 全部用例）
> B. 指定模块 / 指定需求条目
> C. 指定维度（如只看「覆盖」与「追溯」）

推荐项只作说明，**不得代选**。

#### 0.4 初始化问题记录结构

每条问题字段：`编号 [F-n]` / `级别` / `维度` / `位置` / `现象` / `触发条件` / `后果` / `修复建议`。编号 `[F-n]` 按**出现顺序**自增，不按级别分段。

### Step 1：七维度逐项评审

按 `./references/01-review-criteria.md` §评审维度 逐维度执行，**不得跳过任何维度**。每维度发现问题立即记录，全部检查**必须定位到具体用例编号或章节**。

| # | 维度 | 一句话 |
|---|---|---|
| 1 | 需求覆盖完整性 | 范围内每条需求条目是否都有用例；6 大类、等价类、状态流转、E1–E8 是否逐类落实 |
| 2 | 追溯双向闭合 | 有无孤儿用例；编号是否规范；矩阵与正文是否一致 |
| 3 | 可执行性 | 步骤可观察、前置明确、有具体输入、无技术实现语言 |
| 4 | 无歧义 | 预期结果可判定、三层覆盖、单结论、可量化 |
| 5 | 分级正确性 | 双轴齐备、P 级正确、L 级正确（`L1 ⊇ P0 主流程`）、L1 准入集合成立 |
| 6 | 数据独立性 | 可构造、可清理、无顺序依赖、无历史依赖 |
| 7 | 自动化就绪 | 批次有序、断言可自动判定、语义保留、入参可配置 |

**场景枚举反查**：维度 1 必须按 6 大类与 E1–E8 **逐类反查**用例集的「分类覆盖声明」——用例集声明「无」的，评审要核对该理由是否成立（如声明「本需求无外部依赖」，但 PRD 里明确有第三方调用，则属漏测）。

### Step 2：问题分级与统计

按 `./references/01-review-criteria.md` §问题分级 落级（🔴 Critical / 🟠 Major / 🟡 Minor / 🔵 Nit），并统计：

- 按维度统计问题数
- 按级别统计问题数

**结论判定**：

| 结论 | 条件 |
|---|---|
| 通过 | Critical = 0 |
| 有条件通过 | Critical = 0 且 Major > 0 |
| 不通过 | Critical > 0 |

### Step 3：覆盖与追溯核对

产出两张核对表（格式见报告模板 §五）：

1. **覆盖与追溯核对表**：逐条需求条目 → 是否有用例 → 判为问题
2. **场景覆盖核对表**：6 大类 + E1–E8 逐项 → 用例集声明 vs 评审核对 → 结论

### Step 4：报告输出与重评审机制

**必读**（强制前置）`read_file ./templates/review-report-template.md`，按其章节与表格结构输出（**不得增删章节**）。

- **链上模式**：写入 `constraints.output_path`，**回报只给路径**
- **独立模式**：与用例集同目录，或用户指定路径；用户要求「仅会话内输出」时按其要求

**重评审机制**（触发①时由 `refine` 驱动）：

1. 触发：存在 Critical，或用户要求重评审
2. 范围：**只重评修复项及其关联内容**，不重复评审已通过部分
3. 流程：用户确认已修复 → 加载修复后的用例集 → 针对修复项定向复查 → 确认真正修复且未引入新问题 → 更新报告第六节
4. 终止：Critical 清零，或用户显式接受剩余风险

## 阻塞点

| 场景 | 处理 |
|---|---|
| 独立模式下未给出用例集路径 | 按 `./policies/decision-point.md` 询问，不得猜测对象 |
| 评审对象不可读 / 为空 | 明确回报是哪一份、原因；阻断，不臆测内容 |
| 链上派发缺 PRD（覆盖类判据缺失） | 覆盖类维度标「无法执行 + 原因」，**其余维度照常执行**，不整体阻断 |
| 用例集本身处于「多分支未定」状态 | 不阻断，但须在报告中标注「评审时用例集尚未定版」 |

## 退出条件

1. 7 个维度**全部执行**（无法执行的已显式标注原因）；
2. 每条问题均已分级、均已给出可核对定位与改进建议；
3. 报告已按模板落盘，且**明确标注了执行者**（独立 subagent / 主代理内联降级）与**评审标识**（触发①/②）；
4. 覆盖与追溯两张核对表已产出。

未同时满足四条，不得宣告评审完成。

## 上下文压缩恢复

**Step 0–4 是原子流程**（触发判定与加载 → 七维度评审 → 分级统计 → 报告输出），中间**不设恢复点**：中断即从 Step 0 重跑，不要试图「接着上一轮评到哪个维度往下评」。

- 报告已落盘、且被评用例集的指纹未变 → **不重跑**，直接进入「重评审机制」；
- 被评用例集已变 → **必须重跑**全量 7 维度（局部重评只适用于「修复后定向复查」，见重评审机制第 2 条）；
- 恢复依据是**落盘报告**与用例集指纹，不依赖会话记忆 —— 本技能可在任意新会话中接续。
- 「压缩上下文」与「恢复清单」的用词、提示语模板见 `./policies/auto-transition.md` 的「压缩时机与恢复清单」。

> **本技能无「自动衔接下一阶段」章**：它是**服务型技能**——不推进 workflow 游标、不写 `phase`、不登记为阶段。链上由 `refine` Step 6 派发，独立由 flow 的 T03 进入；两种情况都**不产生后续阶段衔接**。
