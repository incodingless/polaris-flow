# 测试用例设计判据（testing 族唯一源）

> 归属：`polaris{{SKN_SPR}}testing` 族。**两个读者**：① `draft` 用来写功能用例集；② `review` 用同一套语言**反查**用例集是否完整（事前枚举 + 事后审计闭环）。
> **边界**：本文档面向**需求级功能用例**（从 PRD 需求条目出发的验证视角）。**代码级单元测试**的场景枚举在 `polaris{{SKN_SPR}}coding{{SKN_SPR}}tasks` 的 `references/test-case-checklist.md`（6 大类），二者**不重合**——本文档 §二 的「需求级扩展表」逐条映射回那 6 大类，并显式标出 6 大类**未覆盖**的项。两套语言互为落点，不互相替代。

---

## 一、场景分类：6 大类（唯一分类语言）

分类语言的**唯一源**是 `polaris{{SKN_SPR}}coding{{SKN_SPR}}tasks` 的 `references/test-case-checklist.md`，本节不复述其定义，只声明**消费方式**：

| 分类 | 需求级落点示例 |
|---|---|
| 正常路径 | PRD 功能点的主流程 + 验收标准 |
| 边界值 | 数值/长度/数量/时间/文件/集合的临界与越界 |
| 异常输入 | 必填缺失、格式错误、非法枚举值 |
| 依赖异常 | 外部系统超时/返回错误/降级 |
| 状态校验 | 非法状态下操作、状态流转冲突 |
| 幂等/并发 | 重复提交、并发修改、竞态 |

**状态校验的建模法**：带状态的对象先建**状态转移表**再出用例，别凭印象挑几个状态。

| 当前状态 | 触发动作 | 目标状态 | 合法性 |
|---|---|---|---|
| … | … | … | 合法 / 非法 |

- **合法转移** → 出「正常路径」用例；
- **非法转移**（目标态不可达 / 已是终态 / 前置未满足 / 乱序提交）→ 出「状态校验」或「异常输入」用例；
- 合法与非法转移**各至少覆盖一次**；状态集合与转移规则取自 PRD 的状态流转描述，PRD 未声明的不臆造。

**适配规则（按被测对象裁剪，不硬强制 6 类）**：无对应场景**必须显式标「无」**，不得静默跳过——这是 `review` 判「漏测」与「本就不适用」的唯一依据。

## 二、需求级扩展表（逐条映射回 6 大类）

PRD 里有一批业务级场景在 6 大类中**没有直接落点**。本文档为它们建扩展项，并逐条给出映射，避免读者误以为漏了。

| # | 需求级场景 | 映射落点（6 大类） | 6 大类是否原生覆盖 | 归属阶段 |
|---|---|---|---|---|
| E1 | **权限异常**（未登录 / 无权限 / 权限过期 / 越权访问） | 异常输入 ∪ 状态校验 | ❌ 未覆盖**角色-资源越权**语义 | `draft` |
| E2 | **业务规则违例**（额度 / 次数 / 时效 / 配额限制） | 异常输入 | ❌ 未覆盖「业务规则」而非「入参格式」 | `draft` |
| E3 | **操作时序错误**（前置未完成即操作、乱序提交） | 状态校验 | ⚠️ 部分（仅覆盖对象状态，不覆盖流程时序） | `draft` |
| E4 | **数据不存在 / 数据冲突 / 重复提交** | 异常输入 ∪ 幂等/并发 | ⚠️ 部分 | `draft` |
| E5 | **弱网 / 中断 / 超时**（用户侧网络中断、请求重试） | 依赖异常 | ❌ 未覆盖**用户侧链路**（6 大类只覆盖服务端外部依赖） | `draft` |
| E6 | **落库一致性 / 事务回滚**（多步操作的原子性、部分失败回滚） | — | ❌ **无落点** | `draft`（穿透） |
| E7 | **性能阈值**（响应时间 / TPS / 并发量） | — | ❌ **无落点** | `refine` |
| E8 | **安全**（注入 / XSS / 越权 / 敏感数据脱敏 / 重放） | — | ❌ **无落点** | `refine` |

**硬规则**：E6–E8 属深层与专项验证，**不在 `draft` 的功能用例集里硬凑**；E6 可在 `draft` 以 L4 穿透用例承载，E7/E8 一律归 `refine`（清单引用 `polaris{{SKN_SPR}}maintance{{SKN_SPR}}codereview` 的 `references/security-checklist.md`，本族不重写安全清单）。

**反向要求**：6 大类中若有某一类在需求级无对应场景，**必须显式写「无」**并说明理由（如「本需求无外部依赖」）；扩展表 E1–E8 亦同——不适用的写「本版不适用」，不得留空。

## 三、用例字段（每条必填）

| 字段 | 要求 |
|---|---|
| 用例编号 | `TC-{需求条目编号}-{两位序号}`，如 `TC-UAP-F01-01-01`、`TC-F3-07-01` |
| 用例标题 | 「条件 + 动作 + 预期」句式，一眼看懂验证什么 |
| 来源需求 | 追溯到 PRD 需求条目编号（功能点 / 业务规则） |
| 场景分类 | 6 大类之一；或扩展表 `E#`（须同时标注映射的 6 大类） |
| 优先级 | `P0` / `P1` / `P2`（§四） |
| 执行分层 | `L1`–`L4`（§五） |
| 前置条件 | 执行前必须满足的数据、权限、环境状态（可构造、可清理，见 §六） |
| 操作步骤 | 编号步骤，每步一个**可观察**动作，含具体输入数据 |
| 预期结果 | 可判定的具体结果：页面表现 + 业务结果 + **数据落库状态**三层 |

**句式**：统一「给定[条件]，当[执行操作]时，应[预期结果]」，可映射 AAA。预期结果**禁止**「功能正常」「显示正确」类模糊表述。

## 四、优先级（唯一优先级轴）

定义与 `polaris{{SKN_SPR}}coding{{SKN_SPR}}tasks` 的 `references/test-case-checklist.md` §三**同源**，本族直接沿用：

| 级别 | 定义 |
|---|---|
| **P0** | 核心业务路径、核心异常、主校验规则；不通过则功能不可用 |
| **P1** | 全部分支异常、全部边界值、状态流转；不通过则存在质量风险 |
| **P2** | 极端输入、非核心规则、小众异常；不影响主流程可用性 |

## 五、执行分层（L1–L4）与准入闸门

**定位**：分层**不是第二条优先级轴**，而是**执行批次 / 准入视图**——回答「按什么顺序跑、跑到什么程度算准入」。

| 层级 | 名称 | 内容 | 执行语义 |
|---|---|---|---|
| **L1** | 主流程（冒烟准入级） | 模块核心业务链路的端到端正常主流程，无分支、无异常 | **准入闸门**：L1 100% 通过才可进入后续测试，否则版本打回 |
| **L2** | 旁支正常流程（功能验证级） | 全部正常业务分支、可选操作、不同入口的正向场景 | 版本集成测试的常规批次 |
| **L3** | 异常流程（边界校验级） | 全部异常分支：参数异常、边界极值、业务规则违例、时序错误、依赖异常 | 质量把关批次 |
| **L4** | 深度穿透（质量兜底级） | 底层逻辑：落库一致性/事务、并发、日志链路、隐含规则、边界性能点 | 按风险选择性执行 |

**与 P 级的映射（写死，避免两套刻度打架）**：

- `L1 ⊇ P0 主流程`：所有 P0 的**主流程**用例必属 L1；P0 的异常用例可落在 L3。
- L2/L3 覆盖 P1 全集；L4 覆盖 P2 中的穿透型用例。
- **准入门禁只认 L1**；P 级只用于排序与取舍，**不承担门禁语义**（这是 L1-L4 与 P 级各自的独有价值，二者不可互相替代）。

## 六、数据独立性

- 前置数据**可构造**：给出构造入口（脚本路径 / SQL / 接口）与参数
- 前置数据**可清理**：给出清理方式，保证用例可重复执行
- 用例**不依赖历史数据**、**不依赖执行顺序**、**不依赖其它用例的残留**
- 需要 mock/桩的依赖，在用例内声明 mock 行为
- **命名规范**：正常数据 `{字段}_valid_{序号}`、异常数据 `{字段}_invalid_{序号}`、边界数据 `{字段}_boundary_{类型}`、唯一性数据 `{字段}_unique_{序号}`；同一用例内前缀一致，便于回查与清理

## 七、追溯矩阵（双向）与覆盖校验

**双向**：

- 正向（需求 → 用例）：每条需求条目至少 1 条用例；无用例的条目给出原因
- 反向（用例 → 需求）：每条用例都必须有来源需求条目编号；**无来源的用例即孤儿用例，必须删除或补来源**

| 需求条目编号 | 需求名称 | L1 | L2 | L3 | L4 | 覆盖状态 |
|---|---|---|---|---|---|---|
| UAP-F01-01 | 载体创建 | TC-…-01 | TC-…-02 | TC-…-03/04 | — | 完整 |

**覆盖校验（`draft` 自检 + `review` 反查共用）**：

| 校验项 | 通过标准 |
|---|---|
| 需求覆盖率 | 有验收标准的需求条目 100% 至少 1 条用例 |
| 场景覆盖 | 6 大类逐类过一遍；不适用者显式标「无」 |
| **等价类完备** | 每个**有效**等价类、每个**无效**等价类**各 ≥1 条**用例（无对应类时显式标「无」） |
| 扩展覆盖 | E1–E8 逐项声明「已覆盖 / 本版不适用」 |
| 优先级分布 | P0 覆盖全部核心主流程与核心异常 |
| 孤儿用例 | 0 条 |
| 数据独立 | 全部用例前置数据可构造、可清理 |

> **等价类**（本族**只取完备性判据，不展开划分法**）：有效等价类＝符合需求规则的输入集合，无效等价类＝不符合的。逐字段/逐约束确认「每个类都至少落一条用例」，防止整类漏测（如「负数」整类一条都没有）。

## 八、反模式（禁止）

| # | 反模式 | 正确做法 |
|---|---|---|
| 1 | 一条用例塞多个验证点 | 场景级粒度，一条用例一个可判定结论 |
| 2 | 预期结果写「功能正常」 | 给出具体文案、状态变化、落库结果 |
| 3 | 只写正常场景 | 6 大类逐类过，不适用者标「无」 |
| 4 | 需求没写的行为也设计用例 | 只基于 PRD 显式声明设计；发现缺失反馈用户补需求 |
| 5 | 用技术实现语言描述步骤 | 用用户可观察的操作与结果描述 |
| 6 | 用例无法追溯来源 | 每条标注来源需求条目编号，输出追溯矩阵 |
| 7 | 把 E7/E8（性能/安全）硬塞进功能用例集 | 归 `refine` 的专项用例，用各自的阈值与清单 |
