# 产品需求业务评审技能

## 定位

对产品需求文档执行系统化、多维度的业务评审，识别需求中的问题、风险与歧义，输出分级问题清单与可操作的评审报告。

**核心原则**：只评审不修改，问题必须分级，所有发现必须有明确的位置定位与改进建议。

<HARD-STOP>
1. ❌ 禁止只给结论不给出问题位置和改进建议
2. ❌ 禁止泛泛而谈，如"需求不够详细"而不说明具体哪里不详细
3. ❌ 禁止将个人偏好作为问题，必须基于评审维度的客观标准
4. ❌ 禁止跳过任何维度（无Baseline时维度7可标记为无法执行，但必须说明）
5. ❌ 禁止不分级，所有问题必须明确 P0/P1/P2/P3 等级
6. ❌ 禁止在评审过程中直接修改文档，评审只输出问题与建议
7. ❌ 禁止将技术实现细节的缺失作为问题（如"未说明用什么框架"），PRD不负责技术方案
</HARD-STOP>

## 输入
- 待评审的产品需求文档
- Baseline 需求基线（用于双向一致性检查，可选但强烈建议）

## 评审总流程

Step1 输入加载与评审范围确认 > Step2 多维度逐项评审 > Step 3 问题汇总与分级 > Step 4 评审报告输出与重评审机制

## Step 1 — 输入加载与评审范围确认

1.1 **加载待评审文档**
   - 完整读取 PRD 文档，按章节建立索引
   - 识别文档类型（初稿/终稿）与章节结构

1.2 **加载 Baseline（如有）**
   - 读取需求基线，逐条拆解需求项并分配 ID
   - 建立基线需求索引，用于维度7的双向一致性检查

1.3 **确认评审范围**

**一次性**按 `./policies/decision-point.md` 询问。推荐规则**只能说明，不能代选**。

> 请确定**审查**的范围：
> A. 全量审查
> B. 指定章节审查

根据用户选择，处理：
- A：全量审查 ，进入Step 1
- B：指定章节审查，列出章节作为选项要求用户选择（多选），选项格式为：<章节号>.<章节名称>。

1.4 写入 `state.yaml`：`build.build_mode: <subagent_dispatch|inline>`。

1.5 **初始化问题记录结构**
   - 每条问题记录字段：问题ID、所属维度、问题标题、问题描述、文档位置（章节+锚点）、问题等级、改进建议、影响范围

## Step 2 — 7维度逐项评审

> 每维度独立执行检查，发现问题立即记录。所有检查必须定位到具体章节/段落，禁止泛泛而谈。

### 维度1：业务一致性

**检查目标**：PRD 内容与业务目标、用户需求、业务场景是否一致，有无偏离业务初衷。

**检查项**：

| 检查点 | 检查方法 | 问题判定标准 |
|---|---|---|
| 业务目标对齐 | 对比第1章业务背景/核心目标与第5章功能需求 | 功能需求无法支撑业务目标，或业务目标无对应功能实现 |
| 用户场景覆盖 | 对比第3章业务场景与第5章功能点 | 核心业务场景无对应功能实现，或功能点无对应业务场景 |
| 角色职责一致 | 对比第3.1节角色定义与各功能点的操作角色 | 功能点中出现未定义的角色，或角色权限与定义矛盾 |
| 业务价值可追溯 | 检查每个功能模块是否有明确的业务价值说明 | 功能模块无业务价值说明，或价值描述与实际功能不符 |
| 术语一致性 | 全文扫描业务术语使用 | 同一业务概念在不同章节使用不同术语，或术语定义与使用不一致 |

**常见问题示例**：
- 业务目标提到"提升审批效率"，但功能需求中无审批时效相关的功能或规则
- 角色定义中有"审计员"，但所有功能点的操作角色中均未出现审计员
- 第3章称"载体流转"，第5章称"载体变动"，实际指同一业务概念

### 维度2：范围完整性

**检查目标**：Baseline 中的所有需求是否在 PRD 中完整覆盖，PRD 中是否有超出 Baseline 的需求蔓延。

**检查项**：

| 检查点 | 检查方法 | 问题判定标准 |
|---|---|---|
| 基线需求正向覆盖 | 遍历 Baseline 每项需求，在 PRD 中检索对应描述 | Baseline 需求在 PRD 中无对应描述（遗漏） |
| PRD需求反向追溯 | 遍历 PRD 每个功能点，在 Baseline 中检索来源 | PRD 功能点在 Baseline 中无来源（需求蔓延） |
| 功能点完整性 | 检查第5章每个功能点的五要素（前置条件/业务逻辑/约束规则/UI交互/验收标准） | 功能点缺少必要要素，或要素描述为空 |
| 模块覆盖完整 | 检查第5章功能模块是否覆盖第3章所有业务场景 | 业务场景无对应功能模块 |
| 异常场景覆盖 | 检查各功能点的异常处理描述 | 关键异常场景无处理逻辑，或异常处理不完整 |
| 边界条件覆盖 | 检查业务规则中的边界条件 | 规则缺少边界条件定义（如最大值、最小值、空值处理） |

**常见问题示例**：
- Baseline 提到"支持批量导入"，但 PRD 中无批量导入功能描述
- PRD 中出现"数据导出"功能，但 Baseline 中无此需求
- 功能点只有业务逻辑，缺少验收标准

### 维度3：逻辑自洽性

**检查目标**：PRD 内部的业务流程、规则、状态流转是否无矛盾、闭环完整。

**检查项**：

| 检查点 | 检查方法 | 问题判定标准 |
|---|---|---|
| 流程闭环 | 检查第3章业务总流程的起点与终点 | 流程无明确起点或终点，或流程中断无后续处理 |
| 状态流转一致 | 对比第7章状态流转规范与第5章功能点中的状态变更 | 功能点中的状态变更与状态流转规范矛盾，或出现未定义的状态 |
| 规则无矛盾 | 交叉对比第6章业务规则与各功能点约束规则 | 同一业务场景在不同章节有矛盾的规则描述 |
| 数据一致性 | 检查第4章数据模型与第5章业务逻辑中的数据操作 | 业务逻辑中操作了数据模型中不存在的字段，或字段类型与业务逻辑不符 |
| 角色权限一致 | 对比第3.1节角色权限与功能点中的操作权限 | 功能点允许角色执行未授权的操作，或禁止角色执行已授权的操作 |
| 事务边界清晰 | 检查多步骤业务逻辑的事务边界 | 多步骤操作无事务原子性说明，失败回滚逻辑不明确 |
| 并发处理 | 检查高并发场景的处理逻辑 | 并发场景无锁机制、幂等性或冲突处理说明 |

**常见问题示例**：
- 状态流转规范定义"已回收"为终态不可回退，但某功能点描述"已回收载体可恢复为在用"
- 业务规则说"载体创建后编号不可修改"，但某功能点的UI交互中有"编辑编号"按钮
- 多步骤操作（如创建主载体+批量生成子载体+写入生命周期记录）无事务说明，部分失败如何处理不明确

### 维度4：规则明确性

**检查目标**：所有业务规则是否明确、无歧义、可量化、可验证。

**检查项**：

| 检查点 | 检查方法 | 问题判定标准 |
|---|---|---|
| 无模糊表述 | 全文扫描模糊词汇 | 出现"大概"、"可能"、"尽量"、"较快"、"较好"等不可量化的模糊表述 |
| 规则可判定 | 检查每条业务规则是否有明确的通过/失败条件 | 规则无法判断是否满足（如"系统应快速响应"无具体时间指标） |
| 条件完整 | 检查规则的触发条件 | 规则缺少触发条件、前置条件或例外情况说明 |
| 枚举完整 | 检查状态枚举、类型枚举的定义 | 枚举值不完整，或业务逻辑中出现未定义的枚举值 |
| 默认值明确 | 检查数据模型和业务规则中的默认值 | 关键字段无默认值说明，或默认值与业务逻辑不符 |
| 计算逻辑清晰 | 检查涉及计算的业务规则 | 计算公式不完整、参数来源不明确、舍入规则未定义 |
| 时效可量化 | 检查时效相关规则 | 时效要求无具体时间单位或数值（如"及时处理"无具体时长） |

**常见问题示例**：
- "系统应在较短时间内返回查询结果" — 无具体时间指标
- "审批通过后更新订单状态" — 未说明更新为什么状态、谁来更新、失败如何处理
- "按优先级排序" — 未说明优先级的定义、相同优先级如何排序
- "支持大量数据批量处理" — 未说明"大量"的具体量级

### 维度5：可实现性

**检查目标**：需求方案在现有技术架构、资源约束、第三方依赖下是否可落地。

**检查项**：

| 检查点 | 检查方法 | 问题判定标准 |
|---|---|---|
| 技术架构兼容 | 对比系统架构概述与功能需求 | 功能需求与现有技术架构冲突，或需要未规划的架构改造 |
| 第三方依赖明确 | 检查涉及外部系统集成的功能 | 第三方依赖未说明、接口能力未确认、SLA未定义 |
| 性能可达成 | 对比第8章性能需求与系统现有能力 | 性能指标超出系统现有能力，且无性能优化方案 |
| 数据可获取 | 检查功能需求中的数据来源 | 功能依赖的数据无法从现有系统获取，或数据质量无法保证 |
| 工作量合理 | 评估功能复杂度与交付周期 | 功能复杂度过高，在既定交付周期内无法完成（需结合团队产能判断） |
| 技术风险识别 | 检查是否有未识别的技术风险 | 高风险功能无风险说明、无备选方案、无降级策略 |
| 依赖关系清晰 | 检查功能模块间的依赖关系 | 存在循环依赖、依赖未排序、前置依赖未明确 |

**常见问题示例**：
- 需求要求"实时同步数据到第三方系统"，但第三方系统只提供批量接口，无实时推送能力
- 性能要求"万级并发下响应时间<1秒"，但现有系统架构为单体应用，无分布式扩展能力
- 功能依赖"用户画像数据"，但用户画像系统尚未建设，数据来源不明确

> 注：本维度评审需要一定的技术背景。如评审者无技术能力，可将本维度问题标记为"待技术确认"，归入待确认事项。

### 维度6：合规性

**检查目标**：需求是否符合权限管理、数据安全、行业监管、审计要求等合规约束。

**检查项**：

| 检查点 | 检查方法 | 问题判定标准 |
|---|---|---|
| 权限控制完整 | 检查第3.1节角色权限与功能点的权限要求 | 敏感操作无权限控制、权限粒度过粗、越权风险未识别 |
| 数据安全 | 检查敏感数据的处理逻辑 | 敏感数据（身份证、手机号、涉密信息等）无加密、脱敏、访问控制说明 |
| 审计留痕 | 检查关键操作的审计记录要求 | 关键操作（删除、修改、权限变更、数据导出）无审计留痕要求 |
| 数据保留 | 检查数据保留与删除规则 | 数据保留周期未定义、删除方式（物理/逻辑）未说明、历史数据归档策略缺失 |
| 行业合规 | 检查是否符合行业监管要求 | 涉密系统无密级管理、金融系统无交易留痕、医疗系统无隐私保护等 |
| 操作可追溯 | 检查状态变更与数据修改的追溯能力 | 关键状态变更无操作人、操作时间、变更原因记录 |
| 导出控制 | 检查数据导出功能的安全控制 | 数据导出无审批、无水印、无导出记录、无敏感字段过滤 |

**常见问题示例**：
- "管理员可删除任意载体记录" — 无删除审批、无操作留痕、无数据恢复机制
- "支持导出全量用户数据" — 无导出审批流程、无敏感字段脱敏、无导出记录
- 状态流转只有状态变更，无变更原因、操作人、操作时间记录

### 维度7：基线双向一致性

**检查目标**：确保 PRD 与 Baseline 之间的双向追溯完整，无遗漏、无蔓延。

> 本维度需要 Baseline 作为输入。如无 Baseline，本维度标记为"无法执行"并在报告中说明。

**检查项**：

| 检查点 | 检查方法 | 问题判定标准 |
|---|---|---|
| 正向覆盖（Baseline→PRD） | 遍历 Baseline 每项需求，在 PRD 中检索对应描述 | Baseline 需求在 PRD 中无对应描述（遗漏） |
| 反向追溯（PRD→Baseline） | 遍历 PRD 每个功能点，在 Baseline 中检索来源 | PRD 功能点在 Baseline 中无来源（需求蔓延） |
| 需求意图一致 | 对比 Baseline 需求描述与 PRD 对应描述 | PRD 描述偏离 Baseline 需求意图，或过度解读/解读不足 |
| 优先级一致 | 对比 Baseline 优先级与 PRD 功能清单优先级 | PRD 中优先级与 Baseline 不一致且无变更说明 |
| 范围边界一致 | 对比 Baseline 包含/不包含范围与 PRD 第1.3节 | PRD 范围边界与 Baseline 不一致 |
| 变更可追溯 | 检查 PRD 中与 Baseline 不一致的内容 | 有变更但无变更原因、变更审批记录 |

**输出**：基线追溯矩阵
| 基线需求ID | 需求描述 | PRD对应章节 | 覆盖状态 | 一致性评价 |
|---|---|---|---|---|
| BL-001 | xxx | 第5.2节 | ✅已覆盖 | ✅一致 |
| BL-002 | xxx | — | ❌遗漏 | — |

## Step 3 — 问题汇总与分级

### 问题等级定义

| 等级 | 定义 | 处理要求 | 示例 |
|---|---|---|---|
| **P0 阻塞** | 影响业务逻辑正确性、范围完整性、可实现性的核心问题，不修复则需求无法进入开发 | 必须修复后才能定稿，修复后重新评审 | 核心业务场景遗漏、状态流转矛盾、关键规则缺失、与基线严重不一致 |
| **P1 重要** | 影响需求质量、可测试性、可维护性的问题，不修复会导致开发误解或测试遗漏 | 建议修复，如不修复需在评审报告中记录风险与接受理由 | 规则模糊、异常处理不完整、验收标准缺失、术语不一致 |
| **P2 一般** | 表述优化、格式规范、建议类问题，不影响需求核心逻辑 | 可选择性修复，不阻塞定稿 | 错别字、格式不统一、表述可优化、建议补充说明 |
| **P3 待确认** | 需要业务方或技术方决策的问题，当前无法判断是否为问题 | 列入待确认事项，明确决策人与决策时间 | 技术可行性待确认、业务规则待业务方决策、第三方依赖待确认 |

### 汇总统计

- 按维度统计问题数量：每个维度各多少个问题
- 按等级统计问题数量：P0/P1/P2/P3 各多少个
- 生成问题分布矩阵：维度×等级的交叉统计

### 报告双视图说明

报告采用「检查过程视图」（七维度发现问题明细）和「处理决策视图」（P0~P3分级清单）双视图呈现同一批问题。检查过程视图按维度组织，便于评审者回溯每个检查点发现了什么；处理决策视图按等级组织，便于产品方按优先级处理。两视图问题ID一一对应、完全一致。

### 问题ID链接规则

为保证两视图间可追溯，输出报告时必须为问题ID建立锚点链接：

- **锚点定义**：在七维度发现问题明细表中，每条问题的「问题ID」单元格内定义锚点，格式 `<a id="{问题ID小写}">{问题ID}</a>`，如 `<a id="d1-001">D1-001</a>`
- **链接指向**：在分级问题清单（P0~P3）中，每条问题的「问题ID」单元格输出为内联链接，格式 `[{问题ID}](#{问题ID小写})`，如 `[D1-001](#d1-001)`
- **锚点ID规则**：统一用问题ID的小写形式作为锚点ID（如 `d1-001`），兼容主流 markdown 渲染器
- **配对要求**：每条问题必须在两处同时出现且配对完整，新增问题时两处同步更新

### 重评审机制

1. **触发条件**：存在 P0 阻塞问题，或用户要求重评审
2. **重评审范围**：仅评审修复的问题及其关联内容，不重复评审已通过部分
3. **重评审流程**：
   - 用户确认问题已修复
   - 加载修复后的文档
   - 针对修复的问题执行针对性检查
   - 确认问题是否真正修复，有无引入新问题
   - 更新评审报告，记录重评审结果
4. **迭代终止条件**：P0 阻塞问题清零，或用户确认接受剩余风险
