# 编写产品需求-编写PRD终稿

基于已人工确认的 PRD 初稿，一次性补全终稿全部章节并执行完整评审，输出可交付的正式需求文档。

**核心设计思路**：严格模板对齐 + 一次性补全 + 完整评审 + L2代码验证

**与初稿（pm-prd-draft）的边界**：
| 维度 | 初稿（draft） | 终稿（final，本技能） |
|---|---|---|
| 定位 | 迭代工作稿 | 正式交付文档 |
| 章节 | 5章轻量结构 | 严格模板10章+附录完整结构 |
| 目标 | 需求逻辑完整表达，减少人工审核量 | 可交付、可评审、可执行的完整需求文档 |
| 评审 | 不执行完整评审 | 执行7维度+可测性双维度完整评审 |
| 输入 | Baseline | 初稿 + Baseline + coding-knowledge |

<HARD-STOP>

- **本技能输出的终稿必须严格遵循 `./templates/prd-template.md` 的标准结构，禁止偏离。**
- ❌ 禁止使用「通用能力层+业务场景层」替代模板的「模块→功能点」结构（第5章必须按模板重构）
- ❌ 禁止省略术语定义（第2章）、业务规则汇总（第6章）、状态流转规范（第7章）、非功能需求（第8章）四个模板强制章节
- ❌ 禁止数据模型章节（第4章）不使用模板标准四列表格（字段名/数据类型/必填/业务规则说明）
- ❌ 禁止功能点不包含模板规定的五要素（前置条件/业务逻辑/约束规则/UI交互说明/验收标准）
- ❌ 禁止状态枚举（第2章、第7章）不标注中间态/终态属性
- ❌ 禁止在终稿阶段修改初稿已确认的核心业务逻辑与范围；如需修改必须走正式变更确认流程
- ❌ 禁止脱离 Baseline 凭空新增需求项；所有终稿内容必须有明确的 Baseline 来源并纳入追溯矩阵
- ❌ 禁止 L2 验证阶段编造代码细节；数据模型与接口契约的字段、枚举、默认值必须来自真实 coding-knowledge
- ❌ 禁止跳过模板一致性终检直接定稿；禁止跳过评审直接定稿
- ❌ 禁止终稿中出现模糊、不可量化的业务规则表述
- ❌ 禁止评审环节省略任意维度；7维度业务评审+可测性检查必须全覆盖
</HARD-STOP>

**技能总流程**: S0 状态检查与中断恢复 > S1 输入加载与分析 > S2 逐章补全生成 > S3 完整评审 > S4 定稿输出

### Step 0：状态检查与中断恢复

```bash
TASK_IDS=$(bash "$PLUGIN_ROOT/scripts/workflow-entry.sh" get-active-changes --skill build --repo-root "$REPO_ROOT" --phase build)
EXIT_CODE=$?
```

- `EXIT_CODE != 0` → **阻断**，按 stderr 处理
- `EXIT_CODE == 0` → `$TASK_IDS` 形如 `["id-a","id-b"]`（可能为 `[]`）

按 `$TASK_IDS` 数组长度解读：

- **唯一匹配**：直接读取 `change_id`
- **多个匹配**：按 `./policies/decision-point.md` 列出候选让用户选择
- **零匹配**：阻断，提示「未找到 draft 阶段的 active change，请先执行 /polaris-flow{{SKILL_NAME_SPLITTER}}prd{{SKILL_NAME_SPLITTER}}draft」

> 若选择的任务已是 `phase=discovery`（中断续跑），可从中断点续跑；不得重新筛成「零匹配」。
> 若上次中断在 plan 中（`discovery.status=in_progress` / apply paused），从中断点续跑；不得因「已是 draft」而报零匹配。

**入口校验**（失败 → 阻断）：

| 检查 | 条件 |
|------|------|
| plan 已完成 | `state.yaml` 中 `plan.status=completed`（或用户明示接受续跑且 `tasks.md` 已是可执行细计划） |
| tasks 可执行 | `openspec/changes/<change_id>/tasks.md` 非空，且含至少一个 `- [ ]` 或（续跑时）未完成项可定位 |
| 工作目录 | 若 `worktree_path` 非空 → 后续 apply / 读 tasks **以该 worktree 为仓库根**；否则用主仓 |

通过后执行：
1. 更新 `state.yaml`：`current_verb: build`，`build.status: in_progress`。

2. 设置语言

执行脚本：
```bash
LANG=$(bash "$PLUGIN_ROOT/scripts/get-language-name.sh")
LANG_EXIT=$?
```

- `LANG_EXIT != 0` → 使用当前用户请求语言
- `LANG_EXIT ==0` → 本阶段所有提问与澄清摘要均采用 $LANG。

输出：`[polaris-flow 需求工程] 编写终稿: change_id=<change_id> ; worktree=<path|main>`

## Step 1：输入加载、模板校验与追溯构建

**输出落盘**：
- `./sessions/_phase1_analysis.md`
- `./sessions/_baseline_trace_matrix.csv`

### 1.1 模板强制加载与校验
- 必须`read_file` `./templates/prd-template.md`，将模板的全部章节标题、子结构、表格格式作为输出的唯一结构基准
- 生成模板章节清单，后续每章生成时对照检查
- **禁止**遗漏章节、禁止改名、禁止调整顺序

### 1.2 全量输入加载
- 读取最新版 PRD 初稿全文，识别已确认的核心内容
- 读取 Baseline 需求基线，逐条拆解需求项并分配唯一基线 ID
- 读取 coding-knowledge 代码库（如有），识别可验证的代码范围（实体类、接口定义、DTO、枚举定义等）

### 1.3 继承章节映射
将初稿内容映射到模板对应章节：
| 初稿章节 | 映射到终稿模板章节 | 处理方式 |
|---|---|---|
| 需求背景 | 第1章 背景与目标 | 继承，增强补全（目标量化、范围边界） |
| 整体业务流程与时序 | 第3章 业务角色与端到端流程 | 继承，增强补全（角色表、场景用例） |
| 需求详情（通用能力层+业务场景层） | 第5章 功能需求详述 | 继承，按模板「模块→功能点」结构重构 |

**继承区保护规则**：
- 允许：优化表述严谨性、补充边界条件、统一术语、补充跨模块锚点
- 禁止：修改核心业务逻辑、流程走向、功能范围、业务约束
- 如需调整继承区核心内容，必须触发正式变更确认，同步更新 Baseline 与追溯矩阵

### 1.4 构建基线-终稿双向追溯矩阵
- 矩阵字段：基线需求ID、业务含义、终稿对应章节（模板章节号）、段落锚点、验证状态
- 终稿所有新增内容必须能反向追溯至对应基线需求项
- 无基线来源的需求不得纳入终稿

### 1.5 补全范围确认
- 按模板章节列出补全清单，标注每章的继承/新增状态、L2验证级别
- 存在 coding-knowledge 时：第4章数据模型、第2章术语定义（枚举部分）、第7章状态流转（枚举部分）标记为 **L2代码验证级**
- 不存在 coding-knowledge 时：标记为 **L1设计级**，明确标注「未经过代码验证，开发前需技术复核」
- 输出补全清单 + 验证级别说明 + 追溯矩阵初版给用户确认
- 用户确认后进入 Phase 2

## Step 2：逐章补全生成（严格按模板章节顺序）

**执行铁则**：
- 严格按模板 文档头→第1章→第10章→附录 的顺序生成
- 每章：生成 → L2验证（如适用）→ 模板结构自检 → 人工确认 → 写入磁盘
- 确认一章，再进入下一章；禁止批量生成多章节
- 继承章节先优化确认，再开始新增章节生成

**输出落盘**：`./sessions/xx-章节名.md`

#### 1.3 范围与边界
**包含范围**：明确本模块覆盖的功能、数据、场景边界，颗粒度到功能点级
**不包含范围**：明确交由外部模块实现、本期不建设、后续迭代扩展的能力边界，避免需求蔓延

### 第5章 功能需求详述（继承初稿，按模板结构重构）

**组织方式**：严格按模板「模块→功能点」分级，**不再使用**初稿的「通用能力层+业务场景层」结构。

**继承映射规则**：
- 初稿通用能力层内容 → 重构为模块级「通用处理流程」+「前置公共约束」
- 初稿业务场景层内容 → 重构为功能模块下的功能点
- 初稿锚点引用 → 转换为模块内功能点引用或跨模块引用

#### 模块级结构（每个功能模块 F0xx）

**模块概述**：简述本模块核心能力与业务价值

**通用处理流程**：本模块所有操作遵循的统一执行顺序，明确事务原子性要求

**前置公共约束**：本模块所有操作必须遵守的准入规则与通用限制，拦截非法操作

**核心算法**（如有）：
- 输入：输入参数与数据来源说明
- 输出：输出结果与作用说明
- 判定逻辑：按条件分支逐条描述

**特殊对象规则**（如有）：特殊类型对象的差异化处理规则

#### 功能点级结构（每个功能点 F0xx-00x）

**前置条件**：逐条列明执行本功能的前提条件

**业务逻辑**：按执行顺序描述处理流程，明确事务边界、数据落库规则、批量生成规则

**约束规则**：逐条列明本功能点的业务约束与限制

**UI交互说明**（页面类功能填写）：
- 查询栏：支持的查询条件列表
- 列表展示字段：字段名称列表，关键字段标注展示规则
- 操作栏：操作按钮名称 + 交互跳转说明
- 分页排序：默认分页条数、排序字段与规则

**验收标准**：逐条列明可验证的验收点，覆盖正常/异常/边界场景

### 第7章 状态流转规范（新增，模板强制，强状态机系统核心章）

#### 7.1 状态枚举定义
**模板标准四列表格**：
| 中文状态 | 枚举Code | 状态类型 | 释义说明 |
|---|---|---|---|
| 状态1 | IN_USE | 正常态/中间态/终态 | 状态业务含义 |

#### 7.2 流转总原则
- 终态不可回退，所有终态操作不可逆
- 聚合状态严格依据算法自动计算，不人工干预
- 中间态流程驳回后，统一回退至操作前状态
- （按实际业务补充）

#### 7.3 典型场景流转规则
- 按业务场景描述完整流转：初始状态 → 流程发起 → 审批通过 → 审批驳回
- 供测试场景设计参考，不作为编码直接依据

**L2验证**（如有 coding-knowledge）：枚举Code与代码状态枚举类对齐校验

### 第9章 验收标准（按模板四维度重构）

#### 9.1 功能完整性验收
- 包含范围中所有功能点全部实现，无遗漏
- 所有前置公共约束生效，非法操作均被拦截
- 状态联动符合聚合算法，无状态冲突

#### 9.2 数据一致性验收
- 统计字段与实际状态实时一致，无数据偏差
- 所有变更均生成对应记录，无遗漏、无重复
- 事务操作失败时整体回滚，无部分落库

#### 9.3 性能验收
- 响应时间达标率
- 并发成功率

#### 9.4 安全与合规验收
- 无物理删除接口，所有变更可追溯
- 权限控制生效，越权操作全部拦截

> 功能点级 GWT 验收标准整合到第5章各功能点下，本章为模块级/系统级验收维度。

1. **模板结构自检**：章节标题、子标题、表格列名是否与模板完全一致
2. **基线追溯自检**：本章内容是否均有对应基线需求来源，无凭空新增
3. **L2验证自检**（如适用）：字段/枚举/默认值是否与代码一致
4. **业务规则自检**：规则是否明确无歧义、无矛盾、可量化
5. **产品语言自检**：除第4章数据模型允许字段名等技术细节外，其余章节无技术实现细节
6. **异常覆盖自检**：7类标准异常场景（网络/服务/权限/数据/并发/第三方依赖/业务状态）是否覆盖

自检通过后，将章节草稿 + 自检结果 + 本章重点校验表一同提交用户确认。

## Step 3：完整评审与人工评审支撑

**输出落盘**：
- `./sessions/_full_review_report.md`
- `./sessions/review-package/`（人工评审支撑包）

### 3.0 探测可用 subagent（Step 3 入口，一次探测全程复用）

**探测方式**：调用 `use_skill("polaris-flow{{SKILL_NAME_SPLITTER}}subagent-probe")`，传入：

- `platform`：从项目配置读取
- `task_type`：`doc_review`（3.1 与 3.2 同类型，共用 `matched_agents` 预筛结果）

> 本步骤的两个评审任务均为**通用型**（general）——不要求专用 agent，只要在独立上下文中执行即可。因此**不传 `subagent_id`**；若项目 `.agents/` 下恰好存在声明 `task_types: doc_review` 的专精 agent，`matched_agents` 预筛会将其排在前面，属能力匹配的正常结果，同样直接使用。

**探测结果消费**：

| `platform_degradation` | 处理动作 |
|---|---|
| `null` | 继续后续编排；3.1 与 3.2 各自从 `matched_agents`（空则 `agents`）中取通用 agent 进入派发 |
| `inline` / `unsupported` | 平台不支持 subagent：3.1 与 3.2 均降级为主代理 inline 执行（通用型任务自动降级，无需询问用户）；在评审报告中标注「宿主平台不支持 subagent，由主代理内联评审」 |

> 探测只做一次；3.1 与 3.2 共享同一次 probe 结果，不重复扫描。

### 3.1 7维度业务评审（subagent-probe + subagent-dispatch 编排）

**编排方式**（probe → 决策 → dispatch）：本技能为编排方。**禁止**直接使用 Agent 工具硬编码 `subagent_type=general-purpose` 启动——必须先经 `subagent-probe` 探测、由本技能选定 agent 后调用 `subagent-dispatch` 派发。

**general 决策**（本步骤无专用 agent 要求，按能力匹配取通用型）：

- `matched_agents` 非空 → 取 `matched_agents[0]`（预筛已按「专精在前、通用在后」排序；通常为通用型 agent）进入派发
- `matched_agents` 与 `agents` 均为空 → 调用 dispatch 时传 `agent=null` 且 `task_spec.constraints` 加 `"dispatch_mode_hint: default_subagent"`（派宿主默认 subagent，独立上下文执行）
- `platform_degradation=inline/unsupported` → 跳过派发，主代理直接 inline 执行（见下方「inline 降级」）

**派发入参构造**：

- `platform`：与 probe 相同
- `agent`：probe 返回 `matched_agents[0]`（含 id / path / tools / source）；或 `null`（agents 为空时）
- `task_spec`：
  - `task_description`：对 PRD 终稿执行 7 维度业务评审。加载并遵循 `polaris-flow{{SKILL_NAME_SPLITTER}}prd{{SKILL_NAME_SPLITTER}}review` 技能的评审方法与 Phase 4 报告格式，产出含分级问题清单、基线追溯矩阵、问题ID锚点链接的完整评审报告。
  - `task_type`：`doc_review`
  - `materials`：
    - PRD 终稿全文路径（Step 2 逐章合并后的最新版）
    - Baseline 路径
    - `polaris-flow{{SKILL_NAME_SPLITTER}}prd{{SKILL_NAME_SPLITTER}}review` 技能 SKILL.md 路径（供 subagent 加载评审方法）
  - `constraints`：
    - 只评审，**禁止**修改任何文档文件
    - 问题必须分级（CRITICAL / IMPORTANT / MINOR），阻塞问题（CRITICAL）必须明确标注
    - 评审范围：全量章节（或按用户指定章节子集）
    - 输出语言：跟随主会话语言
    - agents 为空时追加：`"dispatch_mode_hint: default_subagent"`
  - `language`：跟随主会话语言

**subagent-dispatch 返回消费**：

按 subagent-dispatch 输出结构的 `dispatch.status` 字段分支处理：

| `dispatch.status` | 处理动作 |
|---|---|
| `dispatched` | 已按选定 agent 派发执行；消费 `result.status` 与 `result.output` |
| `degraded_default` | agents 为空时传 agent=null + hint=default_subagent 的正常结果；已派默认 subagent，消费 `result` |
| `degraded_inline` | 已由主代理 inline 执行；消费 `result`；在评审报告中标注「由主代理内联评审」 |
| `unsupported` | 派发失败（如平台无默认 subagent）；降级为主代理 inline 执行（见下方） |

**inline 降级**（通用型任务自动降级，不打断用户）：

以下任一情况，主代理在自己会话内直接执行 7 维度评审（Read 全部 materials 后按 `doc_review` 任务类型产出评审报告），并在报告中标注「由主代理内联评审」及原因：

- probe 返回 `platform_degradation=inline/unsupported`
- dispatch 返回 `dispatch.status=unsupported`
- dispatch 返回 `result.status=FAILED`（如默认 subagent 执行失败）

**7 维度检查内容**（subagent 执行时必须覆盖）：

| 维度 | 检查内容 |
|---|---|
| 业务一致性 | 终稿内容与 Baseline 业务目标、需求意图一致 |
| 范围完整性 | Baseline 所有需求项在终稿中全覆盖，无遗漏 |
| 逻辑自洽性 | 业务流程、规则、状态流转无矛盾，闭环完整 |
| 规则明确性 | 所有业务规则无模糊表述，条件可量化、无歧义 |
| 可实现性 | 方案在现有技术架构与资源约束下可落地 |
| 合规性 | 符合权限管理、数据安全、行业监管等要求 |
| 基线双向一致性 | 正向：Baseline每项需求在终稿中有对应；反向：终稿每项需求在Baseline中有来源 |

**返回结果处理**：

subagent-dispatch 返回后，主 agent 按 `result.status` 处理：

- `DONE` / `DONE_WITH_CONCERNS`：接收 `result.output`（评审报告内容或路径），落盘到 `./sessions/_full_review_report.md` 的业务评审部分
- `BLOCKED`：记录 `result.concerns`，向用户报告阻塞原因，暂停 Step 3 后续
- `NEEDS_CONTEXT`：按 `result.concerns` 补充上下文后重新派发（同一 agent）
- `FAILED`：降级为主代理 inline 执行（自动，见上方「inline 降级」）

### 3.2 可测性专项检查（subagent-probe + subagent-dispatch 编排）

**编排方式**：与 3.1 相同的 probe → 决策 → dispatch 三段式。**禁止**直接使用 Agent 工具硬编码 `subagent_type=general-purpose`。

**general 决策**（本步骤同样无专用 agent 要求）：

- 从 Step 3.0 共享的 probe 结果中取 agent：`matched_agents[0]`（与 3.1 同一 task_type，可用**同一个**通用 agent；dispatch 无状态，同一 agent 并行派发两次互不干扰）
- `matched_agents` 与 `agents` 均为空 → 同 3.1：`agent=null` + `"dispatch_mode_hint: default_subagent"`
- `platform_degradation=inline/unsupported` → 主代理 inline 执行

**派发入参构造**：

- `platform`：与 3.1 相同（与 probe 同源）
- `agent`：与 3.1 相同的 `matched_agents[0]`；或 `null`（agents 为空时）
- `task_spec`：
  - `task_description`：对 PRD 终稿执行可测性专项检查。加载并遵循 `pm-prd-testability` 技能的检查方法与 Phase 4 报告格式，产出含四维度检查记录、分级问题清单（T0~T3）、验收标准补全建议、问题ID锚点链接的完整可测性报告。
  - `task_type`：`doc_review`
  - `materials`：
    - PRD 终稿全文路径（与 3.1 共用同一版本）
    - `pm-prd-testability` 技能 SKILL.md 路径（供 subagent 加载检查方法）
  - `constraints`：
    - 只评审，**禁止**修改任何文档文件
    - 每个不可测点必须给出具体的验收标准补全建议
    - 评审范围：全量章节（或按用户指定章节子集）
    - 输出语言：跟随主会话语言
    - agents 为空时追加：`"dispatch_mode_hint: default_subagent"`
  - `language`：跟随主会话语言

**subagent-dispatch 返回消费**：与 3.1 相同的 `dispatch.status` 分支策略、`result.status` 处理逻辑与「inline 降级」规则，此处不再重复。

**四维度检查内容**（subagent 执行时覆盖）：

| 维度 | 检查内容 |
|---|---|
| 验收标准完整性 | 每个功能点有明确、完整、可验证的验收标准 |
| 业务规则可判定性 | 每条业务规则有明确、可量化、可判断的通过/失败条件 |
| 场景覆盖充分性 | 每个功能点覆盖正常、异常、边界三类场景 |
| 数据指标可验证性 | 非功能需求与数据指标有明确统计口径、验证方法和目标值 |

**返回结果处理**：与 3.1 相同的 `result.status` 处理逻辑；接收后落盘到 `./sessions/_full_review_report.md` 的可测性检查部分。

### 3.2.1 并行执行与结果汇总

**探测共享**：3.1 与 3.2 共用 Step 3.0 的**一次** probe 结果，不重复扫描。

**并行派发**：3.1 与 3.2 的两次 `use_skill("polaris-flow{{SKILL_NAME_SPLITTER}}subagent-dispatch")` 调用可在同一轮并行发起——即使两者使用同一个通用 agent（dispatch 无状态，同一 agent 派发两次互不干扰）；agents 为空时两者均传 `agent=null` + hint=default_subagent，同样可并行。互不依赖。

**并行约束**：
- 两次派发的 `platform` 必须相同（同一宿主，与 probe 同源）
- 两次派发的 `materials` 中 PRD 终稿路径必须指向同一版本（Step 2 合并后的最新版）
- subagent-dispatch 内部不感知并行——它是无状态的单次派发；并行编排由本技能（调用方）负责
- 一方 inline 降级不阻塞另一方——各自独立处理、独立落盘

**结果汇总**：
- 两个 subagent-dispatch 均返回后，主 agent 汇总两份报告，合并到 `./sessions/_full_review_report.md`
- 汇总时保留两份报告的完整内容，按「业务评审」+「可测性检查」两节组织
- 若其中一方 inline 降级也失败（如 materials 不可读），标注该维度「未能执行」，不阻塞另一维度的结果汇总

### 3.3 问题分级与修复机制

- **阻塞问题**：影响业务逻辑正确性、范围完整性、可实现性的核心问题，必须修复后才能定稿
- **一般问题**：表述优化、格式规范、建议类问题，不阻塞定稿
- 阻塞问题修复后，重新执行完整评审；迭代直到阻塞问题清零

### 3.4 生成人工评审支撑包

为集中办公团队的线下评审会议提供标准化材料，降低参会人员信息负荷：

- **评审阅读指引**：标注不同角色（产品/技术/测试）的重点阅读章节与页码，减少无效阅读量
- **重点标注版终稿**：高亮标记待确认点、技术风险点、已收敛争议点
- **评审议题清单**：明确本次评审的讨论范围与禁止讨论话题，锁定会议边界
- **争议停车场模板**：预设争议记录表格（争议内容/提出人/决策人/约定处理时间）
- **行动项模板**：预设任务/责任人/截止时间/完成标准的标准表格

### 3.5 输出完整评审报告

包含：评审维度得分、问题清单（分级）、修复记录、评审结论（通过/不通过）、评审支撑包使用说明
