# 产品语言写作规范
## 核心原则
- 全篇使用产品语言，站在用户与业务视角描述"做什么"，不描述"怎么做"
- 禁止出现技术实现细节，技术细节属于技术方案设计范畴
- 所有业务规则必须明确、无歧义，避免模糊形容词

## 禁止出现的技术细节
以下内容严禁出现在 PRD 初稿中：
1. 代码层面：类名、方法名、函数名、变量名
2. 数据层面：数据库表名、字段名、主键外键、索引设计
3. 接口层面：接口路径、请求参数、返回字段、HTTP 方法
4. 技术选型：框架名称、组件名称、中间件选型
5. 实现方案：具体算法、技术架构、部署方式

## 正确产品语言示例
### 错误写法（技术细节）
- 用 React 实现表格的多列排序功能
- 调用 /api/order/create 接口创建订单
- 用户表新增 is_vip 字段标记会员状态

### 正确写法（产品语言）
- 支持用户对列表数据按多个维度进行排序，支持自定义保存排序规则
- 订单提交后，系统自动完成订单创建并同步至订单管理模块
- 支持标识会员用户身份，并在列表中进行区分展示

## 业务规则表述规范
1. 避免模糊表述：
   - ❌ 系统应在较短时间内响应
   - ✅ 系统响应时间应在 2 秒以内
2. 明确触发条件：
   - ❌ 系统在合适的时机同步数据
   - ✅ 审核通过后 5 分钟内，将数据同步至 ERP 系统
3. 统一术语：全文同一业务对象必须使用完全相同的术语表述

## 场景层引用规范
1. 涉及通用能力时，使用锚点引用格式：`详见 [能力名称](#cap-xxx)`
2. 禁止大段复制通用能力的完整描述
3. 存在差异时，引用后补充"差异说明"段落，仅描述不同点
4. 场景专属功能在场景下完整描述，不得放入通用能力层

## 锚点定义规范（保证文档内链接可跳转）
1. 每个通用能力/业务场景标题处，必须用显式 HTML 锚点定义跳转目标：
   - 通用能力：`<a id="cap-xxx"></a>`（xxx 为 3 位数字，如 `cap-001`）
   - 业务场景：`<a id="scene-xxx"></a>`（如 `scene-001`）
2. 锚点 ID 规则：统一**小写**、**ASCII 连字符 `-`**、数字序号；禁止使用非 ASCII 连字符（如 U+2011 `‑`）或中文标点，否则引用与目标不匹配导致链接无法跳转。
3. 引用必须与目标 ID 完全一致：`[能力名称](#cap-xxx)` 的 `#cap-xxx` 必须精确对应某处 `<a id="cap-xxx"></a>`。
4. 采用显式 `<a id>` 而非依赖标题自动生成的 slug，以兼容主流 markdown 渲染器（VS Code / GitHub / Typora 等）。
