# 编写产品需求-编写PRD初稿

<HARD-GATE>
- **需求源唯一性**：仅以《需求基线》为唯一功能需求来源；澄清纪要仅作权威补充需求源与风险输入，参考文档只控制写作格式。多份冲突输入须由用户指定唯一《需求基线》，禁止 AI 自选。
- **事实与假设分离**：所有未经原文标记或用户确认的内容，不得作为既定业务重点；AI 不主观新增重点、不脑补业务结论。
- **方案域不越界**：初稿不输出数据库表、接口字段、类名、函数、技术实现方案；不实现终稿模块（权限、数据模型、接口契约、埋点、排期），风险与排除项仅写到提纲级（风险点+应对、排除项清单）。
- **准入不可跳过**：未通过前置校验，禁止执行任何文档生成动作；未通过用户确认，禁止进入下一章节。
- **语言无歧义**：禁用模糊主观表述与技术指令性语言，统一采用「用户故事+业务规则」的产品语言；未明确的逻辑判断条件、不统一的术语须改写或标记待确认。
- **变更全程可追溯**：所有对基线/澄清结论的引用与融合，须标注来源与依据，禁止静默改写原文。
</HARD-GATE>

**启动时必须先输出**：`[polaris-flow 需求工程] 进入阶段: 编写PRD初稿 — 使用 polaris{{SKN_SPR}}prd{{SKN_SPR}}draft 技能。`

## 流程

> **压缩上下文通用规则**：每个 Step 收尾时，统一释放该步的中间推导草稿、重复条目、冗余对话与已闭环问题的原始草稿；仅保留已确认结论、剩余待生成章节、交叉校验结果、隐含假设与风险池（下文各「压缩上下文」子步骤只列本步需保留的关键产出）。
>
> **用词与模板的唯一来源**：`./policies/auto-transition.md` 的「压缩时机与恢复清单」。注意「压缩上下文」**不同于**「新开会话」（后者 = 用户关闭窗口重开、历史归零）。**禁止**在步骤中途提压缩，**禁止**用 shell 命令或摘要伪造压缩。

### Step 0：定位任务标识 + 入口校验

```bash
TASK_IDS=$(bash "$PLUGIN_ROOT/scripts/workflow-entry.sh" get-active-changes --kind requirement --skill draft --repo-root "$REPO_ROOT" --phase draft)
RTID_EXIT=$?
```

- `RTID_EXIT != 0` → **阻断**，按 stderr 处理
- `RTID_EXIT == 0` → `$TASK_IDS` 形如 `["id-a","id-b"]`（可能为 `[]`）

按 `$TASK_IDS` 数组长度解读：

- **唯一匹配**：直接读取 `task_id`
- **多个匹配**：按 `./policies/decision-point.md` 列出候选让用户选择
- **零匹配**：阻断，提示「未找到 draft 阶段的 active change，请先执行 /polaris{{SKN_SPR}}prd{{SKN_SPR}}discovery」

> 若选择的任务已是 `phase=draft`（中断续跑），可从中断点续跑；不得重新筛成「零匹配」。
> 若上次中断在 draft 中（`draft.status=in_progress` / apply paused），从中断点续跑；不得因「已是 draft」而报零匹配。

**入口校验**（已完成 → 阻断重跑）：


| 检查         | 条件                                     |
| ------------ | ---------------------------------------- |
| draft 已完成 | `state.yaml` 中 `draft.status=completed` |

执行：

1. 更新 `state.yaml`：`phase: draft`，`draft.status: in_progress`。

```bash
bash "$PLUGIN_ROOT/scripts/task-state-entry.sh" enter-phase \
  --repo-root "$REPO_ROOT" --task-id "$task_id" --kind requirement --phase draft
```

2. 设置语言

执行脚本：

LANG = $(bash "$PLUGIN_ROOT/scripts/get-language-name.sh")

- `LANG_EXIT == 0` → 本阶段所有提问与澄清摘要均采用 $LANG。

输出：`[polaris-flow 需求工程] 编写初稿: task_id=<task_id>`

### Step 1：前置校验（必须全部通过才允许继续）

《需求基线》文档，别名 Baseline，路径：`$REPO_ROOT/.polaris/tasks/<task_id>/req_baseline.md`
《需求澄清纪要》文档，路径：`$REPO_ROOT/.polaris/tasks/<task_id>/req_clarify_summary.md`

校验项：

1. Baseline 不存在，提示：`[polaris-flow 需求工程] 编写初稿 - 未读取到需求基线文档，PRD初稿生成必须依赖需求基线作为唯一需求输入源，请提供Baseline文件路径/完整内容`，终止流程；
2. Baseline 结构完整性：必须包含【需求背景、业务流程、功能/能力清单、业务场景清单】；缺失任意关键模块，输出缺失清单，提示：`请重新运行 /polaris{{SKN_SPR}}prd{{SKN_SPR}}discovery 补齐《需求基线》`，终止流程；
3. 输入源唯一性与澄清纪要加载：
   - 声明本次生成仅以 Baseline 为唯一功能需求来源；参考文档/澄清纪要仅控制写作格式或作补充上下文，**不作为需求来源**；多份冲突输入请用户指定唯一 Baseline。
   - 加载《需求澄清纪要》并校验：若存在澄清纪要，读取其「问题闭环明细-最终答复」与「隐含假设与风险清单」，作为权威补充需求源与风险输入；其最终答复优先于 Baseline 中的待定描述。若无澄清纪要，提示可跳过但建议补齐。
4. 复杂度等级声明：读取 Baseline 元数据区「复杂度最终等级（简单/标准/复杂）」，据此确定初稿内容深度（见 Step 2 复杂度联动规则），并在 Gate 报告中标注。
5. 初稿边界预声明：声明本初稿为「方案大逻辑评审对齐」稿，不含完整权限矩阵/接口字段/数据模型/排期/埋点等终稿细节。
6. 命名标识校验（编号前缀是本初稿全部锚点的命名空间，缺失即无法落锚点）：
   - 读取 `$REPO_ROOT/.polaris/tasks/<task_id>/state.yaml`，取 `req_name_cn`（需求中文名）与 `req_prefix`（需求编号前缀）；`state.yaml` 缺失时回退读取 Baseline 元数据区同名两项。
   - 前缀须满足「大写 ASCII、2–16 位、不以连字符开头结尾」；不合规则规范化后回显再确认。
   - 初稿全部锚点 ID 一律以**前缀小写形式**开头：`{前缀小写}-cap-001` / `{前缀小写}-scene-001`（如 `uap-cap-001`）。

校验结论写入 `$REPO_ROOT/.polaris/tasks/<task_id>/state.yaml` 的 `draft.gate` 字段：

```yaml
draft:
  status: in_progress
  gate:                    # 前置校验结论
    checked_at: <校验时间>
    baseline_id: <Baseline 标识>
    clarify_summary_id: <澄清纪要标识，无则 null>
    complexity: <简单/标准/复杂>
    req_name_cn: <需求中文名>
    req_prefix: <需求编号前缀>       # 锚点命名空间，如 UAP
    passed: true|false
    fail_reason: <失败原因，通过则空>
    boundary: <初稿边界声明>
```

> Gate 不通过（`draft.gate.passed=false`）：直接结束技能，不执行任何文档生成动作。

输出：`[polaris-flow 需求工程] 编写PRD初稿 - 输入文档校验通过：Baseline=<标识>，澄清纪要=<有/无>，复杂度=<等级>，中文名=<中文名>，编号前缀=<前缀>，初稿边界已声明。`

#### 压缩上下文

- 释放：Baseline 全文、缺失模块草稿、冗余校验中间结果
- 保留：Baseline 标识与路径、澄清纪要标识、复杂度等级、初稿边界声明、**需求中文名、需求编号前缀**

### Step 2：加载输入 + 解析

> 静默执行，仅重点环节交互用户

#### 2.1 加载并解析

执行步骤：

1. 完整读取《需求基线》；
2. 解析提取实体：角色、业务场景、通用能力、业务规则，分配锚点 ID：`{前缀小写}-cap-xxx`（通用能力）/ `{前缀小写}-scene-xxx`（业务场景），如 `uap-cap-001`、`uap-scene-001`；构建索引 `baseline_index.json`（须记录 `req_prefix` 字段，供后续章节与 refine 复用）；锚点 ID 一律小写 + ASCII 连字符 `-`，写入文档时须用显式 HTML 锚点 `<a id="uap-cap-001"></a>` 定义目标（规范见 `./policies/writting-rules.md`）；**前缀来自 Step 1 校验通过的需求编号前缀，不得自行另起一套**；
3. 扫描 Baseline 识别人工重点：识别加粗、【重点】标记、高亮注释片段；
4. 如果 Baseline 没有显式重点标记，输出**候选重点清单给用户确认**，用户确认后生成 `key_points.json`；
   - key_points 每条字段：`raw_text(原文片段)、belong_module(归属模块)、keep_mode[完整保留｜保留语义｜允许改写]`
5. 加载规范文档与决策点：读取 `./templates/prd_draft_template.md`（章节内容标准）；
6. **复杂度与逻辑框架构建**：基于 Baseline 复杂度等级确定裁剪档；在内部构建「问题-方案-目标」逻辑框架——问题来自需求背景/痛点证据，方案来自功能架构，目标来自业务目标与验证指标（SMART）；
7. **澄清纪要融合**：读取澄清纪要「最终答复」，标注对 Baseline 的澄清/变更点；读取「隐含假设与风险清单」汇入风险池；
8. **图表需求识别**：识别需绘制的核心图表（架构图/流程图/状态机/线框图）及对应章节，列入生成计划。

**复杂度联动规则**（基于 Baseline「复杂度最终等级」）：


| 等级 | 图表深度                                  | 风险清单（提纲级）             | MoSCoW 严谨度             | 边界声明 |
| ---- | ----------------------------------------- | ------------------------------ | ------------------------- | -------- |
| 简单 | 仅核心业务流程图，可省略架构图/状态机     | 关键风险 1–3 条               | MUST/SHOULD 两级即可      | 轻量     |
| 标准 | 架构图 + 主流程图 + 关键状态机            | 技术/业务/合规/依赖 各 1–2 条 | MUST/SHOULD/COULD 三级    | 标准     |
| 复杂 | 全量图（架构/流程/状态机/线框）+ 图表索引 | 四类完整，含依赖降级           | 四级全用，含 WON'T 排除段 | 详尽     |

输出状态提示：`Baseline已加载完成，复杂度={等级}，识别通用能力{N}个，业务场景{M}个，已确认重点{K}项，澄清纪要={有/无}，准备进入逐章生成阶段`。

> 禁止：AI 自己主观判定哪些是业务重点；重点必须来自原文标记或者用户确认。

输出：`[polaris-flow 需求工程] 编写初稿 - 输入解析完成：通用能力{N}、业务场景{M}、重点{K}项、图表{N}张，准备进入逐章生成。`

#### 2.2 压缩上下文

- 释放：Baseline 全文、原始扫描文本、拆解中间稿、未命中检索结果
- 保留：源文件元数据、复杂度等级、`baseline_index.json`、`key_points.json`、澄清/变更标注、风险池、图表生成计划

### Step 3：逐章生成 + 人工确认

**执行原则**

- **一章一确认**：单章完成（生成-自检-落盘-用户确认）后才允许进入下一章，禁止一次性批量生成多章节；
- **全文单次落盘（省 Token）**：章节全文仅在「写入 sessions 文件」时输出一次；会话中只展示【本章要点摘要 + 重点校验表 + 文件路径（引导预览）】，**不再粘贴全文**——避免全文二次输出，也避免全文长期驻留上下文重复计费；
- **重点不脑补**：AI 不主观判定业务重点，重点必须来自原文标记或用户确认；
- **图表优先**：流程/需求类章节先给图（架构/流程/状态机/线框），再文字描述；
- **引用锚点**：场景层用锚点引用通用能力，禁止大段复制原文，只写场景独有差异。
- **用户修改意见**：用增量编辑修改已落盘文件（只改差异片段，不整章重写），再次展示【摘要+校验表】，确认后才标记该章为 confirmed；

章节顺序严格固定：

1. 01-需求背景.md
2. 02-业务流程与时序.md
3. 03-需求详情-通用能力层.md
4. 03-需求详情-业务场景层.md
5. 04-版本记录.md

**文档头部（合并阶段统一生成，置于首章之前）**：评审重点指引——列出 2—5 条本次评审需重点确认的核心问题，引导评审者按「先业务价值 → 再方案大逻辑 → 最后功能细节」顺序阅读。

#### 每一章统一执行模板

1. 根据 `./templates/prd_draft_template.md` 模板，结合 需求基线 + `baseline_index.json` + 澄清纪要 生成本章草稿；
2. 内部三重自检：
   - 自检 A 编写规则(`./policies/writting-rules.md`)：检查是否混入技术代码、表名、接口名，有则改写为产品语言或者标记待确认；**检查模糊主观表述、技术指令性表述、未明确的逻辑判断条件、术语不统一；统一采用「用户故事+业务规则」格式**；
   - 自检 B 重点项管理(`./policies/key-points-management.md`)：取出本章关联的全部重点项，比对草稿，生成本章重点校验表格；
   - 自检 C 重点优化：核心结论是否用重点摘要区块/加粗突出；重大风险/验收标准是否高亮；不同优先级功能点是否用分隔线分开；标注不过度；
3. **直接写入** `$REPO_ROOT/.polaris/tasks/<task_id>/draft/sessions/xx-章节名.md`（草稿态，全文仅此一次输出，避免二次消耗 Token）；
4. 会话中只输出【本章要点摘要 + 本章重点校验表 + 章节文件路径（引导用户预览确认）】，不粘贴全文；
5. 等待用户反馈（按 `./policies/decision-point.md` 暂停确认）：
   - 用户确认 OK：标记该章 confirmed；进入下一章节；
   - 用户提出修改意见：用增量编辑修改已落盘文件，重新自检，再次输出【摘要+校验表】，重复直到确认通过。

#### 各章内容标准（融入最佳实践，6 章文件名不变）

- **01-需求背景**：按「问题先行（证据链支撑真实业务问题）→ 方案后置（整体思路）→ 目标闭环（SMART 可量化，承接 Baseline 业务目标）」组织；明确 **本次范围 In** 与 **本次不包含 Out／排除项清单**。
- **02-业务流程与时序**：**先图后文**——优先给出架构图、业务流程图（BPMN/泳道）、核心对象状态机图、长链路线框图（mermaid 或文本图），再文字描述主流程与主要分支；**末尾附「风险与应对（提纲级）」**：按 技术/业务/合规/依赖 四类列出风险点与应对策略，源自 Baseline 约束汇总 + 澄清纪要风险清单，仅写提纲级，不展开终稿细节。
- **03-需求详情**：功能点按 **MoSCoW（MUST/SHOULD/COULD/WON'T）分级并排序**，MUST 在前、WON'T 单独排除段；场景层用锚点 `[能力名](#{前缀小写}-cap-xxx)` 引用通用能力（如 `[资源管理](#uap-cap-001)`），禁止大段复制通用能力原文，只写场景触发条件、流程、场景独有差异规则（保留原业务层规则）；每条功能用「用户故事+业务规则」格式。
- **04/05 版本记录、更新记录**：版本号、日期、修订人、修订说明。

#### 业务层特殊规则

> 先写【通用能力层】，后写【业务场景层】；
>
> - 通用能力：完整描述一次，分配锚点 ID；
> - 业务场景层：禁止重复复制通用能力大段原文；使用锚点引用 `详见[xxx](#{前缀小写}-cap-001)`；只写场景触发条件、流程、**场景独有的差异规则**。

#### 压缩上下文

- 释放：各章草稿中间稿、冗余对话、已确认章节原始讨论
- 保留：已落盘章节文件、各章重点校验表、图表资源、未确认章节清单

### Step 4：Baseline 交叉验证 + 重点保留率校验

落盘输出：`$REPO_ROOT/.polaris/tasks/<task_id>/draft/sessions/cross_check_report.md`

执行动作：

1. 功能覆盖校验：遍历 `baseline_index.json` 全部能力、场景条目，在已经落盘的各章节 md 文件检索，生成覆盖矩阵；标记 ✅ 已覆盖 / ❌ 缺失；
2. 锚点完整性校验：检查每个锚点引用 `[xxx](#{前缀小写}-cap-xxx)` / `[xxx](#{前缀小写}-scene-xxx)` 是否存在对应的 `<a id="{前缀小写}-cap-xxx">` / `<a id="{前缀小写}-scene-xxx">` 目标定义；引用存在但目标缺失、ID 大小写/连字符不一致、或缺失编号前缀的，标记异常；
3. 重点内容统计：遍历 `key_points.json`，统计：完整保留数、语义保留数、缺失/偏差项；计算**重点保留率 = (完整+语义保留)/总重点项**；
4. 阈值规则：**保留率低于 95%，不允许进入交付阶段**；
5. 初稿边界检查：校验是否清晰回答「为什么做／做什么／不做什么」三问；范围边界是否明确且无超界；排除项清单是否明确；是否含技术实现细节（应无）；待决事项是否集中标注。任一项不达标，回到对应章修改后重检；
6. 如果存在缺失功能/重点：输出清单，询问用户：「补充到 PRD｜该条目废弃」；选择补充则回到 Step 3 对应章节修改落盘，之后重新完整跑一遍 Step 4 校验；
7. 全部校验通过，写入完整 `cross_check_report.md`，报告包含：功能覆盖矩阵、锚点检查结果、重点保留率、初稿边界检查结果、异常项。

> 本阶段**不评审需求业务合理性**；只做：有没有写、重点是否保留、引用是否合法、初稿边界是否合规。业务好坏属于人工终稿评审范畴。

#### 压缩上下文

- 释放：覆盖矩阵中间草稿、逐条比对原始过程
- 保留：`cross_check_report.md`、异常项清单、待用户决策项（补充/废弃）
