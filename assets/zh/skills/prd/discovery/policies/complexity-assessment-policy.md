# 需求复杂度评估策略

## 1. 评估原则

1. **量化可落地**：所有维度均设置明确阈值与得分标准，无主观模糊判定项，Agent 可稳定复现执行。
2. **变更风险主轴**：复杂度由「变更的风险与代价」决定——变更幅度、回归风险、可回滚性、现状复杂度。增删改查（CRUD）与既有功能轻量迭代稳定落「简单档」，规模与实体数量降为辅助信号（见 §4）。
3. **宁严勿松 + 双向校准**：初审边界模糊就高不就低；二次校准支持双向调整，但**下调需显式确认**（见 §6.2）。
4. **全流程联动**：评估结果直接联动澄清交互、扫描深度、流程档位、评审强度、交付粒度，而非仅影响澄清交互（见 §6.3）。
5. **风险兜底**：高危场景触发分级升档，致命信号不受总分限制一票升档，堵住高风险需求被轻判的漏洞（见 §5）。
6. **持续迭代**：基于历史交付数据定期校准阈值与权重，保障评估结果与实际复杂度匹配。定档时的系统评估值 + 人工覆盖记录（见 §6.4）即为此提供回溯数据源。

## 2. 评估维度与评分细则

### 2.1 总分计算规则

需求复杂度总分 = 业务复杂度得分 + 技术复杂度得分 + 合规风险复杂度得分。**满分 54 分**（业务 20 + 技术 24 + 合规 10），所有维度均为正向加分，得分越高代表需求复杂度与交付风险越高。

### 2.2 业务复杂度（满分 20 分）

| 评估维度 | 评分规则 | 分值 |
|----------|----------|------|
| 涉及用户角色数 | 仅 1 类角色 | 0 |
| | 2 类角色 | 1 |
| | 3 类及以上角色 | 2 |
| 核心业务场景数 | 仅 1 个主场景，无独立分支场景 | 0 |
| | 2-3 个独立业务场景 | 2 |
| | 4 个及以上独立业务场景 | 3 |
| 流程分支复杂度 | 纯线性主干流程，无条件/异常/驳回分支 | 0 |
| | 1-3 个条件/异常/判断分支 | 1 |
| | 4-6 个条件/异常/判断分支 | 2 |
| | 7 个及以上条件/异常/判断分支 | 3 |
| 需求变更幅度 | 纯参数、文案、展示样式调整，不改变业务逻辑 | 0 |
| | 局部业务逻辑调整，不改变主干流程 | 2 |
| | 新增完整业务流程，或重构主干流程 | 4 |
| 业务规则复杂度 | 无复杂计算与判断逻辑，纯数据流转 | 0 |
| | 简单层级判断与基础计算公式 | 2 |
| | 多层嵌套规则、多维度组合判断逻辑 | 3 |
| | 引擎级规则配置、复杂计费/风控类计算逻辑 | 4 |
| 需求完备性与清晰度 | 需求边界清晰、规则无歧义、输入输出明确 | 0 |
| | 存在局部模糊点，需少量澄清确认 | 1 |
| | 需求边界模糊、核心规则不明确，需大量澄清与补全 | 2 |
| 业务域熟悉度 | 成熟业务域，团队具备充分交付经验 | 0 |
| | 全新细分业务域，需一定学习成本 | 1 |
| | 完全陌生业务领域，无历史交付经验 | 2 |

### 2.3 技术复杂度（满分 24 分）

| 评估维度 | 评分规则 | 分值 |
|----------|----------|------|
| 跨独立系统数量 | 单系统内调整，不涉及跨系统交互 | 0 |
| | 横跨 2 个独立业务系统 | 3 |
| | 横跨 3-4 个独立业务系统 | 4 |
| | 横跨 5 个及以上独立业务系统 | 5 |
| 数据模型变更幅度 | 不新增数据表/核心业务对象、不改字段结构 | 0 |
| | 新增/修改现有实体的字段 | 1 |
| | 新增 1 个核心业务实体 | 2 |
| | 新增 2 个及以上核心业务实体，或改造核心数据结构 | 3 |
| 核心链路改造程度 | 不触碰系统核心业务链路、核心数据流转 | 0 |
| | 局部修改核心链路非核心节点逻辑 | 2 |
| | 改造核心链路主干逻辑、核心计算规则 | 4 |
| 第三方系统对接 | 不依赖外部第三方系统/接口 | 0 |
| | 改造现有第三方对接逻辑 | 2 |
| | 新增第三方系统对接 | 3 |
| 非功能性需求要求 | 无特殊要求，沿用现有系统标准 | 0 |
| | 有明确性能/兼容性/安全性增强要求 | 2 |
| | 有高并发、大数据量、等保三级以上严苛要求 | 3 |
| 回归与可回滚风险 | 常规发布，可快速回滚或开关关闭 | 0 |
| | 常规发布，需回归测试 | 1 |
| | 涉及多环境联调或灰度发布 | 2 |
| | 不可回滚，或回滚成本极高 | 3 |
| 现状复杂度（迭代需求必评，全新需求记 0） | 改的是简单功能，现状一眼可辨 | 0 |
| | 现状中等复杂，需梳理现有规则/数据 | 2 |
| | 现状复杂链路/数据/规则，需代码级验证 | 3 |

> **计分互斥说明**：若需求已因「跨独立系统」「第三方对接」计分，「核心链路改造」仅统计本系统内部的核心逻辑改造，跨系统交互部分不重复计分。

### 2.4 合规风险复杂度（满分 10 分）

| 评估维度 | 评分规则 | 分值 |
|----------|----------|------|
| 数据敏感等级 | 仅涉及普通业务数据、公开数据 | 0 |
| | 涉及用户一般个人信息（手机号、地址等） | 2 |
| | 涉及敏感个人信息（身份证、银行卡、生物特征、资金数据） | 4 |
| 监管合规强制要求 | 无明确行业监管、数据合规强制要求 | 0 |
| | 需满足行业通用合规规范 | 2 |
| | 有明确强监管要求，违规存在法律/行政处罚风险 | 3 |
| 合规影响范围 | 仅影响内部用户/少量外部用户 | 0 |
| | 影响全量用户或核心业务数据 | 2 |
| 审计追溯要求 | 无特殊审计留痕要求 | 0 |
| | 需满足全链路操作留痕、可审计追溯 | 1 |

## 3. 复杂度分级标准

| 等级 | 总分区间 | 典型场景 | 核心管控要求 |
|------|----------|----------|--------------|
| 简单需求 | 0-7 分 | 增删改查、简单表单/展示、状态开关；文案/参数/展示样式修改；既有功能轻量迭代（加字段/改规则/完善逻辑）；逻辑简单、不改变核心链路 | 无需正式评审，快速交付，常规功能测试 |
| 标准需求 | 8-20 分 | 多角色、单系统内的新增功能模块；常规业务流程新增；局部逻辑调整；无高合规风险 | 产品+技术常规评审，标准研发流程，全量功能测试 |
| 复杂需求 | 21-33 分 | 跨 2 个系统需求；新增核心业务实体；改造核心链路；涉及第三方对接；中高合规风险 | 架构师参与技术评审，方案先行设计，增强测试覆盖，上线前专项复核 |
| 极复杂需求 | 34 分及以上 | 横跨多系统的核心业务重构；大规模数据模型改造；强监管高危场景；核心生产链路重大调整 | 技术委员会评审，分阶段里程碑交付，专项测试与安全审计，全链路灰度发布 |

## 4. 变更风险主轴与简单豁免

### 4.1 判定主轴

复杂度主轴 = **变更的风险与代价**，由「变更幅度 + 回归风险 + 可回滚性 + 现状复杂度」决定。**逻辑复杂度**（业务规则/状态流转/计算/并发）降为"全新场景"下变更幅度的代理，不再独立当主轴；规模与实体数量为辅助信号，风险分级兜底。

主轴用于**快速分流**（初判选链路）与**简单豁免判定**，是定档的权威路径；§2 评分表降为**主轴边界模糊时的复核工具**（见 §6.4）。

| 主轴信号 | 简单 | 标准 | 复杂 |
|----------|------|------|------|
| 变更性质（首行分流） | 全新 CRUD；既有功能局部迭代 | 全新模块；既有功能多规则扩展 | 全新跨系统；既有核心链路改造 |
| 变更幅度 | 参数/文案/展示/单字段/单条规则 | 局部业务流程/多规则/多字段 | 新增完整流程 / 重构主干 |
| 业务规则变动 | 增改 ≤3 条或极简校验 | 4~15 条明确规则 | >15 条或规则联动/引擎级 |
| 状态流转变动 | ≤2 状态（或不动） | 3~5 状态 | 复杂状态机 / 并发 / 事务 / 幂等 |
| 计算/统计变动 | 无或极简 | 有（聚合/统计/计算） | 复杂计算 / 资金 / 时序 |
| 现状复杂度（迭代必评） | 改的是简单功能，一眼可辨 | 现状中等，需梳理现有规则 | 现状复杂链路/数据，需代码级验证 |
| 回归风险 | 局部展示/单操作，不影响他人 | 多角色受影响，需常规回归 | 核心用户/核心链路受影响 |
| 可回滚性 | 可快速回滚或开关关闭 | 常规发布回滚 | 不可回滚或回滚成本极高 |
| 高危信号 | 无 | 无 | 资金/敏感个人信息/监管/核心链路（**一票复杂起步**，见 §5） |

### 4.2 简单豁免规则

当需求属于以下两类之一，且同时满足对应条件时，规模类维度（`需求变更幅度`、`数据模型变更幅度`、`跨独立系统数量`、`第三方系统对接`）**不计分**，需求落「简单档」。**豁免只作用于规模类加分，风险类维度（`回归与可回滚风险`、`现状复杂度`、`高危信号`）永不豁免。**

**A. 全新极简 CRUD**（标准增删改查 / 简单表单 / 状态开关）：
- 业务规则复杂度 = 0（仅极简校验：必填/唯一/格式/范围）；
- 流程分支复杂度 ≤ 1（条件/异常/判断分支 ≤ 3 个）；
- 无计算/聚合/统计逻辑，无并发/事务/幂等要求；
- 单系统内，无高危信号（§5）。

**B. 既有功能轻量迭代**（参数/文案/展示/单字段/单条规则的局部调整）：
- 不新增完整业务流程、不重构主干流程；
- 不改状态机、不新增计算逻辑；
- 现状复杂度低（改的是简单功能）；
- 回归风险低（局部展示/单操作）；
- 无高危信号（§5）。

> 堵漏：一旦命中任一逻辑复杂度信号（规则 > 0、分支 > 1、有计算/并发），**豁免失效**，规模类维度正常计分。**新增数据实体本身不是升档理由**——CRUD 天然新增实体，逻辑极简即豁免。**一条"改核心链路的单字段"规模上是单字段，但高危信号一票复杂，豁免不生效。**

## 5. 高危场景分级升档

### 5.1 致命高危（一票升档，最低「复杂」起步）

满足以下任意一条，**不受总分限制，直接升档至「复杂」起步**（原档已是复杂则升「极复杂」）：

1. 涉及资金交易、支付结算、财务对账、计费扣费类核心逻辑调整；
2. 涉及用户身份证、银行卡、生物识别、户籍等高度敏感个人信息的核心处理逻辑变更；
3. 改造系统核心生产链路，故障会导致全平台核心业务中断、核心数据一致性错误；
4. 有明确强监管合规要求，违规会导致法律风险或重大行政处罚。

### 5.2 严重高危（逐级升一级）

满足以下任意一条，**当前等级向上提升一级**，最高升至「极复杂」：

5. 涉及批量历史数据迁移、数据清洗、核心数据结构改造，存在数据丢失/不一致风险；
6. 多租户 SaaS 系统的租户隔离逻辑、权限体系核心改造；
7. 涉及底层基础组件（数据库、缓存、消息中间件）核心架构调整；
8. 上线后不可回滚、或回滚成本极高的需求。

### 5.3 判定依据

「核心生产链路」以各系统官方发布的《核心链路清单》为判定依据；无官方清单时，由技术委员会（或用户在确认点）最终裁定。

## 6. 执行与校准机制

### 6.1 评估流程与角色职责

| 步骤 | 时机 | 执行角色（当前平台） |
|------|------|----------------------|
| 初评 | 需求澄清完成、正式进入研发评审前（discovery Step 2.2） | AI 主代理按 §2 逐维评分 + §5 校验高危 |
| 二次校准 | 资源扫描发现隐性信息后（discovery Step 3.4） | AI 主代理重评（见 §6.2） |
| 专项复核 | 技术维度 | subagent 模拟技术负责人/架构师复核 |
| | 合规维度 | subagent 模拟合规/安全负责人复核 |
| 最终确认 | 定档前 | 用户（需求提出人）在确认点最终确认等级（交互与落盘见 §6.4） |

> 理想态（需平台多参与者能力）：初评由需求分析师/产品经理执行，技术/合规由对应负责人复核，研发项目负责人最终确认——列为后续演进。

### 6.2 双向校准

1. 初审默认「宁严勿松」，边界模糊场景就高不就低；
2. 需求方或研发方对结果有异议，可提交佐证材料申请二次校准；
3. **上调复杂度**：由评估人直接调整即可生效；
4. **下调复杂度**：需提交对应维度佐证材料，并经**用户按 `decision-point.md` 显式确认**后方可调整（与 `risk-signals.md` §6「下调须显式确认」同构）。

### 6.3 全流程联动

复杂度等级直接联动以下执行环节：

| 联动项 | 简单 | 标准 | 复杂 / 极复杂 |
|--------|------|------|---------------|
| 澄清交互 | 单轮批量 | 按优先级分 3 轮批量 | 单轮单问 |
| 扫描深度 | 核心 3 维 | 全维 | 全维 + 隐性约束深挖 |
| 流程档位（`workflow.mode`） | tweak | normal | strict |
| 评审强度 | 免评（readiness 免评路径） | review + readiness | review + testability + readiness 全量 |
| 交付粒度 | 单页需求说明 / 变更说明 | 标准 PRD（精简章节） | 完整 PRD（11 章 + 4 附录） |

> 流程档位、评审强度、交付粒度的权威描述在 `docs/design/2026-10-29-prd-graded-workflow-design.md`；本表只声明「联动什么」，不复制流程细节。

### 6.4 定档人机确认与回溯

**触发时机**：discovery Step 3.4 二次校准完成后，立即执行一次「定档确认」（唯一强制确认点）。初判（Step 2.2）只回显不确认；澄清中触发高危升档只回显不确认（升档保底直接生效，见 §6.2）。

**回显内容**：系统评估档位、总分（业务/技术/合规分项）、命中的主轴信号、高危信号、豁免规则、建议流程档位（`workflow.mode`）。

**用户选项**（四档直选，系统建议高亮）：

> A. 简单　B. 标准　C. 复杂　D. 极复杂

- 选系统建议档 = 认可，无需理由。
- 选其它档 = 人工覆盖，须附一句理由：上调直接生效；下调按 §6.2 属显式确认，一并满足。

**回溯落盘**（无论认可或覆盖，均记录）：系统评估值（不可变）与最终值（人工确认后）分两段写入 `state.yaml` 的 `complexity` 块，`req_baseline.md` 元数据区同步留痕——`system_assessment`（tier/score/business/technical/compliance/axis_signals/risk_signals/waiver）+ `final_tier` / `overridden` / `override_direction` / `override_reason` / `confirmed_at` / `confirmed_by`。

> 用途：事后发现误判（简单实为复杂）时，回溯「系统评了什么、人工怎么改、为什么」，据此校准主轴信号与阈值——即 §1.6「持续迭代」的数据来源。

## 7. 与工作流档位的映射

复杂度等级（本 policy 的四档）与工作流档位（`workflow.mode` 三档）的映射**单源声明于此**，其余地方不得内联副本：

| 复杂度等级 | `workflow.mode` | 备注 |
|------------|-----------------|------|
| 简单 | `tweak` | 轻量链路 |
| 标准 | `normal` | 标准链路 |
| 复杂 | `strict` | 严格链路 |
| 极复杂 | `strict` | 严格链路内最高强度（技术委员会/里程碑/专项审计） |

> 与 `risk-signals.md` §1「`trivial → tweak`、`standard → normal`、`critical → strict`」**同构**——PRD 侧输入是「复杂度四档」，coding 侧输入是「变更分级三档」，语义对应（简单≈trivial、标准≈standard、复杂·极复杂≈critical），但**不复用同一张表**（两族输入名不同）。

## 附录：核心术语定义

1. **核心业务场景**：具备独立业务价值、完整用户操作闭环的业务流程；同一功能的增删改查操作属于同一业务场景。
2. **流程分支**：包含正常业务条件分支、异常分支、驳回分支、回退分支，每一个独立的判断路径计为 1 个分支。
3. **核心数据实体**：承载核心业务逻辑、支撑主流程运转的业务对象（如订单、用户、合同）；字典表、配置表、日志表等附属表不计入。
4. **独立业务系统**：具备独立数据库、独立部署、独立服务边界的业务系统；同一系统内的不同模块不算独立系统。
5. **核心生产链路**：支撑平台核心收入、核心用户体验、核心数据流转的关键业务链路，故障会造成重大业务损失或合规风险。
6. **敏感个人信息**：依据《中华人民共和国个人信息保护法》定义的敏感个人信息范畴。
