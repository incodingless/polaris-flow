# 原始需求质量要求与校验

> discovery Step 2.0 的输入质量校验标准。SKILL `read_file` 本文件执行校验，不内联副本。

## 一、定位

discovery 期望接收的输入是**格式化的原始需求**——即**内容覆盖必要要素**的完整需求描述（质量意义上的「格式化」，**非严格表单**，不要求按固定模板 / 字段提交，保留「一句话想法也能启动」的入口）。

本校验是**柔性闸门，不硬阻断**：质量不足时提示补齐；用户执意继续时风险提示 + 留痕放行。

## 二、必要要素清单（按变更性质分流）

先粗判变更性质（全新 vs 迭代），再套对应必备清单：

| 变更性质 | 判定线索 | 必备要素（3 项） |
|---|---|---|
| 全新 | 「做一个 XX」「新增 XX 功能」 | ① 业务背景 / 痛点　② 核心目标　③ 目标用户 / 角色 |
| 迭代 | 「改 / 优化 XX」「给 XX 加字段 / 导出」 | ① 改动对象　② 改动内容　③ 改动原因 |

各必备要素含义与饱满度要求：

| 要素 | 含义 | 要求 |
|---|---|---|
| 业务背景 / 痛点 | 为什么做、现状有什么问题 | 讲清「不做会怎样」 |
| 核心目标 | 做成什么样 | 可验证，非「更好用」这类模糊词 |
| 目标用户 / 角色 | 给谁用、涉及哪些角色 | 从零定义，说清范围 |
| 改动对象 | 改哪个现有功能 | 一句话定位到模块 / 页面 |
| 改动内容 | 改成什么样 | 现状 → 目标 的差异 |
| 改动原因 | 为什么改 | 允许极简一句话 |

**迭代特有规则**：目标用户 / 角色默认沿用现有功能的使用者，无需重述；仅当本次改动涉及角色 / 权限变更时才需说明。

**建议要素（两类通用，缺失不阻断，澄清阶段补）**：

- 范围边界（做什么 / 不做什么）
- 核心流程 / 场景（主路径）
- 约束与依赖（时间 / 技术 / 合规 / 成本 / 依赖）
- 验收预期（怎么样算做成）

> 本清单与已有「五要素（角色 / 场景 / 任务 / 诉求 / 业务目标）+ 5W2H + 必问项 6 项」对齐，不另造体系。范围边界不设必备——实践里很多人提需求时不会主动想「不做什么」，设必备会频繁触发提示变骚扰；但它又是澄清阶段高频必问项，故单列建议并重点标注。

## 三、合格判定

- 必备要素**全覆盖** → 合格，进入 Step 2.1。
- 必备要素**有缺失** → 不合格，回显「缺失清单」（缺哪几项 + 每项一句话怎么补），请用户补齐后重新校验。
- 建议要素缺失 → 不提示（或仅标注），留澄清阶段处理。

## 四、风险提示（用户执意继续时）

用户明确「就这样往下」不补齐时，回显三类后果并放行：

1. **澄清成本上升** —— 缺失要素要在澄清阶段逐个问出，往返更多、更耗时。
2. **复杂度定档可能不准** —— 输入模糊 → 复杂度误判 → 走错链路（该重的走轻 / 该轻的走重）。
3. **产出可能偏离真实诉求** —— 关键要素缺失 → AI 靠猜补全 → 猜错 → 文档跑偏。

**留痕**：《需求基线》标记「原始需求质量不足（缺 X 项），已风险提示，用户执意继续」，供下游追溯——尤其 readiness 的 D2「与原始需求一致」维度会受影响。
