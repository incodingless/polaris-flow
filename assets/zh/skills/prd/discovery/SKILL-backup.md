# 编写产品需求-探索并澄清需求

<HARD-GATE>
- **事实与假设严格分离**：所有未经过原文确认、资源验证、人工澄清的内容，必须标记为假设，禁止当作既定事实。
- **问题域与方案域解耦**：先锚定本质问题与业务目标，再讨论实现路径；禁止用用户提出的方案替代需求本身。
- **极简拆解不脑补**：仅提取字面显性信息，禁止任何形式的反向推导与自动补全。
- **定向扫描不越界**：资源加载严格以检索关键词为边界，禁止无目的泛读；隐性信息捕获必须有明确资源支撑。
- **澄清问题封闭化**：所有待澄清问题必须具体、可直接作答，禁止出现 “还有什么补充” 这类宽泛问题。
- **变更全程可追溯**：所有需求变更必须记录前后对比与依据，禁止静默修改需求基线。
</HARD-GATE>

**启动时必须先输出**：`[polaris-flow PRD] 进入阶段: 探索并澄清需求 — 使用 polaris-flow{{SKILL_NAME_SPLITTER}}prd-discovery 技能。`

### Step 3：需求理解与结构化拆解

仅基于用户需求本身，提取全部显性信息，形成检索关键词与待补全方向，不做任何推导、脑补和方案设计，为后续定向扫描提供精准方向。

#### 3.1 无损固化原始需求

完整读取并在内部保留原始需求全文，作为后续变更对比、范围校验的基准；禁止修改、润色、简化或改写原文。

#### 3.2 极简结构化拆解（仅提取显性信息）

仅从原始需求字面表述中提取以下要素，用户未明确提及则标记为「待补全」，禁止反向推导：

- 明确提到的使用角色、用户类型
- 明确描述的业务场景、触发时机
- 明确提出的核心任务、功能诉求
- 明确说明的业务目标、预期效果
- 明确给出的候选实现方案
- 明确标注的约束条件、时间要求

#### 3.3 生成定向检索输入

基于拆解结果，输出三类检索依据：

- 核心关键词集合：角色名、业务术语、功能模块名、系统名
- 待补全维度清单：当前缺失的五要素项、未定义的术语、不明确的边界
- 待验证假设方向：原始需求中默认成立但未说明的前提线索

#### 3.4 任务名称确认（阻塞点）→ 得到 `task_id`

约束：`task_id` 必须是 **kebab-case 英文**（小写字母、数字、连字符），如 `refine-requirements-doc`。

暂停时必须展示：

- 基于已确认摘要派生的 **2–3 个推荐名**，各附一行范围说明
- 「自行输入名称」选项
- 提示：非合规输入（含中文）会转换为 kebab-case，**转换结果须回显并再次确认**

名称与已有 `$REPO_ROOT/.polaris/tasks/` 目录冲突时，报告冲突并请用户另选。

### Step 4：信息收集调研 + 领域知识补全

以 Step 3 的关键词与待补维度为方向，按需扫描各类资源，补齐上下文、统一定义、发现隐性约束，避免无差别全量扫描的低效与冗余；完成后执行复杂度二次校准。

#### 4.1 信息收集 + 领域知识补全

按优先级依次执行四类资源的定向检索，所有检索结果均标注来源；扫描过程中主动捕获原始需求未提及但高度相关的隐性信息：

1. **本地需求文档定向扫描**：

   - 调用工具：`FileSystemAgent`
   - 检索策略：以核心关键词匹配文档标题与正文段落，优先精读高相关章节，跳过与当前需求无关的文档与段落
   - 重点提取：同类历史需求规则、业务流程说明、已确认的边界约束、跨系统对接约定
2. **项目代码定向扫描**

   - 调用工具：`CodeAgent`
   - 检索策略：按业务关键词定位对应模块代码、接口定义、数据表结构，优先读取注释、配置文件与常量定义
   - 重点提取：现有系统已实现的同类能力、技术栈限制、硬编码业务规则、已有数据结构
3. **MCP 内部资料定向调取**

   - 调用工具：`MCPAgent`
   - 检索策略：按业务域、术语关键词匹配关联规范、历史决策、监管要求
   - 重点提取：企业内部业务规则、行业合规条款、历史需求澄清记录、上下游系统接口标准
4. **网络公开信息定向检索**

   - 调用工具：`WebSearchAgent`
   - 检索策略：针对未定义的行业术语、陌生业务概念、通用合规标准做精准搜索，不做泛化检索
   - 结果校验：优先采信官方标准、权威机构文档，排除非权威来源内容
5. **隐性信息捕获**
   扫描过程中发现的、原始需求未提及但与需求强相关的约束、规则、历史决策，单独归类为「隐性上下文补充项」，标注来源后纳入后续分析。

#### 4.2 需求复杂度二次校准

加载需求复杂度评估策略：`read_file` `./policies/complexity-assessment-policy.md`，基于资源扫描发现的隐性约束、核心链路关联、历史风险点，重新执行复杂度评分。

#### 4.3 增加记录需求理解纪要

需求基线文档路径：`$REPO_ROOT/tasks/<task_id>/req-baseline.md`，增量写入以下内容：

- 第 9 章附录写入：参考资源清单、术语释义表
- 更新元数据区复杂度最终等级与校准说明
- 隐性约束与规则暂存草稿区，待阶段 3 整合

#### 4.4 完成信息收集调研

释放：全部原始扫描文本、未命中检索结果、无关文档片段、原始代码全文
保留：提炼后的约束条目、隐性上下文清单、术语定义、资源引用标识、复杂度最终等级

输出：`[polaris-flow PRD] 完成信息收集调研及领域知识补全`

### Step 5：结构化需求理解 + 方案解耦

基于用户需求、调研及补全的信息等全部上下文，完成正式的、深度的需求结构化拆解，严格区分真实问题与用户提出的实现方案。

#### 5.1 需求五要素建模

结合全部上下文，输出完整的需求五要素画像，所有推导内容必须标注信息来源：

- **角色**：全量涉及的使用者、决策者、受益者、上下游系统角色，及各角色权限边界
- **场景**：完整业务链路、触发条件、使用频率、前置 / 后置条件、异常场景
- **任务**：用户需完成的核心动作、操作流程、输入输出、数据流转
- **诉求**：用户的直接体验诉求、功能诉求、性能诉求
- **业务目标**：底层业务价值、可量化指标、与业务战略的关联

#### 5.2 方案与需求解耦

- 单独归集用户提出的所有具体实现方式，列为「候选实现方案」
- 反向推导每个方案对应的本质问题：如果不采用该方案，用户要解决的核心痛点是什么
- 校验是否存在更优路径可解决同一问题，标记为「可选替代方向」

#### 5.3 约束条件汇总

整合原始需求与资源扫描中发现的全部约束，按时间、成本、技术、合规、业务五类归类。

#### 5.4 增量补充需求基线

需求基线文档路径：`$REPO_ROOT/tasks/<task_id>/req-baseline.md`，增量写入：

- 第 3 章 结构化需求全貌（角色、场景、任务、诉求、业务目标）
- 第 4 章 核心约束汇总
- 第 5 章 方案与本质需求对应说明

#### 5.5 完成结构化需求理解

上下文释放规则：

- 释放：拆解中间稿、方案推导过程、零散要素草稿
- 保留：最终版五要素画像、约束清单、方案对应关系

### Step 6：候选功能架构推导 + 架构层模糊点挖掘

该需求的复杂度为简单需求，则跳过本阶段，直接进入 Step 7。

基于完整需求画像，系统性识别所有不明确、有歧义、缺边界的内容，同时从业务、技术、合规、成本四个维度校验需求合理性，输出待澄清问题全集。

#### 6.1 执行动作

1. **一级模块拆分**：围绕核心业务目标与角色，拆解 3-5 个一级业务模块
2. **二级功能点拆解**：每个一级模块拆解为若干「动词 + 名词」格式的二级功能点
3. **六大方法反向挖掘架构层模糊点**：
   - 模块边界拆解法：逐功能拷问包含 / 不包含、程度深浅、例外场景，识别边界模糊点
   - 角色 - 功能矩阵法：角色与功能交叉校验，识别权限、角色覆盖模糊点
   - 流程链路串联法：串联主干流程，排查失败、超时、中断分支，识别流程模糊点
   - 数据流转推演法：推演输入 - 处理 - 输出全链路，识别数据规则模糊点
   - 通用能力抽取法：识别多模块复用能力，校验一致性与复用规则，识别复用模糊点
   - 依赖关系梳理法：梳理模块间、系统间依赖，识别依赖与降级方案模糊点
4. **L1 代码级存在性验证**：对标记为「已有复用」「需改造」的功能点，逐一验证代码中真实存在性与核心逻辑匹配度，验证不通过的标记为高优先级模糊点
5. **属性标记**：每个功能点标记确认状态（已确认 / 待确认）、重要程度（核心必选 / 重要可选 / 扩展增强）、已有能力映射（已有 / 新增 / 需改造）

#### 6.2 增量补充需求基线

1. 需求基线文档路径：`$REPO_ROOT/tasks/<task_id>/req-baseline.md`，第 6 章写入候选功能架构草案，醒目标注「候选方案，待澄清确认」
2. 所有架构衍生模糊点同步纳入待澄清问题池

#### 6.3 完成候选功能架构推导

- 释放：功能推导草稿、重复功能点、过细实现思路、备选方案推演过程
- 保留：候选功能模块树、模块依赖关系、架构衍生模糊点、已有能力映射结果

### Step 7：全维度模糊点识别 + 需求合理性校验

> 执行粒度遵循复杂度联动规则：简单需求仅扫描核心维度，标准 / 复杂需求全量覆盖。

#### 6.1 多维度扫描

需求扫描维度：


| 维度         | 检查要点                                                         |
| -------------- | ------------------------------------------------------------------ |
| 冲突假设类   | 段落间互相矛盾之处                                               |
| 信息缺失类   | 五要素、5W2H 是否完整，核心输入输出是否明确                      |
| 概念歧义类   | 是否存在主观形容词、量化模糊词、一词多义、未定义术语             |
| 边界范围类   | 功能边界、用户边界、数据边界、场景边界是否清晰，异常流程是否覆盖 |
| 隐含假设类   | 是否存在未言明的业务、数据、技术、使用假设                       |
| 约束缺失类   | 时间、成本、性能、兼容性、合规等约束是否明确                     |
| 优先级依赖类 | 多功能点优先级是否划分，与现有系统 / 功能的依赖关系是否清晰      |
| 缺口         | 缺状态机/权限/失败态/数据归属等                                  |

根据需求复杂度对应的扫描维度逐项扫描完成：

- 简单需求：扫描核心 3 维度（信息缺失、边界范围、约束缺失）
- 标准 / 复杂需求：全量 6 维度扫描（信息缺失、概念歧义、边界范围、隐含假设、约束缺失、优先级依赖），能通过现有资料补全的自动补全，无法补全的列入待澄清清单

#### 6.2 六项必问项强制校验

硬性校验以下 6 项是否覆盖，未覆盖则自动补充为高优先级问题，确保无遗漏：

- 需求命名与模块归属
- 核心范围边界（做 / 不做）
- 角色与权限边界
- 核心业务流程
- 数据指标与效果验证方式
- 配置模型 / 状态枚举验证（涉及现有配置修改时必查）

#### 6.2 需求合理性识别

需求合理性识别维度：

- **实现必要性**：区分是**强痛点**（不做则无法推进工作）还是**痒点**（锦上添花）；是高频普遍问题还是低频个别问题
- **业务合理性**：是否符合业务逻辑，是否与现有规则冲突，是否存在重复建设，目标是否可验证
- **技术可行性**：是否适配现有技术栈，是否依赖未开放能力，是否存在明显性能瓶颈
- **合规性**：是否满足数据安全、隐私保护、行业监管、内部制度要求
- **成本合理性**：投入产出是否匹配，是否存在过度设计，是否有低成本替代方案

根据需求复杂度，完成识别：

- 简单需求：仅做业务合理性单点判断
- 标准 / 复杂需求：业务合理性、技术可行性、合规性、成本合理性四维度全量校验，存疑点列入待澄清清单

#### 6.3 问题分级与预处理

按高 / 中 / 低优先级划分所有问题，基于现有资料为每个问题生成 2-3 个带来源支撑的备选答案。

- 高优先级：业务目标、角色、核心范围、核心流程等底层问题
- 中优先级：功能模块拆分、权限、数据规则、架构边界等问题
- 低优先级：细节体验、边缘场景、优化类问题

#### 8.1 多轮澄清

1. **澄清模式自适应**

   - 简单需求：单轮批量提交所有问题
   - 标准需求：按高 / 中 / 低优先级分 3 轮批量提交
   - 复杂需求：强制单轮单问模式，一次只呈现一个问题，用户答复后再抛出下一个
2. **分层推进规则**
   严格遵循「先业务后架构」顺序，前序问题未确认不进入下一层级：

- 第一层：高优先级业务核心问题（目标、角色、范围、流程）
- 第二层：中优先级架构与规则问题（模块拆分、权限、数据、依赖）
- 第三层：低优先级细节与体验问题

3. 问题呈现格式
   每个问题统一按以下结构呈现，确保信息完整、可直接作答：

> 【问题编号 + 优先级】问题描述
> 背景说明：识别该问题的依据与对应上下文
> 备选答案：
> A. 推荐选项 1（支撑来源：xxx）
> B. 推荐选项 2（支撑来源：xxx）
> C. 其他（请补充说明）

4. 动态更新机制
   每收到一轮 / 一个答复，立即执行：

- 更新 Baseline 中对应章节的草稿内容
- 重新校验需求完整性，识别新增模糊点并纳入后续澄清
- 同步更新合理性结论
- 记录变更前后对比与依据

4. 增量补充
   **每一轮澄清完成后立即更新文档，不等待全部轮次结束**：

- 同步更新《需求理解纪要》（路径：`$REPO_ROOT/.polaris/tasks/<task_id>/understanding-summary.md`） 第 3/4/6/7 章中发生变更的内容
- 向《需求澄清纪要》（路径：`$REPO_ROOT/.polaris/tasks/<task_id>/clarify-summary.md`）写入：问题最终答复、补充说明、确认信息；需求变更记录；隐含假设与风险清单

5. 结束条件
   所有问题均得到明确答复，或用户确认剩余未明确项全部转为「后续待跟进」。
