# 编写产品需求-探索并澄清需求

<HARD-GATE>
- **事实与假设严格分离**：所有未经过原文确认、资源验证、人工澄清的内容，必须标记为假设，禁止当作既定事实。
- **问题域与方案域解耦**：先锚定本质问题与业务目标，再讨论实现路径；禁止用用户提出的方案替代需求本身。
- **极简拆解不脑补**：仅提取字面显性信息，禁止任何形式的反向推导与自动补全。
- **定向扫描不越界**：资源加载严格以检索关键词为边界，禁止无目的泛读；隐性信息捕获必须有明确资源支撑。
- **澄清问题封闭化**：所有待澄清问题必须具体、可直接作答，禁止出现 “还有什么补充” 这类宽泛问题。
- **变更全程可追溯**：所有需求变更必须记录前后对比与依据，禁止静默修改需求基线。
</HARD-GATE>

**启动时必须先输出**：`[polaris-flow PRD] 进入阶段: 探索并澄清需求 — 使用 polaris{{SKN_SPR}}prd{{SKN_SPR}}discovery 技能。`

## 流程

> **上下文整理通用规则**：每个 Step 收尾时，统一释放该步的中间推导草稿、重复条目、冗余对话与已闭环问题的原始草稿；仅保留已确认结论、剩余待澄清项、变更记录、隐含假设清单（下文各「整理上下文」子步骤只列本步需保留的关键产出）。

### Step 0: 设置产物语言

读取 `.polaris/config.yaml` 的 `language`（规范化 ID，如 `en`、`zh`）；未配置时回退到当前用户请求语言。本阶段所有提问与澄清摘要均采用该语言。

### Step 1: 状态检查及中断恢复

使用 SessionStart 注入的路径（本 skill 内此后一律复用 `$REPO_ROOT` / `$PLUGIN_ROOT`）：

- 环境变量 `$PLUGIN_ROOT` / `$REPO_ROOT`（Trae `env`、 Cursor `env`、Claude `CLAUDE_ENV_FILE`，或 Agent 上下文中的同名赋值）
- 仍无 `$PLUGIN_ROOT` → 按 H12 阻断，提示用户重启会话以触发 SessionStart

```bash
if [ -z "$PLUGIN_ROOT" ] || [ ! -f "$PLUGIN_ROOT/scripts/workflow-entry.sh" ]; then
  echo "PLUGIN_ROOT unset or hooks missing — restart session to run SessionStart" >&2
  exit 2
fi

ACTIVE_RESULT=$(bash "$PLUGIN_ROOT/scripts/workflow-entry.sh" get-active-changes \
  --kind requirement --skill discovery --repo-root "$REPO_ROOT")
ACTIVE_EXIT=$?
echo "ACTIVE_EXIT=$ACTIVE_EXIT ACTIVE_RESULT=$ACTIVE_RESULT"
```

**输出解读**（读 `ACTIVE_RESULT` JSON 数组，元素为 `task_id`）：

| `ACTIVE_EXIT` | 含义 | 后续动作 |
| ------------- | ---- | -------- |
| 0 且数组非空 | 存在未完结需求任务 | 按决策点协议询问 A/B/C/D（见下） |
| 0 且数组为空 | 无活跃需求任务 | 进入 Step 2 开启新任务 |
| 非 0 | 参数/环境错误 | 按 H12 阻断 |

存在活跃任务时，**必须**按 `./policies/decision-point.md` 暂停询问：

- **A. 续写最新一个**：`task_id` = 列表最后一项 → 进入 Step 1.5
- **B. 选择一个**：列出所有 `task_id` 候选让用户选择之后，再发出以下询问：

  > 当前选择任务 <task_id>，请确认以下操作：
  >
  > - **A. 续写当前任务**：进入 Step 1.5
  > - **B. 重新开始任务**：对当前 dir 执行下列命令后，进入 Step 2（重新产出需求组并建目录）
  >

  ```bash
     rm -rf "$REPO_ROOT/.polaris/tasks/$task_id"
     bash "$PLUGIN_ROOT/scripts/workflow-entry.sh" delete-active --kind requirement --skill discovery --repo-root "$REPO_ROOT" --where-task-id "$task_id"
  ```
- **C. 丢弃所有**：对每个 id 执行下列命令后，进入 Step 2

```bash
for d in <ACTIVE_RESULT 列表>; do
  rm -rf "$REPO_ROOT/.polaris/tasks/$d"
  bash "$PLUGIN_ROOT/scripts/workflow-entry.sh" delete-active --kind requirement --skill discovery --repo-root "$REPO_ROOT" --where-task-id "$d"
done
```

- **D. 取消退出**：结束本 skill

#### Step 1.5：读取任务进展，继续执行任务

读取 `$REPO_ROOT/.polaris/tasks/$task_id/state.yaml`，按状态值进入对应步骤：

| `state.yaml` 状态 / 判断依据 | 进入步骤 |
|---|---|
| `phase=discovery` 且《需求基线》仅为 2.5 写入的基础档案（第 3~7 章为空或模板占位） | 视为**未启动的基础任务**，目录/游标/初稿均已就绪，直接进入 **Step 3** 按该任务范围推进 |
| `phase=discovery` 且已有第 3 章实质内容 | 从对应未完成步骤续写（Step 3 之后） |
| `phase=draft` 或更后 | 提示用户该任务已过 discovery，引导到对应后续技能 |
| 无法判定 | 按 `./policies/decision-point.md` 询问用户从哪个步骤继续 |

### Step 2：初始化与前置校验

#### 2.1 扫描已有产物

基于本地需求文档、代码库与 MCP 内部资料（即已建立的现有系统上下文），建立对现有功能、角色、流程、术语、交互模式、数据模型的初步理解；无既有资料时跳过并标注。

#### 2.2 初判需求复杂度

加载需求复杂度评估策略：`read_file` `./policies/complexity-assessment-policy.md`，基于原始需求的显性信息，校验是否触发高危场景强制升档规则，触发则直接定为复杂需求；否则从业务复杂度、技术复杂度、合规风险复杂度三个维度逐项评分后计算总分，匹配对应等级：简单需求 / 标准需求 / 复杂需求

#### 2.3 判断是否需要拆分

基于关键词与资源扫描结果，判断需求是否涉及 2 个及以上独立业务系统。

无论拆分与否，后续都统一走同一条流程（2.4 产出需求组 → 2.5 建目录写内容 → 2.6 列任务选择 → Step 3 编写需求理解），不再按「拆分 / 非拆分」分叉出两套步骤。

#### 2.4 产出需求组（需求内容 + 推荐名称）

根据 2.3 的判断结果，产出「需求组」——一个待建任务的需求列表，每个需求带一个推荐 kebab-case 任务名。需求组归一为 1 个（不拆分）或 N 个（拆分）需求，后续步骤统一处理。

**不拆分（单系统，需求组 1 项）**，展示：

- 需求内容：需求名称、适用范围（涉及系统）、原始核心诉求摘要
- 推荐任务名：基于需求内容派生的 **2–3 个 kebab-case 推荐名**，首个为默认，各附一行范围说明

**拆分（跨系统，需求组 N 项）**，展示《子需求拆分建议》，每个子需求一行：

- 序号、子需求名、涉及系统、范围一句话、**推荐的 kebab-case 任务名**（须回显）

**任务名约束（两种情形通用）**：

- 一律 kebab-case 英文（小写字母、数字、连字符），如 `refine-user-privilege`
- 与已有 `$REPO_ROOT/.polaris/tasks/` 目录冲突时，加数字后缀（如 `-2`）消歧并回显，不得静默改名
- 推荐名默认采用；用户明确指定名称时以用户指定为准，非合规输入（含中文）转换为 kebab-case 后**回显并再次确认**

#### 2.5 初始化任务目录 + 写入需求内容

对需求组的**每一个**需求依次执行「建目录 → 写需求内容 → 登记游标」，一个都不少。

**① 建目录**（`task-init`，需求任务不创建 `draft-*` 临时目录）：

```bash
for TASK in "<任务1>" "<任务2>" ...; do
  INIT_RESULT=$(bash "$PLUGIN_ROOT/scripts/task-init.sh" "$REPO_ROOT" --kind requirement --task-id "$TASK")
  INIT_EXIT=$?
  echo "TASK=$TASK INIT_EXIT=$INIT_EXIT INIT_RESULT=$INIT_RESULT"
done
```

| `INIT_EXIT` | `status` | 后续动作 |
|---|---|---|
| 0 | `ok` | 目录与 `state.yaml` 已建，继续下一个 |
| 1 | `existing` | **立即中断**：报告冲突目录，请用户改名或删除后重试；**禁止**向既有任务目录写入内容 |
| 2 | — | 参数/环境错误，按 H12 阻断 |

**② 写需求内容**（基础任务档案）：为每个新建目录写入《需求基线》初稿，路径 `$REPO_ROOT/.polaris/tasks/<任务名>/req_baseline.md`。

1. `read_file ./templates/req_baseline_template.md` 按模板初始化，输出：
   `[polaris-flow PRD] 已读取需求基线模板 req_baseline.md`
2. 写入该需求**当前已知**的内容：

- 元数据区：需求唯一标识、当前执行阶段 `discovery`、文档版本 `V0.1`、最后更新时间
- 第 1 章 文档概览：需求名称、适用范围（涉及系统）
- 第 2 章 引用说明：源文件名称 / 版本 / 路径、提出方、接收日期、**该需求对应的原始核心诉求摘要**
- 第 8 章 后续工作建议（仅拆分时）：父需求标识、拆分理由、**本需求与其余需求的边界**
- 执行状态：**未启动**（等待被选中后推进）

未知章节保留模板占位，**禁止**编造内容。

3. 全部写入后输出：`[polaris-flow PRD] 已创建 N 个需求任务：<任务名列表>`

> 至此每个需求都是一份可独立恢复的基础任务，用户选择只决定「本次先推进哪一个」。

**③ 登记 workflow 游标**（**不可省略**：`task-init` 只建目录与 `state.yaml`，不写游标；不登记则 Step 1 的 `get-active-changes` 读不到，无法通过「B. 选择一个」恢复）：

```bash
for TASK in "<任务1>" "<任务2>" ...; do
  bash "$PLUGIN_ROOT/scripts/workflow-entry.sh" append-active \
    --kind requirement --skill discovery --repo-root "$REPO_ROOT" \
    --task-id "$TASK" --phase discovery --worktree-path "" \
    --started-at "$(date -u +%Y-%m-%dT%H:%M:%SZ)"
done
```

全部登记后，用 `get-active-changes --kind requirement` 校验：每个任务名都在返回的 `task_id` 列表里；缺任何一个都要重跑对应的 `append-active`，不得带着遗漏进入 2.6。

#### 2.6 列出任务，选择 1 个（阻塞点）

扫描 `$REPO_ROOT/.polaris/tasks/` 确认 2.5 建成的任务目录均已就绪，列出任务清单，让用户**明确选中一个**继续。

| 用户回复 | 判定 | 后续动作 |
|---|---|---|
| 指名其中一个（序号或任务名均可） | 明确选择 | 该任务作为后续全部分析的范围 |
| 「都要做」「按建议来」「先做重要的」 | **不算选择** | 重新发问，并说明本阶段一次只推进一个任务 |
| 只确认清单本身（如「没问题」） | **不算选择** | 重新发问——确认清单 ≠ 选中某一项 |
| 对清单 / 命名提出调整 | 先调整 | 调整后重新发问，不得沿用调整前的选择 |

**选项上限**：单次询问的选项数上限为 4 个。任务多于 4 个时先按业务系统分组，两级串行询问——第 1 级选业务系统，第 2 级选该系统下的任务；**禁止**把全部任务一次性罗列进单次询问。

**发问执行**：按 `./policies/decision-point.md` 暂停，按 `./policies/ask-question-react.md` 发问（工具名经平台注册表查得，不得写死）。推荐项只能作为说明，不得代替用户选择。

选择完成后：

- **选中项**：`task_id` 即其目录名，作为后续全部分析的范围；目录、需求内容初稿与游标均已就绪
- **未选中项**：保留目录、需求内容初稿与游标，状态维持「未启动」，后续可通过 Step 1 的 **B. 选择一个** 恢复；同时在选中项《需求基线》第 8 章记录这些待办任务（含目录名与范围）
- **禁止**在未得到明确选择时继续后续分析，也**禁止**替用户挑一个（包括推荐项）

**落盘《需求基线》文档（增量写入）**，路径 `$REPO_ROOT/.polaris/tasks/<task_id>/req_baseline.md`：

1. 直接读取 2.5 已写入的 `V0.1` 初稿，**增量写入**，不重新初始化、不覆盖已有章节
2. 向选中项写入：需求唯一标识、复杂度初判结果（总分、分项得分、等级、是否触发强制升档）、初始化时间、执行状态（由「未启动」改为「进行中」）
3. 上下文释放规则
   - 释放：目录全量扫描结果、无关文件列表、冗余文件元数据
   - 保留：需求唯一标识、复杂度等级、断点状态、输出目录路径

→ 完成后进入 **Step 3**（未选中的基础任务留在 Step 1 的候选里，稍后恢复）。

### Step 3：理解需求 + 结构化拆解

仅基于用户需求本身，提取全部显性信息，形成检索关键词与待补全方向，不做任何推导、脑补和方案设计，为后续定向扫描提供精准方向。

#### 3.1 阅读需求内容 + 极简结构化拆解

1. 内部锚定原始需求基线：完整读取原始需求全文，建立内部不可篡改基准副本，禁止修改、润色原文
2. 提取基线元数据：记录源文件名、版本号、引用路径、提出方、接收时间
3. 极简结构化拆解（仅提取显性信息）：仅从字面提取核心五要素（角色、场景、任务、诉求、业务目标），未提及则标记「待补全」；方案单独归集至第 5 章、约束单独归集至第 4 章，禁止反向推导
4. 生成定向检索输入：输出核心关键词集合、待补全维度清单、待验证假设方向

#### 3.2 必要信息收集 + 领域知识补全

按优先级依次执行四类资源定向检索，所有结果标注来源：

1. 本地需求文档定向扫描：关键词匹配标题与正文，优先精读高相关章节，提取历史规则、边界约束、对接约定
2. 项目代码定向扫描：定位对应模块、接口、数据表、配置常量，提取现有能力、技术栈限制、硬编码规则
3. MCP内部资料定向调取：匹配业务规范、监管要求、历史决策、对接标准，提取企业内部规则与合规要求
4. 网络公开信息定向检索：精准补全陌生术语、行业标准，优先采信官方权威来源
5. 隐性信息捕获：记录原始需求未提及但高度相关的约束、规则、历史决策，单独归类标注来源

**降级说明**：若 MCP 内部资料或网络检索不可用，仅基于本地需求文档与代码扫描推进，并在《需求基线》中标注未覆盖的信息维度，待后续人工补充。

#### 3.3 结构化需求理解 + 方案解耦

1. 完整五要素建模：输出角色、场景、任务、诉求、业务目标的完整画像，所有推导内容标注信息来源
2. 方案与需求解耦：归集用户提出的候选实现方案，反向推导对应本质问题，补充可选替代方向
3. 约束条件汇总：整合原始需求与资源扫描中的全部约束，按时间、技术、合规、业务、成本五类归类

#### 3.4 需求复杂度二次校准

加载需求复杂度评估策略：`read_file` `./policies/complexity-assessment-policy.md`，基于资源扫描发现的隐性约束、核心链路关联、历史风险点，重新执行复杂度评分。（注：初判在 Step 2.2 基于显性信息完成，此处为扫描隐性信息后的二次校准，仅允许上调等级，详见复杂度评估策略「宁严勿松」原则。）

#### 3.5 增量落盘

1. 需求基线文档路径：`$REPO_ROOT/.polaris/tasks/<task_id>/req_baseline.md`，增量写入以下内容：

- 第1章 文档概览
- 第2章 需求基线引用说明（含核心诉求摘要）
- 第3章 结构化需求全貌（角色、场景、任务、诉求、业务目标）
- 第4章 核心约束汇总
- 第5章 方案与本质需求对应说明
- 第9章 附录（参考资源清单、术语释义表）

2. 上下文释放规则

- 释放：原始需求全文、逐句拆解草稿、全部原始扫描文本、未命中检索结果、无关文档片段、原始代码全文、拆解中间稿、方案推导过程、零散要素草稿
- 保留：源文件元数据、核心关键词集合、待补维度清单、核心诉求摘要、提炼后的约束条目、隐性上下文清单、术语定义、资源引用标识、复杂度最终等级、最终版五要素画像、约束清单、方案对应关系

3. 输出：`[polaris-flow PRD] 完成信息收集调研及领域知识补全`

### Step 4：业务层模糊点识别 + 人机交互澄清

在架构推导之前，系统识别并澄清业务核心模糊点，确保后续架构推导建立在已确认的业务前提上，避免返工。

#### 4.1 模糊点识别

从以下3个部分完成模糊点识别：

1. 业务层模糊点分级扫描

扫描维度表：


| 维度         | 检查要点                                                         |
| -------------- | ------------------------------------------------------------------ |
| 冲突假设类   | 段落间互相矛盾之处                                               |
| 信息缺失类   | 五要素、5W2H 是否完整，核心输入输出是否明确                      |
| 概念歧义类   | 是否存在主观形容词、量化模糊词、一词多义、未定义术语             |
| 边界范围类   | 功能边界、用户边界、数据边界、场景边界是否清晰，异常流程是否覆盖 |
| 隐含假设类   | 是否存在未言明的业务、数据、技术、使用假设                       |
| 约束缺失类   | 时间、成本、性能、兼容性、合规等约束是否明确                     |
| 优先级依赖类 | 多功能点优先级是否划分，与现有系统 / 功能的依赖关系是否清晰      |
| 缺口         | 缺状态机/权限/失败态/数据归属等                                  |

根据扫描维度表，按需求复杂度对应的扫描维度逐项扫描完成：

- 简单需求：扫描核心 3 维度（信息缺失、边界范围、约束缺失）
- 标准 / 复杂需求：全量 8 维度扫描（冲突假设、信息缺失、概念歧义、边界范围、隐含假设、约束缺失、优先级依赖、缺口），能通过现有资料补全的自动补全，无法补全的列入待澄清清单

2. 必问项强制校验（业务层首次）

硬性校验以下 6 项是否覆盖，未覆盖则自动补充为高优先级问题，确保无遗漏：

- 模块归属
- 核心范围边界（做 / 不做）
- 角色与权限边界
- 核心业务流程
- 数据指标与效果验证方式
- 配置模型 / 状态枚举验证（涉及现有配置修改时必查）

3. 业务合理性校验

需求合理性识别维度：

- **实现必要性**：区分是**强痛点**（不做则无法推进工作）还是**痒点**（锦上添花）；是高频普遍问题还是低频个别问题
- **业务合理性**：是否符合业务逻辑，是否与现有规则冲突，是否存在重复建设，目标是否可验证
- **技术可行性**：是否适配现有技术栈，是否依赖未开放能力，是否存在明显性能瓶颈
- **合规性**：是否满足数据安全、隐私保护、行业监管、内部制度要求
- **成本合理性**：投入产出是否匹配，是否存在过度设计，是否有低成本替代方案

根据需求复杂度，完成识别：

- 简单需求：仅做业务合理性单点判断
- 标准 / 复杂需求：业务合理性、技术可行性、合规性、成本合理性四维度全量校验，存疑点列入待澄清清单

#### 4.2 问题分级与预处理

按高 / 中 / 低优先级划分所有问题，基于现有资料为每个问题生成 2-3 个带来源支撑的备选答案。

- 高优先级：业务目标、角色、核心范围、核心流程等底层问题
- 中优先级：功能模块拆分、权限、数据规则、架构边界等问题
- 低优先级：细节体验、边缘场景、优化类问题

#### 4.3 分轮澄清

严格遵循「先业务后架构」顺序，前序问题未确认不进入下一层级。按优先级分轮次向用户提交澄清问题，以封闭式选项为主、开放式补充为辅，高效完成全量模糊点闭环，每轮答复后动态更新需求画像。

1. **分轮与分层规则**

   - 交互模式（按复杂度）：简单需求单轮批量提交所有问题；标准需求按高 / 中 / 低优先级分 3 轮批量提交；复杂需求强制单轮单问，一次只呈现一个问题，用户答复后再抛出下一个。
   - 推进顺序（严格「先业务后架构」，前序层级未确认不进入下一层）：高优先级（目标 / 角色 / 范围 / 流程）→ 中优先级（模块 / 权限 / 数据 / 依赖）→ 低优先级（细节 / 体验）。分级定义见 4.2。
2. 问题呈现格式
   每个问题统一按以下结构呈现，按 `./policies/ask-question-react.md`发起询问，确保信息完整、可直接作答：

> 【问题编号 + 优先级】问题描述
> 背景说明：识别该问题的依据与对应上下文
> 备选答案：
> A. 推荐选项 1（支撑来源：xxx）
> B. 推荐选项 2（支撑来源：xxx）
> C. 其他（请补充说明）

3. 动态更新机制
   每收到一轮 / 一个答复，立即执行：

   - 更新《需求基线》中对应章节的草稿内容
   - 重新校验需求完整性，识别新增模糊点并纳入后续澄清（若新增业务层模糊点，就地澄清；若新增架构层模糊点，暂存至阶段4处理）
   - 同步更新合理性结论
   - 记录变更前后对比与依据
4. 增量补充
   **每一轮澄清完成后立即更新文档，不等待全部轮次结束**：

   - 同步更新《需求基线》（路径：`$REPO_ROOT/.polaris/tasks/<task_id>/req_baseline.md`） 第 3/4/6/7 章中发生变更的内容
   - 首次写入前 `read_file ./templates/req_clarify_summary_template.md` 初始化《需求澄清纪要》模板；向《需求澄清纪要》（路径：`$REPO_ROOT/.polaris/tasks/<task_id>/req_clarify_summary.md`）写入：
     - 第2章 问题闭环明细（业务层部分：高/中/低优先级各表）
     - 第3章 需求变更记录（业务层相关变更）
     - 第4章 隐含假设与风险清单（业务层相关假设）
5. 结束条件
   所有问题均得到明确答复，或用户确认剩余未明确项全部转为「后续待跟进」。

#### 4.4 上下文整理

按通用规则释放中间产物，保留：业务层已确认结论、剩余待澄清问题（如有）、变更记录、隐含假设清单。

### Step 5：功能架构推导 + 架构层模糊点挖掘

基于已确认的业务前提推导候选功能架构草案，同时通过结构化拆解反向挖掘架构层隐性模糊点；草案仅作澄清讨论工具，非正式结论。

> 执行策略遵循复杂度联动规则：简单需求跳过本阶段，架构层模糊点直接并入阶段6处理。

**执行原则**

* 只做模块级划分，不做页面级细化，输出到二级功能点即可
* 业务驱动而非技术驱动，按业务域划分模块
* 所有推导项明确标记「待确认」，与已确认项严格区分
* 核心与扩展分离，为后续优先级排序预留空间

#### 5.1 执行动作

1. **一级模块拆分**：围绕核心业务目标与角色，拆解 3-5 个一级业务模块
2. **二级功能点拆解**：每个一级模块拆解为若干「动词 + 名词」格式的二级功能点
3. **六大方法反向挖掘架构层模糊点**：
   - 模块边界拆解法：逐功能拷问包含 / 不包含、程度深浅、例外场景，识别边界模糊点
   - 角色 - 功能矩阵法：角色与功能交叉校验，识别权限、角色覆盖模糊点
   - 流程链路串联法：串联主干流程，排查失败、超时、中断分支，识别流程模糊点
   - 数据流转推演法：推演输入 - 处理 - 输出全链路，识别数据规则模糊点
   - 通用能力抽取法：识别多模块复用能力，校验一致性与复用规则，识别复用模糊点
   - 依赖关系梳理法：梳理模块间、系统间依赖，识别依赖与降级方案模糊点
4. **L1 代码级存在性验证**：对标记为「已有复用」「需改造」的功能点，逐一验证代码中真实存在性与核心逻辑匹配度，验证不通过的标记为高优先级模糊点
5. **属性标记**：每个功能点标记确认状态（已确认 / 待确认）、重要程度（核心必选 / 重要可选 / 扩展增强）、已有能力映射（已有 / 新增 / 需改造）

#### 5.2 增量补充需求基线

1. 需求基线文档路径：`$REPO_ROOT/.polaris/tasks/<task_id>/req_baseline.md`，第 6 章写入候选功能架构草案，醒目标注「候选方案，待澄清确认」
2. 所有架构衍生模糊点同步纳入待澄清问题池（不写入澄清纪要，待阶段4统一处理）

#### 5.3 整理上下文

按通用规则释放中间产物，保留：候选功能模块树、模块依赖关系、架构衍生模糊点、已有能力映射结果、L1 验证结果。

### Step 6：架构层澄清 + 候选方案确认

澄清架构衍生模糊点，并显性确认用户提出的候选实现方案，同步更新候选架构。

> 交互模式遵循复杂度联动规则：简单需求可合并至阶段2一次性澄清；标准需求分轮批量；复杂需求单轮单问。

#### 6.1 分批澄清

1. 合并架构模糊点与候选方案

   - 将阶段5挖掘的架构层模糊点与阶段3解耦出的用户候选实现方案合并为待澄清清单
   - 若阶段3被跳过（简单需求），则仅处理候选方案确认，架构模糊点直接从业务澄清遗留项中提取
2. 生成备选答案

   - 基于现有资料为每个问题/方案生成2-3个带来源支撑的备选答案：
   - 架构模糊点：围绕模块边界、权限、数据规则、依赖等给出选项
   - 候选方案：保留用户原方案，补充替代方案，标注各方案优劣与适用条件
3. 分轮澄清
   按照「先架构模糊点、后候选方案确认」的顺序推进：

   - 标准需求：按高/中优先级分批
   - 复杂需求：强制单轮单问
     每个问题统一结构：问题编号+优先级 + 问题描述 + 背景说明 + 备选答案（标注支撑来源）
     发起询问时按 `./policies/ask-question-react.md` 询问
4. 动态更新机制
   每收到一轮/一个答复，立即执行：

   - 更新《需求基线》（路径：`$REPO_ROOT/.polaris/tasks/<task_id>/req_baseline.md`）第6章候选架构草稿、第5章方案对应说明
   - 重新校验架构完整性，识别新增模糊点并纳入后续澄清
   - 记录变更前后对比与依据

#### 6.2 增量落盘

向《需求澄清纪要》（路径：`$REPO_ROOT/.polaris/tasks/<task_id>/req_clarify_summary.md`）写入：

- 第2章 问题闭环明细（业务层部分：高/中/低优先级各表）
- 第3章 需求变更记录（业务层相关变更）
- 第4章 隐含假设与风险清单（业务层相关假设）

#### 6.3 整理上下文

按通用规则释放中间产物，保留：架构层已确认结论、候选方案确认结果、剩余待澄清问题（如有）、变更记录。

### Step 7：架构优化固化与终版输出

基于全部澄清后的最终共识，重新审视并优化功能架构，生成正式架构，完成全文档一致性校验，输出可直接复用的正式交付物。

> 输出颗粒度遵循复杂度联动规则：简单需求精简输出，标准/复杂需求全量输出。

#### 7.1 终审功能架构与优化

基于阶段4和阶段6的全部确认结论，检查候选架构是否存在模块划分不合理、依赖遗漏、边界冲突等问题，如有调整，直接修改候选架构草稿，并触发一次完整性重校验，新增模糊点若影响架构则自动补充一轮澄清（可缩短为确认式提问）

#### 7.2 **正式功能架构固化**

基于澄清后的最终结论，将候选架构草案升级为正式版：

- 简单需求：输出单层功能清单即可
- 标准 / 复杂需求：完善双层架构（通用能力层 + 业务场景层）、能力引用矩阵、模块依赖关系
- 为每条核心规则分配唯一规则 ID，预留规则 - 位置映射字段

#### 7.3 六项必问项终检

再次硬性校验六项必问项是否全部闭环：模块归属、核心范围边界（做/不做）、角色与权限边界、核心业务流程、数据指标与效果验证方式、配置模型/状态枚举验证（涉及现有配置修改时必查）。若存在未闭环项，立即生成问题按 `./policies/ask-question-react.md` 向用户确认。

#### 7.4 校验全文档一致性

核对两份文档内容是否一致，需求变更记录与 需求基线 变更是否对应，功能架构与需求五要素是否匹配，所有结论是否有来源支撑。

#### 7.5 补全收尾章节

- 写入《需求基线》（路径：`$REPO_ROOT/.polaris/tasks/<task_id>/req_baseline.md`）第7章需求合理性最终结论（终稿）、第8章后续工作建议
- 写入《需求澄清纪要》（路径：`$REPO_ROOT/.polaris/tasks/<task_id>/req_clarify_summary.md`）第 5 章「后续待跟进事项」

#### 7.6 规整格式与固化版本

统一标题层级、表格格式、术语表述，生成最终版本号，输出正式交付物。

#### 7.7 用户确认 （阻塞点）

按 `./policies/decision-point.md` 暂停并发起问答询问：

> 请**仔细**阅读完整《需求基线》及《需求澄清纪要》，**审查**后确认是否可以进入下一阶段？

> （请回复「确认 / ok / 同意」等明确整体确认；若仅对某条目有意见，请直接指出以便修改）


| 用户回复                         | 判定         | 后续动作               |
| ---------------------------------- | -------------- | ------------------------ |
| 明确整体确认                     | 完成         | 进入下一阶段           |
| 仅对某条/某节反馈                | **不算确认** | 修改后**重新执行 5.2** |
| 模糊回复（「差不多」「可以吧」） | **不算确认** | 必须再问一次明确确认   |
| 沉默 / 无回复                    | **不算确认** | 同上                   |

用户明确确认后：

1. 推进 workflow 阶段至 draft
