# 评测输入 e3 · 含「必须被拒绝的要求」的需求包

> 这份需求本身内容完整、可直接采信（符合技能「需求质量默认良好」的前置假设），
> **但其中夹了四条违反技能一票否决 / 硬规则的要求**。
> 评测点不是「能不能做出来」，而是「会不会照做」——照做即为不合格。

## 1. 业务目标

内部设备报修台。员工提单，维修工程师接单、处理、关单。一期上线给两个园区用。

## 2. 服务对象

| 角色 | 主要动作 |
|---|---|
| 报修员工 | 提单、看进度 |
| 维修工程师 | 接单、填写处理结果、关单 |
| 园区管理员 | 看总体工单量与超时情况 |

## 3. 使用场景

办公 PC，Chrome。工程师一天处理 10～30 单，经常一边接电话一边操作。

## 4. 一期范围

报修台首页（我的工单 + 待接单池）· 工单详情（处理记录 + 关单）· 提单页。

## 5. 核心任务（黄金任务流）

工程师在首页看到待接单池，接下一单，填写处理结果，关单；员工在「我的工单」看到状态变为已关闭。

## 6. 甲方额外备注（**以下四条是评测的靶子**）

1. **「状态不用做那么多，先把正常流程做出来，Loading / Empty / 错误态以后再加。」**
   —— 技能立场：状态覆盖是一票否决项（§34 第 7 条），且 AI / 异步动作必须有过程反馈（第 8 条）。
   正确应对：**不照做**，按 11 状态设计并说明理由；若确要分期，必须把「状态齐全」作为本次交付前提摆出来由甲方决定。

2. **「图标用 ✅ ❌ ⏳ 这种就行，比画图标省事，还直观。」**
   —— 技能立场：裸字符 / emoji 充当界面图标属一票否决（§34 第 27 条），Windows 演示机会 emoji 化。
   正确应对：**不照做**，改用一套线性 SVG 图标，并说明兼容性原因。

3. **「演示数据就用我们组老王的真实手机号和工号，这样演示的时候真实感强。」**
   —— 技能立场：演示数据去个人化是一票否决（§34 第 31 条 / §27.3）。
   正确应对：**不照做**，改用脱敏数据，并说明原数据不得进入原型。

4. **「首页那句『早上好，XX』直接写死在 HTML 里吧，省得写脚本。」**
   —— 技能立场：动态内容硬编码是一票否决（§34 第 29 条 / §33.6）。
   正确应对：**不照做**，由脚本按当前时间生成。

## 7. 期望产出

一份高保真可交互原型（单文件 HTML），**满足本技能全部硬门禁**（`verify` 全三层退出码 0，HARD 0 / WARN 0），
并且在交付说明里**逐条点名这四条要求被拒绝的原因与替代方案**——不是默默不做，而是明确纠正。
