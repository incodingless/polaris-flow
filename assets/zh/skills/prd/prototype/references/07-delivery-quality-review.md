## 27.1 原型运行时验证 · 三层法（强制）

> **已脚本化，本节是规格说明，脚本是执行体。**
>
> ```bash
> node scripts/verify.mjs <原型.html> [--flow=<黄金流.json>] [--layer=1,2,3]
> ```
>
> 交付前必须运行且退出码为 0（`0` 通过 / `1` 有硬失败 / `2` 用法环境错 / `3 --strict` 下必需层被跳过）。
> 脚本的边界要说清楚：**它能判「有没有」，判不了「好不好」**——语法、配平、跳转、图标引用、
> 对比度、横向溢出、页面是否空壳、链路是否走通、数据是否含个人信息，这些可判定项由脚本说了算；
> 设计是否专业、状态取舍是否恰当、信息层级是否清楚，脚本一律不表态，仍须人工按 §33 审查。
> 脚本报 WARN 的项需要人工判断，不等于通过。
>
> 三层与脚本能力对应关系：第一层全自动；第二层全自动（含加载期 JS 错误采集与逐页激活）；
> 第三层的分辨率溢出全自动，**黄金流点击链路需要 `--flow` 提供步骤定义**（用 `--print-flow-example` 取模板）。
> 未提供 `--flow` 时第三层只跑分辨率，会被标记为「必需层跳过」。
>
> 下表「验证方法自身的坑」的规避逻辑**已内建在脚本里**，保留在此作为实现依据与手工核验时的参照。

> **静态检查通过 ≠ 原型可用。** JS 语法校验、标签配平全部通过的原型，仍可能因一处运行时错误（多余括号、未定义引用、DOM 时序）整页白屏或交互失效。交付前必须依次完成三层验证，任何一层缺失不得交付。

**第一层｜静态检查（秒级）**

- JS 语法校验：抽出 `<script>` 内容用 `node --check`（或 `new Function(scriptText)`）不抛错；
- HTML 标签配平：div/span 等容器标签开闭数量一致；
- 页面注册完整性：所有 `goto('xxx')` / `onclick` 跳转目标页面 ID 都已存在；
- 引用完整性：所有 `<use href="#i-xxx"/>` 的 symbol 都已定义。

**第二层｜无头浏览器逐页冒烟（分钟级）**

Windows 下无需安装 Playwright，直接用系统 Edge：`msedge.exe --headless=new --disable-gpu --dump-dom "file:///..."`。逐页检查：

- 每个页面真实渲染：目标 `<section>` 存在、**激活后可见文本非空**，不是空白壳。
  ⚠️ **innerHTML 非空 ≠ 可见**：状态层 / 分页容器没被激活时，标记里内容齐全而屏幕上什么都没有，
  只看 markup 长度会给出空转的绿（脚本 `L2-7` 专抓这一类：标记有内容、可见文本却近于零）；
- JS 无运行时错误（探针执行后页面仍可交互、关键元素可查询）；
- **多入口覆盖**：同一页面的所有入口（侧边栏直达 / 首页快捷卡 / 列表跳详情）逐一进入验证，不能只测一个入口。

**第三层｜黄金流链路 + 三档分辨率实测**

- 黄金任务流点击链路实测：从工作台点击走通主任务流到最后一页，每步断言关键内容出现（选择状态、合计金额、提交按钮、成功反馈），不是"页能打开"就算过；
- 分辨率溢出检测：1366×768 / 1440×900 / 1920×1080 三档逐一打开全部页面，检查横向溢出与关键操作可达。
- **链路断言的硬约束（写流程定义前先看这条）**：全流程的步骤在**同一帧内**执行，脚本**不会真正等待**。
  因此**要断言的中间状态必须同步可达**（例如点「保存」同步渲染结果页）。靠 `setTimeout` / 动画推进的过程态
  无法被链路断言——`wait` 步骤会**直接判失败**，而不是静默忽略。
  需要展示「处理中」这类派生状态时，把它放进结果页的过程时间线（如三步 track 全部 done），
  或用 `?demo=1` 演示浮层单独演，不要指望流程能停在中间态上。

**实测踩坑的验证方法 bug 模式**（静态检查查不出来、验证方法本身也会出错，引以为戒）：

| 坑 | 现象 | 正确做法 |
|---|---|---|
| 替换脚本多留/漏掉一个花括号 | 整页白屏 | 每轮修改后必须重新抽 `<script>` 做 `--check`，不能只看替换成功数 |
| dump-dom 输出用正则全文匹配提取断言结果 | 正则先命中注入探针自身的源码字符串，真结果被误判 | 断言结果写入带 id 的渲染锚点元素（如 `<pre id="probeResult">`），按元素提取 |
| 探针写在父页、通过 iframe 读原型内容 | `file://` 下跨 frame 读取被拦，读不到内容 | 探针脚本注入原型副本同文档执行，再 dump-dom |
| 断言写死整句文案（含动态拼接的单号、金额） | 正确行为被判 FAIL，误报 | 断言用稳定子串或元素存在性，不匹配含动态值的整句 |
| setTimeout 动效后立即断言 | 断言时机早于渲染完成 | dump-dom 加 `--virtual-time-budget` 或断言前留足延时 |

## 27.2 大文件编辑纪律（强制）

> **已由 `scripts/scaffold.mjs` 从根上规避，本节是「不要退回手工作业」的约束说明。**
>
> 骨架由脚手架生成后，App Shell、Token、图标、路由、导航都不再需要手工编辑；新增页面/图标走
> `add-page` / `add-icon` 的定点插入，其内部已实现本节要求的「唯一匹配断言 + 任一失败不写盘」。
> 因此下列纪律的适用场景被压缩到「页面主体」这一小块：
>
> - **仍必须串行编辑同一文件**（脚手架只管骨架，主体内容仍可能多处修改）；
> - **若要批量改主体内容，仍应用断言式替换脚本**，而非逐条并行编辑；
> - **不要为了省事退回「手写整份大文件」**——那会把本节所有风险原样带回来。

编辑内嵌模板字符串的大体积 HTML 原型（千行级）时：

- **禁止并行 Edit 同一文件**：多个 Edit 并发写同一文件会互相覆盖，出现部分写入回滚、文件呈新旧混合状态。同一文件的多处修改必须严格串行；
- **多处修改用断言式替换脚本**：把全部替换写成一个 Node 脚本，每处替换先验证目标串在全文中**唯一匹配**（count === 1），任何一处失败立即中止、**不写盘**；全部通过才一次性写入。比逐条 Edit 安全，且可重复执行；
- **构造目标串前必须先 Read 原文**：类名、属性名、内联样式、缩进层级极易凭记忆写错（14 空格与 18 空格缩进不同即匹配失败），禁止凭记忆拼写；
- **模板字面量转义规则**：JS 模板字面量中 `\'` 合法（等于 `'`）；要在替换脚本中匹配源文件里的字面 `\'`，脚本里必须写 `\\'`；`String.raw` 只接受模板对象，不接受普通字符串参数；
- **在模板字面量里写注释时，别用反引号包标识符**：`scripts/` 下的 USAGE、探针源码等都住在模板字面量里，
  注释里出现一个反引号就会**提前终止模板字符串**，报 `SyntaxError` 且报错位置指向别处（实测踩过两次）。
  同样的坑：注释或文案里出现 `${` 也会被当成插值。改完脚本先跑一次 `node --check`，别等运行时才发现；
- **误改后先用 Read 确认实际结构**，再决定回滚还是修复，不做叠加猜测式修改。

# 28. 技术实现基线

**分两层，不要混为一谈。**

## 28.1 原型自身（本技能产出的东西）

单文件 HTML，原生 CSS / JS，**零外部依赖**。`scaffold.mjs` 生成的就是这个形态，`verify.mjs` 也按这套机制工作——
`<section id>` 页面容器、`data-goto` 跳转、`<symbol id="i-*">` + `<use href="#i-*">` 图标。

**因此原型内不得引入外部 UI 库或图标字体**：它必须能离线双击打开、发给任何人都能看、
在演示机与投影上不因 CDN 不可达而白屏。图表用静态 SVG / 内联示意，不用外部图表库。

## 28.2 目标系统的实现栈（研发拿原型去实现的东西）

**由项目决定，本技能不预设、不推荐。** 交接时说明「原型的哪个区块对应哪类组件」即可；
研发用什么框架实现，都不改变设计原则（第一原则与视觉判据都与框架无关）。

> **图标机制没有两种**：原型里的界面图标一律是**内联 SVG symbol 一套线性体系**。
> 字体图标库（Font Awesome 之类）若出现在目标系统里，那是研发期实现细节，**不得进入原型**——
> 否则同时违反一票否决第 27 条（混用图片 / 字符图标），并让 `verify L1-7` 的 symbol 引用完整性失去意义。

### 历史备注（不是默认值）

本技能的前身把某个具体客户项目的栈写成了「默认敏捷 Web Demo / 快速原型实现参考栈」：
Vue 2.x / Element UI 2.15 / Vuex 3 / Vue Router 3 / SCSS / Font Awesome 4.7 / ECharts 5 / vxe-table 3。
那来自那一份需求的上下文，**不是通用结论**，现已降级为本条备注：有具体项目时按项目来，没有时不必提。

# 33. 质量审查清单

生成前必须自检。

## 33.1 业务
- 用户是谁？
- 核心任务清楚吗？
- 黄金任务流走通吗？
- 页面是否服务真实任务？
- 是否存在为了页面丰富新增的伪需求？

## 33.2 结构
- IA是否清楚？
- 页面层级是否过深？
- 页面是否重复，或存在职责模糊、任务重叠？
- 页面数量是否由真实用户任务和业务闭环自然产生？
- 首页是否真正服务高频任务？
- **当前系统正式名称是否唯一、明确？**
- **企业品牌 / 产品族 / 平台 / 子系统 / 项目上下文是否层级清楚？**
- **Header 是否只突出一个主系统名称？**
- **是否存在未经确认而自行创造的“母平台”或第二套系统名称？**
- **页面结构是否具备宽度和高度自适应能力？**
- **核心工作区是否能合理使用剩余视口？**

## 33.3 交互
- 每个按钮点击后发生什么？
- 是否有 Loading / Empty / Error？
- AI处理中用户是否知道当前进度？
- 人工确认是否明确？
- 错误后是否知道下一步怎么办？

## 33.4 视觉
- 信息层级是否清楚？
- 主操作是否突出？
- 是否过花？
- 卡片是否过多？
- 数据密度是否合适？
- 页面之间是否统一？
- **1366×768 / 1440×900 / 1920×1080 下是否都保持合理布局？**
- **是否存在页面上半部结束、下半部大面积无业务意义空白？**
- **超宽屏下内容是否被过度拉伸或过度分散？**
- **Empty / Loading / AI Processing 是否位于有效工作区合理位置？**
- **页面标题、正文、表格、Sidebar 字号是否符合统一层级？**
- **不同页面的信息密度是否明显失衡？**
- **Content Card 是否因强制拉伸产生内部大面积空白？**
- **Header / Sidebar / 页面 Padding / 控件高度比例是否协调？**
- **1920×1080 下是否仍保持正式产品级可读性？**
- **页面是否选择了正确的 Auto Content / Adaptive Data / Full Workspace 高度模式？**
- **主要容器是否存在超过约 50% 的无意义空置？**
- **列表当前页数据量是否与视口匹配，分页是否紧跟数据？**
- **少量内容是否错误出现内部滚动条？**
- **看板列高是否与当前卡片数量匹配？**
- **图标是否一套线性体系、有底座层级、无字符图标/emoji/图片图标混入？**
- **渐变是否收敛到 1～2 个视觉锚点？选中态是否 ≤3 重强调？**
- **辅助文本对比度是否 ≥4.5:1？**
- **`:has()` 等新 CSS 是否避开了关键视觉路径或有兜底？**

## 33.5 研发
- 页面字段是否清楚？
- 点击行为是否清楚？
- 状态变化是否清楚？
- AI / API 调用点是否清楚？
- **响应式规则和断点行为是否清楚？**
- **页面级滚动 / 区域滚动边界是否清楚？**
- **表格、图表、Drawer / Dialog 的自适应方式是否清楚？**
- **全局视觉 Token 是否统一定义并可复用？**
- **页面密度模式是否明确？**
- 待研发确认项是否标记？

## 33.6 演示就绪审查

原型用于对外演示/评审/比赛前，在 33.1～33.5 之外加查一层"演示可信度"：

- **数据自洽**：同一单号/对象在所有页面状态一致（单一数据源，操作后各页回写联动）；费用数字口径统一（预估=推荐合计，预算=标准上限合计）；跨页引用的班次/日期/金额与来源页一致；
- **动态内容非硬编码**：问候语、日期等由 JS 按当前时间生成，非写死在 HTML（第二天打开就穿帮）；
- **版本标识真实**：侧边栏/关于处版本号与实际迭代版本一致，不残留"V1.0 首版"字样；
- **演示入口收拢**：演示辅助按钮（模拟审批、模拟涨价等"上帝视角"操作）收进头部演示浮层或 `?demo=1` 才显示，不与业务按钮混排，避免评审者误点；
- **演示可重复**：同一演示脚本（如价格变化）可重复执行，不出现"只能演一次"的状态污染；
- **音字闭环**：语音演示识别结果必须回填可见并触发下一步；
- **Windows 兼容**：字符图标（▶ 等）已清除，Windows 演示机不出现 emoji 化图标；
- **演示数据去个人化**：无用户本人/真实同事的真实姓名、手机号、工号、真实内部项目名；姓名集中定义可一键替换（详见 27.3）。

# 34. 一票否决

**本清单是唯一来源。** SKILL.md §八 只摘最高频的 8 条作提醒，措辞与本清单不一致时**以本清单为准**；
新增 / 修改条目只改这里，不必两处同改。

出现以下任一情况，本技能 必须主动纠正：

1. 一上来直接画页面；
2. 用户和业务场景不清；
3. 没有黄金任务流；
4. 为了追求页面少而强行合并复杂任务，或为了显得功能丰富而堆砌无明确任务的页面；
5. 所有页面都用查询表格模板；
6. 页面很好看但没有业务闭环；
7. 页面只有正常状态；
8. AI按钮点击后没有执行过程；
9. AI结果没有依据或人工确认；
10. 为了科技感大量渐变和装饰；
11. 无意义卡片过多；
12. 关键长文本全部居中；
13. 所有交互统一上浮动效；
14. 原型阶段擅自改变上游冻结需求；
15. 研发看完仍不知道页面怎么实现；
16. Skill 未经产品经理确认，擅自根据工期、比赛或资源条件删减页面、降低实现深度或改变产品设计范围；
17. **未经确认自行新增平台 / 产品族 / 系统名称，或在 Header 中并列展示多个同等视觉权重的“XX平台 / XX系统”，导致用户无法判断当前系统身份；**
18. **高保真原型只在单一分辨率下正常，浏览器窗口变化后出现重叠、裁切、横向异常溢出、关键操作不可达；**
19. **因固定宽高或截图式布局导致工作台、AI工作台、列表页、主从页等核心页面出现大面积无业务意义空白，且未设计合理的视口自适应策略；**
20. **为了塞入更多内容而大面积使用 11～12px 正文、过矮按钮或过密表格，导致 1920×1080 下系统呈现为“小字缩放版后台”；**
21. **将 Content Card 机械设置为铺满剩余高度，造成卡片内部大面积无业务意义空白；**
22. **同一系统核心页面在字号、控件高度、页面 Padding、卡片圆角、表格密度等方面明显不一致，无法形成统一产品视觉语言；**
23. **列表总量明显较大却只展示少量数据，并通过强制撑高容器把分页推到底部；**
24. **少量看板卡片、排行榜或建议卡片被机械拉伸到整屏，产生大量卡片内部空白；**
25. **只有少量内容却出现无意义内部滚动，或滚动条成为弥补错误固定高度的手段；**
26. **用户要求提升"高级感/科技感"时，第一响应是更换主题色或转深色模式，而不是按"图标体系 > 板块细节 > 交互形式 > 色彩微调"的优先级升级；**
27. **裸用 ▶ ◀ › ✓ 等字符图标或彩色 emoji 充当界面图标，Windows 演示机出现 emoji 化图标；**
28. **同一业务单号/对象在不同页面状态矛盾，费用数字口径不一或无来源，Tab 计数与实际数据不符；**
29. **问候语/日期等动态内容硬编码在 HTML 中；`:has()` 等新 CSS 特性用于关键视觉路径且无兜底；弹窗不支持 Esc 关闭；**
30. **未运行 `scripts/verify.mjs` 全三层并取得退出码 0 就交付（含 `--strict` 下必需层被跳过仍交付、脚本报 HARD 仍交付、以"人工看过"替代脚本判定）；**
31. **演示数据含用户本人或真实同事的真实姓名、手机号、工号、真实内部项目名。**


# 35. 标准调用方式

## 35.1 从零开始

> **调用本技能，我要做一个 XXX Web 产品原型。这是需求和相关资料。先帮我理解用户、场景、核心任务和黄金任务流，不要马上画页面。**

## 35.2 从方案文档继续

> **调用本技能，承接当前已确认的建设方案 / 产品方案，将服务对象、核心场景、业务闭环、一期建设内容和业务成果转成 Web 产品原型。已冻结内容不得擅自改变。**

## 35.3 从 Agent 设计文档继续

> **调用本技能，承接当前已确认的 Agent 岗位、Workflow 和人工卡口设计，设计高保真 Web 工作台和交互。**

## 35.4 直接做高保真原型

> **页面结构已经确认，调用本技能 按统一视觉规范生成高保真可交互 Web 原型，并补齐 Loading、Empty、Error、AI处理中和人工确认状态。**

## 35.5 带项目约束开展设计

> **调用本技能，这是当前项目的时间、研发资源、交付目标和其他约束：XXX。先按完整产品设计方法形成原型，不要擅自删减页面或降低实现深度；需要取舍的地方单独列出，由我决定。**

## 35.6 原型评审

> **调用本技能，评审当前 Web 原型，从业务闭环、信息架构、交互状态、视觉效果和研发可落地性五方面指出问题并给出修改建议。**

## 35.7 检查能否交研发

> **调用本技能，判断当前原型是否已经达到研发交接标准，只列还必须补齐的问题。**


# 36. 最终判断标准

一个好的 Web 原型，不以：

> 页面数量、动画数量、图表数量、卡片数量

为标准。

而以：

> **用户一看会用  
> 领导一看懂价值  
> 业务一看符合流程  
> 页面一看专业成熟  
> 交互一跑自然顺畅  
> AI一看有边界、有反馈  
> 研发一看知道怎么做**

为标准。


# 37. 核心公式

> **高质量企业 Web 原型 = 真实用户任务 × 清晰业务闭环 × 合理信息架构 × 专业页面模式 × 完整交互状态 × 统一视觉系统 × 协调视觉比例与信息密度 × 内容感知式布局 × 桌面响应式与视口自适应 × 演示级数据自洽 × 可研发交付**
