# 现场保全清单（生产通道 · 人在环）

> **使用范围**：仅 `polaris{{SKN_SPR}}debug{{SKN_SPR}}hotfix` 通道的 `triage` 段（生产故障定性时）。
> **定位**：这是技能在故障早期**最高价值的动作**——在任何人重启 / 回滚 / 清理现场**之前**，把「先留证据」喊出来。重启会覆盖现场，这件事只有「更早说」能救。
> **执行方**：**只由人执行**。技能产出这份清单并交人执行，人执行后回填结果；技能**不执行、不声称已执行**（C 档，见 `./policies/capability-tiers.md`）。

## 触发时机

`triage` 段一开始就产出，**抢在止血 / 重启之前**。宁可多留、不可漏留。

## 保全对象（留什么 / 时间窗 / 从哪取 / 为什么）

| # | 留什么 | 时间窗 | 从哪取 | 为什么 |
|---|--------|--------|--------|--------|
| 1 | 错误日志（按异常类型聚类后的**原始**日志） | 异常起始点前推 ≥30min ~ 当前 | 应用日志 / 日志平台导出 / 容器 stdout | 重启 / 滚动发布会清空，是根因定位唯一现场证据 |
| 2 | 链路数据（TraceId 关联的调用链） | 同上 | APM / 链路追踪平台 | 定位跨服务最早异常点 |
| 3 | 核心指标曲线（QPS / 延迟 / 错误率 / 资源） | 异常起始点前推 ≥1h | 监控大盘 / 指标平台 | 判断影响面与扩散点 |
| 4 | 数据库状态快照（关键表计数 / 脏数据样本） | 当前时刻 | DB 只读查询（脱敏） | 数据订正 / 回滚前必须有基线 |
| 5 | 变更记录（代码发布 / 配置变更 / 依赖升级 / 数据变更） | 异常起始点前推 ≥24h | 发布平台 / `git log` / 变更单 | 变更关联是根因定位的第一线索 |

## 优先级（不能等）

1. **错误日志与链路**（最易被重启 / 滚动发布覆盖）
2. **数据库状态快照**（数据污染后再取就晚了）
3. 变更记录、指标曲线（相对稳定，可稍后）

## 执行与回填

- 人按表逐项保全，把「取得的内容 / 导出路径 / 时间戳」回填到 `.polaris/tasks/<issue_id>/diagnose-brief.md` 的「现场保全」段（原始证据原样，不摘要）。
- 取不到的项标「未保全 + 原因」，**不得**伪装已保全。

## 技能侧硬约束

- 技能**只产出清单**，不执行任何保全动作，不声称已保全。
- `diagnose` 段的证据链只能引用**已回填**的保全项，不得引用未保全的项。
