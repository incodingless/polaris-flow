# 需求复杂度评估策略

## 1. 评估原则
1. **量化可落地**：所有维度均设置明确阈值与得分标准，无主观模糊判定项，Agent可稳定复现执行
2. **宁严勿松**：二次校准仅支持上调复杂度等级，不支持下调，优先规避风险漏判
3. **全流程联动**：评估结果联动所有执行阶段的执行粒度，而非仅影响澄清交互模式
4. **风险兜底**：高危场景触发强制升档，不受总分限制，从规则层面堵住高风险需求被轻判的漏洞

## 2. 评估维度与评分细则
### 2.1 总分计算规则
需求复杂度总分 = 业务复杂度得分 + 技术复杂度得分 + 合规风险复杂度得分
满分 33 分，所有维度均为正向加分，得分越高代表需求复杂度越高。

### 2.2 业务复杂度（满分 11 分）
| 评估维度 | 评分规则 | 对应分值 |
|----------|----------|----------|
| 涉及用户角色数 | 仅1类角色 | 0分 |
| | 2类角色 | 1分 |
| | 3类及以上角色 | 2分 |
| 核心业务场景数 | 仅1个主场景，无分支场景 | 0分 |
| | 2-3个业务场景 | 2分 |
| | 4个及以上业务场景 | 3分 |
| 流程分支数 | 仅主干流程，无异常/驳回分支 | 0分 |
| | 1-2个异常/判断分支 | 1分 |
| | 3个及以上异常/判断分支 | 2分 |
| 需求变更幅度 | 纯参数、文案、展示样式调整，不改变业务逻辑 | 0分 |
| | 局部业务逻辑调整，不改变主干流程 | 2分 |
| | 新增完整业务流程，或重构主干流程 | 4分 |

### 2.3 技术复杂度（满分 15 分）
| 评估维度 | 评分规则 | 对应分值 |
|----------|----------|----------|
| 是否跨独立系统 | 单系统内调整，不涉及跨系统交互 | 0分 |
| | 横跨2个及以上独立业务系统 | 5分 |
| 是否新增数据实体 | 不新增数据表/核心数据对象 | 0分 |
| | 新增1个数据实体 | 2分 |
| | 新增2个及以上数据实体 | 3分 |
| 是否改造核心链路 | 不触碰系统核心业务链路、核心数据流转 | 0分 |
| | 修改系统核心业务链路、核心计算逻辑 | 4分 |
| 是否涉及第三方对接 | 不依赖外部第三方系统/接口 | 0分 |
| | 需要新增或改造第三方系统对接 | 3分 |

### 2.4 合规风险复杂度（满分 7 分）
| 评估维度 | 评分规则 | 对应分值 |
|----------|----------|----------|
| 数据敏感等级 | 仅涉及普通业务数据、公开数据 | 0分 |
| | 涉及用户一般个人信息（手机号、地址等） | 2分 |
| | 涉及敏感个人信息（身份证、银行卡、生物特征、资金数据） | 4分 |
| 是否涉及监管合规要求 | 无明确行业监管、数据合规强制要求 | 0分 |
| | 需满足行业监管规范、数据合规条例强制要求 | 3分 |

## 3. 复杂度分级标准
| 等级 | 总分区间 | 典型场景 |
|------|----------|----------|
| 简单需求 | 0-5分 | 单角色、单场景的纯配置调整；文案/参数/展示样式修改；不改变业务逻辑与核心链路 |
| 标准需求 | 6-12分 | 多角色、单系统内的新增功能模块；常规业务流程新增；局部逻辑调整；无高合规风险 |
| 复杂需求 | 13分及以上 | 跨系统需求；新增核心业务实体；改造核心链路；涉及第三方对接；高合规风险需求 |

## 4. 高危场景强制升档（一票否决）
满足以下任意一条的需求，无论总分多少，**直接强制判定为复杂需求**，不受总分区间限制：
1. 涉及资金交易、支付结算、财务对账、计费扣费类核心逻辑
2. 涉及用户身份证、银行卡、生物识别、户籍等高度敏感个人信息
3. 改造系统核心生产链路，故障会导致全平台核心业务不可用
4. 有明确的监管合规强制要求，违规会导致法律风险或行政处罚
