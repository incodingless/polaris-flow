# Polaris Flow — 功能选择入口

本命令是 Polaris Flow 的统一入口，负责**让用户选择要做什么**，然后把执行交给对应的技能。
它只做「选择 + 路由」，不产出任何需求、设计、代码或测试产物；所有产物由被路由到的技能按其自身规范生成并落盘。

<HARD-STOP>
1. ❌ 禁止替用户默认选择某一项，必须等用户明确选择
2. ❌ 禁止跳过菜单直接开始干活
3. ❌ 禁止在本命令内直接产出需求文档、代码或测试用例——本命令只做选择与路由
4. ❌ 禁止用户未选择时自行推进，应重新发起对应级别的询问
5. ❌ 禁止把 15 个功能项一次性塞进单次询问（单 question 选项上限 5 个）
6. ❌ **禁止在第 1 级拿到答案后直接跳去加载技能**——必须立刻发起第 2 级询问
7. ❌ 禁止用纯文本罗列选项代替第 2 级询问——必须发出真实的询问工具调用（文本降级模式除外）
8. ❌ **禁止在未完成上下文收集时加载技能**——必须走完第三步，得到用户明确答复（`无` 也算明确答复）
9. ❌ 禁止写死询问工具名——工具名一律按下方「发问方式」查表得到
10. ❌ **禁止对标注「⚠️ 暂不可用」的选项尝试加载技能**——必须停下并明确告知用户缺什么，不得静默跳过、直接开工、或自行换用其他技能替代
11. ❌ **禁止开发类（M01 / M02 / C01–C03）在需求三要素未满足时加载技能**——该判定由 `polaris{{SKN_SPR}}coding{{SKN_SPR}}intake` 的 Step 2 执行（命令层不再做需求预检），本命令只把用户输入原样交接

## 发问方式：按平台查表

命令文件是宿主中立的 Markdown，安装位置旁没有 `policies/` 目录，因此**内联**本命令所需的
询问工具注册表（与共享策略 `policies/ask-question-react.md` 保持一致，若冲突以策略文件为准）。

**查表步骤**：读 `.polaris/config.yaml` 的 `platform` 字段 → 按下表确定工具名与能力 → 用查得的工具发问。

| `platform` | 询问工具 | 单次多 question | 单 question 选项上限 |
|---|---|---|---|
| `trae` | `AskUserQuestion` | 支持 | 5 |
| `trae-cn`     | `AskUserQuestion` | 支持 | 5 |
| `cursor` | `AskUserQuestion` | 支持 | 5 |
| `qoder` | — | — | 走文本降级模式 |
| `claude`      | `AskUserQuestion` | 支持 | 5 |
| 未登记 / 读不到 config | — | — | 走文本降级模式 |

**文本降级模式**：无法确定平台或询问工具不可用时，在对话中逐个输出编号选项
（`A. … / B. … / C. …`）+ 每项影响 + 要求用户回复编号，然后停止等待。降级后下一个决策点
**重新尝试**查表，不沿用「本会话不可用」的结论。

**通用约束**：每次发问后必须停止等待，不得自答自续；推荐项只作说明，不自动选择。

## 执行状态

执行本命令期间维护四个状态，只有**全部填好**才允许进入第四步（查表并加载技能）：

- `已选类别`：需求 / 原型 / 开发 / 测试 / 维护，五者之一
- `已选功能`：C01–C03 / M01 / M02 / M11 / M12 / R01–R03 / P01–P02 / T01–T03，其中之一
- `需求内容`：用户首次输入的**原文**（原样交接给被加载的技能；**命令层不做预检、不改写、不摘要**）
- `附加上下文`：`待收集` / `无` / 具体清单（文件路径、目录、或文字说明）

每一步结束都回头检查状态：
- 只要 `已选功能` 为空或 `附加上下文` 仍为 `待收集`，就必须继续询问，不得往下走

**快捷路径**：若用户首次输入就已给出具体功能（编号如 `C02`，或名称如 `实现常规功能`），
则直接把前两个状态一并填好，跳过第一步与第二步，进入第三步。给出的是类别名时才需要走第二步。
即使用户已给出功能，第三步仍照常执行——除非用户随命令一并给出了上下文材料，此时可直接填入 `附加上下文`。

> **开发类的前置需求预检与复杂度判档已下沉到 `polaris{{SKN_SPR}}coding{{SKN_SPR}}intake` 技能**
> （Step 1 需求预检 / Step 2 复杂度判档 / Step 3 路由）。
> 本命令**不再**在命令层做需求预检或复杂度评估 —— 只负责「选择 + 路由」，把用户的原始输入与 `附加上下文` 一并交接给被加载的技能。

## 第三步：收集附加上下文

目的是在加载技能前，让用户有机会交代「技能开工前需要读什么」——参考资料、目标文件、约束说明等
（未完成收集不得加载技能，见 HARD-STOP #8）。

### 3.1 询问是否需要附加上下文

用「发问方式」查得的询问工具发问，查表命中 `AskUserQuestion` 时的完整参数如下：

```json
{
  "questions": [{
    "question": "进入技能前，是否需要附加上下文供技能先阅读？",
    "header": "附加上下文",
    "multiSelect": false,
    "options": [
      { "label": "附加文件/目录", "description": "给出路径（如设计稿、接口文档、目标代码），技能开工前先读取" },
      { "label": "补充文字说明", "description": "用文字交代背景、范围、约束、参考资料等" },
      { "label": "直接开始", "description": "无附加上下文，立即加载技能" }
    ]
  }]
}
```

### 3.2 按答复收集内容

| 用户选择 | 处理 |
|---|---|
| **附加文件/目录** | 停下来等用户给出路径（绝对路径优先，支持目录与通配符）。收到后逐个校验存在性：路径不存在或不可读时，**明确报出哪几个路径有问题**并要求用户修正，不得静默忽略。全部通过后才记入 `附加上下文`。 |
| **补充文字说明** | 停下来等用户输入文字。收到后原样记入 `附加上下文`，不要自行改写或摘要。 |
| **直接开始** | `附加上下文` 记为 `无`，直接进入第四步。 |

收集规则：

- 用户迟迟未给出内容或表示跳过时，按 `无` 处理并记录，不得反复追问超过一次
- `附加上下文` 记录的是**原样清单**，不要在收集阶段就读取或总结文件内容

### 3.3 收集完成后的交接口径

把 `附加上下文` 连同 `已选功能` / `需求内容` 一起交接给第四步加载的技能，第四步按本口径显式告知技能：

1. 技能在**自身流程开始前**，先完整读取 `附加上下文` 中的全部文件/目录（及 `需求内容`），或理解文字说明
2. 读取失败、文件不存在或内容与所选功能明显无关时，**先回报用户再决定是否继续**，不得静默跳过
3. 后续各阶段的产物必须以上下文为准绳，与上下文冲突时以用户提供的上下文优先

按 `已选功能` 的编号在上表中查到入口技能。选项名称以第二步选项的 `label` 为准；
用户说「代码评审」「重构」等别名时，按编号等价映射到 **M11 / M12**。

开发类（C01 / C02 / C03 / M01 / M02）的 `需求内容` 一律先经 `intake`（C01–C03）或 `diagnose`（M01 / M02）把关，
命令层**不做**预检。

用户只说「修 bug」「修复缺陷」而未区分场景时，按以下信号判定后再映射，**不得默认选 M01**：

| 信号 | 映射 |
|------|------|
| 生产 / 线上环境、真实用户受影响、来自告警或客服工单 | **M01**（hotfix） |
| 测试环境、提测后回归失败、用例失败、测试同学提单 | **M02**（bugfix） |
| 信号不足或两者皆有可能 | **停下来询问用户是生产还是测试场景**，不做推测 |

**查到「⚠️ 暂不可用」时**（见 HARD-STOP #10）：明确告知用户该功能不可用，照上表「入口技能」列
**照实说出缺的是哪个技能**，并询问是否改选其他功能；改选则回到第二步重新走一遍选择流程。

加载技能时**必须同时交接** `已选功能` / `附加上下文` / `需求内容` 三个字段，并显式告知技能遵守 3.3 的交接口径（先读取全部材料、异常先回报、上下文优先）。
`需求内容` 为空时（仅对非开发类）技能直接按其自身流程执行。
`需求内容` 字段名沿用至 tweak / normal / specify / debug（M01 / M02） / prototype（蓝图 / 建造），被加载技能按以下约定读取：

- tweak / normal：作为「轻量澄清 / intention」输入
- specify：作为 Phase 0 discovery 的 seed
- debug（M01 生产 / M04 测试）：作为故障现象 / 缺陷描述的初始输入。生产的时间线·影响面·变更清单**三对齐**、测试的复现步骤 / 实际结果 / 预期结果 / 环境版本**四要素**统一由 `diagnose` 校验并一次性补全；生产通道的现场保全清单也在 `diagnose` 内产出
- prototype（**P01 制作**：蓝图 / 建造 / 交付）：作为「最低输入 6 项 + 可选增强输入」的来源——需求文档已能判断的用户 / 场景 / 一期范围 / 页面功能 / 核心流程不重复询问（`blueprint` 技能的 `references/02 §4.3`）
- prototype-review（**P02 评审**）：不消费 `需求内容` 作为评审判据，只消费 `附加上下文` 里的原型文件（与可选的需求文档、已确认蓝图）；缺需求文档时按该技能 §三 的「无需求文档取证法」判，不得凭空补需求
- testing（**T01 编写用例**）：不消费 `需求内容` 作为用例来源——用例来源**严格限定为定稿 PRD**；`附加上下文` 中的 PRD / 交互原型 / 数据库表设计 / 接口清单按 `discovery` 的输入约定读取（后三者缺失不阻断，记 `No-Input`）
- testing-review（**T03 评审**）：不消费 `需求内容`；只消费 `附加上下文` 里的**用例集文档**（与可选的《测试计划》/ PRD 作覆盖判据）

## 功能类选项的复杂度判定

C01 / C02 / C03 的差别在于**走的阶段数**，选择时按以下标准判断。本表是 C01–C03 阶段链与产物的**唯一详述出处**（第四步路由表只保留指针）：

| 选项 | 适用特征 | 阶段差异 |
|:---:|---|---|
| **C01** 简单 | 单模块、单文件级改动、无跨模块设计、无复杂状态流转、风险低 | 走 `tweak` 单入口技能：一次会话内完成轻量澄清（change-brief）→ tasks → 实施 → 出口检查，跳过 design / tasks 与独立 verify，产物为 `change-brief.md` + `tasks.md`，由 ship 归档前补齐四件套 |
| **C02** 常规 | 多模块协作、需规格契约与任务拆分、有一定风险 | 走 `normal` 单入口技能：轻量澄清（intention）→ OpenSpec 四件套 → 双向守门 → 终版细计划 → 齐套审查（1 次）→ 实施 → 出口检查；产物为四件套 + intention + tasks，无 detailed-design、无独立 design / tasks 主审 |
| **C03** 复杂 | 跨系统/跨服务、高风险、需专项设计（数据模型/接口契约/领域模型） | 完整链路：specify → plan → design（可选，plan 完成时询问是否深化）→ tasks → build → verify → ship；含专项设计与强制评审。**链尾是 ship**（交付即结束）——`retro` 归档于阶段序列之外：它对 C01/C02/C03 统一适用，是交付后的**可选只读聚合入口**，由用户显式触发，不进阶段序列 |

- 用户**已知复杂度**时直接按其选择（→ 加载 `polaris{{SKN_SPR}}coding{{SKN_SPR}}intake`，由它复核并路由）。
- 用户**描述模糊**时，交由 intake 的 Step 3 按 `assets/zh/policies/risk-signals.md` 判档后向用户确认一次。

## 需求类、原型类与测试类选项的前置依赖

| 选项 | 前置条件 | 缺失时的处理 |
|---|---|---|
| **R02** 编写产品需求 | 无硬前置：原始需求（用户想法 / 需求文档 / 口头描述）即可起步 | 无——已有《需求基线》时可从下游阶段续跑 |
| **R03** 需求就绪度评估 | 需已定稿的 PRD 终稿（`prd-final-v1.0.md`） | **阻断**：提示用户先执行 **R02** 完成终稿定稿。前置两份评审报告（`review` / `testability`）缺失**不阻断**，对应维度按「证据不足」3 分封顶 |
| **P01** 制作原型 | 需可读的需求输入：需求基线 / 定稿 PRD / 建设方案 / Agent 设计文档（任一并可被 `references/02 §4` 映射为用户 × 场景 × 任务） | 提示用户先执行 **R01 / R02**，或在第三步把方案文档附进 `附加上下文` |
| **P02** 评审已有原型 | 需待评审的原型文件（`.html`），**必须**出现在 `附加上下文` 里；需求文档与已确认蓝图为可选但强烈建议（蓝图是取证源 **E2**，能把「是否符合已确认设计」判到确定结论） | 提示用户在第三步附上原型文件路径；有黄金流 JSON 一并附上则链路审查更完整（`verify.mjs --flow=`）；无需求文档不阻断，业务维度按评审技能 §三 的「无需求文档取证法」判 |
| **T01** 编写测试用例 | 需已定稿的 PRD 且含验收标准 | 提示用户先执行 **R02** 或 **T02** |
| **T02** 编写验收标准 | 需需求条目或 PRD 功能点 | 提示用户先执行 **R01 / R02** |
| **T03** 评审测试用例 | 需**待评审的用例集**：活跃测试用例任务的产物（`.polaris/testcases/<task_id>/test-cases.md`），或用户在 `附加上下文` 给出的用例文档路径 | **阻断**：提示用户在第三步附上用例集路径，或先执行 **T01** 产出用例集。配套《测试计划》与 PRD 缺失**不阻断**，覆盖类维度标「无法执行」并说明 |

发现前置缺失时，**明确告知用户缺什么、应先做哪一项**，禁止带缺失输入硬跑。

检查前置时先看 `附加上下文`：用户附加的材料若已覆盖所需前置（例如 R02 需要的《需求基线》就在附加文件里），
视为前置满足，直接放行。

## 第五步：交给技能执行

1. 加载上表对应的入口技能，严格按技能内定义的流程执行（交接口径见 3.3 与第四步）
2. 阶段之间的衔接由**各阶段技能在自己的出口**判定：调用 `polaris-flow state next <change-name>` 读配置（`config.yaml` 与任务 `state.yaml` 的 `auto_transition`）—— auto → 先压缩上下文再执行下一技能；manual → 停下并提示用户**新开会话**输入该技能名。命令层**不代做判定**，也不得在同一会话硬续跑
3. 执行过程中若发现当前选项与实际复杂度不符，向用户提出切换建议，由用户决定是否切换
