# Polaris Flow — 功能选择入口

本命令是 Polaris Flow 的统一入口，负责**让用户选择要做什么**，然后把执行交给对应的技能。

<HARD-STOP>
1. ❌ 禁止替用户默认选择某一项，必须等用户明确选择
2. ❌ 禁止跳过菜单直接开始干活
3. ❌ 禁止在本命令内直接产出需求文档、代码或测试用例——本命令只做选择与路由
4. ❌ 禁止用户未选择时自行推进，应重新发起对应级别的询问
5. ❌ 禁止把 11 个功能项一次性塞进单次询问（单 question 选项上限 4 个）
6. ❌ **禁止在第 1 级拿到答案后直接跳去加载技能**——必须立刻发起第 2 级询问
7. ❌ 禁止用纯文本罗列选项代替第 2 级询问——必须发出真实的询问工具调用（文本降级模式除外）
8. ❌ **禁止在未完成上下文收集时加载技能**——必须走完第三步，得到用户明确答复（`无` 也算明确答复）
9. ❌ 禁止写死询问工具名——工具名一律按下方「发问方式」查表得到
10. ❌ **禁止对标注「⚠️ 暂不可用」的选项尝试加载技能**——必须停下并明确告知用户缺什么，不得静默跳过、直接开工、或自行换用其他技能替代
</HARD-STOP>

## 发问方式：按平台查表

命令文件是宿主中立的 Markdown，安装位置旁没有 `policies/` 目录，因此**内联**本命令所需的
询问工具注册表（与共享策略 `policies/ask-question-react.md` 保持一致，若冲突以策略文件为准）。

**查表步骤**：读 `.polaris/config.yaml` 的 `platform` 字段 → 按下表确定工具名与能力 → 用查得的
工具发问。

| `platform` | 询问工具 | 单次多 question | 单 question 选项上限 |
|---|---|---|---|
| `trae` | `AskUserQuestion` | 支持 | 4 |
| `trae-cn`     | `AskUserQuestion` | 支持 | 4 |
| `cursor` | `AskUserQuestion` | 支持 | 4 |
| `qoder` | — | — | 走文本降级模式 |
| `claude`      | `AskUserQuestion` | 支持 | 4 |
| `cursor`      | `AskUserQuestion` | 支持 | 4 |
| `codebuddy`   | `AskUserQuestion` | 待确认（按宿主实际行为判定；若不支持则按「不支持」分支处理） | 4 |
| 未登记 / 读不到 config | — | — | 走文本降级模式 |

**文本降级模式**：无法确定平台或询问工具不可用时，在对话中逐个输出编号选项
（`A. … / B. … / C. …`）+ 每项影响 + 要求用户回复编号，然后停止等待。降级后下一个决策点
**重新尝试**查表，不沿用「本会话不可用」的结论。

**通用约束**：每次发问后必须停止等待，不得自答自续；推荐项只作说明，不自动选择。

## 执行状态

执行本命令期间维护三个状态，只有**全部填好**才允许进入第四步（查表并加载技能）：

- `已选类别`：需求 / 开发 / 测试 / 维护，四者之一
- `已选功能`：P01–P03 / M01–M03 / R01–R02 / T01–T02，其中之一
- `附加上下文`：`待收集` / `无` / 具体清单（文件路径、目录、或文字说明）

每一步结束都回头检查状态：只要 `已选功能` 为空或 `附加上下文` 仍为 `待收集`，就必须继续询问，不得往下走。

**快捷路径**：若用户首次输入就已给出具体功能（编号如 `P02`，或名称如 `实现常规功能`），
则直接把前两个状态一并填好，跳过第一步与第二步，进入第三步。给出的是类别名时才需要走第二步。
即使用户已给出功能，第三步仍照常执行——除非用户随命令一并给出了上下文材料，此时可直接填入 `附加上下文`。

## 第一步：询问功能类别（第 1 级）

用「发问方式」查得的询问工具发起第 1 级询问。查表命中 `AskUserQuestion` 时，完整参数如下
（**原样使用，不要改写**；降级模式下改输出编号选项并要求回复编号）：

```json
{
  "questions": [{
    "question": "这次要执行哪一类功能？",
    "header": "功能类别",
    "multiSelect": false,
    "options": [
      { "label": "需求", "description": "编写用户需求（需求基线）或产品需求（PRD）" },
      { "label": "开发", "description": "实现新功能，按复杂度分简单 / 常规 / 复杂三档" },
      { "label": "测试", "description": "编写测试用例或验收标准" },
      { "label": "维护", "description": "修复 Bug、代码评审、重构既有代码" }
    ]
  }]
}
```

拿到答案后：把类别记入 `已选类别`，**然后立刻进入第二步**。此处不得加载任何技能，也不得开始干活。

## 第二步：询问具体功能（第 2 级）

**这一步不可跳过。** 按第一步拿到的 `已选类别`，从下面四组中挑**对应的一组**，用「发问方式」查得的
询问工具原样发问。不要一次把所有 11 项都塞进一次询问。

```json
      { "label": "P03 · 实现复杂功能", "description": "跨服务/高风险，含专项设计与交付复盘" }

```

## 第三步：收集附加上下文

**这一步不可跳过，且必须停下来等用户答复。** 目的是在加载技能前，让用户有机会交代
「技能开工前需要读什么」——参考资料、目标文件、约束说明等。

### 3.1 询问是否需要附加上下文

用「发问方式」查得的询问工具发问，查表命中 `AskUserQuestion` 时的完整参数如下：

```json
{
  "questions": [{
    "question": "进入技能前，是否需要附加上下文供技能先阅读？",
    "header": "附加上下文",
    "multiSelect": false,
    "options": [
      { "label": "附加文件/目录", "description": "给出路径（如设计稿、接口文档、目标代码），技能开工前先读取" },
      { "label": "补充文字说明", "description": "用文字交代背景、范围、约束、参考资料等" },
      { "label": "直接开始", "description": "无附加上下文，立即加载技能" }
    ]
  }]
}
```

### 3.2 按答复收集内容

| 用户选择 | 处理 |
|---|---|
| **附加文件/目录** | 停下来等用户给出路径（绝对路径优先，支持目录与通配符）。收到后逐个校验存在性：路径不存在或不可读时，**明确报出哪几个路径有问题**并要求用户修正，不得静默忽略。全部通过后才记入 `附加上下文`。 |
| **补充文字说明** | 停下来等用户输入文字。收到后原样记入 `附加上下文`，不要自行改写或摘要。 |
| **直接开始** | `附加上下文` 记为 `无`，直接进入第四步。 |

收集规则：

- 选了前两项却**还没等到具体内容时，必须停在原地等**，禁止自行假设「没有上下文」往下走
- 用户迟迟未给出内容或表示跳过时，按 `无` 处理并记录，不得反复追问超过一次
- `附加上下文` 记录的是**原样清单**，不要在收集阶段就读取或总结文件内容

### 3.3 收集完成后的交接口径

把 `附加上下文` 连同 `已选功能` 一起交给第四步加载的技能，并在交接时明确要求：

1. 技能在**自身流程开始前**，先完整读取 `附加上下文` 中的全部文件/目录，或理解文字说明
2. 读取失败、文件不存在或内容与所选功能明显无关时，**先回报用户再决定是否继续**，不得静默跳过
3. 后续各阶段的产物必须以上下文为准绳，与上下文冲突时以用户提供的上下文优先

## 第四步：按选择加载技能

| 选项 | 入口技能 | 后续阶段链 |
|:---:|---|---|
| **P01** 实现简单功能 | `polaris{{SKN_SPR}}coding{{SKN_SPR}}tweak` | tweak（轻量澄清 → tasks → 实施 → 出口检查）→ ship |
| **P02** 实现常规功能 | `polaris{{SKN_SPR}}coding{{SKN_SPR}}normal` | normal（轻量澄清 → 四件套 → 双向守门 → 终版细计划 → 合并主审 → 实施 → 出口检查）→ ship |
| **P03** 实现复杂功能 | `polaris{{SKN_SPR}}coding{{SKN_SPR}}clarify` | clarify → propose → design(可选) → plan → build → verify → ship → retro |
| **M01** 修复Bug | `polaris{{SKN_SPR}}maintance{{SKN_SPR}}hotfix` | ⚠️ 暂不可用 · 该技能尚未提供 |
| **M02** 代码评审 | `polaris{{SKN_SPR}}maintance{{SKN_SPR}}codereview` | ⚠️ 暂不可用 · 该技能尚未提供 |
| **M03** 重构 | `polaris{{SKN_SPR}}coding{{SKN_SPR}}refactor` | ⚠️ 暂不可用 · 该技能尚未提供 |
| **R01** 编写用户需求 | `polaris{{SKN_SPR}}prd{{SKN_SPR}}discovery` | discovery（产出需求基线，含功能架构草案） |
| **R02** 编写产品需求 | `polaris{{SKN_SPR}}prd{{SKN_SPR}}draft` | draft → refine → review → ship |
| **T01** 编写测试用例 | `polaris{{SKN_SPR}}testing{{SKN_SPR}}case` | case（产出用例集 + 追溯矩阵） |
| **T02** 编写验收标准 | `polaris{{SKN_SPR}}testing{{SKN_SPR}}acceptance` | acceptance（产出 GWT 验收标准清单） |

按 `已选功能` 的编号在上表中查到入口技能。选项名称以第二步选项的 `label` 为准；
用户说「代码评审」「重构」等别名时，按编号等价映射到 **M02 / M03**。

**查到「⚠️ 暂不可用」时，不要尝试加载技能**，改为明确告知用户并停下：

1. 说明该功能当前不可用，并照上表「入口技能」列**照实说出缺的是哪个技能**
2. 询问用户是否改选其他功能；改选则回到第二步重新走一遍选择流程

禁止在技能缺失时直接开工或用其他技能顶替——用户必须明确知道这次什么都没做，而不是拿到一份错位产物。

加载技能时**必须同时交接** `已选功能` 与 `附加上下文`，并显式告知技能：
开工前先读取上下文清单中的全部材料（详见 3.3）；`附加上下文` 为 `无` 时直接按其自身流程执行。

## 功能类选项的复杂度判定

P01 / P02 / P03 的差别在于**走的阶段数**，选择时按以下标准判断：

| 选项 | 适用特征 | 阶段差异 |
|:---:|---|---|
| **P01** 简单 | 单模块、单文件级改动、无跨模块设计、无复杂状态流转、风险低 | 走 `tweak` 单入口技能：一次会话内完成轻量澄清（change-brief）→ tasks → 实施 → 出口检查，跳过 design / plan 与独立 verify，产物为 `change-brief.md` + `tasks.md`，由 ship 归档前补齐四件套 |
| **P02** 常规 | 多模块协作、需规格契约与任务拆分、有一定风险 | 走 `normal` 单入口技能：轻量澄清（intention）→ OpenSpec 四件套 → 双向守门 → 终版细计划 → 合并主审（1 次）→ 实施 → 出口检查；产物为四件套 + intention + tasks，无 detailed-design、无独立 design / plan 主审 |
| **P03** 复杂 | 跨系统/跨服务、高风险、需专项设计（数据模型/接口契约/领域模型） | 完整链路（design 可选，propose 完成时询问是否深化）+ 专项设计与强制评审，交付后复盘 |

用户已明确复杂度时直接按其选择；用户描述模糊时，用上表判定后向用户确认一次。

## 需求类与测试类选项的前置依赖

| 选项 | 前置条件 | 缺失时的处理 |
|---|---|---|
| **R02** 编写产品需求 | 需已存在《需求基线》 | 提示用户先执行 **R01** 产出需求基线 |
| **T01** 编写测试用例 | 需已定稿的 PRD 且含验收标准 | 提示用户先执行 **R02** 或 **T02** |
| **T02** 编写验收标准 | 需需求条目或 PRD 功能点 | 提示用户先执行 **R01 / R02** |

发现前置缺失时，**明确告知用户缺什么、应先做哪一项**，禁止带缺失输入硬跑。

检查前置时先看 `附加上下文`：用户附加的材料若已覆盖所需前置（例如 R02 需要的《需求基线》就在附加文件里），
视为前置满足，直接放行。

## 第五步：交给技能执行

1. 加载上表对应的入口技能，严格按技能内定义的流程执行；技能须先消费 `附加上下文` 再进入自身流程
2. 阶段之间是否自动衔接，由宿主的自动衔接配置决定；未自动衔接时，按技能产出提示用户手动触发下一阶段
3. 执行过程中若发现当前选项与实际复杂度不符，向用户提出切换建议，由用户决定是否切换

## 路由后的职责边界

- 本命令只负责「选择 + 路由」，不产出任何需求、设计、代码或测试产物
- 所有产物由被路由到的技能按其自身规范生成并落盘
