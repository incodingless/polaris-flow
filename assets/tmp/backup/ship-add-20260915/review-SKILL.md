# 原型交付评审

对**已有** Web 原型做交付评审：判断能不能交研发，产出分级问题清单与整改建议。

用途：原型评审 / 交付前把关 / 研发交接判定 / 一票否决核对 / 三层运行时验证复核 / 问题清单与整改建议

<HARD-STOP>
1. ❌ **禁止改动原型任何一行**——不生成新版原型、不顺手修 Token、不换图标、不"我先把这个问题解决了"。评审只输出问题与建议，改不改由用户决定
2. ❌ 禁止只给结论不给定位：每条问题必须带**可核对的定位证据**（`verify` 检查项 ID / 判据 §号 + 页面 `<section id>` + 触发动作 / 三档分辨率中哪一档可复现）
3. ❌ 禁止不分级：所有问题必须标 P0 / P1 / P2 / P3
4. ❌ 禁止臆测：无法从原型与输入材料判定的事项，写进「证据不足 / 待确认」区——**既不写成缺陷，也不写成通过**
5. ❌ 禁止跳过任何维度：无证据的维度标「证据不足 + 缺什么证据」，不得静默略过
6. ❌ **禁止不跑工具就给人工结论**：三层运行时验证必须实际执行；跑不了就标注「未执行 + 原因」，不得写成通过、也不得当作已覆盖
7. ❌ 禁止替产品经理决定范围 / 页面取舍 / 实现深度（`§31.2`，唯一来源：`polaris{{SKN_SPR}}prototype{{SKN_SPR}}build` → `references/00-basis.md §二` / `§34` 第 16 条）；只给建议并声明"最终由产品经理确认"
8. ❌ 禁止改判据：发现 `§33` / `§34` 本身有问题时回报用户并停止，不得在本轮评审里私自换标准
</HARD-STOP>

## 二、输入契约

| # | 输入 | 必需性 | 缺失处理 |
|---|---|---|---|
| 1 | 待评审原型 `.html`（单文件、零外部依赖、可离线双击打开） | **必需** | 无文件 → **阻断**：停下来要路径，不得凭口头描述评审 |
| 2 | 黄金流定义 `flow.json` | **强烈建议** | 缺 → 允许，但 L3 黄金流链路无法执行，报告须列「未执行」 |
| 3 | 需求文档 / PRD / 建设方案（取证源 **E1**） | 可选 | 缺 → `§33.1` 业务维度改用 §三 的「无需求文档取证法」（E5）判，**且结论按 §二 规则 1 降级为「证据不足 / 待需求方确认」** |
| 4 | **经人工确认的《原型蓝图》**（`blueprint.md` + 任务理解卡 / 黄金流 / IA / 页面清单，取证源 **E2**） | **强烈建议** | 缺 → 「原型是否符合已确认的设计」无法核对，该项进「证据不足」；**不得因此判缺陷**。未经确认的草稿按 E3 对待 |
| 5 | 设计系统 / 视觉规范 CSS | 可选 | 缺 → 无法判「Token 取值是否来自规范而非技能兜底基线」；**不得因此判缺陷** |
| 6 | 研发交接说明 / 页面结构与状态说明 | 可选 | 缺 → `§33.5` 研发维度标「证据不足」，不得替研发判断能否落地 |
| 7 | **建造移交包**（`polaris{{SKN_SPR}}prototype{{SKN_SPR}}build` 交付时移交：原型 + `flow.json` + 需求文档 + 落盘产出物 + 设计规范） | **入口 B 必需**；入口 A 不可得 | 缺 → 不阻断，按上表逐项走缺失处理 |

### 取证源分级（决定「能判到什么程度」：材料再多也不能越级取证）

同为材料，**证明力不同**。先看它能证明什么，再决定结论能写到多硬：

> **命名区分**：本节 `E1`–`E5` 指**取证源等级**；Step 2 三层验证与报告里的 `L1`–`L3` 指**验证层**（静态 / 冒烟 / 黄金流）。
> 两者是不同坐标系，不得互换。

| 级 | 取证源 | 能证明 | **不能**证明 |
|:--:|---|---|---|
| **E1** | 需求方的**需求文档 / PRD / 建设方案** | **业务方向对不对**：用户与场景、核心任务覆盖、一期范围、真需求 vs 伪需求 | 页面级实现细节 |
| **E2** | **经人工确认的《原型蓝图》**（`blueprint.md` + 理解卡 / 黄金流 / IA / 页面清单 + 确认记录） | **设计结论已被需求方认可**：范围取舍、页面划分与职责、任务流走向是确认过的——原型偏离它即「未按已确认的蓝图实现」 | **这个设计结论是否符合需求方原始意图**（那是 E1 的事）；原型是否忠实实现它（那是 E4） |
| **E3** | 建造侧**自述产物**（页面结构与状态说明 / 研发交接说明；**未经确认的蓝图草稿也归这一级**） | **内部一致性**：各份设计之间是否自洽 | **任何涉及业务意图或范围认可的判断**——它是被评审方自己写的 |
| **E4** | **原型自身**（`.html` + `flow.json`）+ Step 2 实测结果 | 有没有、能不能跑通、三档分辨率下可否完成 | 业务意图的任何判断 |
| **E5** | 本技能 Step 3 的「无需求文档取证法」五条 | 「有」还是「没有」的**存在性** | 业务方向对不对（它自己就这么声明） |

**三条硬规则**（写结论前对一遍）：

1. **降级不升格**：缺 E1 时，业务维度（`§33.1`）最高只能写到「**证据不足 / 待需求方确认**」——**材料再多也不能把 E2 当成 E1 用**。
   E2（经确认的蓝图）能把「**原型是否符合已确认的设计**」判到确定结论，但**证明不了这个设计本身对不对**——
   蓝图确认的是"照这个做"，不等于需求方的原始意图已被完整表达。典型误判：拿《任务理解卡》里的"用户是谁"去给 `§33.1` 打勾。
2. **交叉偏差分四种定性**，不可混为一谈：
   - **原型 ≠ E2**（没照已确认的蓝图做）→ **是缺陷**，按 `§33.2` / `§33.3` 的对应条款定级；
   - **原型 ≠ E3**（没照自己写的结构 / 状态说明做）→ **是缺陷**，按 `§33.2` / `§33.3`；
   - **E2 ≠ E1**（理解偏差，已确认的蓝图本身不照需求来）→ **不得定为缺陷**，进 **P3 待确认**并声明"最终由产品经理确认"（HARD-STOP #7）；
   - **原型 ≠ E1**（需求覆盖有缺口）→ **是缺陷**，按 `§33.1`。
3. **读不到就当没有**：产物缺失、空壳或与实际原型对不上时按缺失处理，在「证据不足」节写清缺哪一份，**不得凭文件名推断内容**。
   蓝图**未确认**（无确认记录 / `blueprint.status != confirmed`）时按 E3 自述产物对待，不得享受 E2 的证明力。

> **E2 为什么单独成级**：它把「做没照着设计做」从**被评审者自述**（E3）升级为**需求方已背书的事实**——
> 这是它比 E3 硬的原因；也正因为它仍然只是"设计侧的产物"，所以永远顶替不了 E1。

**两种入口**（决定 Step 0 / Step 1 怎么走，不改变判据与分级）：

- **入口 A · 用户主动发起**：材料由用户提供，用途与范围当面确认。
- **入口 B · 流程移交**（由 `flow.md` 在原型交付前发起的门禁，`build` 环节结束后调用）：调用方在移交时已声明**用途 = 交付前把关、范围 = 全量**。据此**不再询问**用途与范围（不重复询问原则），仍必须执行 Step 0 声明与 Step 1 指纹登记。
  ⚠️ **独立性**：入口 B 常由建造者在**同一会话**内接着执行——此时评审者 = 建造者，独立性受限。报告须在「评审对象与范围」一节如实注明这一点；**不因此放宽任何判据、也不因此降低等级**。

不重复询问原则：用户已提供或调用方已声明的信息，不再问第二遍——入口 B 下典型要跳过的就是用途与范围两项。

## 三、评审流程

`Step 0 只评不改声明 → Step 1 输入加载与范围确认 → Step 2 第一层：实际执行可执行验证 → Step 3 第二层：五维人工走查 → Step 4 第三层：一票否决核对 → Step 5 问题汇总与分级 → Step 6 报告输出 → Step 7 重评审`

### Step 0 — 只评不改声明（开工前必须做，**两个入口的等待行为不同**）

**入口 A（用户主动发起）**：先声明再动手，**等用户确认**：

> 本次**只评审不修改**：我不会改动原型的任何一行。发现的问题以「分级清单 + 定位证据 + 整改建议」形式给出，改不改由你决定。
> 评审对象：`<原型文件路径>`。

**入口 B（建造移交）**：照原样念出同一段声明，**不等待确认**——移交方已在 `polaris{{SKN_SPR}}prototype{{SKN_SPR}}build` 交付前声明过，这是流水线内的一步，停下来问等于卡死门禁。若 §二 的独立性注记适用（同一会话），声明末尾补一句「**注：本轮评审者与建造者相同，独立性受限**」。

### Step 1 — 输入加载与范围确认

1. **登记评审对象指纹**：路径 + 字节数 + `sha256`（`shasum -a 256 <file>`，Linux 用 `sha256sum`）。它是「评审对象 = 交付对象」的证据，也用于事后证明评审过程没动过文件。
2. **加载可选输入**：需求文档 / 设计规范 / 研发交接说明，按 §二 的缺失处理分类。**入口 B** 还要加载建造移交包里阶段 1–8 的落盘产出物（任务理解卡 / 黄金流 / IA / 页面清单 / 页面结构）——它们是建造侧的判断依据，可用来核对原型是否与设计结论一致，**但不能代替原型本身的取证**：原型里看不到的东西，仍然按「证据不足」处理。
3. **确认评审范围**——**入口 B 跳过**（调用方已声明「全量」，不再询问）；入口 A 按 `./policies/ask-question-react.md` 的「平台询问工具注册表」查表发问（工具名不得写死；查不到走文本降级）：

```
A. 全量评审——五维 + 一票否决 + 三层验证全套（默认，交付前把关用这个）
B. 指定页面评审——先按 <section id> 列出页面清单，让用户勾选后只审这些页面
```

选 B 时必须在报告中写明「本次未覆盖的页面」，**不得**让局部评审的结论看起来像全量结论。
4. **确认用途**：交付前把关 / 研发交接判定 / 独立复核（用途决定结论措辞的严格度，见 §四）。**入口 B 固定为「交付前把关」**（调用方已声明，不再询问）。

### Step 2 — 第一层：实际执行可执行验证（不是"读一遍脚本"）

```
node scripts/verify.mjs <原型.html> --flow=<黄金流.json> --strict
```

- 必须在 `polaris{{SKN_SPR}}prototype{{SKN_SPR}}build` 技能目录下执行（`scripts/verify.mjs` 属该技能）；选项见 `--help`。
- **原样记录**：三层各自 PASS / FAIL / 未执行、退出码（0 / 1 / 2 / 3）、HARD 计数、WARN 计数、命中的检查项 ID。
- 退出码 `3` = `--strict` 下必需层被跳过 → 按**未完成**计，不得按通过计。
- 环境跑不了（无 Node / 无可用浏览器）→ 报告标注「未执行 + 原因」，并说明这会让哪些维度失去取证依据。
- **HARD 项一律 P0**。WARN 项必须人工判读：`verify` 报 WARN 不等于缺陷，全绿也不等于合格（脚本只判「有没有」，判不了「好不好」）。

### Step 3 — 第二层：五维走查

`read_file` `./references/01-quality-criteria.md` 加载质量标准文档
按 `§33` 的五个维度（业务 / 结构 / 交互 / 视觉 / 研发）**逐维独立走查**，每维走完立即记录问题，禁止边看边下总评。
`§33.6` 演示就绪审查在「对外演示 / 比赛」用途下必做。

**交叉核对**（拿到 E2 / E3 设计产物时**必做**，定性规则见 §二 规则 2）——这一步把「有没有真的走过设计」从声称变成可核对的事实：

| 对比 | 查什么 | 命中怎么判 |
|---|---|---|
| 《页面清单》↔ 实际 `<section id>` | 清单有、原型没有；原型有、清单没有 | 清单有而原型没有 → 缺陷（`§33.2`）；原型多出的页面 → 查它是否服务真实任务（`§33.1`，缺 E1 时按**证据不足**处理） |
| 《核心用户任务流》↔ Step 2 的 L3 链路结果 | 黄金流每一步在原型里是否真能点通 | 有断点 → 缺陷（`§33.1` / `§33.3`），并引用 L3 的具体失败节点 |
| 《IA》↔ 页面清单 / 原型导航 | 导航项有无落地页面；页面有无入口 | 无入口或永远走不到的页面 → 伪需求页面候选（`§33.2`） |
| 《页面结构与交互说明》↔ 实际页面 | 文档声明的 11 种状态是否真写进页面 | 声明了但页面里没有 → 缺陷（`§33.3`） |

交叉核对是 **E2 / E3（设计产物）对 E4（原型）** 的核对，**不掺入 E1**——它回答「做没照着自己的设计做」，不回答「这个设计对不对」。

**无需求文档取证法**（缺输入 3 时，`§33.1` 业务维度的替代取证，即 §二 的 E5）：

1. 黄金流能否走通（用 Step 2 的 L3 结果，不靠肉眼）；
2. 每个页面是否有明确入口与出口——**无入口或永远走不到的页面 = 伪需求页面候选**，逐页列出；
3. 页面是否围绕同一条核心任务，还是"首页 → 列表 → 详情 → 设置"式的模板拼盘；
4. 演示数据是否自洽——同一业务单号 / 对象跨页面一致、Tab 计数与真实数据一致；
5. 是否存在无来源数字、无依据结论。

这五条只能证明「有」还是「没有」，**证明不了业务方向对不对**；凡涉业务意图的判断一律进「证据不足」，写成「待需求方确认」，不得写成缺陷。

### Step 4 — 第三层：一票否决核对（加载同一文件的 `§34`）

逐条核对 31 条，命中即 **P0**。
注意第 30 条自身就是流程项——「未运行 `verify` 全三层并取得退出码 0 就交付」，所以 Step 2 没执行时**它本身就成为 P0**。

### Step 5 — 问题汇总与分级

每条问题必须五要素齐备，缺一不可：**问题 ID / 标题 / 定位证据 / 等级 / 整改建议**。

**定位证据的合格形态**（三选一，必须可被第三方核对）：

| 形态 | 示例 |
|---|---|
| 工具结论 | `verify L1-9 对比度 3.00:1 < 4.5:1`（附脚本原文结论） |
| 判据 + 位置 + 动作 | `§33.3`：`<section id="review">` 页「上传合同」按钮点击后无 Loading 态 |
| 分辨率 + 位置 + 现象 | 1366×768 下 `<section id="workbench">` 右侧栏被裁切，1920×1080 正常 |

**不接受的形态**：「整体感觉不够专业」「状态覆盖不全」「视觉不够统一」——这是结论不是问题，必须补足位置与证据，否则降级为 P3 待确认或删掉。

问题 ID 规则：`<维度码>-<三位序号>`，维度码 = `BIZ` 业务 / `IA` 结构 / `IX` 交互 / `VIS` 视觉 / `DEV` 研发 / `VETO` 一票否决 / `ENV` 可执行验证。同一问题在「按维度明细」与「按等级清单」两处出现，**ID 一一对应**；导出 markdown 时给 ID 加锚点链接（明细侧 `<a id="biz-001">BIZ-001</a>`，清单侧 `[BIZ-001](#biz-001)`），便于两视图来回跳转。

### Step 6 — 报告输出

按 `./templates/prototype_review_report_template.md` 输出，落盘位置由用户定；未指定时默认与原型文件同目录，文件名 `原型评审报告_<原型文件名>_<YYYYMMDD>.md`。

### Step 7 — 重评审机制

- **触发**：存在 P0，或用户要求重评审。
- **范围**：只重审已修复的问题及其关联页面，**不重复评审已通过部分**（已通过项引用上一轮结论与 ID）。
- **必做**：重新登记 `sha256`——重评审报告里必须能看出「这轮审的是改后版本」。
- **收口**：P0 全部关闭 → 结论可从「不得交付」升级为「修复后可交付」或「可交付」，并注明依据。

## 四、问题分级 P0–P3

| 等级 | 判据 | 阻断交付 | 处置建议 |
|---|---|---|---|
| **P0 阻断** | 命中 `§34` 任一条；或 `verify` 退出码非 0；或核心任务在三档分辨率下不可完成；或原型无法离线双击打开 | **是** | 必须修复后重评审 |
| **P1 重要** | 未触一票否决，但影响业务闭环 / 信息架构 / 关键交互状态（如 Error 无下一步、AI 结果无依据或人工确认、页面职责重叠、黄金流有断点） | 是 | 交研发前必修，可在本轮修复后免重评审 |
| **P2 一般** | 不阻断交付但破坏产品语言一致性（视觉一致性、命名冗余、密度不一致、图标风格不统一） | 否 | 随迭代修 |
| **P3 待确认** | **需要产品经理决策**的事项（页面取舍、一期范围、实现深度、是否接受某约束） | 否 | 不作为缺陷；**不得**替产品经理决定 |

结论只有三个取值：**可交付** / **修复后可交付** / **不得交付**（存在 P0 一律「不得交付」）。写结论时以 `§36` 的 7 条「一看」为最终口径。

## 五、交付物

一份评审报告（模板见 `./templates/prototype_review_report_template.md`），必须含：

1. 评审对象与范围（路径 + 字节数 + `sha256` + 覆盖范围 + **未覆盖项** + **本次可用的取证源**：E1–E5 各有哪些、哪些缺席 —— 它是「结论为什么只能写到这个硬度」的说明；入口 B 同会话执行时的独立性注记也在这一节）
2. 结论（可交付 / 修复后可交付 / 不得交付）
3. 三层可执行验证结果（逐层 PASS / FAIL / 未执行 + 退出码 + HARD / WARN 计数）
4. 问题分布矩阵（五维 × P0–P3）
5. 分级问题清单（P0 / P1 / P2 + P3 待确认），每条含定位证据与整改建议
6. 证据不足与未执行项（**独立成节，不得混进问题清单**）
7. 重评审记录（`sha256` + 上一轮结论 + 本轮关闭 / 新增项）
8. 「只评不改」声明与实际执行情况（有无改动原型）
