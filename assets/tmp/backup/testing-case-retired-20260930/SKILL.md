# 编写测试用例

## 定位

把已定稿的产品需求转换为结构化、可执行的测试用例集，并给出「需求-用例」追溯矩阵，确保每条需求都有对应用例、每类场景都有覆盖。

**核心原则**：用例源于需求，不源于想象。需求没写的，不设计用例；需求写了的，必须有用例。

<HARD-STOP>
1. ❌ 禁止编写需求中未定义行为的用例（脑补的交互、未声明的提示文案、未约定的错误码）
2. ❌ 禁止在用例步骤中写技术实现细节（调用哪个接口、改哪张表、加什么日志）
3. ❌ 禁止用例步骤不可执行（如"检查系统是否正常"），每步必须是可观察的动作或状态
4. ❌ 禁止预期结果模糊（如"功能正常"），必须给出可判定的具体结果
5. ❌ 禁止只覆盖正常场景，异常与边界场景必须纳入
6. ❌ 禁止忽略追溯关系，每条用例必须标注来源需求编号
7. ❌ 禁止在需求存在 T0 级可测性问题时硬写用例，应先提示用户补全验收标准
</HARD-STOP>

## 输入

- **必需**：定稿的 PRD（终稿优先，初稿需用户确认）
- **必需**：PRD 中的验收标准；若缺失，先建议执行 `polaris{{SKN_SPR}}prd{{SKN_SPR}}testability` 或 `polaris{{SKN_SPR}}testing{{SKN_SPR}}acceptance` 补全
- **可选**：可测性报告（`reviews/testability-report.md`），用于规避已知风险点
- **可选**：测试范围说明（全量 / 指定模块 / 指定需求条目）

## 总流程

Step1 输入加载与测试基线建立 > Step2 三类场景用例设计 > Step3 覆盖校验与追溯矩阵 > Step4 输出测试用例文档

## Step 1 — 输入加载与测试基线建立

### 执行步骤

1. **加载 PRD 并拆解需求条目**
   - 完整读取 PRD，提取功能点、业务规则、非功能需求
   - 为每项分配稳定编号（沿用 PRD 原编号，无编号则按 `F{章节}-{序号}` 补编）
   - 建立「需求条目清单」作为用例设计的唯一来源

2. **建立测试基线**
   - 统计需求条目总数、已有验收标准的条目数
   - 若存在无验收标准的条目 → 列为待补全项，不为其设计用例
   - 若已有可测性报告 → 读取其 T0/T1 问题，作为用例设计的风险提示

3. **确认测试范围与粒度**
   - 默认全量覆盖
   - 与用户确认粒度：功能级（一条用例覆盖一个功能点主流程）或场景级（每条用例只验证一个场景）
   - 未指定时默认**场景级**，一条用例只验证一个可判定结论

## Step 2 — 三类场景用例设计

> 每个需求条目按「正常 → 异常 → 边界」顺序设计，禁止跳类。

### 场景1：正常场景（Happy Path）

验证需求声明的主流程在标准输入下产生预期结果。

| 设计要点 | 说明 |
|---|---|
| 来源 | PRD 功能点的主流程描述与验收标准 |
| 前置条件 | 数据已就绪、用户已具备权限 |
| 步骤 | 按用户实际操作顺序，每步一个动作 |
| 预期 | 与验收标准一致，含界面反馈与数据变化 |

### 场景2：异常场景（Exception Path）

验证需求声明的约束、校验、错误处理在非法输入或异常状态下被正确拦截。

**7 类标准异常源**（按需选取，需求未声明的类别不设计）：

1. 输入异常：空值、格式错误、超长、特殊字符
2. 权限异常：未登录、无权限、权限过期
3. 状态异常：在非法状态下执行操作、状态流转冲突
4. 数据异常：数据不存在、数据冲突、重复提交
5. 并发异常：并发修改、竞态条件
6. 依赖异常：外部系统超时、返回错误、服务降级
7. 业务规则异常：触发限制条件（额度、次数、时效）

### 场景3：边界场景（Boundary）

验证数值、数量、长度、时间等边界值的行为符合需求声明。

| 边界类型 | 取点方法 |
|---|---|
| 数值边界 | 最小值、最小值-1、最大值、最大值+1、0、负数 |
| 长度边界 | 空、1 字符、最大长度、最大长度+1 |
| 数量边界 | 0 条、1 条、上限、上限+1 |
| 时间边界 | 生效前、生效瞬间、失效瞬间、失效后 |
| 空数据 | 列表为空、查询无结果、必填项全空 |

### 用例编写规范

每条用例包含以下字段：

| 字段 | 要求 |
|---|---|
| 用例编号 | `TC-{需求编号}-{序号}`，如 `TC-F001-001-01` |
| 用例标题 | 「条件 + 动作 + 预期」句式，一眼看懂验证什么 |
| 优先级 | P0 核心主流程 / P1 重要异常 / P2 边界与次要 |
| 来源需求 | 追溯到的 PRD 需求条目编号 |
| 前置条件 | 执行前必须满足的数据、权限、环境状态 |
| 测试步骤 | 编号步骤，每步一个可观察动作，含具体输入数据 |
| 预期结果 | 可判定的具体结果（提示文案、状态变化、数据变化） |

**不合格 vs 合格示例**：

| 不合格 | 合格 |
|---|---|
| 验证载体创建功能 | 验证「载体编号已存在」时创建被拦截：Given 系统中已存在编号 C001，When 再次提交编号为 C001 的创建请求，Then 提示"载体编号已存在"，且不新增任何记录 |
| 检查查询是否正常 | 验证查询无结果时的空态：Given 系统中无符合条件的载体，When 输入查询条件并查询，Then 列表区展示空态提示"暂无数据"，不报错 |
| 测试批量导入 | 验证批量导入超上限：Given 准备 1001 条合法数据，When 提交导入，Then 提示"单次导入不超过1000条"，导入任务未创建 |

## Step 3 — 覆盖校验与追溯矩阵

### 覆盖规则

| 校验项 | 通过标准 |
|---|---|
| 需求覆盖率 | 每个有验收标准的需求条目 ≥1 条用例 |
| 场景覆盖 | 每个功能点至少覆盖正常 1 条；复杂功能点（多分支/多状态）须含异常与边界 |
| 优先级分布 | P0 覆盖全部核心主流程 |
| 孤儿用例 | 不存在无法追溯到需求条目的用例 |

### 追溯矩阵

输出「需求 → 用例」双向矩阵：

| 需求编号 | 需求名称 | 正常用例 | 异常用例 | 边界用例 | 覆盖率 |
|---|---|---|---|---|---|
| F001-001 | 载体创建 | TC-F001-001-01 | TC-F001-001-02/03 | TC-F001-001-04 | 完整 |

对未覆盖或覆盖不足的需求条目，输出待补用例清单并说明原因（如需求缺验收标准）。

## Step 4 — 输出测试用例文档

输出到 `openspec/changes/<task_id>/test/test-cases.md`，内容按以下结构组织：

```
# 测试用例集 — {需求/变更名称}

## 1. 测试基线
- 需求条目总数 / 已覆盖数 / 覆盖率
- 测试范围与粒度说明
- 待补全项（无验收标准的需求条目）

## 2. 追溯矩阵
（Step 3 的双向矩阵）

## 3. 测试用例
### 3.1 正常场景
### 3.2 异常场景
### 3.3 边界场景
（每条用例按 Step 2 字段表输出）

## 4. 覆盖结论与风险
- 覆盖率统计
- 未覆盖项及原因
- 测试执行前置依赖（环境、数据、账号）
```

输出后向用户报告：用例总数、按优先级分布、需求覆盖率、待补全项。

## 常见错误

| # | 反模式 | 正确做法 |
|:---:|---|---|
| 1 | 需求没写的行为也设计用例 | 只基于 PRD 显式声明设计；发现缺失反馈用户补需求 |
| 2 | 一条用例塞多个验证点 | 场景级粒度，一条用例一个可判定结论 |
| 3 | 预期结果写"功能正常" | 给出具体文案、状态、数据变化 |
| 4 | 只写正常场景 | 正常/异常/边界三类必须全部过一遍 |
| 5 | 用技术语言描述步骤 | 用用户可观察的操作与结果描述 |
| 6 | 用例无法追溯来源 | 每条标注来源需求编号，输出追溯矩阵 |
