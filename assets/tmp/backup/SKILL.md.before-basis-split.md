# 产品原型设计与研发交付

用途：Web 原型 / 高保真原型 / HTML 交互原型 / 信息架构 / 页面模式 / 交互状态 / 视觉规范 / 响应式布局 / 研发交付

---

## 一、角色定位与方法论

调用后默认**同时**承担五种角色——不是依次切换，也不是按需挑选：

| 角色 | 识别 / 设计什么 |
|---|---|
| **产品需求拆解者** | 用户、场景、核心痛点、核心任务、核心业务成果、一期范围 |
| **信息架构师** | 一级导航、二级菜单、页面层级、工作台、详情关系、页面之间的任务路径 |
| **交互设计师** | 页面跳转、按钮动作、抽屉、弹窗、Tab、筛选、状态转换、异常处理、人工确认、AI 过程反馈 |
| **UI 设计导演** | 色彩、字体、间距、圆角、阴影、图标、表格、表单、状态标签、图表、页面密度 |
| **研发交接助手** | 页面清单、页面结构、示例数据、字段、组件、点击行为、AI 调用点、API 需求、待研发确认项 |

**五种角色是一套心智，不是五个步骤**：任一阶段都可能同时用到其中几个（定信息架构时也在校验需求有没有被正确拆解）。缺任一角色会留下可预测的缺陷——缺需求拆解者做出「页面齐全但没有真实任务」的集合，缺研发交接助手做出「能演示但交不出去」的原型。

一句话方法论：

> **先理解任务，再设计流程；先确定结构，再设计页面；先保证业务闭环，再追求视觉效果；页面既要好看，也必须好用、能演示、能开发。**

> **需求决定页面，任务决定结构，体验决定交互，视觉服务业务。**

默认输出形态：**高保真可交互 HTML 原型 + 页面/交互说明 + 研发交接清单**。

## 二、能力边界与决策边界

**能力边界**：需求理解、用户与场景分析、核心任务识别、业务闭环、用户任务流、信息架构、页面体系、页面模式选择、页面职责、页面结构、交互设计、状态设计、AI 交互、视觉设计、高保真原型、研发交接说明、设计质量自检（**交付前独立评审归 `polaris{{SKN_SPR}}prototype{{SKN_SPR}}review`**）。

**非本技能职责**：评审已有原型——用户拿一个已有原型 / 交付物来问"能不能交研发"，输出提示：使用技能 `polaris{{SKN_SPR}}prototype{{SKN_SPR}}review`完成评审

**决策边界——不替产品经理决定**：页面数量上限 / 下限、项目范围取舍、产品建设批次、页面开发优先级、原型实现深度、前后端研发排期、开发资源分配、比赛策略、工期压缩策略、哪些页面「只做静态、哪些做真实实现」。这些由产品经理结合**业务价值、项目阶段、研发资源、时间、预算、客户要求和演示目标**自主决定。本技能发现缺口只能标记（`WEB-DESIGN-CHANGE-XXX`，见 §三 冻结规则），不得擅自改写。

**建议而非替代决策**：用户明确提出「帮我分析哪些内容应该先做」「只有 6 小时，怎么安排」「哪些页面值得优先开发」「一期范围怎么切」时，可基于当前原型给出**建议**，但必须声明：**这是范围 / 实施建议，不属于原型设计方法论的强制规则，最终由产品经理确认。**

## 三、核心原则与冻结规则（最高优先级）

**第一原则：Web 原型不是页面集合，而是任务系统。** 设计前必须先回答：用户为什么进入系统？最重要的 3～5 个任务是什么？最核心的一条业务任务如何从开始走到结束？禁止一上来直接"首页 → 列表 → 详情 → 设置"而没有真实用户任务。

**冻结原则**：上游（建设方案、PRD、Agent 设计等）已确认的用户、一期范围、核心业务闭环、Agent 职责、AI/人边界、**平台/系统正式名称、品牌层级、项目/租户/组织上下文名称**，不得擅自改变、扩展或重新命名。**若上游或需求方提供了设计系统 / 视觉规范，Token 取值以它为准**（`scaffold.mjs --tokens=<规范.css>`）——技能自带的那套只是"没有规范时的兜底基线"，不得用它覆盖真实规范。尤其禁止为"让系统看起来更完整"自行创造上级平台、产品族或第二套系统名称。发现缺口必须标记：

> **WEB-DESIGN-CHANGE-XXX｜原型设计发现的产品变更建议**（命名冲突用 **WEB-DESIGN-CHANGE-NAME-XXX**）

**不重复询问原则**：已有资料能判断用户、场景、一期范围、页面功能、核心流程的，不重复询问用户。

## 四、设计流程：9 个阶段（1–8 判断层 · 9 执行层）

**本技能只负责建造**：用户要给新需求做原型时，走下面的阶段 1 → 9。

### 4.1 两层结构：判断层与执行层

| 层 | 阶段 | 性质 | 门禁 |
|---|---|---|---|
| **判断层** | 1–8 | 同一份设计的八个视角，顺序是**建议**，回填是**常态** | **无锁**；每阶段给产出物与完成判据 |
| **执行层** | 9 | 设计结论落成可交付原型 | **硬门禁**：`verify` 退出码 0 + 评审无 P0 |

**回填规则（判断层）**：阶段 5 选模式推翻阶段 4 的页面划分、阶段 7 状态设计暴露阶段 3 的 IA 缺口，都是正常动作——**回填不是违规**。但回填后必须复检受影响的下游产出物（改了 IA 就重看页面清单，改了页面清单就重看结构与状态说明），并在交付物里留一句回填说明。

**前置假设**：输入需求质量良好，阶段 1–3 的产出可直接采信，故不设需求复核回路；若发现需求本身有缺陷，按 §二（§31）报回产品经理，不自行改写。

### 4.2 标识约定

输出目录由用户指定；未指定时默认与原型文件同目录。文件名用户有指定时以用户为准，否则按下列建议：

| 项 | 文件 | 说明 |
|---|---|---|
| 原型（核心成果） | `<原型名>.html` | 单文件、零外部依赖、可离线双击打开 |
| 黄金流（机器读） | `<原型名>.flow.json` | 《核心用户任务流》的机器可读孪生，供 `verify --flow=` 消费；模板取 `verify.mjs --print-flow-example`。**与第 2 份文档同源，不额外计入 6+1** |
| 任务理解卡 | `task-card.md` | 阶段 1 |
| 核心用户任务流 | `golden-flow.md` | 阶段 2 |
| 信息架构 | `ia.md` | 阶段 3 |
| 页面清单与职责 | `page-list.md` | 阶段 4 |
| 页面结构、状态与交互 | `page-structure.md` | 阶段 6–7 |
| 研发交接说明 | `handoff.md` | 阶段 9.4 |

**产出物必须落盘**，不能只写在对话里——这些文件就是本技能的状态记录（没有额外状态文件），上下文压缩后靠它们恢复进度。

**第二重身份：它们是 9.3 评审的取证输入。** 评审拿它们核对「原型是否忠实实现了你自己定的设计」（页面清单 ↔ 实际 `<section id>`、黄金流 ↔ 链路实测、页面结构 ↔ 状态是否真写进页面），所以写的时候要点写得**可被第三方核对**（Page ID、`<section id>`、状态名要能对着找），不要写成只有自己看得懂的草稿。

⚠️ **但它们不能用来证明业务方向对不对**——那是需求方文档的事；你的理解卡写给谁用、目标是什么，评审只能照单核对原型，判断不了理解本身有没有偏。取证资格怎么分级、结论能写到多硬，见 `polaris{{SKN_SPR}}prototype{{SKN_SPR}}review` `§二 取证源分级`（唯一来源，本技能不重复）。

### 4.3 阶段 1–8（判断层）

每阶段三件套：**产出物（含落盘文件）/ 完成判据 / 是否门禁**。

**阶段 1｜需求理解与产品快速定义**：先出《Web 原型任务理解卡》（一句话定位、主要用户、场景、当前问题、核心目标、3～5 个核心任务、业务成果、一期范围、已知/待确认信息）。需求转换公式：**原始需求 → 用户 × 场景 × 任务 × 问题 × 结果**。确认后过 Gate 1。

- 产出：`task-card.md`　判据：3–5 个核心任务各能追到一个真实用户场景；一期范围有边界；待确认项已列出而非留白　门禁：无

**阶段 2｜黄金任务流 Golden Flow**：找到最能体现产品价值的一条完整任务闭环（如"上传合同 → AI 解析 → AI 审查 → 查看风险 → 查看依据 → 人工确认 → 生成审查成果"）。先保证闭环、优先高频高价值、页面围绕任务生成、演示/竞赛模式下原则上只保留 1～2 条。输出《核心用户任务流》。

- 产出：`golden-flow.md`（＋阶段 9.1 落 `<原型名>.flow.json`）　判据：有起点、有终点、有业务成果，且覆盖阶段 1 里最高频高价值的那个任务　门禁：无

**阶段 3｜信息架构 IA**：先设计产品结构不直接画页面。高频业务优先、一级导航控制数量、"管理/配置"后置、不为"大系统感"堆菜单、每个导航项对应明确用户任务。输出《Web 产品信息架构 IA》。**命名与品牌层级规范（产品身份、Header 单一主名称、多层品牌、名称冲突、菜单命名去冗余）见 `references/05 §16.1`——本阶段就要用，不要等视觉阶段再回头改名字。**

- 产出：`ia.md`　判据：每个一级导航项对应一个明确用户任务；Header 主名称唯一且全站一致　门禁：无

**阶段 4｜页面体系与职责划分**：不设页面数量机械上下限，由"用户任务 + 业务闭环 + 信息架构 + 页面职责 + 交互复杂度"自然推导。每个页面必须能回答"用户为什么需要进入这个页面"。输出《Web 页面清单与页面职责说明》（Page ID、名称、角色、主任务、业务对象、入口、出口、对应任务、待确认事项）。

- 产出：`page-list.md`　判据：每页都能回答「用户为什么进这个页面」且入口、出口齐全　门禁：**软**——定稿即 `scaffold.mjs init` 的输入，此后增删页面走 `add-page`，不再重排

**阶段 5｜页面模式选择**：不得所有页面都用"查询 + 表格 + 弹窗"。九种模式按需选择：标准工作台、标准列表页、对象详情页、主从式工作页、对照审核页、流程办理页、配置管理页、分步向导页、AI 工作台（详见 `references/03`）。

- 产出：并入 `page-list.md` 的模式列　判据：非全部「查询 + 表格 + 弹窗」；模式与页面主任务对得上　门禁：无

**阶段 6｜页面结构设计**：每个 P0 页面定义 12 项（Page ID、名称、角色、目标、进入条件、看到什么、做什么、页面区域、离开方式、业务状态、响应式行为、密度模式与容器高度策略）。每页先用"任务—信息—操作"三层法自查，不支持其一的区域审查必要性。其中**密度模式见 `references/05 §15.5`**，**容器高度策略与内容感知布局（Auto Content / Adaptive Data / Full Workspace）见 `§16.2–16.3`**——这两段在结构阶段就要定，等写完页面再补就是大面积空白类返工。

- 产出：`page-structure.md`　判据：12 项无缺项；密度模式与容器高度策略已选定（不是留到写页面时再说）　门禁：无

**阶段 7｜交互与状态设计**：高质量原型不能只有"正常页面"。每个 P0 页面至少考虑 11 种状态：**Initial、Loading、AI Processing（显示"正在解析→检索→分析→生成"而非只转圈）、Skeleton、Empty、Success、Partial Success、Error（必须给出下一步：重试/修改/重新上传/转人工）、Human Review、No Permission、Disabled**。

- 产出：并入 `page-structure.md`　判据：每个 P0 页面覆盖适用状态；Error 有下一步；AI 有过程、有依据、有人工确认　门禁：无

**阶段 8｜视觉设计系统**：确定视觉系统的**规则与阈值**（接口契约、对比度硬指标、视觉比例基线、密度一致性判据），并把取值落到原型自己的 Token 区（详见 `references/05`）。**具体取值不写在技能里**：需求方给了设计规范就用它（`init --tokens` / `set-tokens --tokens`），没有才用技能兜底基线 `assets/default-tokens.css`。高级感来源按"图标体系 > 板块细节 > 交互形式 > 色彩微调"优先级投入，禁止以换主题色回应"不够高级"类反馈。

- 产出：落进原型的 Token 区（不是独立文档）　判据：取值来源已定（需求方规范 or 兜底基线）；对比度 / 字号 / 密度阈值已定　门禁：无

### 4.4 阶段 9（执行层 · 硬门禁）

**9.1 实现** —— 阶段 4 页面清单定稿即可 `scaffold.mjs init` 落骨架，不必等阶段 5–8 全部结束；随后按阶段 5–8 的结论逐页替换占位块填主体，并把 11 种状态写入对应页面；增删页面 / 图标一律走 `scaffold.mjs add-page` / `add-icon`，不手工编辑区域外内容。同步落 `<原型名>.flow.json`。

**9.2 验证** —— 跑全三层（静态 → 逐页冒烟 → 黄金流链路 + 三档分辨率）：

```bash
node scripts/verify.mjs <原型.html> --flow=<黄金流.json> --strict
```

| 退出码 | 含义 | 后续动作 |
|---|---|---|
| 0 | 三层全过 | 进入 9.3 |
| 1 | 有 HARD 项 | **阻断**：修复后重跑，不得进入 9.3 |
| 2 | 用法 / 参数错误 | 修正命令后重跑 |
| 3 | `--strict` 下必需层被跳过 | **按未完成计**，不得进入 9.3 |

脚本报 WARN 的项需人工判断——**脚本全绿 ≠ 设计合格**，设计质量仍按 `§33` 审查（见评审技能的 `references/01-quality-criteria.md`）。

**9.3 评审（交付前门禁，不可跳过）** —— 调用 `polaris{{SKN_SPR}}prototype{{SKN_SPR}}review`，用途声明为「交付前把关」、范围为「全量」，移交材料：原型 `.html` + `<原型名>.flow.json` + 需求文档 + 阶段 1–8 的落盘产出物 + 设计规范（如有）。

| 评审结论 | 后续动作 |
|---|---|
| 可交付 | 进入 9.4 |
| 修复后可交付 | P0 全部关闭后进 9.4，并在交付物里注明依据 |
| 不得交付 | **阻断**：修复 → 重跑 9.2 → 重评审，P0 未清零不得交接 |

评审的调用方已声明用途与范围时，评审侧不再重复询问（不重复询问原则）。

**9.4 交接** —— 输出《研发交接说明》与需求追踪，即 6+1 交付物（§29 / §30）。

### 4.5 退出条件

1. 6 份文档 + 原型 + `flow.json` **全部落盘**（不是只在对话里出现过）
2. `verify.mjs --strict` 退出码 0
3. 评审结论为「可交付」，或「修复后可交付」且 P0 已全部关闭并注明依据
4. 骨架与增删页面走的是 `scaffold.mjs`，未手工编辑区域标记外的内容

### 4.6 上下文压缩恢复

重载：原型路径、输出目录、已完成到哪个阶段、6 份文档中哪些已落盘、`flow.json` 是否生成、`verify` 最近一次退出码、评审最近一次结论与未关闭的 P0。

- **恢复依据就是落盘的产出物**——本技能没有额外状态文件，产物即状态
- 停在阶段 1–8 → 按已落盘的最后一份文档续做，**不要重跑阶段 1**
- 停在 9.2 → 从 `verify` 重跑；停在 9.3 → 从评审结论续；停在 9.4 → 补齐缺失交付物

## 五、AI 产品交互专项（涉及 AI/Agent 必执行）

（1）AI 结果不能只显示一句结论，优先呈现：**结论 / 事实 / 依据 / 风险或重要程度 / 建议动作**；（2）AI 结果应可追溯：能定位原始资料/原文/原图/原数据；（3）按业务风险提供人工确认操作：接受、调整、不采纳、重新生成、升级处理、转人工；（4）AI 状态视觉编码区分：待执行、执行中、已完成、部分失败、失败、待人工确认；（5）AI 失败必须有降级策略：是否重试、能否跳过、是否保留已完成结果、能否人工继续、是否影响正式业务结果；（6）AI 工作台须形成任务主视图（输入配置区 + AI 主工作区：执行步骤、原始证据、识别结果、事实依据、人工确认），Empty/Processing/Result 三态共享同一工作区骨架。

> **本节是摘要，不是第二份规范。** 完整判据与阈值一律以 `references/` 为准；本节的职责只是让红线不被漏掉。
> 括号里的 § 号就是该条的唯一出处——数字型阈值不在本节重复。

**字号**：大面积正文不得为了塞内容压到 11～12px，1920×1080 下不得呈现「小字缩放版后台」；表格正文、Sidebar 菜单、按钮文字用正文级字号。底线口径与脚本分工见 `references/05 §15.2`。

**密度**：标准 / 紧凑 / 展示三种密度模式，同系统页面密度逻辑必须一致；紧凑密度靠减少 Padding，不靠缩小字体。定义见 `references/05 §15.5`。

**布局高度**：三种内容感知模式——Auto Content（内容决定高度）、Adaptive Data（数据量自适应，分页紧跟数据）、Full Workspace（任务决定高度）。容器空置率、内部滚动门槛、看板卡片与首屏占用的判据见 `references/05 §16.3`。

**命名与品牌**：Header 原则上只允许 1 个视觉主系统名称，系统名称在登录页、浏览器标题、Header、导出文件等位置保持一致。细则见 `references/05 §16.1`（**阶段 3 就要用**）。

**响应式**：必检 1366×768 / 1440×900 / 1920×1080 三档（建议加 2560×1440）；禁止「截图式布局」；宽屏增加的是工作空间，不是把元素等比拉长。规则见 `references/06`。

**对比度与兼容**：文本 Token 对白底有对比度硬指标（**`verify L1-9` 强制，见 `references/05 §14.3`**），禁止凭「看起来还行」定灰度；2023+ 新 CSS 特性禁止在关键视觉路径裸用，必须配显式兜底或不采用；问候语、日期等动态内容禁止硬编码在 HTML 里（`verify L1-16` 会提示）。

**图标与高级感**：高级感来源优先级 **图标体系 > 板块细节 > 交互形式 > 色彩微调**；收到「不够高级 / 不够科技感」反馈时，禁止第一反应换成深色主题或更换主色。界面图标必须全站一套内联 SVG symbol 线性体系，禁止混用彩色 emoji、字符图标与图片图标（`verify L1-10` 强制）。做法见 `references/05 §24.3`。

**演示数据自洽**：同一业务单号 / 对象在所有页面状态一致（单一数据源）；费用类数字口径统一、不得出现无来源数字；跨页面引用的日期金额与来源页一致；Tab 计数用真实可数数据。矛盾按 P0 缺陷处理，判据见 `§33.6`（评审技能的 `references/01-quality-criteria.md`）。

**交付门禁（强制）**：交付前必须运行 `scripts/verify.mjs` 全三层并取得**退出码 0**（静态 → 逐页冒烟 → 黄金流链路 + 三档分辨率）；退出码非 0 不得交付，WARN 项需人工判断。**脚本只判「有没有」，判不了「好不好」**——设计质量仍按 `references/07` 人工审查。规格见 `references/07 §27.1`。

**文件编辑（强制）**：骨架与增删一律走 `scripts/scaffold.mjs`（`init` / `add-page` / `add-icon` / `set-tokens`）——它用区域标记做定点插入，锚点命中不唯一即中止且不写盘。**禁止对同一份原型并行发起多条编辑**（并发写会互相覆盖）。详见 `references/07 §27.2`。

**演示数据去个人化（强制）**：禁止出现用户本人或真实同事的真实姓名、手机号、工号、真实内部项目名；统一用通用演示身份（如「林远 / 陈默」等明确虚构名），姓名集中在数据区定义供一键替换。**已由 `verify L1-15` 自动扫描**，见 `references/07 §27.3`。

## 七、研发交付与需求追踪

**技术栈分两层，别混**：**原型自身**是单文件 HTML + 原生 CSS / JS、**零外部依赖**——不引外部 UI 库或图标字体（必须能离线双击打开），图表用静态 SVG，界面图标一律内联 SVG symbol。**目标系统的实现栈**由项目决定，本技能不预设也不推荐，研发换什么框架都不改变设计原则。详见 `references/07 §28`。

每个 P0 页面研发交接至少包含：Page ID、名称、目标、角色、数据字段、组件、关键操作、点击行为、跳转、业务状态、Loading/Empty/Error、AI 调用点、API 需求、权限、响应式规则、滚动策略、断点行为、视觉 Token、容器高度策略、待研发确认项。

需求追踪链：**业务场景 → 用户任务 → Flow → Page → 交互 → API/AI → Test Case**。无法追溯到明确任务的页面重新判断必要性。

固定交付物 6+1：《Web 原型任务理解卡》《核心用户任务流》《Web 产品信息架构 IA》《Web 页面清单与页面职责说明》《页面结构、状态与交互说明》《研发交接说明》+ **高保真可交互 Web 原型**（核心成果）。**落盘文件名见 `§四 4.2`**——产出物必须落盘，产物即状态。

**可执行脚本（两个，配套使用，零外部依赖）**

`scripts/verify.mjs` —— §27.1 三层验证的可执行实现（静态检查 / 无头浏览器逐页冒烟 / 黄金流链路 + 三档分辨率实测）。交付前必须运行并全绿。

```bash
node scripts/verify.mjs <原型.html> --flow=<黄金流.json>    # 退出码 0 才算过
node scripts/verify.mjs --print-flow-example                # 取 --flow 的 JSON 模板
node scripts/verify.mjs --help                              # 全部选项
```

`scripts/scaffold.mjs` —— 原型骨架生成器。一次性产出 App Shell、设计 Token、图标 symbol 库、页面容器、路由与导航，并用 4 个区域标记（`@TOKENS` / `@ICONS` / `@NAV` / `@PAGES`）圈出可增长的部分；此后新增页面与图标走带守卫的定点插入（标记必须唯一命中，否则中止且不写盘）。**§27.2 的大文件编辑纪律因此从「要求模型照做」变成「工具保证」**——有了骨架就不存在千行级手工并行编辑的场景。脚手架只产骨架，页面主体（信息层级、状态覆盖、交互）一律留白，不替业务做决定。

```bash
node scripts/scaffold.mjs init --out=<原型.html> --title=… --app=… --pages="workbench:工作台:i-dashboard,order-list:订单列表:i-list" \
                                  [--tokens=<需求方规范.css>]    # 不传则用技能兜底基线 assets/default-tokens.css
node scripts/scaffold.mjs add-page <原型.html> <page-id> --title=… [--icon=i-list] [--no-nav] [--after=<已有页面 id>]
node scripts/scaffold.mjs set-tokens <原型.html> [--tokens=<规范.css>]   # 中途拿到规范 / 换品牌时用
node scripts/scaffold.mjs add-icon <原型.html> <icon-id> (--builtin=<内置名> | --path="<SVG 子元素>")
node scripts/scaffold.mjs list <原型.html>   # 页面 / 导航 / 图标 / Token 对比度 / 区域标记总览
node scripts/scaffold.mjs icons              # 内置 20 个线性图标
```

推荐顺序：`scaffold init` → `verify --layer=1` 取静态基线（骨架应即刻全绿）→ 填页面主体 → `verify --flow=… --strict` 全三层 → 移交评审（§四 9.3）。

**样例与评测（自带，用于校准与回归）**

`example/` —— 一份走完 9 阶段的完整样例：输入需求包（`requirement.md`）、6+1 交付物（`deliverables.md`）、
成品原型（`prototype.html`）、黄金流定义（`flow.json`）。设计前可先读它对齐交付物形态；
它的原型本身就是回归样本：`node scripts/verify.mjs example/prototype.html --flow=example/flow.json --strict` 应退出码 0。

`evals/` —— 三个评测用例（能力基线 / 设计系统覆盖 / 一票否决）+ 零依赖评测器：

```bash
node evals/run.mjs --selftest                        # 参照物应 PASS、反例应 FAIL（证明断言有牙齿）
node evals/run.mjs --case=e1 --artifact=<原型.html>   # 拿自己的产出跑能力基线
node evals/run.mjs --case=e2                         # 自带夹具，验证设计规范覆盖与三道守卫
```

**改动页面机制、Token 命名契约或脚本判定后，必须重跑 `--selftest`**，否则会出现「脚本全绿但规范已变」的假通过。

脚本只判可判定项（语法、标签配平、跳转与图标引用完整性、Token 对比度、字号底线、接口字符图标、演示数据去个人化、页面空壳、运行时 JS 错误、三档横向溢出、黄金流是否走通）。**设计是否专业、状态取舍是否恰当，脚本不表态**，仍须人工按 `§33` 审查（见评审技能的 `references/01-quality-criteria.md`）。

> 两个脚本共享同一套页面机制约定——`<section id>` 页面容器、`data-goto` 跳转、`<symbol id="i-*">` 图标、`--text-*` Token 命名。**改动任一约定必须同步改两个脚本**，否则会出现「脚本全绿但规范已变」的假通过。完整契约表见 `references/05 §14.1`。
>
> **取值可整套替换，命名不可替换。** 换设计规范只换 Token 文件，命名契约不变——`scaffold.mjs` 会校验命名契约与覆盖率（模板用到的变量缺一个就失败），`verify.mjs` 则按同一契约查对比度。这样"规范全绿但什么都没查"的假通过无处发生。

## 十、交付前自检（先跑这 16 条）

（1）是否先完成需求理解和任务理解卡，而不是直接画页面；
（2）是否找到并走通黄金任务流，形成完整业务闭环；
（3）每个页面是否服务真实用户任务，页面数量是否自然推导；
（4）每个 P0 页面是否覆盖 Loading / Empty / Error / AI Processing / 人工确认等状态，错误是否给出下一步；
（5）AI 结果是否有结论、事实、依据、建议和人工确认入口，失败是否有降级策略；
（6）Header 是否只有一个主系统名称，系统名称是否全站一致、未自创上级平台；
（7）字号、控件高度、间距、圆角、密度是否跨页面统一，1920×1080 下是否保持正式产品可读性；
（8）容器高度模式（Auto Content / Adaptive Data / Full Workspace）是否选对，有无大面积无效空白或无意义内部滚动；
（9）1366×768 / 1440×900 / 1920×1080 三档下核心任务是否都可完成，无横向异常溢出；
（10）研发交接信息（字段、行为、状态、API、响应式规则）是否足以让研发直接实现，需求追踪链是否完整；
（11）若做过视觉升级：升级是否落在图标体系、板块细节、交互形式上，而不是只换了主题色；图标是否一套线性风格、无字符图标/emoji 混入；
（12）示例数据是否自洽：同一单号跨页面状态一致、费用数字口径统一、Tab 计数与实际数据一致、动态内容（问候/日期）非硬编码；
（13）原型骨架是否由 `scripts/scaffold.mjs` 生成（而非手写整份大文件后再做破坏性编辑）；页面与图标的新增是否走 `add-page` / `add-icon` 的定点插入；
（14）Token 取值是否来自正确的来源：需求方提供了设计系统 / 视觉规范时，是否已用它覆盖（`--tokens`），而不是留着技能兜底基线？换过规范后是否重跑了 verify（对比度阈值与取值来源无关，换规范后仍须 ≥4.5:1）；
（15）是否已运行 `node scripts/verify.mjs <原型.html> --flow=<黄金流.json> --strict` 且退出码为 0：静态检查 → 无头浏览器逐页冒烟（多入口、零运行时错误）→ 黄金流链路 + 三档分辨率实测（规格见 references/07 §27.1，脚本是其执行体）。退出码非 0 不得交付；脚本报 WARN 的项需人工判断；演示数据去个人化已并入脚本（L1-15），无需另行人工扫描。**脚本过了只说明 9.2 完成——交付门禁是 9.3 的评审结论，不是脚本退出码**（见 `§四 4.4`）。

（16）交付物形态是否对照 `example/deliverables.md` 校准过（6+1 交付物各自是否到位，而不是只有一份原型）；若本次改动涉及页面机制、Token 命名契约或脚本判定，是否已重跑 `node evals/run.mjs --selftest` 并全绿——`example/` 与 `evals/` 是活的，改了规范不改它们，就等于把假通过留在仓库里。
