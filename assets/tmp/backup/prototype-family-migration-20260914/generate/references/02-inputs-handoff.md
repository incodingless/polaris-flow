# 4. 标准输入

用户不需要一次提供全部信息，有什么给什么。

## 4.1 最低输入

至少需要：

1. 产品 / 题目是什么；
2. 主要用户是谁；
3. 最大业务问题是什么；
4. 最重要的用户任务是什么；
5. 原型用途：
   - 领导汇报；
   - 客户交流；
   - 竞赛演示；
   - 研发交付；
   - 正式项目；
6. 是否已有方案、流程、Agent 设计、旧系统或参考截图。

## 4.2 可选增强输入

有则提供：

- 建设方案 / 产品方案；
- AI Agent 设计文档（岗位、Workflow 等）；
- 业务流程图；
- Word / PPT / Excel / PDF；
- 旧系统截图；
- 公司 Logo；
- 品牌色；
- 参考产品截图；
- 字段表；
- API；
- 数据样例；
- 用户反馈；
- 竞品页面。

## 4.3 不重复询问原则

如果从已有资料中可以判断：
- 用户；
- 业务场景；
- 一期范围；
- 页面功能；
- 核心流程；

则不重复询问用户。


# 5. 与上游方案 / Agent 设计文档的衔接

## 5.1 承接建设方案 / 产品方案

方案中的以下内容可以作为本技能的标准输入：

1. 服务对象；
2. 核心痛点；
3. 核心业务场景；
4. 业务闭环；
5. 一期建设内容；
6. AI 能力；
7. 一期范围；
8. 业务成果。

本技能 必须将其转换为：

> **方案能力 → 用户任务 → 页面流 → 页面 → 交互**

不得机械把“建设内容”直接变成菜单。

## 5.2 承接 Agent 设计文档

如果上游已经有 Agent 设计：

> Agent 岗位 → 任务 → Workflow → 人工卡口 → 业务成果

本技能 必须进一步转换为：

> **用户如何发起 → 如何看到 AI 执行 → 如何查看 AI 结果 → 如何确认 → 如何进入真实业务动作**

## 5.3 冻结原则

上游已经确认的：
- 用户；
- 一期范围；
- 核心业务闭环；
- Agent 职责；
- AI / 人边界；
- **平台 / 系统正式名称；**
- **企业品牌、产品族、平台、子系统之间已确认的层级关系；**
- **项目、租户、组织等业务上下文名称。**

本技能 不得擅自改变、扩展或重新命名。

尤其禁止在没有明确依据时，为了“让系统看起来更完整”自行创造一个上级平台、产品族、品牌名称或第二套系统名称。

如果原型阶段发现缺口，必须标记：

> **WEB-DESIGN-CHANGE-XXX｜原型设计发现的产品变更建议**

等待产品确认。
