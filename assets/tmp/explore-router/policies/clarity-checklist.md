# 需求清晰度自检清单

## 一、使用说明

本清单用于量化判定需求的规范化程度，以此决定是否可以跳过 openspec-explore 提案前预研环节，匹配此前的 L1/L2/L3 分级工作流执行。

**评分规则**：每项满足得 1 分，不满足 / 不确定得 0 分，满分 15 分

**核心原则**：边界、验收、风险三项是核心判定依据，仅功能流程描述详细不等于高清晰度需求

**举证要求（explore-router 强制执行）**：每项打分必须引用需求文档原文片段，或明确标注「文档未提及」。禁止凭感觉给 1 分。

---

## 二、详细检查项（按维度）

### 维度 1：业务边界与目标（4 分）

| ID | 检查项 | 举证要求 |
|----|--------|---------|
| D1-1 | 业务目标有明确可量化指标（如「接口响应耗时降低 30%」「下单成功率提升至 99.9%」），而非「优化体验」「提升效率」等模糊表述 | 引用文档中的具体数字/阈值；若仅有形容词则 0 分 |
| D1-2 | 明确列出本次需求不包含的范围（排除项），不存在模棱两可的灰色边界 | 引用「不包含 / Out of Scope / 排除」章节；无此章节则 0 分 |
| D1-3 | 需求优先级、上线时间约束清晰，无多目标并行的优先级冲突 | 引用优先级标注（P0/P1）与 deadline；冲突未解决则 0 分 |
| D1-4 | 目标用户 / 使用场景明确，不存在「所有用户都能用」的泛化定义 | 引用具体角色/场景描述；泛化表述则 0 分 |

### 维度 2：验收标准（4 分）

| ID | 检查项 | 举证要求 |
|----|--------|---------|
| D2-1 | 核心功能场景已按 Given/When/Then 格式梳理，可直接映射为自动化测试用例 | 引用 GWT/Gherkin 场景；仅用户故事无 AC 则 0 分 |
| D2-2 | 覆盖异常分支、错误处理、边界值场景，异常场景占比不低于 30% | 统计 happy path vs 异常场景数量；无法验证占比则 0 分 |
| D2-3 | 非功能需求（性能、安全、兼容性）有明确的量化验收阈值 | 引用 NFR 具体数值；「要快」「要安全」则 0 分 |
| D2-4 | 验收主体与通过标准明确，不存在「差不多就行」的模糊判定空间 | 引用验收方与 pass/fail 条件；模糊则 0 分 |

### 维度 3：影响范围与依赖（3 分）

| ID | 检查项 | 举证要求 |
|----|--------|---------|
| D3-1 | 明确变更涉及的业务模块、接口、数据表，无未知的隐性耦合 | 引用模块/接口/表清单；仅功能描述无技术影响面则 0 分 |
| D3-2 | 上下游依赖、联动团队、第三方接口已提前确认，不存在待沟通的外部依赖 | 引用依赖方与确认状态；「待确认」则 0 分 |
| D3-3 | 数据变更、存量数据兼容 / 迁移方案已明确，无数据风险盲区 | 引用迁移/兼容方案；涉及数据变更但无方案则 0 分 |

### 维度 4：技术实现路径（2 分）

| ID | 检查项 | 举证要求 |
|----|--------|---------|
| D4-1 | 实现方案属于团队既定技术栈内的常规开发，无需引入新技术、新组件 | 引用技术选型；新组件/新框架则 0 分 |
| D4-2 | 无架构选型争议，团队对实现路径已达成共识，无需额外技术预研 | 引用已达成共识的证据；存在争议则 0 分 |

### 维度 5：合规与规则对齐（2 分）

| ID | 检查项 | 举证要求 |
|----|--------|---------|
| D5-1 | 需求符合项目宪法（constitution.md）中的架构原则、编码规范、安全红线 | 对照 `openspec/memory/constitution.md` 逐条检查；冲突则 0 分 |
| D5-2 | 不突破现有权限体系、数据隔离规则、合规审计要求 | 引用权限/隔离/审计相关说明；未涉及则结合 constitution 判断 |

## 三、分级判定标准

结合变更风险等级差异化执行，风险越高，对清晰度的门槛要求越严格。

| 变更等级 | 可完全跳过 explore | 建议轻量化 explore | 必须全量 explore |
|---------|-------------------|-------------------|-----------------|
| L1 轻量变更 | ≥ 8 分 | 5~7 分 | ≤ 4 分 |
| L2 标准功能 | ≥ 12 分 | 8~11 分 | ≤ 7 分 |
| L3 重大变更 | 不建议完全跳过 | 推荐轻量化模式（风险扫描 + 影响面分析） | 需求模糊时全量执行 |

**轻量化 explore 定义**：不做业务发散与需求澄清，仅执行「边界校验 + 隐性影响面扫描 + 实现方案对比 + 合规预检」4 项定向动作，输出 1 页补充报告，Token 与时间成本控制在全量模式的 20% 以内。

---

## 四、核心三维硬性检查（explore-router 叠加规则）

维度 1（边界）、维度 2（验收）、维度 3（影响范围）是核心判定依据：

- 任一核心维度得分 ≤ 1 时，即使总分达到 SKIP 门槛，**也不得路由为 SKIP**（最多 LIGHT）
- 维度 2 异常场景占比无法验证且主流程占绝对多数时，维度 2 至少扣 2 项

---

## 五、常见误判提醒

- **文档篇幅长≠清晰度高**：很多需求文档篇幅很长，但只描述了正常主流程，缺少排除项、异常场景、量化指标，本质仍属于低清晰度需求
- **业务视角清晰≠技术视角清晰**：产品侧的清晰常遗漏技术实现层面的隐性依赖、历史兼容、并发边界等问题，技术侧需独立校验影响范围
- **主流程清晰≠整体清晰**：80% 的开发返工来自异常分支、边界场景、兼容逻辑的缺失，仅主流程明确不足以跳过预研
- **历史做过≠本次清晰**：同类需求的历史经验不能替代本次的范围确认，需求边界的微小差异可能导致实现方案完全不同
