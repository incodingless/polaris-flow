# 变更等级推断规则（L1 / L2 / L3）

## 用途

explore-router 在用户未显式提供 `change_level` 时，按本文档推断变更等级，并**必须**让用户确认后才能进入打分。

---

## 等级定义

| 等级 | 名称 | 典型特征 |
|------|------|---------|
| **L1** | 轻量变更 | 单模块局部改动、无 schema/权限/架构变更、可快速回滚 |
| **L2** | 标准功能 | 标准功能交付、跨 1-2 模块、团队既定技术栈内常规实现 |
| **L3** | 重大变更 | 架构调整、数据迁移、合规变更、多团队协作、新技术引入、不可逆决策 |

---

## 推断信号（满足多数即倾向该级）

### 倾向 L1 的信号

- 改动范围限定在单一模块/单一接口/单一页面
- 不涉及数据库 schema 变更或仅增字段无迁移
- 不涉及权限体系、数据隔离规则变更
- 可 feature flag 或快速回滚
- 无外部团队/第三方依赖需协调

### 倾向 L2 的信号

- 新增或改造标准业务功能（CRUD、工作流节点、报表等）
- 跨 1-2 个业务模块，但边界已在文档中明确
- 使用团队既定技术栈，无架构争议
- 有常规集成（内部 API），无跨组织协调
- 数据变更可控（增量表/配置项），无大规模迁移

### 倾向 L3 的信号（满足任一即强烈倾向 L3）

- 架构重构、微服务拆分/合并、核心链路改造
- 大规模数据迁移、存量兼容、双写/灰度切流
- 引入新技术栈、新中间件、新基础设施
- 涉及合规审计、安全红线、权限体系重构
- 需 3+ 团队/外部供应商协同，存在未确认依赖
- 上线后难以回滚或回滚成本极高
- 性能/可用性 SLO 有量级变化（如 10x 流量）

---

## 推断输出格式

推断后必须向用户呈现以下模板并等待确认：

```
📊 变更等级推断

推断等级：L{x}（{轻量变更 / 标准功能 / 重大变更}）

推断依据（引用需求文档或上下文）：
  · <信号 1>
  · <信号 2>
  · <信号 3>（如有）

对 explore 路由的影响：
  · L1：SKIP 门槛 ≥8 分
  · L2：SKIP 门槛 ≥12 分
  · L3：不建议 SKIP，推荐 LIGHT

请确认：
  A. 同意推断等级 L{x}
  B. 改为 L1（我认为这是轻量变更）
  C. 改为 L2（我认为这是标准功能）
  D. 改为 L3（我认为这是重大变更）
  E. 补充信息后重新推断（请直接写出补充内容）
```

---

## 用户回复处理

| 用户回复 | 后续动作 |
|---------|---------|
| A（同意） | 锁定 `change_level`，进入 15 项打分 |
| B / C / D（改为 Lx） | 采用用户指定等级，记录「用户覆盖推断」到报告 |
| E（补充信息） | 合并补充内容后重新推断，再次呈现确认模板 |
| 用户一开始就提供了等级 | 跳过推断，记录「用户提供」到报告，直接进入打分 |

**禁止**：未收到用户明确确认（A 或 B/C/D）前进入打分步骤。
