### G2【高】评审的输入契约未与建造的 6+1 交付物对齐 —— ✅ **已闭合（2026-09-14 第十六轮）**

**采纳的判断（原建议「把 4 份产物提升为强烈建议」已被推翻，理由见下）**：原建议是错的——它默认「材料越多审得越深」，
但材料**证明力不同**，堆材料会让低证明力的东西顶替高证明力的位置。本轮改为**取证源分级**（`prototype-review/SKILL.md §二`）：

| 级 | 来源 | 能证明 | 不能证明 |
|:--:|---|---|---|
| L1 | 需求方文档 | **业务方向对不对** | 页面细节 |
| L2 | 建造侧 6+1 | **内部一致性**（原型是否照自己定的设计做） | **这个设计符不符合需求方意图** |
| L3 | 原型 + flow.json + Step 2 实测 | 有没有、能不能跑通、三档分辨率 | 业务意图 |
| L4 | 无需求文档取证法五条 | 存在性（有 / 没有） | 业务方向 |

三条硬规则：①**降级不升格**——缺 L1 时 `§33.1` 结论最高只到「证据不足 / 待需求方确认」，**材料再多也不能把 L2 当 L1**；
②**交叉偏差分三种定性**：原型≠L2 是缺陷（`§33.2`/`§33.3`）、L2≠L1 只能进 P3 待确认（HARD-STOP #7 禁替 PM 决策）、
原型≠L1 是缺陷（`§33.1`）；③L2 读不到就当没有，不得凭文件名推断内容。

**为什么《任务理解卡》不能顶替需求文档**：它是**被评审方自己写的转述**——用它证明业务方向，等于让被评审者自己定义合格线，
与 G9 的「同会话自评」是同一个漏洞的两种形态。它的正确用途是 L2 内部一致性核对，不是业务方向的取证源。

**执行侧落地**（规则在 §二，动作在 §三，不算双源）：Step 3 新增「交叉核对」四组对照 **L2 ↔ L3**——
页面清单 ↔ `<section id>`、黄金流 ↔ L3 链路结果、IA ↔ 页面清单/导航、页面结构 ↔ 11 种状态是否真写进页面；
§六 报告第 1 项要求写明**本次可用的取证源**，作为「结论为什么只能写到这个硬度」的说明。

**同步**：建造侧 `§四 4.2` 加一段「第二重身份」——6+1 产物是 9.3 的取证输入，须写得**可被第三方核对**
（Page ID / `<section id>` / 状态名要能对着找），并写明取证分级以评审侧为唯一来源（版本 1.1.0 → 1.2.0 为评审侧）。

**尚未做（建议但本轮未擅自动）**：给评审 evals 加第 4 条断言——「业务维度结论在缺 L1 时是否被写成通过」。
没有断言的硬规则会随时间失效，这条建议留给用户定。

**现状（改前）**：

- 评审 `SKILL.md:47-53` 输入：①原型（必需）②`flow.json`（强烈建议）③需求文档（可选）④设计规范（可选）⑤研发交接说明（可选）。
- 建造侧 6+1 交付物（`prototype/SKILL.md:122`）：任务理解卡 / 核心用户任务流 / IA / 页面清单与职责 / 页面结构状态交互说明 / 研发交接说明 + 原型。
- 映射缺失：**任务理解卡、核心用户任务流、IA、页面清单**四项在评审输入表里**根本没有出现**。

**后果**：评审的 `§33.1` 业务维度（用户、核心任务、黄金流）与 `§33.2` 结构维度（IA、页面必要性、命名层级）缺少取证材料，只能退到 `SKILL.md:101-109` 的「无需求文档取证法」——那段自己也声明「**证明不了业务方向对不对**」。也就是说：**建造侧辛辛苦苦产出的前 4 份文档，评审时一个都用不上，评审深度被输入缺口锁死**。

**建议**：输入契约加一列「来自建造侧哪份交付物」，把任务理解卡 / 黄金任务流 / IA / 页面清单从「未列出」提升为「强烈建议」，并写明缺哪一份会削弱哪个维度。

新族没有等价物，它的模型是「发现问题 → 回 `refine` 由 PM 处理」（`prototype` §31 亦明示不自改需求）。

**本次的止血方式**（不新增规范，只把路由写明）：指针文件里保留这一段责任划分——
① 发现涉及**需求内容** → 走本族 `prd-update` L2；② 发现涉及**原型自身** → 回 `polaris…prototype`；
