## 0. 结论速览

**内容底子优秀，工程化与合规是短板。综合 5.5 / 10（评审初始快照；整改后见下表后的现状说明）。**

这是一份写得非常"厚"、非常专业的**设计方法论 + 规范手册**，交互状态覆盖、AI 交互专项、运行时验证三层法、演示数据自洽等章节明显超出公开同类技能的水平。但它作为**可被 Agent 稳定执行的 Skill** 存在三类硬伤：

1. **事实层面：它不是原创技能，而是市场技能 `web-hifi-prototype` 的改名副本**（references 逐字节相同）。
2. **规范层面：缺少标准必填字段 `description`，`name` 保留未替换占位符且与目录名不一致。**
3. **工程层面：全篇是"规则"而非"步骤 + 脚本"，没有脚手架、没有可运行的验证脚本、没有示例与评测**——它甚至要用"大文件编辑纪律"去补救自己因缺少脚手架而制造的问题。

## 1. 事实核查：这是改名副本，不是新技能

| 证据 | 结果 |
|---|---|
| `references/01–07` 与 `~/.workbuddy/skills/web-hifi-prototype/references/*` | **7 个文件逐字节相同（IDENTICAL）** |
| SKILL.md 差异 | 仅 `name`、`display_name`、`description` 首句（去掉"企业级"）、标题 |
| 来源 | `_skillhub_meta.json`：`source: marketplace`，`skillId: skill_2096562385859952640` |

**这意味着三件事，必须先明确意图再往下做：**

1. **技能路由歧义（当前真实风险）**：你机器上同时存在 `web-hifi-prototype`（市场版）和这份 `generate-prototype`，两者描述几乎同义、触发词完全重叠（"画原型 / 高保真 / HTML 原型 / 交互原型"）。宿主会把两者都注入元数据，模型选择时将出现不稳定路由。**必须二选一或做差异化描述。**
2. **Fork 而不改，等于维护负债**：如果目的是"polaris 内定制版"，那么现在没有任何定制内容，后续市场版更新无法合并、又会在本地逐渐漂移。
3. **许可与署名缺失**：作为市场技能副本，frontmatter 没有 `license`、没有来源标注。上架或内部分发前应补。

> 建议：明确这个技能在 polaris 体系里的**唯一职责**。若只是"高保真交付阶段"的承接者，应重命名为差异化名称（如 `polaris-hifi-prototype`）并重写描述，把触发边界与 `lofi-prototype`（低保真验证 IA/流程）、`prd-to-prototype`（零提问直出）划清。

## 2. 规范合规问题（Agent Skills 开放标准）

### 2.1 【P0】缺少必需字段 `description`

当前 frontmatter 只有 `description_zh` / `description_en`，**没有标准的 `description` 字段**（已核实：`^description:` 匹配数为 0）。

- WorkBuddy 宿主支持 `description_zh/en`，因此**在本地大概率仍能加载**；
- 但 Agent Skills 开放标准明确 `description` 为**必填**，跨宿主、上架市场、被第三方解析时会**直接判定不合格或无法发现该技能**。
- 参考：`lofi-prototype`（agent_created）同时写了标准 `description` + `description_zh/en`；`prd-writer` 只有标准 `description`。

**注意**：不能把现有两个描述简单合并成 `description`——`description_zh` 327 字符 + `description_en` 862 字符合计已超 1024 字符上限。需要**重写一条简洁的标准描述**（一句 what + 一句 when，中文优先，触发词保留）。

### 2.2 【P0】`name` 非法且与目录名不一致

```
name: polaris{{SKN_SPR}}prototype      # 目录名: generate-prototype
```

- `{{`/`}}` 不属于 `[a-z0-9-]`，不满足 `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`，超过 64 字符也无需讨论——**它连字符集都不合法**；
- 仓库内其他技能是自洽的（`constitution → polaris{{SKN_SPR}}constitution`、`subagent-dispatch → polaris{{SKN_SPR}}subagent-dispatch`），即"目录名 = 占位符后段"。唯独这里目录是 `generate-prototype`、占位符后段是 `prototype`，**破坏了仓库自身的命名约定**。
- 另：标准要求 `name` **精确匹配目录名**，而本仓库的做法（加 `polaris` 前缀）本身就不满足这一条。如果 polaris 是靠构建期替换出一套带命名空间的技能名，请确认宿主侧是"插件命名空间"而非"SKILL.md name 字段"——否则安装后会以非法 name 注册。

### 2.3 【P2】元数据缺失

无 `license`、无 `agent_created: true`（`lofi-prototype`、`prd-writer` 均有）。后者会影响后续用 SkillManage 修改该技能的能力。

## 3. 结构：分层是对的，但重复与切分维度错了

### 3.1 做得对的部分

- SKILL.md 161 行 < 500 行，符合官方建议；
- 使用了渐进式披露：SKILL.md 作总览 + §九"参考文件（按需加载）"表明确"何时读"——这一点比多数公开技能做得好；
- 7 个 references 独立成文件，不占常驻上下文。

### 3.2 问题一：SKILL.md 与 references 大段重复

| 内容 | 出现位置 | 重复次数 |
|---|---|---|
| 一句话方法论 | `SKILL.md §一`（唯一来源） | **3 → 1（7.16 已收敛）** |
| 第一原则"原型是任务系统" | SKILL.md §三、ref01 §3 | 2 |
| 流程总览（阶段 1–5 详述） | SKILL.md §四、ref03 §6 | 2（摘要 / 详述，属**有意分层**） |
| **一票否决 31 条** | SKILL.md §八、ref07 §34 | **2（逐条完整重复）** → 8 条摘录（7.13 已收敛） |
| 6+1 交付物 | SKILL.md §七、ref07 §32 | 2 |
| 最终判断标准 | `ref07 §36`（唯一来源） | **2 → 1（7.16 已收敛）** |
| **职责边界「不处理」** | SKILL.md §二、ref03、ref07 §31.2–§31.3 | **3 → 1（7.15 已收敛）** |

同一规则的两份副本必然漂移——改一处忘一处，模型读到哪份取决于加载顺序。**最佳实践是"单一事实来源 + 索引"**：SKILL.md 只保留不可推演的少数高阶不变量（第一原则、冻结原则、一票否决的**清单目录**），全文只在 references 里存在一份。

### 3.3 问题二：references 按"章节区间"切，而非按"任务/领域"切

官方建议按 **domain 或"什么时候需要"** 切分。当前却是按原文书的章节区间切，直接后果是**按需加载失效**：

## 4. 可执行性：这是最大的结构性缺口

官方最佳实践明确两条：**"优先用脚本处理确定性操作——写 validate.py，而不是要求 Claude 生成校验代码"**、**"按任务脆弱性匹配具体度"**。本技能几乎全部违背。

### 4.1 【P0】该脚本化的两条主线，全写成了"文字要求"

| 应该有 | 现在 | 对照公开技能 |
|---|---|---|
| 脚手架脚本：生成 App Shell + Token 变量 + 图标 symbol 库 + 页面注册表 | 无 `scripts/`，靠模型即兴手写千行 HTML | `web-artifacts-builder`（9.8 万安装）有 `scripts/init-artifact.sh` + `bundle-artifact.sh`；`lofi-prototype` 有 `scripts/scaffold.py` |
| 验证脚本：把"三层验证"落成可运行的 `verify.mjs` | 27.1 写成了 40 行"提醒模型照做"的文字 | 官方明确要求关键校验用脚本 |
| 模板 / 示例 HTML | 无 `assets/`、无 example | `lofi-prototype` 有 `assets/shell.html`、`lofi.css`、`example.html` |

### 4.2 一个讽刺的因果链

技能里写了「**大文件编辑纪律（强制）**」（禁止并行 Edit、必须用断言式替换脚本、`count===1` 校验），以及「**运行时验证三层法（强制）**」。这两条**都是在补救"没有脚手架"造成的后果**：

- 因为没有模板，模型必须一次性写出并反复改千行级内联 HTML → 才有"并发写覆盖""整页白屏"的坑；
- 因为验证没脚本化，模型要手搓 `--dump-dom` 正则探针 → 才有"正则命中注入源码""断言写死动态整句"的坑表。

**根治办法不是把纪律写得更细，而是提供 `scaffold` 与 `verify` 两个脚本。** 现有 27.1 的踩坑表恰恰是这两个脚本最好的 `.md` 规范——转成代码即可，成本很低，收益很大。

### 4.3 工作流缺"最后一公里"

§四定义的"标准工作流：8 个阶段"里，**没有一个是"实现"或"构建"**：阶段 1–8 全是设计阶段（需求→任务流→IA→页面体系→页面模式→结构→交互状态→视觉系统），然后 §七直接跳到"研发交付"。**技能名叫 `generate-prototype`，却没有"生成"这一步的结构化描述。**

- 建议补 **阶段 9｜实现与验证**：脚手架 → 分页实现 → 数据落盘 → 三层验证 → 交付；
- 同时明确输出契约：**单文件还是多文件**（27.1 提到 `goto('xxx')`/`<section>`，暗示单文件多 section，但从未明说）、**文件名与落盘路径**、**如何呈现给用户**（present_files）。这些缺失会直接导致不同会话产出结构不一致。

### 4.4 无迭代回路，也没有保真度分级

原型方法论（NN/g、GV 设计冲刺、BA Times 等）的共识是 **build → measure → learn**：先低/中保真验证 IA 与黄金流，再上高保真；且必须有干系人/用户验证轮。本技能：

- **只有 Gate 1**（需求理解后确认），此后一路线性推到高保真交付，**中途无验证卡点**；
- 直接产出"高保真"，**没有中保真阶段**去低成本试错 IA 与任务流（这恰好是 `lofi-prototype` 的职责，但两者没有衔接说明）。

**建议**：Gate 1（任务理解）→ **Gate 2（IA + 黄金流 + 页面清单，中保真确认后再投高保真）** → 交付后明确"反馈轮"机制。

### 4.5 无模式档位，小请求会被过度执行

31 条一票否决 + 8 阶段 + 11 种状态，对"给这个列表页加一列""改一下主色调"这类 tweak 请求**严重过重**，而模型会当真跑完整流程。你自己的 `polaris-flow` 已有 `tweak/normal/full` 三档——本技能应对齐：

- **quick**：在既有原型上增删页面 / 调样式，跳过阶段 1–3；
- **normal**：单条黄金流的完整设计到高保真；
- **full**：多角色、多任务流的完整 8+1 阶段。

### 4.6 缺"提问协议"

只有"不重复询问原则"，没有规定**缺关键信息时最多问几个、以什么形式集中问、什么时候必须停下等人**。实践里会走向两个极端：反复追问，或照 35.4"直接做"闷头猜。建议：明确"最低输入 6 项缺失 ≤ N 项时，一次性集中提问；≥ N 项缺失时先给假设版任务理解卡请其确认"。

## 5. 内容专业度：亮点要保住，主观门禁要拆掉

### 5.1 明确的亮点（应保留并作为 polaris 差异化资产）

1. **"原型不是页面集合，而是任务系统"** 的第一原则 + 先 IA/黄金流后画页面 —— 与 IA-first 最佳实践一致，比多数公开原型技能更清醒。
2. **交互状态覆盖 11 种**（Initial/Loading/AI Processing/Skeleton/Empty/Success/Partial Success/Error/Human Review/No Permission/Disabled）—— 公开同类几乎不谈状态管理，这是碾压性优势。
3. **AI/Agent 交互专项 7 节**：结论-事实-依据-风险-建议、可追溯、人工确认六动作、失败降级五问、多轮上下文合并、置信度展示翻译、语音闭环、等待期出路。**公开技能里没有对等物。**
4. **运行时验证三层法 + "验证方法自身的坑"对照表** —— 罕见、且明显来自实战踩坑，价值极高。
5. **演示就绪审查 + 演示数据去个人化** —— 公开技能完全空白，是真实演示场景的刚需。
6. **内容感知布局三模式**（Auto Content / Adaptive Data / Full Workspace）+ 空置率检查 —— 比通用"响应式"更贴合后台场景。
7. **"高级感 = 图标体系 > 板块细节 > 交互形式 > 色彩微调"** —— 一条很好的反谄媚规则（明确拒绝"用换主题色回应不够高级"），值得保留。

### 5.2 问题：一票否决粒度失控，混入大量主观不可判定项

31 条一票否决里，一批是**可机械校验的硬门禁**（应保留在门禁），另一批是**主观审美判断**（"无意义卡片过多""是否过花""为科技感大量渐变""无意义内部滚动"），还有一批是**流程纪律**：

- 语义上"一票否决"意味着**阻断交付**，但主观项根本无法稳定判定，结果是模型只能两种反应：**橡皮图章式全部宣称通过**，或**误伤正确设计**。这会稀释真正硬门禁的权威性。
- **建议三分**：
  - **硬门禁（可脚本校验，阻塞）**：语法通过、标签配平、跳转目标存在、symbol 引用完整、三档无横向溢出、对比度 ≥4.5:1、动态内容非硬编码、无字符图标/emoji、数据自洽（单号跨页一致）、无真实姓名/手机号/工号。
  - **设计启发式（不阻塞，产出问题清单）**：卡片数量、渐变、留白、视觉焦点等。
  - **流程纪律（转为脚本或清单，不作门禁）**：并行编辑、断言式替换、版本标识等。

### 5.3 技术栈与产出形态自相矛盾，且已过时

- §七/§28 把默认栈写为 **Vue 2.x + Element UI 2.15 + Vuex 3 + Font Awesome 4.7 + ECharts 5**，但 §27 要求产出**高保真可交互单文件 HTML 原型**。重工程栈与单文件原型存在概念张力——实际产出到底走 CDN 轻栈还是工程栈，技能没交代。
- **时效性问题（官方明确要求避免 time-sensitive 信息）**：
  - **Vue 2 已于 2023-12 停止维护（EOL）**；
  - **Element UI 2.15 停止维护**；
  - **Font Awesome 4.7 是 2016 年版本**。
  这套栈会让原型呈现"过时感"，与技能自身目标"企业级、专业、现代"直接冲突。
- §28 有一句正确的解耦表述（"视觉、交互和页面设计原则保持不变"），但 §七又把栈写成"默认技术参考栈"，前后不一致。
- **建议**：把技术栈彻底降级为"可选实现参考"，或升级为中性轻栈（原生 HTML/CSS/JS，或 Vue3/React + Tailwind，参照公开 `artifacts-builder` 的做法）；并把"避免 AI slop"的正面取向（避免过度居中、紫色渐变、统一大圆角）纳入。

### 5.4 设计 Token 需要自证

- 默认主色 `--primary-color: #4b55fa`（靛蓝）与 §24.2"避免大面积渐变 / AI 页面满屏科技蓝光"存在张力；若 polaris 已有设计语言应对齐，而不是沿用市场技能默认色。
- §14.3.1 自己要求"定义文本 Token 时必须用公式校验对比度"，但**给出的 `--title-color: #2d3b8d`、`--text-placeholder: #999999` 等并未附实测值**。其中 `#999999` 对白底约 2.8:1（不达 4.5:1），若用于辅助文本即违反自身规则。**规则应先满足自己。**

### 5.5 缺失：示例、评测、鲁棒性分支

- **无 example / golden 输出**：官方要求"至少 3 个评测用例 + 具体输入输出示例"。技能连一个示例原型都没有（`lofi-prototype` 至少有 `assets/example.html`）。这是**最高性价比的补强项**——一个标准 example 能同时充当模板、风格锚点和验收基准。
- **无鲁棒性分支**：输入不是桌面 Web（移动 App / 小程序 / 大屏）、需求互相矛盾、上游 PRD 本身有缺陷、用户中途改需求时怎么办——均未定义。技能只在 §二"不处理"里排除了范围决策。

## 7.7 P1 整改记录：scaffold.mjs（2026-09-11）

`scripts/scaffold.mjs`（零外部依赖，仅用 Node 内置模块）已落地，定位是**薄脚手架**——只产骨架，不替业务做决定。

**为什么是它，而不是继续细化 §27.2 的纪律**：§27.2 要求"多处修改用断言式替换脚本、构造目标串前先 Read 原文、禁止并行 Edit 同一文件"——这些要求本身都对，但它们是在补救"没有脚手架"制造出来的问题。给了骨架，千行级手工并行编辑的场景就不存在了。所以这个脚本本质是**把技能自己已经写好的规则，落到它自己要求的那个位置上**。

**四个区域标记是核心设计**：`@TOKENS`（CSS 注释）/ `@ICONS` / `@NAV` / `@PAGES`（HTML 注释），各自使用所在语境的原生注释语法。`add-page` / `add-icon` 只在这四个区域里定点插入，插入前断言标记**唯一命中**，命中数不为 1 就中止且不写盘——即 §27.2 要求的断言式替换，由技能交付而非每次现写。

| 命令 | 作用 |
|---|---|
| `init` | 生成 App Shell + 设计 Token + 20 个线性图标 symbol + 页面容器 + 路由 + 导航 |
| `add-page` | 追加页面：同一次操作原子写入页面容器与导航项，并做 id 唯一性守卫（支持 `--after` 定点插入、`--no-nav` 只建页不上导航） |
| `add-icon` | 追加图标 symbol：`--builtin=<内置名>` 或 `--path="<SVG 子元素>"` |
| `list` | 总览页面 / 导航可达性 / 图标定义与引用 / 断链 / **文本 Token 对比度自检** / 区域标记 |
| `icons` | 列出内置图标集 |

**与 verify.mjs 的契约（两者必须一起演进）**：`section[id]` 页面容器、`data-goto` 跳转、`symbol#i-*` 图标、`--text-*` Token 命名、`window.goto()` 路由——都是 verify 第一/二/三层赖以工作的前提。

**实测（脚手架产物 + 增量 + 反例）**

| 场景 | 实测结果 |
|---|---|
| `init` 3 页 → verify 全三层 | L1/L2/L3 PASS；3 页均经 `fn:goto` 激活、`visible=true`、内容长度 173～174、零溢出（1366/1440/1920 三档）、零运行时错误 |

**过程中被 verify 自己抓到的问题**（值得一提）：初版模板在注释里写了 `<use href="#i-xxx"/>` 和 `goto('xxx')` 作为**文档说明**，结果被 verify L1-4 / L1-7 判 HARD——它把注释里的字面量当成真实引用与真实跳转。这不是误报，而是**契约的边界**：注释里的示例语法同样会被扫描。改为描述性文字后通过，这条约束已写进脚手架的生成模板注释。

**诚实交代的边界**：脚手架能让「骨架层面」的 L1/L2/L3 立刻全绿，但**页面主体一旦开始填充，回归仍可能随时变红**——这正是 verify 存在的意义。另外 `init` 生成的页面占位块（约 170 字符）是为了跨过 verify 的空壳阈值，它是**占位而非内容**，必须整体替换后才可交付。
